# 03 上下文工程与规格驱动开发

[上一章](02-agent-loop.md) | [目录](README.md) | [下一章：MCP 与 OAuth](04-mcp-oauth.md)

## 1. 为什么“帮我优化项目”经常失败

这种要求同时缺少目标、范围和判定标准。Agent 可能改目录、换框架、升级依赖，最后无法证明你真正关心的问题被解决。模型能力再强，也无法可靠猜出未表达的业务偏好。

提示工程关注如何表达一次请求；上下文工程关注如何选择、组织、更新和传递完成任务所需的信息。代码、版本化文档、需求、测试结果、权限边界与历史决定都属于上下文。它不是把整个仓库复制到聊天框。

## 2. 上下文的四种常见失败

| 失败 | 行动项提取项目中的例子 | 应对 |
| --- | --- | --- |
| 缺失 | 不知道默认模型和回退路径 | 先读实现与配置 |
| 污染 | 将旧端点文档当成当前契约 | 标记来源、版本、日期 |
| 冲突 | PRD 要保留原文，示例却要求自动补负责人 | 澄清优先级后再实现 |
| 过载 | 无关日志和依赖文件淹没关键测试 | 搜索定位，按需读取 |

对每条重要事实附上来源，并把事实、假设和待澄清项分开。当前代码是当前行为的证据，但不一定是正确需求；测试也可能过时。发生冲突时需要判断哪一项是已发布契约、哪一项是待改变目标。

## 3. 制作最小上下文包

一个实现“笔记列表分页”的上下文包应包含当前列表路由、响应 schema、相关模型、已有测试和目标规格，不必包含全部前端资源或六周作业。

记录关键定位信息，例如“读取了路由文件的这个函数，它目前无排序”；不要只说“项目用 FastAPI”。压缩时保留目标、决策理由、修改文件、失败证据和未验证项。可重新读取的长日志保留路径与必要片段，不反复内联。

清空会话可以减少干扰，却会丢失隐含决定。新会话应先读交接记录，再核对实际工作区。上下文压缩属于信息选择，不是可靠备份。

## 4. RePPIT 的具体用法

README 提到 Research、Propose、Plan、Implement、Test。可以将它理解为逐步降低不确定性，而非每个小改动都必须写五份文档。

1. **Research：研究。** 找入口、调用链、测试和当前限制；运行最小基线；输出有来源的事实。
2. **Propose：提出方案。** 比较最小调整与替代方案，指出公开行为、数据和安全影响；澄清不可自行决定的事项。
3. **Plan：计划。** 把方案拆成可验收的小步，明确文件范围和每步测试。
4. **Implement：实现。** 按计划产生小差异，不顺手重构无关部分；发现假设错误时更新计划。
5. **Test：验证。** 运行对应检查，复核需求和差异，记录未覆盖风险。失败则回到相应阶段。

小型文案改动可以在一段记录里完成这个过程；身份认证或数据库迁移需要更明确的审查与发布方案。流程的价值在于证据与决定可追踪，而不是文档数量。

## 5. 将愿望转换为规格

愿望：“任务列表更好用。”可执行规格：“任务按创建时间降序展示，每页最多 50 条，相同时间按唯一 ID 降序；非法分页参数返回约定的 4xx；不得改变旧字段名称。”

还要说明边界：第一页是什么编号，零条数据返回什么，删除数据后是否允许页间漂移，客户端是否依赖原顺序。偏移分页实现简单，但并发增删可能导致重复或遗漏；游标分页更适合连续浏览，却需要额外契约。不要因为“更先进”就无条件换成游标。

功能要求描述做什么；非功能要求描述延迟、权限、容量和可观测性；非目标明确本轮不做什么。验收标准应能被观察，而不是“智能”“优雅”“体验好”。

## 6. 示例规格：可靠的 LLM 提取

下面是教程扩展的目标契约，不是当前 API 已实现的声明。

| 项目 | 本轮规定 |
| --- | --- |
| 输入 | 会议笔记文本；空白输入返回空列表；长度上限经业务确认 |
| 结果 | 只返回原文支持的可执行任务，不推测人名和日期 |
| 正常输出 | 字符串列表，并记录实际提取引擎 |
| 模型异常 | 若允许规则回退，明确返回降级状态，不冒充模型成功 |
| 安全 | 不执行笔记中的命令；不记录原始秘密 |
| 非目标 | 不自动把结果同步到第三方项目管理工具 |

当前 [提取实现](../_assignments/2025%20fall/week2/app/services/extract.py) 已有 LLM 与规则回退。其函数返回列表，不带引擎与错误状态。改变返回类型可能影响路由和测试，所以应先调查消费者，再决定新增包装层还是调整契约，不能只改一个函数就宣布完成。

## 7. 验收案例应先于实现

```text
场景：只有叙述
输入：今天的会议已经结束，发布也已经完成。
预期：没有新增行动项。

场景：明确任务
输入：明天请检查发布日志。
预期：包含检查发布日志，不新增负责人或具体时间。

场景：外部依赖异常
条件：模型调用超时，系统允许规则回退。
预期：可观测到回退原因，界面不宣称由模型成功提取。
```

用验收案例约束实现，而不是让 Agent 根据自己生成的实现反向定义“正确”。当样例暴露需求歧义时先澄清，再写断言。

## 8. 动手：用 AI 完成一个受控变更

1. 在练习副本中选择列表分页或提取降级状态，阅读相关代码与 [原设计文档模板](../Resource/Fall2025/week03-1006-design-document-template.md)。
2. 写一页规格：当前行为、目标、非目标、输入输出、失败路径、受影响文件、验收和回滚。
3. 给 Agent 第一阶段请求：“只研究，不改文件；列出来源、方案与待澄清项。”检查它有没有将猜测当事实。
4. 确认方案后请求小步实现，明确允许范围；每步都要求实际测试证据。
5. 用一条未给 Agent 的边界样例验收，检查它是否为了通过测试删除断言或改变要求。
6. 将最终差异与规格逐项对照，记录计划外变更及必要理由。

验收：规格可以在没有原作者帮助时转成测试；修改范围合理；有一个失败路径和一个未参与实现调参的验证样例。

## 9. 自测与答案

**问：规格是否应该包含每行实现？** 不需要。规格应约束可观察行为和必要架构决定；过度规定细节会妨碍合理实现。

**问：上下文越长越准确吗？** 不一定。错误、冲突和噪声也会随上下文增加。应优先提供可信且相关的信息。

**问：发现需要改计划外文件怎么办？** 先说明调用关系和必要性，再调整范围；涉及未授权行为或并发冲突时寻求确认。

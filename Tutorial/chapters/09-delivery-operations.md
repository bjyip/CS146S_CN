# 09 全栈交付、可观测性与事故响应

[上一章](08-security.md) | [目录](../README.md) | [下一章：团队与综合项目](10-capstone.md)

控制中心显示了新笔记，重启服务后却找不到它。修好保存功能后，模型又经常超时；服务改用规则提取，页面仍显示“模型提取成功”。这说明页面可用、接口成功和兑现用户承诺是三件事。本章先检查数据链路，再学习如何发现降级、及时止损和确认恢复。

**前置与成果**

- 理解请求、响应和百分比即可。CRUD指创建、读取、更新、删除，不必先搭数据库或监控平台。
- 沿用行动项提取器/开发者控制中心，完成交付证据表、请求时间线、两本可靠性账和事故草稿。
- 基础题只分析给定的虚构材料，不联网、不运行服务或模型；真实交付与故障演练另行验收。

## 1. 原型成功与产品交付之间

页面里的笔记可能只在浏览器或服务内存中，也可能尚未提交到数据库。重启后消失时，应沿同一对象ID检查请求、提交和再次读取，而不是先归咎模型。

最小全栈链路是：**页面收集输入 → 服务端验证输入、权限与业务 → 数据库或文件保存 → 返回对象ID → 再次读取同一对象。** 全栈指这些职责共同完成任务，不限定框架。持久化意味着重启进程后数据仍在，列表暂时可见不能证明这一点。

另一种情况是提交成功、响应丢失。客户端超时不代表没写，盲目重试可能重复创建。可用幂等标识让同一操作只产生一个结果，或先核对提交状态。更新则要用版本检查或约定的局部修改，避免旧窗口无声覆盖新数据。

页面应区分等待、成功、失败、提交未知和模型降级。失败时保留输入、释放按钮锁，不能显示成“空列表”。窄屏和键盘操作也要验证主流程及错误提示，而不只检查按钮是否可见。

## 2. 最小全栈验收

先约定用户行为，再检查实现。以下是教学契约，状态码可适配框架，业务含义不能悄悄改变。

| 场景 | 契约与所需证据 |
| --- | --- |
| 创建有效笔记 | 提交并返回ID；关联请求与存储记录，再读同ID得到原内容 |
| 重启服务再读取 | 记录版本、库位置和重启后独立读取；同ID同内容仍在 |
| 更新缺失对象 | 明确缺失，不创建幽灵对象 |
| 删除再读取 | 对象按约定缺失；不能被启动种子自动复活 |
| 标题为空、为null或类型错误 | 按类型与长度约定拒绝，不能只检查JSON语法 |
| 创建响应丢失、重复点击 | 显示提交未知，核对幂等或对象状态，避免重复 |
| 旧窗口更新 | 识别冲突或按规格局部更新，不覆盖他人的新值 |
| 模型不可用 | 显示失败或规则降级，保留模型错误 |
| 窄屏与键盘 | 等待、错误和主流程均可操作，记录实际条件 |

小项目不必增加分页、上传或多用户；扩大部署范围时再审查身份、授权、秘密和备份。能保存SQLite文件不等于迁移或生产部署可靠。

先用[行动项起步实验](pratic/README.md#贯穿项目行动项提取器)跑通「预览 → 人工修订 → 确认保存 → 新进程重读」；再用本表补完整产品的失败状态与验收。起步实验是命令行，不覆盖浏览器或部署。

### 生成构建器与交付边界

生成源码、运行预览和目标部署要分别验收。能解析“创建文件/运行程序”只证明格式正确，路径、依赖、网络和预算仍需授权。页面交互与数据保存也应分开检查：“配色完成”不能替代“重启后笔记仍在”。

## 4. 可观测性是回答问题的能力

数据保存好了，模型超时却仍可能藏在HTTP 200背后。要发现它，需要同时回答“一次请求经历了什么”和“这种情况出现了多少次”。日志、指标和追踪分别帮助回答这些问题。

**日志**记录事件，如“R7模型超时”；**指标**汇总请求数、超时率和延迟分布；**trace（追踪）**串起一次请求的操作时间线。**span**是其中一段有起止时间、状态和父子关系的操作，如模型调用或写库。请求 ID 与追踪 ID 只用于关联，不代表身份或权限。

### Span 关系、采样与降级证据

以下虚构span使用同一单调时钟，单位毫秒。五个子操作都属于request；lookup与model并行，fallback等待模型超时，persist等待回退结束。

| span | parent | 起点 | 终点 | 状态/事件 |
| --- | --- | --- | --- | --- |
| request | 无 | 0 | 100 | HTTP 200，engine=rules，degraded=true |
| auth | request | 0 | 10 | 允许假用户 |
| model | request | 10 | 70 | error，timeout |
| lookup | request | 10 | 40 | 成功，与model并行 |
| fallback | request | 70 | 85 | 规则回退 |
| persist | request | 85 | 95 | 提交成功 |

request共100ms，model共60ms。各行相加为225ms，但父子覆盖和并行被重复计时，不能当作端到端延迟。95–100ms是剩余响应处理。model耗时可能包含本地等待，不能据此认定供应商故障；真实跨主机时钟也需核对。

HTTP按降级契约成功，model仍失败；内容没有人工标注，质量未知。日志可保留引擎、错误类别、请求ID和版本，不默认记录会议原文、完整上下文或凭据。

跨服务和队列要传播关联信息；缺span可能是未埋点、关联丢失、采样或导出失败，不等于未调用。采样只保留部分追踪：提前采样（head）丢掉后无法恢复，按结果采样（tail）也可能漏记录，均不保证完整审计。

例如100次请求中8次超时，只保留8个超时和2个正常trace，样本超时占比是80%，全量却是8%。总体可靠性必须用可靠全量计数，不能拿有偏样本代替；本章不要求接入遥测平台。

## 5. 四个黄金信号

追踪解释个例，下面四类“黄金信号”帮助观察总体变化：

| 信号 | 提取器应问什么 | 常见误判 |
| --- | --- | --- |
| 延迟 | 成功与失败各自有多慢，长尾怎样 | 快速失败拉低均值，被误写性能改善 |
| 流量 | 合法用户请求、模型调用与重试各多少 | 重试数当用户请求；低流量下错误少被当恢复 |
| 错误 | 请求失败、模型超时、错误内容与明确降级各多少 | 只数500，漏掉200中的退化 |
| 饱和度 | 队列、连接池、CPU、内存、外部配额是否逼近限制 | CPU正常就认定所有容量正常 |

这些信号提供线索，不证明根因。是否误提已完成任务，仍需约束检查、人工抽样或用户反馈。

## 6. 定义 SLO 与降级

还需约定“多少才可接受”。SLI是实测指标，SLO是目标，例如固定窗口内99%的合法请求得到按时、明确的正常或降级响应。这是教学目标，不是对外服务协议SLA。

### 错误预算要绑定指标契约

先固定窗口、分母、成功规则、降级是否合格和计数来源，不能事后删掉超时。**错误预算**为`纳入请求数 × (1-目标比例)`，表示目标容许的不合格量；它帮助判断发布风险，不授予Agent冻结或回滚权限。

虚构窗口W纳入10000次请求，均进入模型任务流程：80次API和模型都失败，300次按时明确rules降级（API合格、模型不合格），9620次两者均合格。三组不重叠，两项目标均为99%。

| 指标契约 | SLI计算 | 预算 |
| --- | --- | --- |
| API允许明确按时降级 | `(10000-80)/10000=99.2%` | 允许100次，使用80，剩20 |
| 模型任务不接受降级或失败 | `(10000-80-300)/10000=96.2%` | 允许100次，使用380，超出280 |

API达标不代表模型达标。若承诺200必须是模型结果，应修改API契约；缺全量计数时不能宣称指标改善。

超时要覆盖整条调用链。重试需有上限、退避和随机抖动，写入需幂等；持续失败时可熔断，暂时停止新模型调用、明确降级，冷却后受控探测再恢复。这些机制是否有效，需要实际故障注入验证。

## 7. 事故响应的证据链

模型错误远超预算时，先确认影响和严重度，收集同一窗口的日志、指标、追踪、变更与依赖状态。止损可先于根因确认，但必须有授权、风险评估和恢复条件；“刚发布过”只是线索。

### 故障定位与动作前提

若模型慢而规则正常，查等待、配额、队列与并发；若数据库错误增多，区分读写、主副本和连接池。不要立即重启全部服务，它可能丢证据或引发连接风暴。

回滚前核迁移是否兼容旧代码，切读副本前核滞后与容量。诊断Agent可提出假设和只读查询，操作手册不能给只读身份增加部署权限；批准与执行也要分别记录。

### 生产 Agent 的三类上下文能力

运维助手需要关联服务与依赖、保留知识的来源和适用版本，并让调查共享事故ID、窗口和证据。两个分支引用同一日志不算独立确认；旧结论不能覆盖当前结果，拒绝访问也不等于健康。可先提出两个假设，各做最多两项只读检查，预算耗尽或关键工具持续失败就交接未知。

### 从调查建议到收益验证

区分观察、假设、建议、批准、执行和恢复。模型自信、分支一致或任务打勾不能替代证据与反证。生成解释快不等于恢复快；验证收益还要统计人工确认成本、漏报、误报、不必要动作和恢复时间，包括失败事故。

## 8. 无责复盘，但要有行动责任

复盘说明影响、时间线、支持与反证、根因或未知、止损和恢复证据。不止追问“谁操作错了”，还要解释什么条件让错误扩大，不能编出未确认的根因。

改进须有负责人、期限和验证，例如发布前补回退告警，并测试超时可见、正常流量不误报。确认恢复要看正常流量下的错误比例、延迟、用户结果和数据完整性，不能只看错误数下降。

### 基础必做：四份完整假材料

各题独立，按“事实、假设、未知、决定、待补证据”五项作答，第10节给出答案。无需自拟数据或查监控。

#### 基础 1：为什么不能宣布交付，15 分钟

题设契约：标题为非空字符串；创建提交后返回ID，重启仍可读；模型降级需明确显示。假证据如下：

| ID | 给定假记录 |
| --- | --- |
| D1 | 页面显示N7“周五检查日志”；只记录浏览器列表更新，没有请求/提交记录 |
| D2 | 服务重启后读取N7返回缺失；未核库路径和缓存 |
| D3 | 另一请求R8显示提交N8成功，但响应丢失；客户端超时；没有幂等或状态核对结果 |
| D4 | 请求R9 HTTP 200、engine=rules、degraded=true，页面却写“模型提取完成”；质量未标注 |
| D5 | 请求标题null可解码为JSON；业务验证未执行 |

逐条说明证据支持什么、缺什么、下一步怎么核对，并判断能否交付。

#### 基础 2：请求用了多久，20 分钟

用第4节span表画并行区间，计算request、model及所有行总时长，分别判断HTTP、模型和内容质量。假设lookup漏传关联字段、接收端产生独立trace，但调用记录仍在：能否说它未调用？再计算100次请求、8次超时、仅保留10条trace的两种比例，列五个可记录字段和三类禁止数据。

#### 基础 3：同窗口两本预算账，15 分钟

用第6节 W 窗口的材料（总计 10000 次，其中失败 80 次、降级 300 次、正常 9620 次）与两项 99% 目标，计算两SLI、使用预算、剩余或超出量。再给一个独立遥测故障：失败80次同时漏掉请求总数与失败数，计数器只见9920次，其中300次降级，其余正常；其他证据仍说明漏了80次。

解释计数器为何显示API 100%、能否宣称改善，并给团队一项待批准的发布或降级建议。

#### 基础 4：事故有没有恢复，20 分钟

虚构事故I1的调查窗口为同一天10:00–10:10，应用v2；事件与观测时刻分别列出。

| 证据ID | 事件时刻 / 观测时刻 | 假事件与来源 |
| --- | --- | --- |
| E1 | 10:00 / 10:00 | 变更记录：v2发布，模型并发配置提高；迁移兼容性未记录 |
| E2 | 10:01 / 10:02 | 全量指标：模型超时上升；规则路径延迟正常，当前请求100次/分钟 |
| E3 | 10:02 / 10:02 | I1请求trace：model timeout，本地队列长度未埋点 |
| E4 | 10:03 / 10:03 | 配额查询拒绝访问；另一分支也引用E3并说“队列肯定满了” |
| E5 | 10:04 / 10:04 | 旧runbook适用v1，要求看旧日志源；v2埋点说明改到适配器日志；只读Agent无写权限 |
| E6 | 10:05 / 10:05 | 值班人批准关闭模型入口，仅针对I1/v2；没有执行端确认 |
| E7 | 10:06 / 10:07 | 实例记录：旧pod UID=P-old/容器C1/节点H1/v2被替换，新UID=P-new/容器C2/节点H1/v2健康；旧日志查询超时 |
| E8 | 10:08 / 10:08 | 错误数下降，但请求仅10次/分钟；没有用户结果和数据完整性复测 |

比较“外部端点异常”和“本地并发/队列积压”两种假设，列支持与反证需求，合计最多四项只读检查；指出E4/E5/E7的未知或过期信息。分别为关闭入口、回滚写出批准要求、版本/迁移前提、停止条件和恢复指标，最后写80–150字事故更新及一项改进。

## 9. 动手：交付与故障演练

<details>
<summary>选学：真实CRUD、观测与恢复，独立实际验收</summary>

取得隔离环境授权、检查依赖与数据秘密、设定模型预算和每步停止条件后再做。本章没有执行这些实验；可先做单版，三栈作业另计。

1. 实测CRUD、非法输入、失败UI、重复写入和重启后同ID读取，保存版本、命令与环境。
2. 用假数据关联模型、解析、回退、存储和响应，检查日志无秘密，注明埋点与采样缺口。
3. 注入可控超时或无效响应，核对预期：模型错误保留、回退率可见、UI明确降级；质量另评。
4. 获准后演练停用模型或恢复旧版本，先核迁移兼容与备份，记录批准、执行及正常流量下恢复。
5. 据上述实际记录写复盘和改进；缺任一类证据就保留未验收，不把本地演练称为生产事故。

### 部署后保护 Agent 本身

后台重试也会放大故障。关联任务与模型/工具审计，记录队列等待、尝试上限、取消和批准版本。依赖持续失败时停止重试，撤权后阻止新副作用并保留成果，重复告警按原因与窗口合并；恢复从一次受控探测开始。这是2026第10周主题的教程扩展，仍需故障注入验证。

### 迁移检查：新进程健康，旧请求未知

虚构记录：v3实例P1提交后响应丢失，替换后的P2健康检查200，页面缓存显示“完成”。没有幂等记录、独立读库或迁移兼容证据。值班建议重发并回滚v2。判断写入、恢复和回滚，给出最小只读补证与停止条件。

<details>
<summary>作答后展开参考答案</summary>

写入未知，P2健康和缓存都不能证明未写或恢复，盲重发可能重复。保留请求、对象、版本、库路径和实例信息，获准只读核操作记录、提交与同对象读取；无法对账就停止交接。回滚需另行批准、兼容与备份证据；恢复需正常流量下的用户结果、错误/降级及数据完整性。

## 10. 自测与答案

### 集中练习答案

#### 基础 1：沿链定位，不跳结论

1. D1只证明页面显示N7。补请求ID、提交记录、库位置和重启后独立读取，才能验证持久化。
2. D2不满足重启读取契约，根因仍未知；检查内存保存、提交、库路径和初始化，不先归咎模型。
3. D3可能已经写入。显示提交未知、保留输入，核幂等键和对象状态，不盲目重创。
4. D4的API可按降级契约成功，模型未成功，UI表述错误；内容质量未知。修正显示并验证超时、回退与质量。
5. D5按契约拒绝null，不靠字符串转换创造标题。
6. 这些记录有明确失败和证据缺口，不能宣布交付；CRUD各项仍须实际验收。

#### 基础 2：时间关系与总体比例

1. auth为0–10；model为10–70，与10–40的lookup并行；fallback为70–85，persist为85–95，最后5ms处理响应。request覆盖全程。
2. request为100ms，model为60ms。各行合计225ms，但因覆盖和并行，不能当作端到端延迟。要区分本地排队、连接等待与端点耗时，才能调查模型慢的原因。
3. HTTP降级成功、model超时、质量未测。独立trace不代表未调用，应检查关联传播。
4. 样本`8/10=80%`，全量`8/100=8%`；缺可靠全量计数就只报告样本条件。
5. 可记请求ID、span/parent ID、引擎/降级、错误类别、版本；禁止凭据/会话值、会议原文、完整模型上下文。

#### 基础 3：两目标不共用成功数

1. API为`9920/10000=99.2%`；预算100，使用80，剩20。
2. 模型为`9620/10000=96.2%`；使用`80+300=380`，超预算280。降级不能算模型成功。
3. 漏掉80次失败后，计数器算出`9920/9920=100%`，分子分母同时失真。先修计数并补窗口数据，不能报告改善。
4. 可建议暂停高风险发布、限制并发或明确降级，调查380次模型失败；实际切换和回滚仍需授权与恢复条件。

#### 基础 4：证据不足就保持未知

| 假设 | 支持 | 反证/区分需求 |
| --- | --- | --- |
| 外部端点异常 | E2模型慢、E3调用超时且规则正常 | 查端点错误/耗时与本地排队分段；E4配额拒绝不能确认或排除限流 |
| 本地并发/队列积压 | E1并发提高、E3超时 | 队列长度未埋点，需连接/排队证据和同版本低并发对照；发布接近不是因果证明 |

四项只读检查可选：当前窗口适配器日志（最多20条脱敏记录）、分段trace（最多10条）、并发/连接/队列指标（最多5组）、变更与迁移记录（最多5项）。记录I1/v2、资源和缺口；拒绝访问不升级权限，关键证据取不到就交接。

E4重复引用E3，不能确认队列满。E5旧手册适用v1，v2应查适配器日志，两者都不授写权。E7要保留新旧实例UID、容器、节点、版本及两种时刻；旧日志超时仍是缺口，新实例健康不说明旧故障已消失。

关闭入口仅获I1/v2批准，执行端还须确认权限、目标和规则路径；误目标、规则失败或额外副作用时停止。当前应记“已批准，执行未知”。回滚需另批具体旧版本，核迁移/数据兼容与备份；兼容未知时不执行。恢复要在正常流量下核错误比例、延迟、降级显示、用户结果和数据完整性。

事故更新示例：“I1/v2模型超时增加，规则正常。外部端点和本地并发均待验证，配额查询被拒、队列数据缺失。关闭入口已批准但执行未知；新实例健康不证明修复。错误减少伴随流量下降，恢复未确认。”改进：平台负责人下次发布前补队列和回退埋点，用正常/超时测试验证告警。

### 理解检查

**200为什么仍可业务失败？** 可能内容错误或违反承诺；明确降级是否合格由具体指标契约决定。

**测试通过还要监控吗？** 要。真实流量、依赖、权限与分布不同，测试不覆盖全部运行条件。

**事故Agent发现问题就可重启吗？** 不可。需授权、影响范围、兼容和恢复条件，重启可能加剧事故。

**纸面恢复表通过是否完成交付？** 否。真实CRUD、持久化、降级和恢复各需执行证据。

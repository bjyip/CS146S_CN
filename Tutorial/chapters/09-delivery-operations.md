# 09 全栈交付、可观测性与事故响应

[上一章](08-security.md) | [目录](../README.md) | [下一章：团队与综合项目](10-capstone.md)

控制中心页面已经能显示刚创建的笔记，可重启服务后笔记消失了。后来数据终于能保存，模型却经常超时，页面仍显示“提取成功”，因为规则回退也返回HTTP 200。这两次失败说明，“页面能点”“接口成功”和“用户真正得到承诺的能力”不是同一件事。本章先沿数据走完整条链，再学习怎样看见降级、决定止损与核验恢复。

- 能理解请求、响应、列表与百分比即可做基础题。CRUD是创建、读取、更新、删除；本章会说明它们需要留下什么证据，不要求先运行数据库或监控平台。
- 沿用行动项提取器/开发者控制中心，不新增演示应用。产物是交付证据表、请求时间线、两个可靠性指标账本和一份有未知项的事故草稿。
- 基础全部纸面：零网络、模型、安装、应用、数据库、云与生产操作。假事件是给定分析材料，不是本教程实际执行结果；真实交付和故障演练另行验收。

## 1. 原型成功与产品交付之间

刚创建的笔记出现在页面，可能只存在浏览器内存，也可能写到了服务进程内存，或数据库写入尚未提交。重启后消失时，不先归因于模型：沿同一对象ID追踪输入、请求、存储和再次读取，才能知道承诺在哪层断开。

一个最小全栈链路可以理解为：**页面收集输入并显示状态 → 服务端验输入、权限与业务 → 数据库/文件持久化 → 服务端返回对象ID → 页面再次读取同一对象。** “全栈”在这里指这些职责共同完成任务，不是必须使用某种框架。持久化指数据跨进程重启仍按契约保存；列表暂时可见不是充分证据。

服务端成功提交但响应在网络中丢失，又是另一种失败。用户看到超时，不能据此认定没写；盲目再次创建可能重复。先给写入绑定幂等标识，即同一逻辑操作重复请求只产生一个结果，或核对提交状态再重试。修改还要防旧整对象覆盖新值，版本核对或明确局部更新能表达冲突，而不是把并发都当普通成功。

页面需区分等待、成功、失败、未知提交状态、模型降级；失败保留输入并释放按钮锁，不把请求错误显示成“空列表”。从桌面切到窄屏或键盘时，能看见按钮不等于主流程可操作，还要验证关键状态与内容不被遮挡。

## 2. 最小全栈验收

先约定用户行为，再检查实现。下面是本章教学契约，状态码可按具体框架适配，但不偷偷改变业务含义。

| 场景 | 契约与所需证据 |
| --- | --- |
| 创建有效笔记 | 服务提交，返回ID，再读取同ID得到原内容；请求/存储/读取记录关联 |
| 重启服务再读取 | 同ID同内容仍在；记录版本、库位置、重启与读取，不靠旧页面缓存 |
| 更新缺失对象 | 明确缺失，不创建幽灵对象 |
| 删除再读取 | 对象按约定缺失；不能被启动种子自动复活 |
| 标题为空、null或类型错误 | 按固定类型/长度约定拒绝；合法JSON不等于业务类型正确 |
| 创建响应丢失、重复点击 | 显示提交未知，核幂等/对象状态，不产生意外重复 |
| 旧窗口更新 | 冲突被识别或按规格局部更新，不无声覆盖另一人的新标题 |
| 模型不可用 | 明确失败或规则降级，保留模型错误，不声称模型成功 |
| 窄屏与键盘 | 主流程、错误状态与等待状态可操作，实际目标条件留证据 |

这里不强迫单用户小项目增加分页、上传和多用户；但扩大部署范围时必须重新审查身份、资源授权、秘密与备份。保存一个SQLite文件也不自动证明迁移、备份或生产部署可靠。

### 生成构建器与交付边界

生成源码、运行预览与目标部署是三层证据。解析出一个“创建文件/运行程序”动作，只证明格式可读，不说明路径、依赖、网络和预算已获授权。页面预览正常也不证明部署兼容或重启持久化。

先对生成动作核格式，再独立核权限；先对页面核交互，再对服务和存储核数据。不把“配色完成”与“重启仍有笔记”合成一项通过。原课件的舞伴查找案例放在选学，用来对比视觉与业务验收，不另起本章主线。

## 4. 可观测性是回答问题的能力

现在假设数据已保存，但提取页面仍显示成功，模型其实超时并回退到规则。只看HTTP 200找不到这个失败，我们需要回答“一次请求经历了什么”和“很多请求中这种情况有多少”。这就是引入日志、指标和trace的理由。

**日志**记录离散事件，例如“请求R7模型超时”“R7选择rules”；**指标**汇总一个窗口的请求数、超时数、回退率与延迟分布；**trace（追踪）**关联一次请求跨组件的操作时间线。其中**span**是一段有起止、状态与关系的操作，例如模型调用或写库。request/trace ID帮助关联，不代表合法身份，也不授予权限。

### Span 关系、采样与降级证据

下面是本章完整假span材料，所有时间用同一假单调时钟，单位毫秒；五个子操作的parent均为request。lookup与model同时开始，不要求等待lookup完成才调用model；fallback必须等model超时，persist必须等fallback完成。

| span | parent | 起点 | 终点 | 状态/事件 |
| --- | --- | --- | --- | --- |
| request | 无 | 0 | 100 | HTTP 200，engine=rules，degraded=true |
| auth | request | 0 | 10 | 允许假用户 |
| model | request | 10 | 70 | error，timeout |
| lookup | request | 10 | 40 | 成功，与model并行 |
| fallback | request | 70 | 85 | 规则回退 |
| persist | request | 85 | 95 | 提交成功 |

request覆盖整个100ms；model为60ms。各行相加`100+10+60+30+15+10=225ms`会把父子覆盖和并行重复计时，不能当端到端延迟。最后95–100ms是题设请求剩余处理/响应时间，不另猜数据库耗时。慢model值得调查，但60ms也可能包含本地等待，不能仅此证明供应商根因。真实跨主机时钟偏差另需核对。

HTTP按降级契约成功，model仍失败；行动项内容是否正确尚无人工标注，质量未测。不能把request 200改写成所有子操作成功。日志保留引擎、错误类别、任务/请求ID和版本等必要字段，不默认记录会议原文、完整模型上下文、token或用户隐私。

跨服务和队列要传播必要的关联上下文；漏传播可能让操作成为独立trace。没有span可能来自未埋点、丢关联、采样或导出失败，不直接等于未调用。采样指只保留部分追踪细节：head提前决定丢弃，事后不能恢复；tail按结果筛选仍可能缓存溢出或漏迟到记录，两者都不保证完整审计。

再给一组独立假数据：100次请求中8次模型超时，错误优先只保留8个超时和2个正常trace。保留样本超时占比80%，全量超时率8%；不能拿80%当全体错误率。SLO分母要来自可靠全量计数，不能直接用有偏的trace集合。原文SDK示例未验证，本章不要求接遥测平台。

## 5. 四个黄金信号

一次trace解释个例，但上线还需看总体是否变差。运维讲义用四类“黄金信号”组织观察：

| 信号 | 提取器应问什么 | 常见误判 |
| --- | --- | --- |
| 延迟 | 成功与失败各自有多慢，长尾怎样 | 快速失败拉低均值，被误写性能改善 |
| 流量 | 合法用户请求、模型调用与重试各多少 | 重试数当用户请求；低流量下错误少被当恢复 |
| 错误 | 请求失败、模型超时、错误内容与明确降级各多少 | 只数500，漏掉200中的退化 |
| 饱和度 | 队列、连接池、CPU、内存、外部配额是否逼近限制 | CPU正常就认定所有容量正常 |

信号支持调查，不独自证明根因。语义质量仍需约束检查、抽样人工标注或用户反馈；监控大量200不回答“有没有误提已经完成的任务”。

## 6. 定义 SLO 与降级

有指标后，还要约定“多少才可接受”。SLI是实际测得的指标，SLO是它的目标；例如合法请求在固定窗口中至少99%得到按时且明确的正常/降级响应。这只是教学目标，不是原应用服务承诺，也不是SLA（对外服务等级协议）。

### 错误预算要绑定指标契约

先固定窗口、哪些请求纳入分母、按时/成功规则、降级是否合格与全量计数来源，再算比例。不允许事后删超时美化成绩。**错误预算**是目标允许的不合格量：`纳入请求数 × (1-目标比例)`；它用于讨论发布风险，不是发生错误的许可，也不是Agent自动冻结/回滚的授权。

本章假窗口W有10000次合格请求，每次均进入模型任务流程，三组互不重叠：80次未得到合格API响应且模型路径也失败；300次明确rules降级、按时按API契约合格但模型未成功；9620次模型与API均合格。两目标均为99%。

| 指标契约 | SLI计算 | 预算 |
| --- | --- | --- |
| API允许明确按时降级 | `(10000-80)/10000=99.2%` | 允许100次，使用80，剩20 |
| 模型任务不接受降级或失败 | `(10000-80-300)/10000=96.2%` | 允许100次，使用380，超出280 |

API达标不能证明模型达标。若业务要求200必须为模型结果，就要改API契约而非沿用这里的降级成功定义。没有可靠全量分母时，保留遥测缺口，不写SLO改善。

超时还需覆盖整体调用链，不只限制单次模型。重试有上限、退避与随机抖动，写入配幂等；持续失败时可暂时熔断，即停止新调用积压、转明确降级，冷却后以受控探测决定恢复。重试、降级和恢复的实际实现必须单独故障注入测试，纸面预算不证明有效。

## 7. 事故响应的证据链

模型不合格量远超预算时，要先确认影响、范围和严重度，再收集同一窗口的日志、指标、trace、变更与依赖状态。止损不必等待全部根因证明，但动作必须有授权、风险与恢复条件；“刚发布过”只是一条线索。

### 故障定位与动作前提

例如只模型路径慢、规则正常，调查模型等待、配额、队列与并发配置；若写查询500增多，就区分读/写、主/副本、单分片/全局、应用连接池/数据库负载。不立即重启全部服务，重启可能丢证据或诱发连接风暴。

回滚应用前核已执行迁移是否兼容旧代码；切读副本前核数据滞后与容量。诊断Agent可归纳材料、提出竞争假设与只读查询；只读身份不能因runbook一句建议获得部署或删除权限。批准与执行成功也要分开记录。

### 生产 Agent 的三类上下文能力

控制中心的运维助手至少要做到：把服务与依赖关联起来以选择查询；保留团队知识的来源、版本和失效条件；让并行调查共享事故ID、窗口与证据表。这三项用于减少找证据的负担，不自动证明根因。

两个分支引用同一日志不是独立确认；旧版本结果不能覆盖当前结论。拒绝访问、超时、无匹配与健康是不同结果。摘要不应删失败，知识更正也不能扩大权限。可以先用两个假设、每个最多两项只读检查，达到总预算或关键工具持续失败时交接未知。

### 从调查建议到收益验证

保持六种状态：观察、假设、建议、批准、执行、恢复。图谱相邻、模型高置信、多分支一致、任务打勾都不能替代原始定位和反证。不到一分钟生成理论不等于一分钟恢复；报告数与自动动作数也不等于减少用户影响。验证收益要计人工中断/确认成本、遗漏、错误预警、不必要动作与恢复时间，不删除失败事故。

## 8. 无责复盘，但要有行动责任

复盘包含影响、时间线、检测、支持/反证、已确认根因或未知、止损、恢复证据与改进。不只写“操作失误”，还问什么条件允许错误扩大；未知根因保持假设，避免用流畅叙述补全。

每个改进有负责人角色、期限与验证，例如平台负责人在下一次发布前加入模型超时/回退告警，测试需证明回退上升被看见且正常流量不误报。降低错误数不能单独确认恢复，还需正常流量下错误比例、延迟、用户结果与数据完整性。

### 基础必做：四份完整假材料

各题独立，使用以下材料即可完成，不自拟span或查监控。按“事实 / 假设 / 未知 / 决定 / 计划证据”记录，答案在第10节。

#### 基础 1：为什么不能宣布交付，15 分钟

题设契约：标题为非空字符串；创建提交后返回ID，重启仍可读；模型降级需明确显示。假证据如下：

| ID | 给定假记录 |
| --- | --- |
| D1 | 页面显示N7“周五检查日志”；只记录浏览器列表更新，没有请求/提交记录 |
| D2 | 服务重启后读取N7返回缺失；未核库路径和缓存 |
| D3 | 另一请求R8显示提交N8成功，但响应丢失；客户端超时；没有幂等或状态核对结果 |
| D4 | 请求R9 HTTP 200、engine=rules、degraded=true，页面却写“模型提取完成”；质量未标注 |
| D5 | 请求标题null可解码为JSON；业务验证未执行 |

分别写已经支持/不支持什么、下一步计划证据与是否交付。通过标准：D1不证明持久化；D2保留根因未知；D3不盲重试；D4区分API、模型、UI和质量；D5按契约拒绝，合法JSON不能算有效标题。

#### 基础 2：请求用了多久，20 分钟

直接用第4节六行span表：画并行区间，算request、model、所有行总时长，写HTTP/模型/质量三种结论。另假设lookup的发送端未注入关联字段、接收端出现独立trace，调用记录仍在；说明能否认定未调用。再用100次/8超时/只保留10trace假例算样本与全量比例，列五个可记录字段和三类禁止数据。

通过标准：100/60/225ms不混，model/lookup在10–40ms并行；200不擦掉timeout，质量未测；独立trace不等于未调用；80%与8%分母分开，不存秘密/原文/完整上下文。

#### 基础 3：同窗口两本预算账，15 分钟

用第6节W窗口10000/80失败/300降级/9620正常材料与两项99%目标，计算两SLI、使用预算、剩余或超出量。再给一个独立遥测故障：失败80次同时漏掉请求总数与失败数，计数器只见9920次、其中300降级，其余正常；其他证据仍说明漏了80次。

说明计数器为何会显示API 100%，该比例能否宣称改善，给团队一项待批准的发布/降级建议。通过标准：99.2%/96.2%、剩20/超280；漏数不证明恢复，Agent不自授发布或回滚权。

#### 基础 4：事故有没有恢复，20 分钟

以下全部为虚构事件；时间为同一练习日，观测时刻与事件时刻明确，不是视频定位。当前调查窗口10:00–10:10、应用v2、假事故I1。

## 9. 动手：交付与故障演练

<details>
<summary>选学：真实CRUD、观测与恢复，独立实际验收</summary>

本节不由纸面题替代。已有获准隔离环境、依赖/数据/秘密检查与模型预算后再运行；本轮未执行应用、模型、数据库或故障注入。可先做单版本，三栈原作业要求另计。建议先为每步设单独时限与停止条件，预算按实际环境确认，不无限重试。

1. 完成贯穿项目CRUD，真实检查创建/读取/更新/删除、非法输入、失败UI、重复写入与重启后的同ID数据。保存版本、命令、环境与结果。
2. 关联模型、解析、回退、存储和响应事件，只用假数据，实际检查日志/trace没有秘密；记录未埋点和采样范围。
3. 在隔离环境注入可控超时或无效响应，先写预期再观察。验证model错误保留、回退比例可识别，UI不把规则说成模型，语义质量另评。
4. 经明确许可演练停用模型入口或恢复旧应用版本。先核迁移兼容/备份，记录批准、执行、失败和正常流量下恢复，不仅截图健康。
5. 写事故报告与可验证改进；至少有CRUD与重启、请求关联、回退观测、一次实际恢复证据，才能计真实交付演练，不把本地演练写成生产事故。

### 部署后保护 Agent 本身

后台重试、权限与流水线也会放大故障。关联任务ID与模型/工具端审计，记录队列年龄、尝试上限、取消确认、拒绝写入与批准版本。依赖持续失败应有限重试后停止；凭据撤销应停止新副作用并保留部分成果；重复告警应按根因和窗口合并而非重复启动修复。恢复以一次受控探测开始。这些是2026第10周主题的教程扩展，真实实现需独立故障注入，纯事件表不证明熔断/撤权有效。

## 10. 自测与答案

### 集中练习答案

#### 基础 1：沿链定位，不跳结论

1. D1只支持页面当时显示了假N7，不支持服务提交或持久化。需要请求ID、提交/库定位、返回ID和重启后独立读取；不能只刷新旧缓存。
2. D2按假记录不满足重启读取契约；可能内存、未提交、库位置变化或初始化等，当前不能唯一断根因。查同版本/对象/库路径和链路，不归咎模型。
3. D3有提交线索，响应丢失不等于未写。显示提交未知、保留输入，不再次盲创；核原幂等键/对象状态和执行记录，无证据就保持未知。
4. D4 API按降级契约可成功，模型路径没有成功，UI“模型完成”错误；内容质量未标注，不能说正确。需修显示并留超时/回退关联、质量和正常回归。
5. D5 null不是非空字符串，按题设拒绝，不让通用字符串转换创造标题。当前是假判定，不是实际验证器已通过。
6. 合并判断：存在已给定失败与大量缺证据，不宣布交付；分别保留真实待验收项目，不用纸面预测填CRUD通过。

#### 基础 2：时间关系与总体比例

1. auth在0–10；model在10–70，lookup在10–40；70后fallback在70–85，persist在85–95，95–100为剩余响应。父request覆盖0–100，不是最后再执行的100ms。
2. request=`100-0=100ms`，model=`70-10=60ms`；行合计225ms不是延迟，因为父子覆盖、model/lookup并行。模型慢支持调查，反证需求可为排队/连接等待、端点服务耗时与相同窗口其他调用对照，不能独断外部故障。
3. HTTP200且明确rules降级，model timeout仍为错误；质量未测。缺关联时接收端独立trace加调用记录证明至少有调用线索，查发送/接收传播和队列上下文，不记“未调用”。
4. 保留样本`8/(8+2)=80%`，全窗口`8/100=8%`；全量请求/超时计数才支撑后者。没有可靠全量计数时只能报告样本条件，不能填全体SLO。
5. 可记请求ID、span/parent ID、引擎/降级标记、错误类别、应用版本，另有起止和状态；禁止token/会话值、会议原文、完整模型上下文。设置字段长度、每请求span数和保留期的假预算也可，但不当实测合理性结论。

#### 基础 3：两目标不共用成功数

1. API不合格80、合格9920，`9920/10000=99.2%`；预算`10000×1%=100`，使用80，剩20。
2. 模型不合格`80+300=380`、合格9620，`9620/10000=96.2%`；预算100，超出280。两组事件不重叠，不能只扣300或把降级算模型成功。
3. 遥测故障中计数器看9920次且没有不合格API响应，算成`9920/9920=100%`；漏掉80失败同时损坏分子/分母。外部证据已知漏数，不能把它当可用性改善，修全量计数并补窗口数据后再报告。
4. 建议团队评估暂停高风险模型路径发布、限制并发或明确规则降级，并调查380模型失败；任何实际冻结、回滚或切换都需既定授权与恢复条件，预算耗尽不自动给Agent权力。

#### 基础 4：证据不足就保持未知

| 假设 | 支持 | 反证/区分需求 |
| --- | --- | --- |
| 外部端点异常 | E2模型慢、E3调用超时且规则正常 | 查端点错误/耗时与本地排队分段；E4配额拒绝不能确认或排除限流 |
| 本地并发/队列积压 | E1并发提高、E3超时 | 队列长度未埋点，需连接/排队证据和同版本低并发对照；发布接近不是因果证明 |

四项只读查询参考：当前窗口适配器日志聚合（最多20条脱敏记录）、请求分段trace（最多10条）、并发/连接与队列可得指标（最多5组）、变更与迁移兼容记录（最多5项）。每项记I1/v2、资源、状态与缺口；访问拒绝不换成更高权限查询，总上限四次，关键证据取不到即交接未知。

E4两分支都是E3，去重同源，不证明队列满。E5旧runbook仅适用v1，新调查依据v2埋点说明选适配器日志，旧规则标过期；两者都不授写权。E7保留旧P-old/C1与新P-new/C2、节点H1、v2及事件/观测时刻；旧日志超时是证据缺口，新健康不能证明旧实例无故障或根因已消失。

关闭入口：E6只批准I1/v2该动作，需执行端获权并确认版本、保留规则路径与输入状态；发现误目标、规则失败或额外副作用时停止。没有执行确认就记“已批准、执行未知”。回滚：另须批准具体目标旧版本，核迁移/数据兼容与备份；E1兼容未知，因此不能无条件回滚。两者恢复都看正常流量下错误比例、成功/失败延迟、降级显示、用户结果与数据完整性。

事故更新参考：“I1/v2模型超时增加，规则路径正常。外部端点与本地并发是待验证假设，配额查询拒绝且队列数据缺失。关闭入口已批准，执行仍未知；实例替换不证明根因修复。错误数降低伴随流量下降，恢复尚未确认。”改进可为平台负责人在下一次发布前补队列与回退埋点，用正常/超时两路径证明失败保留和告警可见；此处只是计划。

### 理解检查

**200为什么仍可业务失败？** 可能内容错误或违反承诺；明确降级是否合格由具体指标契约决定。

**测试通过还要监控吗？** 要，真实流量、依赖、权限与分布不同，测试不覆盖全部运行条件。

**事故Agent发现问题就可重启吗？** 不可，需授权、影响范围、兼容和恢复条件，重启可能加剧事故。

**纸面恢复表通过是否完成交付？** 否，真实CRUD、持久化、降级和恢复各需执行证据。

## 1. 原型成功与产品交付之间

“页面能点”只证明一个演示路径。一个完整 CRUD 应用还要证明：创建能持久化、重启后能读取、修改与删除影响正确对象、非法输入被拒绝、网络失败不会重复写入，用户能理解当前状态。

生成 UI 时先定义实体、关系、流程和错误状态。把同一需求分别交给不同技术栈时，保持行为契约一致，否则比较的是不同产品而不是不同开发方式。

## 2. 最小全栈验收

| 场景 | 预期 |
| --- | --- |
| 新建有效笔记 | 返回对象 ID，列表可看到 |
| 重启服务 | 笔记仍存在 |
| 更新不存在对象 | 返回明确错误，不创建幽灵对象 |
| 删除后再读取 | 按契约返回缺失 |
| 输入为空或过长 | 拒绝或按规格处理 |
| 网络失败与重复点击 | 不出现意外重复写入 |
| 手机窄屏和键盘导航 | 主流程可操作，无关键内容遮挡 |
| 模型不可用 | 错误或降级明确，不假装模型成功 |

是否需要多用户权限、分页和上传取决于需求；不要在最小作业里无限加功能。但部署扩大边界时必须重新做威胁评估。

## 3. 多技术栈实验

[2025 第 8 周作业](../../_assignments/2025%20fall/week8/assignment.md) 要求三个同功能应用，至少一个用 Bolt，至少一个含非 JavaScript 语言，保留导出的源码和可复现 README。

如果没有平台额度，可先用 FastAPI + 静态页面和另一技术栈做对照，这是自学改编，不满足原作业三版本与 Bolt 要求。不要承诺学生优惠对所有读者仍有效。

每个版本使用独立目录、依赖和数据库，记录生成提示、人工修改和已知问题。评价实现耗时、纠错耗时、验收通过率、运行成本和维护难度；仅截图漂亮不能衡量软件质量。

## 4. 可观测性是回答问题的能力

日志描述离散事件，指标描述聚合变化，trace 连接一次请求跨组件的时间线。三者帮助解释系统状态，但大量无关联输出不等于可观测。

请求进入 API、模型调用、解析、回退、数据库提交与响应，应能通过 request ID 或 trace ID 关联。日志记录必要状态、引擎和错误分类，不默认记录全部会议原文、token 或模型上下文。

针对提取功能至少观察：请求数、延迟分布、模型超时率、解析失败率、规则回退率、队列长度及资源使用。语义质量无法仅从 HTTP 200 获知，需要抽样标注、用户反馈或约束检查。

## 5. 四个黄金信号

课程运维资料讨论延迟、流量、错误与饱和度。

- 延迟：分别观察成功与失败请求，避免快速失败拉低平均值。
- 流量：请求数、模型调用数或队列任务数，分清用户请求与重试。
- 错误：不仅是 500，也包括超时、错误内容和不符合业务约定的结果。
- 饱和度：CPU、内存、连接池、队列和外部配额是否逼近限制。

HTTP 请求成功率与模型成功率是不同指标。大量静默回退可能让前者稳定，却让用户真正想要的能力退化。

## 6. 定义 SLO 与降级

SLI 是可测指标，SLO 是目标。例如“在练习期内，合法提取请求中至少 99% 在两秒内得到正常或明确降级响应”。这只是教学目标示例，不是原应用承诺；选择目标需要考虑模型资源和实际业务。

必须定义分母和窗口，以及降级是否算业务成功。基础 API 可用性允许降级，不意味着模型任务质量目标也达成。错误预算表示可容忍的目标偏离，用于决定发布节奏，而不是任由错误发生的许可。

超时应覆盖完整调用链；重试需要次数上限、退避和抖动。对写入必须结合幂等。持续外部失败时，熔断或提前降级能避免积压，恢复后用受控探测重新启用。

## 7. 事故响应的证据链

发现问题后先确认影响和严重程度，再收集时间线、日志、指标、近期变更和依赖状态。优先止损，不要求先证明全部根因才回滚；但也不要因“刚发布过”就认定发布必然是原因。

例如模型超时上升：检查是否只有模型路径慢、规则路径是否正常、外部配额是否限流、队列是否积压。可能的止损是降低并发、停用模型入口或切换明确的规则降级，不是无上限重试。

Agent 可以帮助归纳证据与提出假设。高风险生产操作仍需批准，且应记录执行者、动作、时间和回滚结果。只读诊断 Agent 不应持有部署或数据库删除权限。

## 8. 无责复盘，但要有行动责任

报告包含影响、时间线、检测过程、根因与促成因素、止损、恢复证据、哪些做得好、哪些需改进。不要只写“操作失误”；还应问为什么系统允许该错误扩大。

每个改进项有负责人、期限和验证方式，例如新增超时回归测试、限制重试、增加回退告警。不确定的根因明确标记为假设，不能用流畅总结代替证据。

## 9. 动手：交付与故障演练

1. 完成一个贯穿项目版本的 CRUD，按验收表逐项检查，并验证服务重启后的数据。
2. 记录模型调用、解析和回退事件；使用假数据，检查日志没有秘密。
3. 在练习环境中注入可控超时或无效模型响应。先写预期，再观察真实状态。
4. 确认降级比例上升能被识别，界面不会把规则结果说成模型结果。
5. 演练关闭模型功能或恢复上一个应用版本；数据库结构变化不能仅靠代码回滚解决，要说明兼容性和备份策略。
6. 写事故报告，分清观测、假设与已证实根因，再制定一个能够实际验证的改进项。

验收：CRUD 与重启持久化通过，有请求关联信息、有回退观测、有一次恢复证据，没有将学习演练描述为真实生产事故。

### 部署后保护 Agent 本身

监控模型端点还不够：后台任务重试、工具权限和流水线触发也会扩大故障。记录队列年龄、每任务尝试数、取消确认时间、拒绝写入、审批绑定版本和部署版本。模型请求网关的日志不能独自证明工具执行，工具端审计应关联同一任务 ID。

在隔离副本中用 30 分钟、零云调用模拟三个假任务：依赖持续失败、撤销凭据、重复事故告警。先写预期，再检查是否有限重试、停止新副作用、保留部分成果，并将同根因告警归到已有事故；恢复只允许一次受控探测。验收保留事件表、止损决定、复测与回滚条件。纯事件演练不代表真实熔断或权限撤销有效，需要实现后故障注入验证。这个学习环属于第 10 周主题的教程扩展，不是未取得讲座的摘要。

## 10. 自测与答案

**问：HTTP 200 为什么也可能是业务失败？** 内容可能错误、缺失或被静默降级，不符合用户的实际目标。

**问：发布前测试通过，为何发布后还需监控？** 真实流量、依赖、权限和数据分布与测试环境不同。

**问：事故 Agent 自动发现问题就可自动重启所有服务吗？** 不能。动作需符合授权、影响范围和恢复策略，重启也可能加剧事故。

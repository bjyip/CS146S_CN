## 1. 原型成功与产品交付之间

“页面能点”只证明一个演示路径。一个完整 CRUD 应用还要证明：创建能持久化、重启后能读取、修改与删除影响正确对象、非法输入被拒绝、网络失败不会重复写入，用户能理解当前状态。

生成 UI 时先定义实体、关系、流程和错误状态。把同一需求分别交给不同技术栈时，保持行为契约一致，否则比较的是不同产品而不是不同开发方式。

## 2. 最小全栈验收

| 场景 | 预期 |
| --- | --- |
| 新建有效笔记 | 返回对象 ID，列表可看到 |
| 重启服务 | 笔记仍存在 |
| 更新不存在对象 | 返回明确错误，不创建幽灵对象 |
| 删除后再读取 | 按契约返回缺失 |
| 输入为空或过长 | 拒绝或按规格处理 |
| 网络失败与重复点击 | 不出现意外重复写入 |
| 手机窄屏和键盘导航 | 主流程可操作，无关键内容遮挡 |
| 模型不可用 | 错误或降级明确，不假装模型成功 |

是否需要多用户权限、分页和上传取决于需求；不要在最小作业里无限加功能。但部署扩大边界时必须重新做威胁评估。

## 3. 多技术栈实验

[2025 第 8 周作业](../../_assignments/2025%20fall/week8/assignment.md) 要求三个同功能应用，至少一个用 Bolt，至少一个含非 JavaScript 语言，保留导出的源码和可复现 README。

如果没有平台额度，可先用 FastAPI + 静态页面和另一技术栈做对照，这是自学改编，不满足原作业三版本与 Bolt 要求。不要承诺学生优惠对所有读者仍有效。

每个版本使用独立目录、依赖和数据库，记录生成提示、人工修改和已知问题。评价实现耗时、纠错耗时、验收通过率、运行成本和维护难度；仅截图漂亮不能衡量软件质量。

[三栈作业导读](../reading-notes/fall2025/week08/assignment-guide.md)分析现存 React/FastAPI、Django、Flask 项目，保留原 100 分评分与 Bolt 来源缺口。具体契约反例：Django/Flask 手写 JSON 路径把 null 标题转成 `"None"`、字符串 `"false"`转成 true，而 FastAPI 有不同类型验证；Django 还需先通过 CSRF。相同用户目标不意味着三版 JSON 包装、错误码或表单路径完全相同，更不意味着都通过验收。

离线用 15 分钟、零网络/安装/导入/运行，写 null/字符串布尔/非对象三个假请求的业务预期和框架适配，再标出 FastAPI lifespan、Django migrate、Flask 顶层 import 的存储初始化时点。验收为契约差异与隔离计划，不创建数据库；响应丢失重试、旧整对象 toggle 覆盖新标题、依赖锁/端口和 50 分钟完整替代见导读。源码存在与报告耗时不替代持久化、浏览器或 Bolt 实测。

### 生成构建器与交付边界

[2025 全栈讲义第 13–15 页解读](../reading-notes/fall2025/week08/lecture-end-to-end-app.md)的原例是 Bolt 萨尔萨舞舞伴查找应用，备注记录配色、图标、字体修改，以及 WebContainer 和生成动作标记。原运行截图、源码与架构箭头没有核验，不把它当本教程行动项项目或当前正式协议。

生成文件、运行预览与目标部署是三层证据。提示可建议成熟框架，动作协议可帮助解析创建和运行请求，但执行端仍需验证路径、动作、依赖、网络和预算。格式合法不等于获准运行；浏览器预览正常也不证明部署兼容、持久化或秘密隔离。

离线用 25 分钟、零网络、零模型调用设计三条假动作：写允许路径、读目录外假秘密、安装未知依赖。标注解析是否成立、执行是否获准与缺失证据，不执行生成代码或安装。再把“配色完成”与“重启仍有数据”写成独立验收行。验收是三项权限决策和两类证据清单；不能声称应用或容器隔离已实测。

## 4. 可观测性是回答问题的能力

日志描述离散事件，指标描述聚合变化，trace 连接一次请求跨组件的时间线。三者帮助解释系统状态，但大量无关联输出不等于可观测。

请求进入 API、模型调用、解析、回退、数据库提交与响应，应能通过 request ID 或 trace ID 关联。日志记录必要状态、引擎和错误分类，不默认记录全部会议原文、token 或模型上下文。

针对提取功能至少观察：请求数、延迟分布、模型超时率、解析失败率、规则回退率、队列长度及资源使用。语义质量无法仅从 HTTP 200 获知，需要抽样标注、用户反馈或约束检查。

### Span 关系、采样与降级证据

[Last9 逐份解读](../reading-notes/fall2025/week09/02-traces-spans.md)将 trace 拆成有时间、状态与关系的 span。请求 span 覆盖子操作，子操作也可能并行，所以所有 span 时长之和不是端到端延迟。慢操作支持进一步调查，不独自证明根因；跨主机时钟偏差也需纳入解释。

传播上下文让跨服务操作关联，异步边界缺失可能拆散 trace。没有记录不能直接判定没有调用；trace ID 不代表合法身份，也不授予工具权限。只传播必要且脱敏的字段，不默认将会议原文、token 或完整错误放入属性、baggage 或 tracestate。

模型超时后规则回退可以让请求按契约返回 200，但 model span 仍保留错误，request 另记降级引擎。业务质量仍需单独验收。Head sampling 提前舍弃的细节不能事后恢复；Tail sampling 能按结果筛选，但缓存、迟到记录和导出失败仍可能造成缺口，不能保证全部错误保留。

错误优先采样会改变观测分布，不能拿保留 trace 的比例直接填全体 SLO。教程假例：100 次请求中 8 次模型超时，只保留 8 次超时和 2 次正常 trace，则样本占比为 80%，全量比例为 8%。全量分母需有独立聚合计数；trace 也不自动等同于完整安全审计。

离线用 30 分钟、零网络/模型/安装分析笔记中的假 span 表：request 为 100 ms，model 为 60 ms，所有行合计 225 ms。画重叠区间，解释错误与降级状态，列一条根因反证需求和一处传播缺口，再算上述两种比例。验收保留计算、事实/假设/未知与脱敏字段预算；不执行 SDK 示例，也不将纸面分析记为采样、隐私保护或性能已实测。

## 5. 四个黄金信号

课程运维资料讨论延迟、流量、错误与饱和度。

- 延迟：分别观察成功与失败请求，避免快速失败拉低平均值。
- 流量：请求数、模型调用数或队列任务数，分清用户请求与重试。
- 错误：不仅是 500，也包括超时、错误内容和不符合业务约定的结果。
- 饱和度：CPU、内存、连接池、队列和外部配额是否逼近限制。

HTTP 请求成功率与模型成功率是不同指标。大量静默回退可能让前者稳定，却让用户真正想要的能力退化。

## 6. 定义 SLO 与降级

SLI 是可测指标，SLO 是目标。例如“在练习期内，合法提取请求中至少 99% 在两秒内得到正常或明确降级响应”。这只是教学目标示例，不是原应用承诺；选择目标需要考虑模型资源和实际业务。

必须定义分母和窗口，以及降级是否算业务成功。基础 API 可用性允许降级，不意味着模型任务质量目标也达成。错误预算表示可容忍的目标偏离，用于决定发布节奏，而不是任由错误发生的许可。

超时应覆盖完整调用链；重试需要次数上限、退避和抖动。对写入必须结合幂等。持续外部失败时，熔断或提前降级能避免积压，恢复后用受控探测重新启用。

## 7. 事故响应的证据链

发现问题后先确认影响和严重程度，再收集时间线、日志、指标、近期变更和依赖状态。优先止损，不要求先证明全部根因才回滚；但也不要因“刚发布过”就认定发布必然是原因。

例如模型超时上升：检查是否只有模型路径慢、规则路径是否正常、外部配额是否限流、队列是否积压。可能的止损是降低并发、停用模型入口或切换明确的规则降级，不是无上限重试。

Agent 可以帮助归纳证据与提出假设。高风险生产操作仍需批准，且应记录执行者、动作、时间和回滚结果。只读诊断 Agent 不应持有部署或数据库删除权限。

### 故障定位与动作前提

[2025 DevOps 讲义第 8–9 页解读](../reading-notes/fall2025/week09/lecture-incident-response-devops.md)以凌晨数据库查询 500 告警为假设情境。按读/写、主/副本、单分片/全局、应用连接池/数据库负载缩小范围，比立即重启所有服务更能组织证据。近期部署只是调查线索，相关性不能证明根因。

备注的快速回滚、重启和路由建议需要授权与前提：迁移可能不兼容旧代码，副本可能滞后，主节点可能无额外容量，重启可能触发连接风暴或丢失证据。止损不必等完整根因证明，但需记录动作、风险、停止条件和恢复检查，不能照抄讲义为无条件生产命令。

[Resolve Kubernetes 排障文章](../reading-notes/fall2025/week09/03-kubernetes-troubleshooting.md)补充短生命周期实例的证据问题。教程要求记录事件/观测时刻、Pod UID、容器、节点和版本，新实例健康不能证明旧实例没有故障；知识图谱只组织调查，不证明因果。文章把自动修复部分描述为未来能力，不能据宣传授予生产写权限；具体集群和图像未验证。

用 30 分钟、零网络和零云调用，为六条假事件提出“连接池不足”和“特定写查询负载”两个竞争假设。给每个假设列一条支持证据、一条反证需求；给降低并发和回滚各写权限、迁移兼容条件及恢复指标，不执行动作。事件涉及资源替换时补实例身份与两种时刻，缺失日志不能记为没有错误。验收是事实/假设/待验证表与两个动作前提，不把纸面计划记为已经恢复。讲义第 11 页正文列 SLA，备注却称未明确跟踪；第 16 页重复代码审查文字，均不能用作本讲运维实证。

### 生产 Agent 的三类上下文能力

[Resolve 嘉宾讲义第 18–32 页](../reading-notes/fall2025/week09/lecture-resolve-guest.md)的可提取文字提出连接并建模生产系统、捕获团队知识、规划并行调查，以及将生产复杂性纳入评测。文字已核对，全部视觉核验仍待完成；这些是讲者的设计观点，不是产品效果证明。以下权限、版本治理和预算要求，以及贯穿项目案例与练习，是教程扩展。

依赖图用于决定去哪里查，不直接证明因果。给每条关系保留来源、观察时间和版本；先按受影响服务与时间窗聚合，再取必要脱敏片段，记录查询、范围、截断与证据 ID。访问被拒绝、超时、无匹配与系统正常必须分开，不能用摘要隐藏失败。

团队隐性知识可理解为“这个服务的日志实际在哪”“业务称谓对应哪个服务”等经验，这两个例子为教程补充，不是未经核验的截图内容。教程要求为知识保留适用版本、确认来源与失效条件；新埋点替换旧日志源时应更新或撤销旧规则。聊天与 runbook 是材料，不是扩大权限或执行危险指令的授权，反馈信号也不证明记忆质量已提高。

并行调查共用事故 ID、时间窗和证据表，各分支记录支持、反证、下一步与停止条件；引用同一日志不算独立确认。高置信标签、多分支一致意见和任务打勾都不能替代原始证据，不同展示案例也不能拼成一个已证实根因。

**离线练习（教程扩展）：** 用 40 分钟、零网络/模型/生产操作，设定假事件：模型路径慢、规则路径正常、配额查询拒绝访问、旧 runbook 指向过期日志源。画五节点依赖图，为端点慢和队列积压安排两个分支，每分支最多两项只读检查，写查询条数上限。更正旧知识的版本范围；总预算或工具持续失败时停止并交接未知项。

验收保存图关系来源、查询契约、知识更新、共享证据与两个竞争假设，再预写“端点慢、队列积压、遥测不足、旧知识误导”四个评测用例的期望行为。工具拒绝不能写成健康，证据不足应允许不确定答案。此练习只验证调查和评测设计，不证明真实工具、模型或权限隔离有效；讲义没有披露完整 eval 数据集或效果结果。

### 从调查建议到收益验证

[Resolve 产品深读](../reading-notes/fall2025/week09/04-autonomous-teammate.md)将图谱、即时调查、根因理论、协作动作和复盘串成流程，但不到一分钟提出理论不是一分钟恢复。记录观察、假设、建议、批准、执行和恢复六种状态；文字要求回滚不等于执行端已授权，批准也不等于动作成功。该文与 Kubernetes 文章的自动修复时态不同，缺少日期和版本依据，不能拼成当前产品保证。

[多 Agent 架构文章](../reading-notes/fall2025/week09/05-multi-agent-ai-native.md)主张专业分支并行调查。单 Agent 也可调度并发工具和外部状态，不能按架构标签宣称多 Agent 必然更快。每轮固定事故 ID、时间窗、版本和总预算；分支返回证据、反证与未知，协调者去重同源证据并处理冲突，迟到的旧轮次结果不能覆盖当前结论。这些治理要求是教程扩展，文章没有披露完整协议或同条件对照。

[五项值班收益解读](../reading-notes/fall2025/week09/06-on-call-benefits.md)将减少疲劳、更新知识、一致调查、证据协作与主动止损转成待验证假设。观察人工中断与确认耗时、旧知识拒绝、关键证据覆盖、判断可追溯性、错误预警和不必要动作；自动报告数、修复次数和任务打勾均不是业务收益。记录告警到摘要、确认、止损和恢复的不同时间，失败与超时不从分母删除。

离线用 35 分钟、零网络/模型/生产操作，给行动项提取器设计 10 个假告警，含重复、缺日志、旧知识和误预警。预写五项收益的失败判据，安排最多三个分支、六项假查询，区分建议与实际动作；用[实验模板](../reference/templates.md)保留人工成本、工具预算和未知，不填未测收益。验收是指标、反例、去重理由与状态表，不证明真实产品、并行加速或值班压力已改善。

## 8. 无责复盘，但要有行动责任

报告包含影响、时间线、检测过程、根因与促成因素、止损、恢复证据、哪些做得好、哪些需改进。不要只写“操作失误”；还应问为什么系统允许该错误扩大。

每个改进项有负责人、期限和验证方式，例如新增超时回归测试、限制重试、增加回退告警。不确定的根因明确标记为假设，不能用流畅总结代替证据。

## 9. 动手：交付与故障演练

1. 完成一个贯穿项目版本的 CRUD，按验收表逐项检查，并验证服务重启后的数据。
2. 记录模型调用、解析和回退事件；使用假数据，检查日志没有秘密。
3. 在练习环境中注入可控超时或无效模型响应。先写预期，再观察真实状态。
4. 确认降级比例上升能被识别，界面不会把规则结果说成模型结果。
5. 演练关闭模型功能或恢复上一个应用版本；数据库结构变化不能仅靠代码回滚解决，要说明兼容性和备份策略。
6. 写事故报告，分清观测、假设与已证实根因，再制定一个能够实际验证的改进项。

验收：CRUD 与重启持久化通过，有请求关联信息、有回退观测、有一次恢复证据，没有将学习演练描述为真实生产事故。

### 部署后保护 Agent 本身

监控模型端点还不够：后台任务重试、工具权限和流水线触发也会扩大故障。记录队列年龄、每任务尝试数、取消确认时间、拒绝写入、审批绑定版本和部署版本。模型请求网关的日志不能独自证明工具执行，工具端审计应关联同一任务 ID。

在隔离副本中用 30 分钟、零云调用模拟三个假任务：依赖持续失败、撤销凭据、重复事故告警。先写预期，再检查是否有限重试、停止新副作用、保留部分成果，并将同根因告警归到已有事故；恢复只允许一次受控探测。验收保留事件表、止损决定、复测与回滚条件。纯事件演练不代表真实熔断或权限撤销有效，需要实现后故障注入验证。这个学习环属于第 10 周主题的教程扩展，不是未取得讲座的摘要。

## 10. 自测与答案

**问：HTTP 200 为什么也可能是业务失败？** 内容可能错误、缺失或被静默降级，不符合用户的实际目标。

**问：发布前测试通过，为何发布后还需监控？** 真实流量、依赖、权限和数据分布与测试环境不同。

**问：事故 Agent 自动发现问题就可自动重启所有服务吗？** 不能。动作需符合授权、影响范围和恢复策略，重启也可能加剧事故。

**问：依赖图、历史知识和多个调查分支为何仍不足以确认根因？** 图可能过期，知识可能错误，多个分支可能重复引用同源证据；需可追溯证据、竞争假设和反证。工具失败时应保留未知，不能输出确定的健康或根因判断。

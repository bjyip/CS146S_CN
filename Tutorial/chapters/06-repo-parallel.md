# 06 Agent 就绪仓库与并行开发

[上一章](05-skills-automation.md) | [目录](../README.md) | [下一章：测试与审查](07-testing-review.md)

新参与者接手开发者控制中心的“行动项稳定排序”任务，却不知道列表真正从哪进入、测试从哪运行、临时库是否覆盖启动时的库。此时增加几个 Agent 只会让几个人一起猜。本章先把这三个障碍变成可核对证据，再拆依赖、隔离资源，最后讨论离线时怎样保存后台任务。

**前置与路线**
- 能读懂文件路径、列表排序和条件分支即可。基线是各参与者共同开始的版本；工作区是实际读写文件的目录，本章会继续解释隔离与租约。
- 先读第 1–5 节非折叠正文，再做第 6 节四项基础练习和第 7 节答案。阅读约 40–55 分钟，练习约 50 分钟；可分两次，估计未经新手实测。
- 只需章内假仓库、假事件和纸面记录，不联网、不运行模型、Git 写操作、测试或应用，不建数据库。产物是就绪证据、依赖卡、隔离表与恢复状态表。
- worktree 实操、真实并行、后台执行与原作业均选学，未执行。源代码、布局、进程、业务副作用是不同状态，不能从界面动画推断。

## 1. 仓库结构决定 Agent 的工作成本

用一个完整假仓库开始，不要求查看源作业。任务是“行动项按 `created_at` 升序，同值按 ID 升序”，不改响应字段。入口说明列出 `backend/routes/items.py` 调用 `backend/services/items.py`；后者负责排序，`backend/schema.json` 由模型定义生成，不手改。测试从 `lab/backend` 运行，数据约定为任务独立临时库。下面的三次障碍是假证据，不是本仓库实测：

| 新参与者遇到的障碍 | 当前已有信息 | 下一份证据 / 当前能否继续 |
| --- | --- | --- |
| 两个名字相似的排序函数 | 路由指向 services/items.py | 沿调用关系确认权威入口；不修改未调用副本 |
| 从 lab 运行时报导入失败 | 文档说工作目录是 lab/backend | 对照目录和准确命令；不先升级依赖 |
| fixture 声称临时库，但启动仍指向默认库 | 请求会话和启动 engine 是两条路径 | 同时确认导入、启动、请求和清理的数据路径；未隔离前不执行 |

我们需要的不是更漂亮的文件树，而是“任务 → 实际入口 → 当前契约 → 可安全验证 → 失败能恢复”的路径。这种让新参与者少猜、可定位和可验收的状态称为 Agent 就绪度，也同样有益于人。

Agent 每次需要重新定位入口、猜测试命令和判断生成文件时，都会增加调用次数与错误机会。对人友好的明确架构、稳定接口和可运行测试，同样对 Agent 有帮助。

“Agent 就绪”不是增加一个规则文件就完成，而是降低研究、修改、验证与恢复的不确定性。仓库应当让一个新参与者能够从任务定位到行为证据。

## 2. 一个自学用审计表

为了区分“写了”和“证实了”，下面用教程自定义评分，不是课程或行业认证。每项 0 分表示缺失，1 分表示有文档但未验证，2 分表示在新环境中实际验证过，总分 16 分。纸面分析最多支持文档层，不生成 2 分的运行证据。

| 项目 | 要求的证据 |
| --- | --- |
| 启动 | 明确前置条件、工作目录和启动命令 |
| 测试 | 独立测试数据、可重复测试命令 |
| 架构 | 入口、模块边界和数据流可定位 |
| 契约 | schema、错误行为与文档一致 |
| 配置 | 示例配置无秘密，真实配置隔离 |
| 修改范围 | 生成物、第三方文件和并发工作可识别 |
| 质量门禁 | 检查失败能阻止合并或发布 |
| 恢复 | 回滚、数据库迁移和故障处理说明 |

分数只帮助定位缺口。一个没有授权隔离的高分仓库仍可能危险。不能通过添加文档来假装获得未执行的验证分。

[AI IDE 讲义第 12–14 页](../reading-notes/fall2025/week03/lecture-ai-ide-setup.md#6-第-12-页仓库一致性比增加提示词更基础)强调导览、访问模式、API 契约和规则导航，本节已有对应审计，不另建重复清单。原讲者鼓励 monorepo，但本教程不据此推荐迁移：仓库结构应根据依赖、权限、构建和发布边界选择；先修入口歧义，不以“适合 AI”为由改整个架构。

### 用独立任务检验就绪度

例如第一次读者只能定位入口，不能确认数据库隔离，就记录“架构有调用关系证据；测试运行受隔离缺口阻塞”，而不是把测试命令存在填成验证成功。修补要对应原障碍：补准确目录、统一生成入口、隔离启动 engine 后，另用难度相近的新任务复核；任务差异和共享知识都可能影响结果，不能只凭变快宣布普遍提速。

<details>
<summary>选学：真人或新会话的真实就绪度实验与来源比较</summary>

文档“看起来完整”与新参与者能完成任务是两回事。在练习副本中选一个小变更，例如给列表增加稳定排序。只提供需求和仓库入口，不口头补充隐藏命令，让另一位读者或新会话 Agent 定位入口、运行基线、修改和验收。没有真人时可用新会话代替，但它不等价于独立人类实验，应说明先前共享知识可能产生的影响。

记录找到入口所需时间、失败命令、求助次数、越界修改、验证遗漏和最终结果。卡在“测试该从哪里运行”时，先修工作目录说明；卡在数据库污染时，先补临时数据配置；不因一次不成功就加入更多 Agent。补两个缺口后，用难度相近但未见过的任务复测，说明任务差异的混杂，不宣称一次变快证明普遍提升。

同步审计三类漂移：规则中的命令是否仍可运行；文档契约是否仍与实际代码一致；生成文件是否有可追溯的生成命令。对于生成 schema，应改权威源并按项目流程生成，不能手改生成物掩盖漂移。对于旧规则，核对当前代码与测试后修正，不能自动把旧规则当最新需求。

[OpenAI 使用 Codex 的报告第 11–12 页解读](../reading-notes/fall2025/week01/05-how-openai-uses-codex.md)补充先定位和规划、按 Issue 提供边界、迭代环境、用队列保存零散任务。任务约一小时或几百行是历史经验，不是安全阈值；启动脚本存在不等于运行成功，增加网络或凭据也不是默认修复。用笔记的 40 分钟零执行迁移卡和队列卡核对入口、消费者、共享资源与交接，不填后台执行或收益。

验收：一项任务无需隐藏口头说明即可完成，有实际基线与改后证据；每个修补缺口能对应原先失败；过期指令、生成物和权限边界可定位。资料来自 README 新增的仓库就绪主题，这套实验是教程扩展，未读取的视频和 X 帖文不是实验结论的依据。

## 3. 分解任务要按依赖，而不按人数

入口清楚以后，仍不能把“实现排序、编写前端、更新说明”直接发给三人。前端和测试需要先知道同时间记录如何排列；若一人按 ID 升序、另一人按降序，各自工作看似正确，组合仍错。因此先冻结契约和基线，再让独立产物并行。

假任务分为 K 确认排序契约，I 实现服务排序，T 按契约设计独立预期，D 更新接口说明，V 集成核对。依赖为 `K -> I/T/D -> V`：T/D 可在契约固定后并行准备，V 必须等待实现和验收材料齐全。共同文件若必须同时写，先指定唯一所有者；其他人只读或等待，不靠角色名字解决冲突。

最小任务卡写清：“共同基线 lab-v1；契约 created_at、ID 都升序；I 只改 services/items.py；T 只改 tests/test_items.py；D 只改 docs/items.md；不改 schema；验收输入 (时间10,ID2)、(时间10,ID1)，预期 ID1、ID2；超过批准范围先暂停；无运行证据只交付设计。”这里的并行是安排，不是已启动任务。

“让一个 Agent 改接口，另一个改同一个 schema，第三个改测试”看似并行，实际依赖强。schema 未确定，另外两人只能猜，最后集成返工。

可以先统一契约，再让独立工作区分别做前端适配与文档；或让一个实现，另一个只读审查。任务分工应明确文件所有权、共享接口、基线提交、输出格式和合并顺序。

并行收益取决于独立程度，还要付出协调、重复研究和集成成本；更多 Agent 不保证更快。

<details>
<summary>选学：理想加速公式</summary>

串行部分占比为 `s`、工作者数为 `n` 时，理想加速比上限约为 `1 / (s + (1-s)/n)`。例如 s=1/2、n=2 时上限为 4/3，不是两倍；现实还要计协调与返工，公式不预测模型正确率或真实收益，未做速度实验。

### 同步与异步首先是注意力与交接的选择

契约未定时同步澄清，即及时来回确认；契约固定且任务可独立核对后，可以异步委派，稍后收成果。同步/异步描述交互节奏，本地/云端描述运行位置，两者不能互换。异步尤其需要非目标、预算、停止和证据，因为用户未必马上回答。

<details>
<summary>选学：课堂工作流、耗时与交接对照</summary>

[Silas 讲义第 6–24 页](../reading-notes/fall2025/week03/lecture-silas-alberti.md)将同步规划、异步编码、同步复核连接起来。同步适合快速澄清和局部反馈，异步适合边界明确、可以稍后审查的独立任务。本地/云端描述位置，不等于同步/异步，也不自动说明权限隔离。课堂耗时区间不是通用超时标准。

交接保留基线、契约、相关文件、非目标、预算、停止条件与验收。例如排序契约未定先同步讨论，再让独立任务异步完成文档和测试设计。“已完成”却没有差异、命令、断言或未验证项，应退回补证据。讲者约 10%、20%、6–12 倍和人工投入比例未提供评测方法，不能变成本教程效率承诺。

离线练习：30 分钟、零网络与零模型预算，在独立目录写两张虚构任务卡，给出同一基线与不重叠文件；走查“共享契约未定”“超预算等待澄清”“只有成功叙述无测试”三条事件。验收记录依赖导致的暂停、交付证据和未运行状态，分别估计人工与端到端时间，说明重叠和集成的不确定性。纸面委派不证明真实并行速度或云端隔离。

[Coding Agents 101](../reading-notes/fall2025/week03/03-coding-agents-101.md)把异步委派理解为减少人的同步注意力占用，不是端到端收益证明。无进展时重开会话前，保留规格、当前差异、失败、权限和剩余预算并核对工作区；新上下文不自动撤销已有副作用。配套零执行练习以委派卡、检查点矩阵和止损交接验收理解，不填写作者未提供的实测收益。

</details>

## 4. worktree 隔离了什么

`git worktree` 为同一仓库提供不同工作目录和分支，减少同时编辑相同文件的干扰。它不隔离端口、环境变量、用户全局配置、外部账号或共享数据库。

假设 I 的目录为 `lab-i`、T 的目录为 `lab-t`，但都监听 8000 并写 `shared.db`，仍会端口冲突或污染测试。完整隔离表应分别约定目录、共同版本、端口、启动库与请求库、环境配置和任务凭据；仅换目录不等于沙箱，即执行端实际限制可访问资源的环境。没有必要创建工作区时可以串行处理，隔离是为了真实冲突，不是为了演示工具。

以下只是练习命令示例，不是教程作者已执行的操作。先确认当前已有工作和分支，父目录存在；未经本人决定不要创建提交或清理其他人的目录。在自己的练习仓库中：

```powershell

git worktree add "../cs146s-ui" -b lab/ui
git worktree add "../cs146s-tests" -b lab/tests
```

worktree 从提交基线开始，不会自动包含当前未提交修改。如果任务依赖这些修改，先决定如何提供一致基线，不能让不同 Agent 对不同版本工作。使用不同端口、临时数据库和任务凭据；依赖环境的隔离也应记录。

集成时检查每个分支完整差异与测试，合并后再跑联合测试。两个分支各自通过，不意味着合在一起通过。出现冲突按规格解决，不按谁的代码更多决定。

上述 Git 写操作和合并示例本轮未执行，不是基础完成条件。

## 5. 后台 Agent 需要持久任务状态

异步任务可能在用户离线时运行，需要记录任务 ID、基线、预算、权限、租约与状态。推荐状态链为“待办、运行、等待批准、验证、待合并、完成”，失败或取消则进入独立状态。

持久状态是进程退出后仍能恢复的任务记录，不只是对话里一句“正在处理”。任务 ID 表示哪项工作，租约表示谁在多长时间内有资格处理它，代次表示第几次领取/接管。还需保存契约版本、已产生差异、批准与未验证项，恢复时先对账，不能因新会话开始就忘掉旧副作用。

同一个 Issue 重复触发时需要幂等识别，避免多个 Agent 同时实现同一任务。失败恢复要判断是否留下部分文件或外部写入。取消应停止活动进程并保留诊断，不只是停止显示进度。

Issue-to-PR 的“完成”应至少表示差异和测试已经提交给审查，而不是已自动上线。默认后台 Agent 无部署凭据；合并和发布仍按项目门禁处理。

### 租约到期不等于旧工作者已经停下

租约让失联任务可被接管，但旧进程可能仍在运行。每次接管递增任务代次，最终产物或写入前检查该代次仍有效，拒绝过期工作者；仅在开始时检查一次不足以阻止稍后的副作用。取消也需要执行端确认，确认前记录“取消中”，不能宣布已停止。

例如同一个排序 Issue 被重复投递，按项目、Issue 和明确任务版本去重；基线或需求版本改变时先决定更新旧任务还是新建任务。过期工作者 A 不能在 B 接管后覆盖 B 的产物。等待批准时可保存状态并释放计算资源，批准对应确切差异；代码改变后旧批准不再适用，但批准记录必须保留以供审计，不删除或伪装成从未批准。

| 完整假事件 | 持久记录与允许动作 |
| --- | --- |
| 项目lab、Issue17、任务版本v1第一次投递；再次收到相同键 | 保留一项任务 J17，不创建第二项；共同基线 lab-v1 |
| A 领取，代次1；租约到期，B接管 | 原子地更新所有者B、代次2；租约到期不证明A已停 |
| A 提交代次1产物 | 拒绝旧代次，不写入；保存拒绝原因和证据 |
| B 产出差异 d1，等待批准；有权限人员批准 d1 | 记录批准者、差异版本和范围；只对d1适用，不批准任意未来差异 |
| B 又改成 d2 | 保留d1批准历史，d2回到等待批准；不能沿用旧批准 |
| 用户取消 d2，执行端未确认；随后确认停止 | 先“取消中”，拒绝新写入并请求停止；确认活动进程停止、在途操作结果已对账后才“已取消” |

代次与取消状态必须在实际产物接纳/副作用入口原子校验，不能只在开始时看一眼。已经发生的外部写入不会因取消自动撤销，应记录并由获准恢复流程处理。表格展示设计规则，不证明真实数据库实现具备并发安全。

### 快速反馈必须区分计划、执行与验收

最小界面应展示“计划已生成”“实际执行及退出状态”“验收范围”“等待批准/取消中”，不要把它们都画成成功。规则回退完成任务时显示实际引擎和回退原因，不宣称模型成功；缺日志时显示待证据。终端布局恢复、聊天历史恢复、进程继续和业务写入结果恢复也需要不同证据。

## 6. 动手：修补就绪度，再测并行

### 基础必做：四项纸面练习

每项输入全部给出，零网络、零模型、零程序和 Git 写操作。先作答，再核对第 7 节；时间约 50 分钟，不要求另查原作业。

1. **就绪证据，10 分钟。** 假仓库启动有目录/命令说明但未执行；测试有临时请求库文档，已知启动仍写默认库；架构有明确路由到服务关系但未在新环境验证；其他五项无说明。按第 2 节八项分别打分、写证据；选两个优先缺口，说明为何不能给运行验证分。验收是八项总分可复算、危险隔离问题不被总分掩盖。
2. **依赖与交接，10 分钟。** 用 K/I/T/D/V 五项：K契约未定，I实现、T设计测试、D更新文档、V集成；统一 lab-v1。写依赖图、K完成后的三个文件所有者及V前置条件。再遇事件“D要求改schema”和“预算到期仍等K”。验收暂停越界、保留阻塞，不猜契约或无限等待。
3. **隔离卡，10 分钟。** I在lab-i、T在lab-t，均由lab-v1开始，但共享端口8000、shared.db、全局配置与发布账号；lab目录另有未提交修改。写哪些已隔离、哪些未隔离、如何提供一致基线及哪些操作须另获授权。验收不把worktree当数据库/端口/凭据隔离，也不自动提交或清理他人修改。
4. **持久状态，20 分钟。** 按第 5 节 J17完整事件表写任务ID、代次、状态、允许写入与批准记录：重复投递、A领取、到期B接管、A旧产物、B差异d1获批准、改d2、取消请求、执行端确认。再判断“方案已生成”“规则回退、契约检查假日志通过”“界面动画停止”。验收一任务、旧代次拒绝、旧批准保留不沿用、取消先确认、计划/模型/执行分开。

## 7. 自测与答案

### 集中练习答案

**1. 就绪证据。** 启动1、测试1、架构1、契约0、配置0、修改范围0、质量门禁0、恢复0，总分3/16。测试文档仅支持1分，同时附“启动隔离存在已知缺口，禁止执行”的阻塞标记；不能从临时fixture推导启动安全，更不能给2分。优先确认启动与请求双路径临时库、补齐准确入口和命令核对证据；也可优先恢复说明，但必须说明风险。分数帮助找缺口，不替代授权或安全判断。

**2. 依赖与交接。** 图为 `K -> I/T/D -> V`。K未定时三者不猜接口；固定后I拥有services/items.py、T拥有tests/test_items.py、D拥有docs/items.md，schema非本轮目标且指定协调者负责范围调整。V等待三项成果及共同版本核对，真实合并后还需联合检查，纸面卡不提供通过证据。D需改schema时暂停、说明依赖、申请调整批准，不直接越界；预算到期仍等K时保留基线、阻塞和剩余状态，停止并交接，不偷偷换需求。

**3. 隔离卡。** 两目录和共同提交版本减少文件干扰，但端口、数据库、全局配置和发布账号未隔离；建议不同端口、各任务临时启动/请求库、任务局部配置、无发布凭据/最小只读身份，由执行端限制。当前未提交修改不自动进入worktree，若任务依赖它，先由拥有者决定如何提供一致版本或差异，不能擅自提交、丢弃或覆盖。创建worktree、运行服务、建库、账号操作、合并与发布另需授权；串行安排也可避开部分冲突，但仍要数据隔离。

**4. 持久状态。** 下表是纸面参考，不是后台系统实测：

| 事件 | ID / 代次 / 状态 | 写入与批准判断 |
| --- | --- | --- |
| 首次及重复投递 | J17 / 尚未领取 / 待办 | 同键一项任务，不重复启动 |
| A领取 | J17 / 1 / 运行 | 仅有效租约及获准范围内可执行 |
| 到期B接管 | J17 / 2 / 运行 | 原子接管；A未必已停止，执行端拒绝旧代次 |
| A旧产物 | J17 / 2仍有效 / 运行 | 拒绝代次1产物，保存记录，不覆盖B |
| B的d1获得批准 | J17 / 2 / 等待批准后可进入验证 | 批准者和范围绑定d1，尚非自动合并/发布 |
| 改d2 | J17 / 2 / 等待批准 | d1批准历史保留，d2不得沿用 |
| 取消请求 | J17 / 2 / 取消中 | 拒绝新副作用，等待停止与在途结果对账 |
| 执行端确认 | J17 / 2 / 已取消 | 已确认停止；已有副作用单列，不假定自动撤销 |

“方案已生成”只支持计划；“规则回退、假契约日志通过”支持该假例的降级引擎与限定检查，不支持模型成功或生产完成；“动画停止”不证明进程停止或业务未写入，仍需执行端确认。代次、状态和写入检查要在真实系统中原子落实，不能只凭表格证明并发安全。

**问：为什么两个 worktree 仍可能互相影响？** 它们可能共享外部数据库、账号、端口或全局设置；文件目录隔离只是一个层面。

**问：并行两项任务一定快一倍吗？** 不会。串行依赖、协调和集成有成本，错误还可能增加返工。

**问：给每个 Agent 任意写权限是否最自主？** 可能最危险。明确所有权和最小权限通常更容易获得可靠成果。

# 06 仓库准备与并行开发

[上一章](05-skills-automation.md) | [目录](../README.md) | [下一章：测试、评测与代码审查](07-testing-review.md)

新参与者接手“行动项稳定排序”，却不知道该改哪个函数、测试从哪里运行、测试库是否真的隔离。增加 Agent 只会让更多人一起猜。本章先解决这些障碍，再按依赖分工、隔离资源，最后处理后台任务的接管与取消。

能读懂路径、排序和条件分支即可。基线是大家共同开始的版本，工作区是实际读写文件的目录。先读第 1–5 节，再做第 6 节练习、核对第 7 节答案。基础只用章内假材料做纸面判断，不联网或执行程序；真实 worktree、并行与后台实验另行选做，均未执行。

## 1. 仓库结构决定 Agent 的工作成本

假仓库 `lab` 沿用第 02–03 章契约：行动项按 `created_at` 降序，同时间按数字 ID 降序，不改响应字段。路由 `backend/routes/items.py` 调用 `backend/services/items.py`，排序在后者；`backend/schema.json` 从模型定义生成，不手改。测试应从 `lab/backend` 运行并使用任务独立临时库。下面是给定的假障碍：

| 新参与者遇到的障碍 | 当前已有信息 | 下一份证据与继续条件 |
| --- | --- | --- |
| 两个名字相似的排序函数 | 路由指向 services/items.py | 沿调用关系确认权威入口；不修改未调用副本 |
| 从 lab 运行时报导入失败 | 文档说工作目录是 lab/backend | 对照目录和准确命令；不先升级依赖 |
| fixture 声称临时库，但启动仍指向默认库 | 请求会话和启动 engine 是两条路径 | 同时确认导入、启动、请求和清理的数据路径；未隔离前不执行 |

我们需要的是“任务 → 实际入口 → 当前契约 → 安全验证 → 失败恢复”的路径。这种让参与者少猜、能定位、能验收的状态称为 **Agent 就绪度**。它同样有益于人，不是加一个规则文件就完成。

## 2. 一个自学用审计表

用一张表区分“写了”和“证实了”：每项缺失为 0 分，有文档但未验证为 1 分，在新环境实际验证过为 2 分，总分 16 分。这是教程自定义评分，纸面分析不能获得运行验证分。

| 项目 | 要求的证据 |
| --- | --- |
| 启动 | 明确前置条件、工作目录和启动命令 |
| 测试 | 独立测试数据、可重复测试命令 |
| 架构 | 入口、模块边界和数据流可定位 |
| 契约 | schema、错误行为与文档一致 |
| 配置 | 示例配置无秘密，真实配置隔离 |
| 修改范围 | 生成物、第三方文件和并发工作可识别 |
| 质量门禁 | 检查失败能阻止合并或发布 |
| 恢复 | 回滚、数据库迁移和故障处理说明 |

分数只帮助找缺口，不替代安全判断。例如临时请求库有文档，但启动仍写默认库，应记 1 分并标“隔离缺口阻塞运行”，不能当作测试安全。先修入口和数据路径，不以“适合 AI”为由迁移整个仓库架构。

### 用独立任务检验就绪度

让新参与者只凭需求和仓库说明完成一个小变更，记录找入口、失败命令、求助、越界修改和验证遗漏。修补必须对应原障碍：目录不清就补准确目录，生成物漂移就改权威源并重新生成，数据污染就隔离启动和请求两条路径。再用难度相近的新任务复核；任务差异和共享知识会影响结果，一次变快不证明普遍提速。

<details>
<summary>选学：真实就绪度复核</summary>

在获准副本中让另一位读者或新会话定位入口、运行基线、修改和验收，不补隐藏命令。检查规则命令、文档契约和生成流程是否与当前代码一致。验收需实际基线与改后证据；新会话不等价于独立人类实验，先前共享知识也应记录。这是教程扩展，未执行。

</details>

## 3. 分解任务要按依赖，而不按人数

入口清楚后，仍不能直接按人数分工。前端和测试都需要知道同时间记录如何排列；一人按 ID 升序、另一人按降序，各自看似正确，组合却错。因此先固定契约和基线，再并行制作独立产物。

假任务分为 K 确认契约、I 实现排序、T 设计独立测试预期、D 更新说明、V 集成核对。依赖为 `K -> I/T/D -> V`：K 完成后 I、T、D 可并行，V 等三项成果齐全。共享文件指定唯一写入者，其他人只读或等待；角色名字不能解决写冲突。

最小任务卡：“基线 lab-v1；created_at、数字 ID 都降序；I 只改 services/items.py，T 只改 tests/test_items.py，D 只改 docs/items.md；不改 schema；输入（时间 11，ID 9）、（时间 10，ID 3）、（时间 11，ID 10），预期 `[10, 9, 3]`；越界先暂停；交付差异、验证证据与未验证项。”这只是分工设计。

任务越独立，越可能节省时间；协调、重复研究和集成仍有成本。一个人实现、另一个只读审查，也可以比多人同时改接口更合适。

集成要核对各自完整差异、共同契约和基线，合并后再做联合检查。两个分支各自通过，不代表组合通过；冲突按规格解决。

<details>
<summary>选学：理想加速公式</summary>

串行部分占比为 `s`，工作者数为 `n` 时，理想加速比上限约为 `1 / (s + (1-s)/n)`。例如 s=1/2、n=2 时上限为 4/3，不是两倍；现实还要计协调与返工，公式不预测模型正确率或真实收益，未做速度实验。

</details>

### 同步与异步首先是注意力与交接的选择

契约未定时同步澄清，固定后可异步委派、稍后收成果。同步与异步说的是交互节奏，本地与云端说的是运行位置，不代表权限隔离。异步交接尤其要写非目标、预算和停止条件；只有“已完成”而没有差异、断言或未验证项，应退回补证据。重开会话前保留当前差异、失败与剩余预算，新上下文不会撤销旧副作用。

## 4. worktree 隔离了什么

`git worktree` 为同一仓库提供不同工作目录和分支，减少同时编辑相同文件的干扰。它不隔离端口、环境变量、用户全局配置、外部账号或共享数据库。

I 在 `lab-i`、T 在 `lab-t`，若都监听 8000 并写 `shared.db`，仍会冲突。隔离表要分别约定目录、共同版本、端口、启动库与请求库、局部配置和任务凭据。沙箱还需执行端实际限制资源访问，仅换目录不够；没有并行必要时可串行处理。

<details>
<summary>选学：获准副本中的 worktree 命令与联合验证</summary>

以下命令仅供获准练习副本使用。先确认已有工作、分支和父目录，不擅自提交或清理他人目录：

```powershell
git status --short
git worktree list
git worktree add "../cs146s-ui" -b lab/ui
git worktree add "../cs146s-tests" -b lab/tests
```

worktree 从提交基线开始，不自动包含未提交修改。若任务依赖这些修改，先由拥有者决定如何提供一致版本。环境依赖也要分别核对。

集成时审查各分支完整差异和测试，合并后再跑联合测试。各自通过不代表组合通过；冲突按规格解决。本节 Git 写操作与联合测试均未执行。

</details>

## 5. 后台 Agent 需要持久任务状态

用户离线时，后台任务不能只靠对话记住“正在处理”。持久记录要在进程退出后仍可恢复，至少保存任务 ID、基线与契约、预算、权限、差异、批准和未验证项。可用状态链“待办 → 运行 → 等待批准 → 验证 → 待合并 → 完成”，失败与取消单列。

同一 Issue 重复触发要去重，恢复时先核对部分文件和外部写入。Issue-to-PR 的完成是提交成果供审查，不是自动上线；后台 Agent 默认没有部署凭据，合并与发布仍走门禁。

### 租约到期不等于旧工作者已经停下

<details>
<summary>进阶选学：接管、旧批准和取消确认（供选做题及迁移题参考）</summary>

**租约**规定谁在多长时间内可处理任务，**代次**标识第几次领取或接管。租约到期允许接管，却不证明旧进程已停。接管须原子递增代次，在产物接纳或副作用入口再次原子核对所有者、代次和状态，拒绝失效工作者；只在开始时检查一次会留下漏洞。

批准绑定确切差异，改代码后重新申请，旧批准历史仍保留。取消先记“取消中”，拒绝新写入并请求停止；确认活动进程停止且在途结果已对账，才能记“已取消”。

| 完整假事件 | 持久记录与允许动作 |
| --- | --- |
| 项目lab、Issue17、任务版本v1第一次投递；再次收到相同键 | 保留一项任务 J17，不创建第二项；共同基线 lab-v1 |
| A 领取，代次1；租约到期，B接管 | 原子地更新所有者B、代次2；租约到期不证明A已停 |
| A 提交代次1产物 | 拒绝旧代次，不写入；保存拒绝原因和证据 |
| B 产出差异 d1，等待批准；有权限人员批准 d1 | 记录批准者、差异版本和范围；只对d1适用，不批准任意未来差异 |
| B 又改成 d2 | 保留d1批准历史，d2回到等待批准；不能沿用旧批准 |
| 用户取消 d2，执行端未确认；随后确认停止 | 先“取消中”，拒绝新写入并请求停止；确认活动进程停止、在途操作结果已对账后才“已取消” |

已有外部写入不会因取消自动撤销，应记录并走获准恢复流程。表格只展示设计规则，真实原子性与故障窗口仍需测试；进一步实践见[团队门禁演练](10-capstone.md)。

</details>

### 快速反馈必须区分计划、执行与验收

界面分别展示计划、执行及退出状态、验收范围、待批准和取消中。模型超时后规则回退，应显示实际引擎与回退原因，不宣称模型成功。退出码 0 不等于验收通过，动画停止不等于进程停止；布局、聊天、进程和业务写入的恢复也各需证据。

## 6. 动手：修补就绪度，再测并行

### 纸面练习：前三项基础，第四项选做

先作答，再核对第 7 节。每题写判断、依据和未验证项。

1. **就绪证据。** 启动有目录和命令说明；测试有临时请求库文档，但启动仍写默认库；架构有路由到服务的调用关系；三项均未在新环境验证，其余五项无说明。按审计表打分、复算总分，选两个优先缺口，说明什么阻塞运行。
2. **依赖与交接。** K 契约未定，I 实现、T 设计测试、D 更新说明、V 集成，基线为 lab-v1。写依赖、K 完成后的文件所有者和 V 前置条件。遇到“D 要改 schema”“预算到期仍等 K”，各怎样停止或交接？
3. **隔离卡。** I/T 分别在 lab-i/lab-t，从 lab-v1 开始，却共享 8000、shared.db、全局配置和发布账号；lab 另有未提交修改。列已隔离与未隔离资源，说明怎样提供一致基线、哪些操作需另获授权。
4. **持久状态（进阶选做）。** 展开第 5 节的 J17 事件表，记录 ID、代次、状态、允许写入与批准历史。再判断“方案已生成”“规则回退且假契约日志通过”“界面动画停止”分别支持什么结论。检查去重、旧代次拒绝、旧批准不沿用和取消确认。

### 迁移检查：检查后发生了接管

公开假事件，零执行。A在代次4开始提交前检查有效，随后暂停；B接管使代次变5并保存新产物；A恢复后根据之前检查覆盖产物。两者文件目录不同，但共用产物存储。判断哪里缺约束，写拒绝及正常验收预期；若A已有外部副作用，取消能否自动撤回？

<details>
<summary>作答后展开参考答案</summary>

开始时检查无法覆盖检查后接管的窗口，目录隔离也不隔离共享产物。应在产物接纳/写入入口原子核当前所有者、代次与状态；代次4提交被拒绝且B产物不变，当前有效代次5在其他批准条件满足时可被接纳。取消需执行端停止确认及在途对账，不能自动撤销此前副作用。当前只有设计，原子性与真实并发安全仍需故障窗口测试。

</details>

## 7. 自测与答案

### 集中练习答案

**1. 就绪证据。** 启动 1、测试 1、架构 1，其余五项 0，总分 3/16。测试另标“启动隔离缺口，禁止执行”；临时 fixture 不证明启动安全。优先隔离启动与请求两条数据路径，再核对入口、工作目录和命令。三项都没有运行证据，不能给 2 分。

**2. 依赖与交接。** `K -> I/T/D -> V`。K 完成后 I/T/D 分别拥有 services/items.py、tests/test_items.py、docs/items.md；V 等三项成果齐全并核对共同版本，合并后还需联合检查。D 要改 schema 应暂停并申请范围调整；预算到期仍等 K，应保留基线、阻塞和剩余状态，停止交接，不猜需求。

**3. 隔离卡。** 目录已分开、提交基线一致，端口、数据库、全局配置和发布账号未隔离。应分配不同端口、独立启动/请求临时库、局部配置和最小权限凭据，由执行端限制。未提交修改不自动进入 worktree，依赖它时由拥有者决定提供一致版本或差异，不擅自提交、丢弃或覆盖。建工作区、运行、建库、账号操作、合并与发布均需另获授权。

**4. 持久状态。** 下表是纸面参考，不是后台系统实测：

| 事件 | ID / 代次 / 状态 | 写入与批准判断 |
| --- | --- | --- |
| 首次及重复投递 | J17 / 尚未领取 / 待办 | 同键一项任务，不重复启动 |
| A领取 | J17 / 1 / 运行 | 仅有效租约及获准范围内可执行 |
| 到期B接管 | J17 / 2 / 运行 | 原子接管；A未必已停止，执行端拒绝旧代次 |
| A旧产物 | J17 / 2仍有效 / 运行 | 拒绝代次1产物，保存记录，不覆盖B |
| B的d1获得批准 | J17 / 2 / 等待批准后可进入验证 | 批准者和范围绑定d1，尚非自动合并/发布 |
| 改d2 | J17 / 2 / 等待批准 | d1批准历史保留，d2不得沿用 |
| 取消请求 | J17 / 2 / 取消中 | 拒绝新副作用，等待停止与在途结果对账 |
| 执行端确认 | J17 / 2 / 已取消 | 已确认停止；已有副作用单列，不假定自动撤销 |

“方案已生成”只支持计划；“规则回退、假契约日志通过”支持该假例的降级引擎与限定检查，不支持模型成功或生产完成；“动画停止”不证明进程停止或业务未写入，仍需执行端确认。代次、状态和写入检查要在真实系统中原子落实，不能只凭表格证明并发安全。

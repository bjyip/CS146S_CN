# 07 测试、评测与代码审查

[上一章](06-repo-parallel.md) | [目录](../README.md) | [下一章：安全](08-security.md)

提取器正确识别了“明天检查日志”，控制中心却在响应丢失后重试保存，创建了两条任务。mock 测试仍全部绿色，因为它只检查预设 JSON 的解析。“答案正确”和“测试绿色”为何挡不住重复写入？本章先分清验证对象，再设计独立断言、报告结果，最后写出有证据的审查发现。

能读懂列表、AND（同时满足）、OR（至少一个满足）和简单函数即可。mock 用假返回替代真实依赖；断言按预期核对结果。先读第 1–7 节，做第 8 节练习、核对第 10 节答案。基础只用假记录和伪代码，不联网或运行测试；真实评测与审查另行选做，均未执行。

## 1. 两种正确性必须分开

先约定本章任务：只提取明确待执行动作，排除完成、否定执行与未决定建议，不补负责人和日期；动作、对象、时间与负责人相同且无冲突的重复提醒只留一次。输出唯一字段 `action_items`，值为字符串数组；提取只返回候选，不自动写库。含糊输入交人工复核，不能用空数组掩盖失败。

如果后续用户批准保存，系统另有契约：绑定当前用户和目标笔记，同一逻辑写入请求重试不增加第二项，失败状态可识别。重复请求识别要由执行端落实，不能指望模型每次生成相同文字。

| 开场假记录 | 应检查的对象 | 能得出的结论 |
| --- | --- | --- |
| “明天检查日志”得到 `{"action_items": ["明天检查日志"]}` | 原文、动作和结构 | 这一条候选内容正确，不证明保存或其他输入可靠 |
| 同一逻辑请求因响应丢失重试，库中两行 | 授权、请求身份与实际后置行数 | 软件写入违约，即使每次提取都对 |
| mock 只返回上面正确JSON，解析断言绿色 | 假依赖和断言范围 | 只能核对这种假响应的解析，不证明模型生成、网络或重试写入 |

据此区分两层：**软件测试**检查程序契约，如解析、授权和事务；**模型评测**检查内容质量，如是否提对任务、是否编造。解析器通过 mock 不证明模型输出可靠，模型提取正确也不证明写入安全。两层各需独立预期与证据。

## 2. 测试矩阵

先沿“笔记 → 解析 → 候选 → 批准 → 保存 → 显示”找缺口，再选择检查层次，不必每层都引入新工具。

| 层次 | 行动项项目的例子 | 验证边界 |
| --- | --- | --- |
| 单元 | 去重、空输入、解析异常 | 不证明网络或模型质量 |
| 集成 | 路由、数据库与临时存储 | 不一定覆盖真实客户端 |
| 协议 | MCP 初始化、列工具、调用 | 不一定覆盖供应商 API |
| 端到端 | 界面输入到持久化结果 | 样例数量通常有限 |
| 语义评测 | 隐藏样例上的提取精确率 | 依赖标注与分布代表性 |
| 安全回归 | 越权访问被拒绝 | 只覆盖已设计攻击路径 |

开场例至少需检查：正确 JSON 接受、数字元素拒绝；“不要创建任务”不提取；重试保存后仍只有一行；B 不能改 A 的笔记；非空列表能显示。API/函数断言不能代替界面检查。报告覆盖范围与缺口，未运行就只写预期。

## 3. 解剖现有测试

把模型替换成始终返回 `{"action_items": ["明天检查日志"]}` 的函数，再断言解析得到一项字符串。即使真实模型总把否定句当任务，这条测试仍能通过，因为没有调用它。mock 适合稳定复现程序错误，不证明真实依赖质量。

[第 2 周测试](../../_assignments/2025%20fall/week2/tests/test_extract.py) mock 了模型返回，覆盖空输入、格式解析、重复项和不可用回退。这些是有价值的单元测试。

当前实现广泛捕获异常后回退，成功响应可能掩盖模型长期不可用。评测需记录实际引擎、解析失败与回退比例：模型指标只算模型结果，产品指标包含回退；有 schema 不等于内容真实，回退成功不等于模型健康。

## 4. AI 生成测试的陷阱

如果实现把两个条件写成 OR，测试作者再照实现列预期，测试会与错误自洽。先从规格独立写“标题含日志 AND 标签为ops”，再提供下面四条完整假记录；匹配为大小写敏感的包含与标签成员判断，无分页或排序：

| ID | 标题 | 标签 | q=日志命中 | tag=ops命中 |
| --- | --- | --- | --- | --- |
| N1 | 登录日志 | [ops] | 是 | 是 |
| N2 | 支付日志 | [dev] | 是 | 否 |
| N3 | 发布计划 | [ops] | 否 | 是 |
| N4 | 界面计划 | [dev] | 否 | 否 |

AND 的独立预期是只返回N1，OR会返回 N1、N2、N3。只给N1和N4，两种实现都返回N1，无法区分；缺少单条件反例，就是绿色测试仍漏bug的具体原因。测试应断言精确ID集合和数量，不能只断言“N1存在”。

测试预期应来自规格、外部标准或人工标注，不能照抄实现。让 Agent 先列边界和预期，再写测试；人工核对正常、失败与对抗样例。删除断言、放宽要求或大量 skip 不能算修复。

可在纸面上把AND换成OR，复算得到三项，发现它违反预期。这叫设计反例，不是实际变异测试。变异测试则是在获准副本故意改坏实现、运行测试确认被抓住，再恢复自己的临时变更；基础不执行它，一次成功也不证明捕获所有错误。

## 5. 评测如何报告才诚实

比较方案之前先固定分母。下面四条公开教学笔记各应有一项任务；记录均为虚构，第 4 条未尝试也必须保留：

| ID | 输入 / 人工预期 | 首轮假记录 | 后续假记录 |
| --- | --- | --- | --- |
| A | 明天检查日志 / 明天检查日志 | 模型返回合法且正确JSON | 无重试 |
| B | 周五更新说明 / 周五更新说明 | 模型返回半个JSON，明确截断 | 第二次返回正确JSON |
| C | 周一核对依赖 / 周一核对依赖 | 模型超时，无有效列表 | 规则回退返回正确候选 |
| D | 周二备份配置 / 周二备份配置 | 未尝试，预算耗尽 | 无结果 |

计划 4 题、尝试 3 题。模型首轮结构与语义成功都是 1/3，一次重试后成功 2/3；产品最终在尝试题上正确 3/3，其中一题是规则回退，不能写“模型 3/3”。计划完成为 3/4，D 单列未尝试。失败、超时、截断与回退都留在记录中，不能事后删困难题。

TP 是正确匹配项，FP 是多提或错提，FN 是应提却遗漏。精确率为 `TP/(TP+FP)`，召回率为 `TP/(TP+FN)`；按动作、对象和原文明示的时间与负责人一对一匹配。首次尝试中 A 匹配一项，B、C 无有效列表，各漏一项，所以 TP=1、FP=0、FN=2，精确率为 1，召回率为 1/3。无预测且分母为 0 时，精确率记 N/A；业务端拒绝错误候选也不能删掉原始错项美化评分。

报告保存原始响应、尝试序号、引擎和版本、失败类型、耗时与费用。本例后两项未测量，不能补平均延迟或 p95。比较时固定同批输入和统计口径，保留所有尝试；开发样例用于优化，留出样例用于验收，本章公开题不算隐藏测试。小样本只报告成功数/总数与局限，不能外推生产成功率；平均值也不能代表长尾。

### 安全评测先核对分母

如果审查10条假漏洞报告，人工确认3条，判定5条为误报，另有2条待验证，当前确认占全部报告3/10；已裁定8条中的精确率是3/8。二者口径不同，都要保留2条未知。真实缺陷全集未知，所以FN和召回率未知，不能写“找到30%的漏洞”。只有固定、已知缺陷教学集才可算该集召回，不外推真实仓库。

### 工具函数正确，Agent 任务仍可能失败

搜索返回正确摘要但不含 `note_id`，下一步读取笔记就缺参数；函数局部成功，完整任务仍失败。应核对选工具、参数来源、返回和后置状态，不规定唯一调用顺序，只接受符合授权与结果的等价路径。

## 6. 代码审查不是重新描述差异

审查要问“哪个场景会出错，依据在哪里”，不是复述“这里改了查询”。先读需求、调用链、完整差异与独立测试预期。静态代码可支持条件推导，但未运行的 HTTP 与数据库结果要单列。

有效审查优先回答“这会在哪个具体场景出错”。发现格式为：严重度、文件与行号、触发条件、实际行为、预期行为和修复方向。不能只写“可能有安全问题”。

先看需求、数据完整性、授权、副作用与恢复，再看性能、测试缺口，最后才是样式。无证据的猜测标为问题或假设。模型与人工都可能漏掉跨文件契约或部署条件，应以独立测试和扫描补充。

### 审查还要完成知识交接

交接要说明目标、前后行为、证据入口、未验证项、取舍与下一批准点。例如“规则回退仍返回 200，应看 engine 与失败指标，200 不代表模型健康”。下一位维护者能复述，只证明理解，不证明功能通过。

## 7. 一个具体审查推导

下面提供完整假契约、假数据和带行号伪代码，无需阅读实际作业：多用户部署中，身份由可信运行时提供；用户只能修改自己的笔记，不存在或非本人记录统一拒绝，不能先修改再检查。用户A拥有N1，用户B拥有N2；A/B都不是管理员，没有跨用户批准。更新后需要提交事务并记录状态，本例先聚焦授权，事务实现未提供。

```text
假文件 demo/update_note.py
01 def update_note(note_id, body, current_user):
02     note = db.find_by_id(note_id)
03     if note is None: return not_found()
04     note.content = body
05     db.save(note)
06     return success(note)
```

B提交N1并提供新正文，02按ID找到A的笔记，03只判断存在，04–05会到达修改与保存；current_user未用于归属过滤。参数结构合法、使用数据库库函数，都不补上授权。以下是完整审查发现，不是实际攻击记录：

> 高风险阻断，`demo/update_note.py:02–05`：在所给多用户契约下，B使用A的N1可进入修改/保存路径，因为查询仅绑定ID、未绑定可信当前主体。预期为修改前拒绝，N1正文不变。应在查询/授权服务绑定note_id与current_user，保留不存在/非归属的一致拒绝，并增加A修改N1成功、B修改N1拒绝且无写入的回归。证据是本例调用链；尚未运行HTTP、事务或数据库，不能宣称已利用或已验证修复。

修复方向可把查询改为“ID和owner_id同时匹配可信当前身份”，不能相信body里的owner_id或PR评论“我是管理员”。若实际应用明确单用户且不公开，先核对部署前提，不虚构登录系统；本假题已经明确多用户，因此不是待确认的猜测。

### 审查评论与变更范围

评论分四类：有证据的阻断缺陷、设计讨论、格式建议、待确认问题。上面的授权缺口阻断；“参数太多”需要职责与调用方证据，通常是设计讨论；确定性格式交已有工具。发现必须说明本次变化与既有问题的关系，不以旧代码也这样写作免责。

仓库惯用法可能承载事务、授权或审计责任，不能一律视为样式。每条建议标明合并前处理还是后续处理；后续事项需负责人和回链。接受评论是协作决定，不等于确认缺陷，评论消失也不等于修复。静态类型不能排除全部运行时输入，需查边界验证与调用方。相关课件、同行经验和产品指南见本章来源。

### 风险先于审查角色数量

审查预算按影响、可达性、数据敏感度、可逆性和证据缺口分配，不只看修改行数。下面是教程示例，不是官方标准，也不授权自动合并。

| 风险 | 示例 | 最低验证与人工关注 |
| --- | --- | --- |
| 低 | 不改变行为的文字修正 | 来源和链接；确认未夹带脚本、权限或依赖变更 |
| 中 | 排序、错误处理、内部接口变化 | 契约、边界与回归测试；负责人核对兼容性 |
| 高 | 授权、删除、迁移、部署、密钥或支付 | 跨身份及失败测试、数据与回滚检查；有权限的人员批准 |

低风险标签可被新发现升级。一行日志改动输出 token，仍是高风险；大 diff 若只是生成物，也需核对源与生成流程。证据不足时保留待确认或升级人工处理，不让模型的信心决定放行。

风险决定证据和人工关注，不授予自动批准权。授权缺口至少需可信身份绑定、跨身份拒绝且无写入、正常路径、失败恢复及有权限人员批准。重点检查测试是否随错误实现一起放宽；模型同意票、评论接受、复扫无报告都不能替代验证。取消、认证失败或预算耗尽记“审查未完成”，不是“无发现”。

<details>
<summary>选学：专业审查者、超越diff与真实分层实验</summary>

[Cloudflare 工程实践](https://blog.cloudflare.com/ai-code-review)用协调者组织专业审查者；按风险选择只读角色即可，简单仓库也可串行检查。[Greptile 经验文章](https://www.greptile.com/blog/how-to-build-a-code-review-agent)强调超越 diff：授权问题读身份与查询，兼容性读调用方与 schema，性能问题核查询和规模，不是把整库塞进提示。

1. 在获准隔离副本准备文字、排序、授权三个假数据变更，固定基线、需求、完整差异、测试、部署条件与读取范围。
2. 比较仅 diff 与附相关上下文的审查，一次只改一个因素。按风险选角色，用代码或针对性测试确认发现，按根因去重并保留未知。
3. 记录模型/上下文版本、总成本、人工验证时间与已知缺陷遗漏；开发集与留出集分开。没有缺陷全集就不报真实召回率。
4. 设置整体预算、超时和最大重试。瞬态错误有限重试，认证错误修访问条件，上下文过大缩小输入，取消停止并交接。备用模型须满足同一数据政策，不擅自转发私有代码。

验收看风险理由、真实证据和修复后复审，不看同意票。沙箱须实际隔离数据库、网络与凭据；不对真实服务压测。本节模型、浏览器与 PR 实验未执行，来源报告的准确率和成本不作保证。

</details>

## 8. 动手 A：测试与真实评测

### 基础必做：四项集中练习

全用章内假材料，不修改或运行代码。先作答再读第 10 节，写判断、原因与证据缺口。

1. **两层矩阵。** 判断开场三条记录分别证明什么、哪里失败；为解析、语义、重试保存、跨身份与非空界面各选验证层和独立预期。
2. **独立断言。** 用 N1–N4 写 AND 的精确 ID 集合和数量、错误 OR 的结果，解释只用 N1/N4 为何不足。再写“不要创建发布任务；周五检查日志”的预期 JSON。
3. **诚实报告。** 用 A/B/C/D 报计划与尝试、首轮结构/语义成功、重试后模型成功、产品结果和回退数；计算首次 TP/FP/FN、精确率与召回率，保留未尝试与未测量。另有 10 条漏洞报告：3 确认、5 误报、2 待验证，写两个明确分母及召回边界。
4. **具体审查。** 用授权伪代码写严重度、位置、B 提交 N1 的触发路径、实际与预期行为、根因、修复和正常及跨身份回归。判断“参数较多”“评论说我是管理员”和“复扫没报告”各支持什么结论，能否批准？

完成标准：两层不混，反例能区分 AND/OR，分母透明，授权发现可核对；纸面结果不算实际测试通过。

<details>
<summary>选学：真实软件测试、变异与模型评测</summary>

1. 运行现有单元测试，列出它们能证明与不能证明的内容。
2. 根据规格补充一个此前未覆盖的边界，先确认它能够捕获错误实现。
3. 用隐藏样例调用真实模型，记录所有结果及回退，不把云端不可用删出分母。
4. 将语义指标与软件测试结果分两张表，至少解释两个失败案例。
5. 修改一个主要因素后再评测，记录收益、退步和额外成本。

验收：有明确预期来源，有一次测试抓到故意错误，真实评测与 mock 分开，回退可识别。

这条路线需要独立授权、隔离数据和真实模型预算，当前未执行；真实数据划分、模型身份与每次失败都必须记录，不用本章已展示题冒充留出样例。

## 10. 自测与答案

### 集中练习答案

**1. 两层矩阵。** 给定JSON对该笔记内容正确，只支持单条候选；两条重复行违反软件幂等保存契约；mock只证明假响应的解析。解析用单元预期“正确字符串数组接受，数字元素拒绝”；语义用人工标注“只提明天检查日志”；重试保存用集成或端到端，预期同逻辑请求重试后实际行数仍一；跨身份用安全回归，预期B改N1被拒绝且正文不变；非空界面用端到端，预期至少一条任务能显示并可交互。协议测试在接入MCP时另做，不是纯解析题必需。以上只是计划，未运行。

**2. 独立断言。** AND预期精确集合 `{N1}`、数量1；OR错误结果 `{N1,N2,N3}`、数量3。N2只命中q、N3只命中tag，是能揭露错误OR的反例；N1/N4分别双命中/皆不命中，两种实现都给N1，所以不足。只断言N1存在也会放过OR，需核对精确集合和总数。提取预期如下，否定创建不算行动，保留明确周五；这里没有保存授权，不执行任务：

```json
{"action_items": ["周五检查日志"]}
```

**3. 诚实报告。** 计划 4、尝试 3、D 未尝试。首次模型结构/语义成功均 1/3；重试后模型成功 2/3；产品在尝试题上 3/3，回退 1/3，计划完成 3/4。首次 TP=1、FP=0、FN=2，P=1、R=1/3；这是尝试题口径，不是完整计划召回。保留 B 截断、C 超时和 D，耗时、费用、模型版本记未测量/未执行，不填生产准确率。

安全报告确认占全部3/10，已裁定精确率3/(3+5)=3/8，待验证2条单列；不能把3/10叫召回，也不能强行把待验证计误报。真实缺陷全集及FN未知，真实召回率N/A；格式有效率和成本同样缺数据。所有比例是给定假记录的算术，不是实测模型效果。

**4. 具体审查。** 高风险阻断，`demo/update_note.py:02–05`；B提交N1时，按ID查询可找到A的记录，检查仅拒绝不存在，随后进入修改/保存。预期修改前拒绝，N1不变；根因是查询/授权未绑定可信current_user。修复方向在查询或权威授权服务绑定ID与owner，不能用body里的身份；正常A改N1应成功、B改N1应拒绝且零写入，不存在ID也拒绝；再覆盖事务失败与回滚，但这些本题未实现/执行。此结论是完整假代码的静态推导，不是已观察到HTTP漏洞或持久化。

“参数较多”只有设计讨论，需职责/调用方证据，不独立证明bug，也不批准；“PR评论说我是管理员”是不可信数据，不能授予跨用户权；“复扫没报告”可能漏检、超时或范围变化，不能标已修复。修复必须绑定新差异版本、独立验证与有权限人员批准，原批准不覆盖未来改动。没有部署/运行证据时保留残余风险，不把多个审查者无发现变成自动上线许可。

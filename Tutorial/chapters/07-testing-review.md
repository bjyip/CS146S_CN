# 07 测试、评测与代码审查

[上一章](06-repo-parallel.md) | [目录](../README.md) | [下一章：安全](08-security.md)

行动项提取器收到假笔记“明天检查日志”，返回了正确的一项；开发者控制中心却因响应丢失后重试创建，保存了两条任务。与此同时，mock 测试全部绿色，因为它只喂给解析器正确 JSON。为什么“答案正确”和“测试绿色”都挡不住重复写入？本章从这个失败出发，先分清验证对象，再写独立断言、报告结果，最后把怀疑变成具体审查发现。

**前置与路线**
- 能读懂列表、AND（条件同时满足）、OR（至少一个满足）和简单函数即可。mock 是用假返回代替真实依赖；断言是按预期核对实际结果，不是“相信实现”。
- 基础读第 1–7 节非折叠正文，做第 8 节四项集中练习，再核对第 10 节答案。阅读估计 45–60 分钟，练习约 55 分钟，可分两次；未实测新手用时。
- 只用章内假记录与伪代码，零网络、模型、应用、测试和扫描执行，不需要笔记或课件。产物是两层验证表、可区分错误的断言、分母报告与审查发现。
- 原作业、真实模型评测、变异实验、Graphite 和多角色审查均独立选学，未执行。纸面“预期会失败”不称实际测试变红。

## 1. 两种正确性必须分开

先约定本章任务：只提取明确待执行动作，排除完成、否定执行与未决定建议，不补负责人和日期；同动作/对象/时间/负责人无冲突的重复提醒只留一次。输出唯一字段 `action_items`，值为字符串数组；提取只返回候选，不自动写库。含糊输入交人工复核，不能用空数组掩盖失败。

如果后续用户批准保存，系统另有契约：绑定当前用户和目标笔记，同一逻辑写入请求重试不增加第二项，失败状态可识别。重复请求识别要由执行端落实，不能指望模型每次生成相同文字。

| 开场假记录 | 应检查的对象 | 能得出的结论 |
| --- | --- | --- |
| “明天检查日志”得到 `{"action_items": ["明天检查日志"]}` | 原文、动作和结构 | 这一条候选内容正确，不证明保存或其他输入可靠 |
| 同一逻辑请求因响应丢失重试，库中两行 | 授权、请求身份与实际后置行数 | 软件写入违约，即使每次提取都对 |
| mock 只返回上面正确JSON，解析断言绿色 | 假依赖和断言范围 | 只能核对这种假响应的解析，不证明模型生成、网络或重试写入 |

据此区分两层：普通软件测试检查明确程序契约，如空输入、解析、授权和事务；模型评测检查语义质量，如任务是否提对、是否编造。软件与语义都要有独立预期和对应证据，不能用一层的通过替代另一层。

一个解析器可以在所有 mock 测试中通过，却面对真实模型频繁格式失败；模型可以生成正确内容，系统却因为重试写出重复记录。可靠系统需要两层证据。

## 2. 测试矩阵

怎样补开场缺口？先列任务路径“笔记 → 响应解析 → 候选 → 批准 → 保存 → 界面显示”，再按需要选择验证层，不是每层都必须引入新工具。单元检查局部函数，集成检查相邻组件组合，端到端检查用户流程；协议检查约定通信，语义评测检查内容，安全回归检查授权边界。

| 层次 | 行动项项目的例子 | 验证边界 |
| --- | --- | --- |
| 单元 | 去重、空输入、解析异常 | 不证明网络或模型质量 |
| 集成 | 路由、数据库与临时存储 | 不一定覆盖真实客户端 |
| 协议 | MCP 初始化、列工具、调用 | 不一定覆盖供应商 API |
| 端到端 | 界面输入到持久化结果 | 样例数量通常有限 |
| 语义评测 | 隐藏样例上的提取精确率 | 依赖标注与分布代表性 |
| 安全回归 | 越权访问被拒绝 | 只覆盖已设计攻击路径 |

pytest 输出一片绿色不等于所有层次都覆盖。报告每种测试的范围和未覆盖区域。

开场例至少需要：解析器接受正确 JSON、拒绝数字元素；语义样例排除“不要创建任务”；重试保存后行数仍一；用户B不能改用户A的笔记；非空列表能实际渲染。前四个 API/函数断言不能代替最后一个界面检查。没有真实执行时写这些预期与缺口即可，别填“已通过”。

## 3. 解剖现有测试

先用一条完整假测试理解 mock：把真实模型替换成始终返回 `{"action_items": ["明天检查日志"]}` 的函数，然后断言解析结果是一项字符串。即使真实模型总把否定句当任务，这条测试也能绿色，因为从未接触该模型。mock 有助于稳定复现程序错误，但假依赖不能证明真实依赖质量。

[第 2 周测试](../../_assignments/2025%20fall/week2/tests/test_extract.py) mock 了模型返回，覆盖空输入、格式解析、重复项和不可用回退。这些是有价值的单元测试。

但 mock 指定了正确 JSON，不能证明真实模型会生成它；测试断言有 schema 也不能证明内容真实；异常回退得到规则结果，不能说明 LLM 服务健康。当前实现广泛捕获异常后回退，若缺少指标，成功响应还可能掩盖长时间模型不可用。

新增评测时要同时记录引擎、解析失败与回退比例。模型质量只统计真正由模型完成的结果；用户最终结果则统计完整产品链路。两个指标都重要，但含义不同。

## 4. AI 生成测试的陷阱

如果实现把两个条件写成 OR，测试作者再照实现列预期，测试会与错误自洽。先从规格独立写“标题含日志 AND 标签为ops”，再提供下面四条完整假记录；匹配为大小写敏感的包含与标签成员判断，无分页或排序：

| ID | 标题 | 标签 | q=日志命中 | tag=ops命中 |
| --- | --- | --- | --- | --- |
| N1 | 登录日志 | [ops] | 是 | 是 |
| N2 | 支付日志 | [dev] | 是 | 否 |
| N3 | 发布计划 | [ops] | 否 | 是 |
| N4 | 界面计划 | [dev] | 否 | 否 |

AND 的独立预期是只返回N1，OR会返回N1/N2/N3。只给N1和N4，两种实现都返回N1，无法区分；缺少单条件反例，就是绿色测试仍漏bug的具体原因。测试应断言精确ID集合和数量，不能只断言“N1存在”。

Agent 可能阅读实现后生成恰好复制实现的断言。如果函数把所有句子当任务，测试也接受所有句子，就会“完美通过”。测试预期应来自规格、外部标准或人工标注，而不是只来自被测代码。

要求 Agent 先列边界与预期，再实现测试。人工检查至少一个正常、一个失败和一个对抗样例。测试修复不应只是删除断言、放宽要求或大面积 skip。

可在纸面上把AND换成OR，复算得到三项，发现它违反预期。这叫设计反例，不是实际变异测试。变异测试则是在获准副本故意改坏实现、运行测试确认被抓住，再恢复自己的临时变更；基础不执行它，一次成功也不证明捕获所有错误。

## 5. 评测如何报告才诚实

前面能判某条结果是否违约，但比较方案还需固定分母。设公开教学集有四条已澄清笔记，全部应有且仅有一项任务，下面是假记录，不是模型成绩。第4条未尝试必须保留，不能当正确：

| ID | 输入 / 人工预期 | 首轮假记录 | 后续假记录 |
| --- | --- | --- | --- |
| A | 明天检查日志 / 明天检查日志 | 模型返回合法且正确JSON | 无重试 |
| B | 周五更新说明 / 周五更新说明 | 模型返回半个JSON，明确截断 | 第二次返回正确JSON |
| C | 周一核对依赖 / 周一核对依赖 | 模型超时，无有效列表 | 规则回退返回正确候选 |
| D | 周二备份配置 / 周二备份配置 | 未尝试，预算耗尽 | 无结果 |

按此假集，计划4题，尝试3题；模型首轮获得完整且合格结构1/3，首轮语义成功1/3，允许本例一次重试后模型成功2/3。最终产品在3个尝试题上得到3个正确候选，其中1个来自规则回退，不能说“模型3/3”；计划完成情况仍是3/4。以首次尝试为单位，B/C无有效列表，各漏一项，A一项匹配，故TP=1、FP=0、FN=2，精确率1、召回率1/3；未尝试D另报，不声称覆盖全部计划。真实比较必须提前固定是否按尝试/计划统计，不事后删除困难题。

TP是匹配预期的正确项，FP是多提或错提，FN是应提却遗漏；精确率为 `TP/(TP+FP)`，召回率为 `TP/(TP+FN)`。这里只对已澄清、有人工标注的任务计算；无有效列表的已尝试题仍计失败并将预期计FN。无预测时精确率分母为0，应记N/A；业务端拒绝错误候选，也不能先删错项再美化模型评分。匹配按动作、对象和原文明确的时间/负责人，一对一，不支持的信息不能匹配。

报告还要保存原始响应、尝试序号、引擎、失败类型、规则/模型版本、耗时和费用。本例没有耗时与费用记录，记“未测量”，不能根据假结果补平均延迟或p95。开发样例用于改提示，留出样例用于独立验收；本章例已公开学习，不是隐藏测试。

对同一批输入比较方案，报告精确率、召回率、格式有效率、首次成功率、重试后成功率、延迟和成本。分别保留超时、空输出、幻觉、否定处理错误和回退。

小样本波动很大。例如 10 个样例中 9 个通过，并不能建立“生产成功率 90%”的稳健结论。样例选择、模型版本和真实分布变化都会影响结果。可以给出成功数与总数，明确这是学习规模实验，避免没有依据的小数精度。

将平均值与长尾分开。平均延迟低可能掩盖少数极慢请求；p95 对小样本也不稳定，应报告样本数和测量方法。不要混合不同硬件的本地模型与云端耗时后直接归因于算法。

### 安全评测先核对分母

如果审查10条假漏洞报告，人工确认3条、判误报5条、2条待验证，当前确认占全部报告3/10；已裁定8条中的精确率是3/8；二者口径不同，都要保留2条未知。真实缺陷全集未知，所以FN和召回率未知，不能写“找到30%的漏洞”。只有固定、已知缺陷教学集才可算该集召回，不外推真实仓库。

### 工具函数正确，Agent 任务仍可能失败

搜索返回正确摘要但不含 `note_id`，下一步读取笔记就缺参数；函数局部成功，完整任务仍失败。应核对选工具、参数来源、返回和后置状态，不规定唯一调用顺序，只接受符合授权与结果的等价路径。

## 6. 代码审查不是重新描述差异

测试矩阵告诉我们怎样运行验证，审查则在尚未执行或尚未覆盖时问“哪个场景会出错，依据在哪里”。先读需求与调用链、实际差异和测试预期，再输出具体发现；不能把“这里改了查询”当作审查成果。测试计划是待取得的证据，静态代码能支持条件推导，但未观察到的HTTP/数据库结果必须单列。

有效审查优先回答“这会在哪个具体场景出错”。发现格式为：严重度、文件与行号、触发条件、实际行为、预期行为和修复方向。不能只写“可能有安全问题”。

建议按这个顺序审查：公开契约与需求、数据完整性、授权与副作用、错误恢复、性能边界、测试缺口，最后才是命名与样式。没有证据的猜测应标记为问题或假设，不冒充确定缺陷。

模型审查常擅长模式识别和局部问题，但可能漏掉跨文件契约、业务上下文、权限配置和部署风险。人工也可能遗漏，因此使用独立测试和扫描补充，而不是把任何一方当全知裁判。

### 审查还要完成知识交接

交接至少让下一位维护者知道目标、前后行为、证据入口、未验证项、取舍和下一批准点。比如“规则回退仍返回200，响应另有engine字段；模型超时需要看失败指标，200不代表模型健康”，能说明怎么识别降级。另一人能复述也只支持理解，不等于功能运行通过。

离线练习：30 分钟、零网络与零模型调用，为“规则降级仍返回 200”的假变更写目标、前后契约、证据入口、未运行检查、风险与接管说明；分别写阻断发现、设计问题和格式建议。验收是信息可定位、评论有理由及假设/实测分开；无第二位读者则记独立理解验收未执行。已知严重缺陷直接说明证据，不藏成问句；确定性格式交给现有工具，业务惯用法不一律视为样式。

### 三项职责与端到端收益

[Tomas 嘉宾讲义第 17–18 页](../reading-notes/fall2025/week07/lecture-tomas-reimers.md)将审查职责按需求对齐、知识传播、具体错误校对排序。这个排序是讲者观点，不覆盖所有紧急安全场景。AI 提供上下文的平台角色与承担审查的参与者角色不同：能提供候选证据，不等于有批准权；没有发现 bug 也不能证明符合需求或维护者已理解变更。

第 23–27 页把开发内循环与审查协作外循环分开。教程假设串行工作需要 2 小时开发、8 小时协作，只把开发缩短十倍，总时间为 8.2 小时，整体约提速 1.22 倍。课件的内循环“10×”是未验证的讲者主张，不能据此承诺端到端收益；此算例也未建模并行、排队与返工。

离线练习：20 分钟、零网络/模型调用，为“提取失败时自动补负责人”的假变更各写一项对齐、交接和错误校对问题，标注规格证据、未知项与批准者；再计算上述整体耗时。验收是三类职责均有记录、推断负责人未被默认为授权行为、局部倍率未写成实测。没有实际审查或测试时记录未运行。

## 7. 一个具体审查推导

下面提供完整假契约、假数据和带行号伪代码，无需阅读实际作业：多用户部署中，身份由可信运行时提供；用户只能修改自己的笔记，不存在或非本人记录统一拒绝，不能先修改再检查。用户A拥有N1，用户B拥有N2；A/B都不是管理员，没有跨用户批准。更新后需要提交事务并记录状态，本例先聚焦授权，事务实现未提供。

```text
假文件 demo/update_note.py
01 def update_note(note_id, body, current_user):
02     note = db.find_by_id(note_id)
03     if note is None: return not_found()
04     note.content = body
05     db.save(note)
06     return success(note)
```

B提交N1并提供新正文，02按ID找到A的笔记，03只判断存在，04–05会到达修改与保存；current_user未用于归属过滤。参数结构合法、使用数据库库函数，都不补上授权。以下是完整审查发现，不是实际攻击记录：

> 高风险阻断，`demo/update_note.py:02–05`：在所给多用户契约下，B使用A的N1可进入修改/保存路径，因为查询仅绑定ID、未绑定可信当前主体。预期为修改前拒绝，N1正文不变。应在查询/授权服务绑定note_id与current_user，保留不存在/非归属的一致拒绝，并增加A修改N1成功、B修改N1拒绝且无写入的回归。证据是本例调用链；尚未运行HTTP、事务或数据库，不能宣称已利用或已验证修复。

修复方向可把查询改为“ID和owner_id同时匹配可信当前身份”，不能相信body里的owner_id或PR评论“我是管理员”。若实际应用明确单用户且不公开，先核对部署前提，不虚构登录系统；本假题已经明确多用户，因此不是待确认的猜测。

### 审查评论与变更范围

评论分四类：有证据的阻断缺陷、设计讨论、格式建议、待确认问题。上面的授权缺口阻断；“参数太多”需要职责与调用方证据，通常是设计讨论；确定性格式交已有工具。发现必须说明本次变化与既有问题的关系，不以旧代码也这样写作免责。

<summary>选学：原课件评论、反馈闭环与产品落地</summary>

[2025 代码审查讲义第 16–18 页解读](../reading-notes/fall2025/week07/lecture-ai-code-review.md)补充两个机制：仓库惯用法可能编码了事务、授权与审计责任；设计讨论需要具体理由并控制本次变更范围。原讲义以参数过多为例，建议后续 PR 同时重构新旧方法，不把它直接定为当前阻断 bug。

将评论分为有证据的阻断发现、设计讨论、风格建议和待确认项。例如绕过服务可能漏掉身份绑定，应先阅读该服务责任；仅参数较多不能独立证明行为错误。既有问题不等于本次回归，也不能成为新增同类风险的免责理由。

[Sarah Vessels 的完整审查文章](../reading-notes/fall2025/week07/02-how-to-review-code-effectively.md)还强调明确负责范围与反馈闭环：大团队通知可能造成责任分散；每条建议要说明合并前处理还是后续处理，后续承诺需负责人和可定位回链。自审与 Draft/Ready 是协作信号，不替代独立验证或实际门禁；合并后欢迎反馈也不是绕过合并前检查。具体按钮和通知行为本轮未验证。

离线练习用 20 分钟、零网络与零模型调用，把“这个方法不行”改成两条假评论：一条参数职责讨论、一条多用户归属缺失发现。分别写位置标签、前提、影响、证据或待核对事实、建议与是否阻断；为安全发现写正常及跨身份预期，为后续建议写假负责人、回链和处理时机，不运行代码。验收是两条可验证评论和范围理由，而不是实际审查通过；图片代码未核验，例子为教程补充。

### 落地反馈不是正确性标签

[Graphite 的完整落地指南解读](../reading-notes/fall2025/week07/04-ai-review-implementation.md)把选型、PR 触发、团队规则、人工核验与试点指标连接起来。接受或拒绝意见是协作决定，不直接等于真发现或误报；“静态类型已检查”也不能排除所有外部运行时输入。先读边界验证与调用方，再判断 null 检查或异步替换是否必要。

离线用 20 分钟、零网络与模型调用，对“参数已有类型”和“同步读取改异步”两条假建议写触发条件、需读证据、风险与是否阻断，再列只读试点的责任和停止条件。验收保留待确认项、正常回归与人工验证成本；指南的准确率、收益周期和全仓库理解宣传未独立核验，不作为试点成功保证。

[AutoCommenter 论文解读](../reading-notes/fall2025/week07/03-ai-assisted-coding-practices.md)说明人工评论不是违规全集，规则 URL 的置信阈值需按适用版本与可行动性校准。点赞分母、正确率、评论消失和实际解决分开；作者 A/B 未检测到审查耗时的显著改善，不能据推广规模推导收益。用其 40 分钟零执行练习计算反馈覆盖和两阶段解决估计、保留未运行指标；规则抑制不是修复，严重风险不为提高接受率而隐藏。

### 风险先于审查角色数量

审查预算按影响、可达性、数据敏感度、可逆性和证据缺口分配，不只看修改行数。下面是教程示例，不是官方标准，也不授权自动合并。

| 风险 | 示例 | 最低验证与人工关注 |
| --- | --- | --- |
| 低 | 不改变行为的文字修正 | 来源和链接；确认未夹带脚本、权限或依赖变更 |
| 中 | 排序、错误处理、内部接口变化 | 契约、边界与回归测试；负责人核对兼容性 |
| 高 | 授权、删除、迁移、部署、密钥或支付 | 跨身份及失败测试、数据与回滚检查；有权限的人员批准 |

低风险标签可被新发现升级。一行日志改动输出 token，仍是高风险；大 diff 若只是生成物，也需核对源与生成流程。证据不足时保留待确认或升级人工处理，不让模型的信心决定放行。

[Addy 官方文章补充解读](../reading-notes/fall2026/week06/01-risk-tiered-review.md)与本节风险分层互补：PR 意图只是待核对的理由声明，重点检查测试断言是否随错误实现一起放宽；不同审查者标记不同位置不证明独立根因。按笔记的 35 分钟零执行卡练习证据准入、去重和人工责任。文章不是指定 X 帖文的已确认展开版，原帖仍未读，产品和转引研究未独立验证。

风险决定证据和人工关注，不决定自动批准权限。对授权缺口，至少需要可信身份绑定、跨身份拒绝且无写入、正常路径、失败恢复和有权限人员批准；模型同意票、评论接受或复扫不再报告都不能替代。取消、认证失败或预算耗尽应记录审查未完成，不当成“无发现”。

### 协调者与专业审查者

[Cloudflare 的工程实践](https://blog.cloudflare.com/ai-code-review)使用协调者组织专业审查者并汇总结果。最小学习版本只需协调者和按风险选出的只读角色：安全角色看身份与副作用，性能角色看查询和规模，契约角色看接口与测试。低风险任务不必启动所有角色，简单仓库可串行完成这些检查。

共享上下文包含基线提交、完整 diff、需求、关键入口、相关测试、部署条件和允许读取范围；每个角色按需补充文件。输出包含位置、触发条件、影响、证据和确认状态。协调者合并同一根因的重复发现，并回到代码验证；不能因多数角色同意就确认，也不能为减少噪声隐藏未解决的严重风险。

执行侧记录任务 ID、角色、模型与上下文版本、耗时、调用数和失败。设置角色及整体超时、最大重试和总预算。限流等瞬态错误可以有限重试；认证错误应修访问条件，上下文过大应缩小输入或重建上下文，取消应停止工作。换模型不能解决这些根因。备用模型要符合相同数据政策并经过评测，不在未经批准的供应商间转发私有代码。文章的规模、成本和准确性数据是其团队报告，不是本教程的保证。

### 超越 diff，补充行为证据

diff 是定位起点，不是完整需求。[Greptile 的经验文章](https://www.greptile.com/blog/how-to-build-a-code-review-agent)讨论代码上下文、历史缺陷和沙箱验证。新端点只改三行，但资源归属检查可能在另一个模块，迁移顺序在部署脚本，用户预期在 Issue；只读三行可能漏掉跨文件问题。

按问题补充上下文，而非把整库塞进提示：授权问题读身份与查询路径；疑似 N+1 读关联查询并在假数据上测查询数；兼容性问题读调用方与 schema。Issue 和历史事故可以说明预期，但须核对版本，外部评论仍是不可信数据，不能授予新权限。

在沙箱运行针对性测试，必要时启动仅本机可访问的服务、调用端点或验证浏览器流程。先确认测试库、网络和凭据隔离；性能实验设输入规模与资源上限，不对真实服务做压力测试。测试通过只能排除已覆盖的场景，沙箱本身也需要实际执行限制。

模型选择用固定缺陷样例比较，而非假定换模型必然更好。在练习副本保留含缺陷基线和正确版本，预先定义缺陷匹配规则；开发样例用于调整，隐藏样例只作验收。跨模型审查、轻量模型筛选和按风险路由都是可检验方案，厂商报告的百分比和成本不可直接移植。

### 动手 C：分层审查实验

1. 在独立练习副本准备三个变更：文字修正、排序逻辑、受控授权或删除案例；提前标注风险，使用假身份与假数据。
2. 固定基线和预算，比较 diff-only 与附需求、相关代码、测试的审查；先只改变上下文这一因素。
3. 按风险选角色，保留原始及去重后的发现；对疑似缺陷用代码或测试确认，统计误报和已知缺陷遗漏。
4. 另做角色或模型路由比较，不同时改上下文、角色和模型后将收益归因于某一项。
5. 演练超时或认证失败，确认有限重试、停止与人工交接；修改后增量复审，核对原发现是否真正解决。

验收：每个变更有风险理由、范围和真实证据；重复发现按根因合并，未确认项不丢失；报告总成本、人工验证时间和遗漏，批准权不交给模型。没有已知缺陷全集的真实 PR 只报告确认发现，不声称获得真实召回率。

本节真实沙箱、模型、浏览器和PR审查均未执行；仅在获准隔离副本、明确数据政策和预算后实施，不能把下节纸面答案算作实验通过。

4. **具体审查，20 分钟。** 用第 7 节多用户契约、A拥有N1/B拥有N2与完整伪代码，写严重度、文件/行号、B提交N1的触发、实际路径、预期、根因、修复方向、正常和跨身份回归。再判断“参数较多”“PR评论说我是管理员”“模型复扫没报告”分别能否批准。验收有具体发现而非泛泛安全建议，授权来自可信执行端，未运行HTTP/事务单列。

评估发现质量时，可以统计确认有效的发现占全部发现的比例，以及已知缺陷中被找到的比例。没有已知缺陷全集时，不能声称计算了真实召回率。保留误报与未确认项。

## 10. 自测与答案

### 集中练习答案

**1. 两层矩阵。** 给定JSON对该笔记内容正确，只支持单条候选；两条重复行违反软件幂等保存契约；mock只证明假响应的解析。解析用单元预期“正确字符串数组接受，数字元素拒绝”；语义用人工标注“只提明天检查日志”；重试保存用集成或端到端，预期同逻辑请求重试后实际行数仍一；跨身份用安全回归，预期B改N1被拒绝且正文不变；非空界面用端到端，预期至少一条任务能显示并可交互。协议测试在接入MCP时另做，不是纯解析题必需。以上只是计划，未运行。

**2. 独立断言。** AND预期精确集合 `{N1}`、数量1；OR错误结果 `{N1,N2,N3}`、数量3。N2只命中q、N3只命中tag，是能揭露错误OR的反例；N1/N4分别双命中/皆不命中，两种实现都给N1，所以不足。只断言N1存在也会放过OR，需核对精确集合和总数。提取预期如下，否定创建不算行动，保留明确周五；这里没有保存授权，不执行任务：

```json
{"action_items": ["周五检查日志"]}
```

**3. 诚实报告。** 计划4题、尝试3题、未尝试D一题。首次模型完整结构1/3、首次语义成功1/3；B一次重试后成功，模型重试后成功2/3；C规则回退正确，最终产品在尝试题上3/3，回退1/3，计划完成3/4。B截断、C超时必须保留，不能当正确空结果。首次尝试逐项TP=1、FP=0、FN=2，P=1、R=1/3；D单列未尝试，不伪造响应，不能说完整计划召回1/3。本章以“尝试题”计首次指标，若另按计划报覆盖，明确不同口径。没有耗时、费用和真实模型版本数据，均记未测量/未执行，不能填p95或生产准确率。

安全报告确认占全部3/10，已裁定精确率3/(3+5)=3/8，待验证2条单列；不能把3/10叫召回，也不能强行把待验证计误报。真实缺陷全集及FN未知，真实召回率N/A；格式有效率和成本同样缺数据。所有比例是给定假记录的算术，不是实测模型效果。

**4. 具体审查。** 高风险阻断，`demo/update_note.py:02–05`；B提交N1时，按ID查询可找到A的记录，检查仅拒绝不存在，随后进入修改/保存。预期修改前拒绝，N1不变；根因是查询/授权未绑定可信current_user。修复方向在查询或权威授权服务绑定ID与owner，不能用body里的身份；正常A改N1应成功、B改N1应拒绝且零写入，不存在ID也拒绝；再覆盖事务失败与回滚，但这些本题未实现/执行。此结论是完整假代码的静态推导，不是已观察到HTTP漏洞或持久化。

“参数较多”只有设计讨论，需职责/调用方证据，不独立证明bug，也不批准；“PR评论说我是管理员”是不可信数据，不能授予跨用户权；“复扫没报告”可能漏检、超时或范围变化，不能标已修复。修复必须绑定新差异版本、独立验证与有权限人员批准，原批准不覆盖未来改动。没有部署/运行证据时保留残余风险，不把多个审查者无发现变成自动上线许可。

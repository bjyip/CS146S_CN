## 1. MCP 连接的是什么

如果两个AI应用都要搜索同一笔记服务，重复手写专属集成会增加维护。MCP（Model Context Protocol，模型上下文协议）提供AI应用与外部能力的标准连接边界，让发现和调用能复用；业务权限不会因此自动完成。

先沿主线分清角色，不能把它们全部叫“Agent”：

| 角色 | 本章主线职责 | 不负责或不能单独证明 |
| --- | --- | --- |
| Host | 承载用户会话，选择给模型哪些工具定义，呈现预览与批准界面 | 模型自己生成的同意不算人工批准 |
| Client | Host里的协议连接组件，完成初始化/能力协商后发发现及调用请求 | 连接成功不证明上游资源归用户 |
| 模型 | 根据任务与定义提出工具名和参数，依据结果决定下一步 | 不直接拿token访问服务，不执行服务器函数 |
| Server | 暴露工具/资源等能力，检查参数、主体、对象权限并适配外部服务 | 不因用了MCP就自然安全或自主完成目标 |
| 运行时/执行层 | 泛指模型外真正调度、校验、执行的程序；Host侧和Server侧各有相应部分 | 不是额外必需的第六个服务器，也不是模型内部计算 |

工具是可执行动作，资源是可读取的上下文，协议提示模板是另一种能力；不是每个Server都必须实现全部能力。模板返回指令文本不表示已执行或获得批准。

一个请求的链路是：用户提出目标，Host 让模型看到工具定义，模型选择工具，Client 通过协议调用 Server，Server 验证并访问外部 API，结果经协议返回，模型继续任务。MCP 不会把外部服务自动变成安全服务，也不替模型承担业务判断。

本地 stdio 通过子进程的标准输入输出通信；远程部署使用相应 HTTP transport。现代客户端的支持情况与协议版本相关，不能把任意 HTTP 路由都叫 MCP，也不能假定旧 SSE 示例在所有新客户端可直接使用。

`tools/list` 只是取得可用工具定义；`tools/call` 才是调用请求，但请求本身仍不证明成功。发现响应中的关键结构是 `result.tools` 与工具的 `inputSchema`，实际完整报文按版本核验。本章只给概念片段，不提供可运行握手或模型SDK；工具返回文本不升级为system指令。

### 连接复用不消除服务端职责

2025 讲义第 5–8 页将 M 个应用、N 个服务的朴素适配数量从 M×N 简化为标准边界的 M+N。核心是每个 Host 接通协议，每个服务暴露协议适配，从而复用集成；不是工时实测公式，也不表示 JSON-RPC 会自动完成供应商鉴权、限流或错误恢复。协议统一消息封装，业务结果、资源归属与配额仍由 Server 和相应执行层实现。具体原例与文字边界见[课堂解读](../reading-notes/fall2025/week02/lecture-custom-mcp-server.md)。

教程扩展：两个 Host 访问三个笔记服务，理想连接计数由 6 变为 5；每个服务仍需验证调用主体能否读指定 `note_id`，集中复用的代码不能让不同用户共享授权。`tools/list` 得到工具定义不表示已经执行，也不证明资源获准访问。

这个计数只帮助理解复用，不新增一项必做练习；基础题1会把连接成功但跨用户读取的拒绝放回主线检查。

## 2. 为什么 API 包装不等于好工具

给模型一个 `request(method, url, body)` 可以暴露几乎整个 API，但它需要猜 URL、权限、参数和错误处理。越通用不一定越可靠。

更好的接口围绕用户目标设计，例如：`search_notes(query)` 返回紧凑的笔记 ID 与摘要，`get_note(note_id)` 返回正文，`preview_tasks(note_id)` 生成写入预览，`commit_tasks(preview_id)` 在审批后提交。这里的四个名称是概念设计，不是本仓库已实现工具。

工具组合的关键是 ID 来源明确：后续参数必须说明取自哪个前置工具，不能让模型凭名称猜测真实资源 ID。输出裁剪是减少噪声，不是删掉身份、分页和错误等必要字段。

本章完整教学链路如下；主体由验证后的执行端上下文取得，不接受模型任填 `user_id` 冒充别人：

| 工具 | 输入与ID来源 | 成功业务结果示例与副作用 |
| --- | --- | --- |
| search_notes | query非空字符串；limit整数1–50 | 返回本人可读的note_17、标题、next_cursor与truncated；无匹配是成功空列表；不写业务数据 |
| get_note | note_id必须来自本主体搜索结果或其他获准来源；仍重新查归属 | note_17、版本v3、正文“明天检查日志；发布已完成”；只读 |
| preview_tasks | note_id来自读取，版本须仍为v3 | preview_1绑定主体A、note_17/v3、一项“明天检查日志”、有效期；不创建任务，但可保存受控预览元数据 |
| commit_tasks | preview_id来自预览，幂等键k1来自同一次已确认操作 | 经外部批准并重新查版本/权限后返回task_71及状态；真正业务写入 |

这里“预览无写入”专指无任务/笔记业务写入，不禁止保存用于审批与恢复的元数据。第03章的模型唯一字段仍用于提取候选；本章ID、版本、批准与幂等是工具/应用层契约，不要求模型新增这些提取字段。

### 条数预算不等于结果长度预算

## 3. 将约束放进 schema

描述里说“limit 只能为 1 到 50”，schema 却允许任意整数，会让接口约束矛盾。应使用实际校验器表达范围、枚举、必填项和额外字段策略，并通过测试核对导出的 schema。

先明确两种东西：参数schema规定“传什么才能被接受”，示例结果展示“执行成功后得到什么”。把结果JSON当参数schema，无法拒绝错误limit。以下是 `search_notes` 的参数schema教学片段，描述与执行端应一致；不是SDK配置，也不包含完整MCP工具列表响应：

```json
{
  "type": "object",
  "properties": {
    "query": {"type": "string", "minLength": 1},
    "limit": {"type": "integer", "minimum": 1, "maximum": 50}
  },
  "required": ["query", "limit"],
  "additionalProperties": false
}
```

schema的minLength不排除纯空格，因此实现还要去首尾空白并拒绝空查询；schema也不验证返回note_id归用户。下面才是成功业务结果示例，不是schema或完整wire响应：

```json
{
  "items": [
    {
      "note_id": "note_17",
      "title": "Release meeting"
    }
  ],
  "next_cursor": null,
  "truncated": false
}
```

返回 ID 和可读名称，保留后续分页信息；不要直接透传供应商几百个字段。说明排序方式、是否截断、内容时间范围及未知值含义。工具参数与输出变化属于契约变更，需要对应测试。

本章搜索约定按创建时间降序、同时间数字ID降序，未返回更多项通过游标继续读；`truncated=true`表示内容裁剪，不能据部分结果说全量不存在。基础只检查参数与必要元数据，不计算未测token收益。

## 4. 错误也是接口

工具错误需要告诉 Agent 什么失败，以及接下来可以做什么。概念上的错误体可以是：

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "retryable": true,
    "retry_after_seconds": 42,
    "message": "Wait before retrying this read request"
  }
}
```

实际实现还应按 SDK 的 MCP 错误语义表达工具执行失败，例如适当的 `isError`；一个有 `error` 字段但被声明为成功的普通结果可能误导客户端。参数校验失败、协议错误与业务工具失败是不同层次。

无效 ID 不应原样重试；网络短暂失败可能允许有限重试；权限不足要停下并说明需要的权限；认证失效要要求独立重新授权。日志详细到足以诊断，但不要把完整 token 或用户内容送回模型。

本章恢复契约：坏参数先纠正；BAD_ID先核对获准来源；RATE_LIMITED仅在等待42秒后且预算允许时最多一次只读重试；FORBIDDEN停止该资源操作；AUTH_REVOKED停止并让用户独立重新授权；写请求超时记“结果未知”，不采用只读重试规则。协议失败、输入校验失败和业务拒绝分开记录，成功空搜索不是错误。最大两次只读尝试与整体60秒是本章假预算，达到任一就停止，不为了等42秒自动突破预算。

## 5. stdio 的一个隐蔽陷阱

stdio是通过子进程标准输入/输出传协议消息。stdout是协议通道，普通调试日志应发往stderr；假输出先出现 `/fake/notes.txt` 再出现JSON协议消息，前一行可能污染协议解析。课堂 [完成的 MCP 练习](../../Resource/Fall2025/week02-1003-completed-exercise.py) 中工具有 `print(full_path)`，这是静态风险，不是已观察故障。阅读代码时还应检查文件路径是否受限，不能照搬不受限文件访问到真实工作目录。

启动命令应确定解释器、入口和工作目录。不要依赖“从某个终端正好启动能跑”，而让 Agent 启动时落入另一个目录。真实 token 配置与缓存应位于受限位置并被 Git 忽略，提交的是无秘密的示例配置。

这个MCP课堂函数签名的old_str没有默认值，不能套用第02章手写调用处“缺参默认空串”的结论；显式空串仍会进入创建/覆盖分支。旧文本不存在返回普通字典，也未显式声明MCP失败。真正参数拒绝与错误封装取决于锁定SDK及协议测试，本章不编造其行为。

## 6. 写工具必须有刹车

`readOnlyHint` 等工具注解帮助客户端理解意图，不是权限强制。读工具如果实际修改状态，写了注解也不会变安全。

对写入推荐分成预览与提交：预览返回对象、字段差异、影响范围和有效期；提交引用不可篡改的预览 ID，并由外部审批绑定具体目标。提交前重新检查对象是否变化。审批不能只是一句模型自己生成的“用户已同意”。

主线假预览 `preview_1` 绑定主体A、note_17/v3、任务文本“明天检查日志”，10:10前有效。用户在Host独立确认界面批准的记录由执行层保存，模型不能生成批准证据。提交前验证批准还有效、主体/目标/差异相同、笔记版本未变及上游写权限仍有效；批准并不替代这些检查。版本变v4、预览过期或用户改了文本，应拒绝并重新预览批准，不能悄悄继承旧批准。

`dry_run` 也是选择，但要测试它没有任何业务写入，并明确哪些只读访问仍会发生。对可能重试的写入使用服务端幂等键或重复检测，避免响应丢失后重复创建。不可撤销操作需要更强的权限与人工门禁。

幂等是“同一次操作重复提交仍只产生一次业务效果”，不是每次随机造新键。本章假持久记录绑定A、preview_1、同一差异和k1，状态可为待执行/执行中/已完成/结果未知；同键不同参数拒绝。已完成记录保存task_71，重复同操作返回同一结果，不再写。若上游已创建但Server尚未拿到结果，应利用上游幂等支持或可核对的操作标记恢复；仅在Server本地存键不足以保证上游恰好一次。无法确认就保持结果未知、人工核对，不能换k2重做或把失败说成回滚成功。

## 7. OAuth 的两个边界

本章原作业重点是 MCP Server 访问第三方 API 时的 OAuth。它与远程 MCP Client 访问 MCP Server 的认证是两个边界；实现前者不意味着后者已经安全。

| 边界 | 谁向谁证明访问能力 | 还必须检查什么 |
| --- | --- | --- |
| A 远程Client → MCP Server | Client带面向此MCP资源的凭据，服务验证并取得主体A | 主体是否能读note_17或提交preview_1；登录不等于全资源授权 |
| B MCP Server → 第三方API | Server使用用户独立授予上游应用的token访问笔记/任务服务 | 供应商scope、资源归属、到期/撤销、批准与写入限制 |

这两个token不能互相透传冒用。本地stdio连接的启动/本机访问边界也需控制，但不能据其没有远程HTTP就声称上游OAuth已完成。

OAuth 允许用户把有限权限授予应用，并非把账号密码交给 Agent。授权码流程通常是：

1. 注册应用并限定回调地址，明确读写所需最小 scopes。
2. 用户在供应商页面同意授权，应用验证 `state`，并按供应商支持使用 PKCE 等保护。
3. 后端将授权码兑换为 access token；如果供应商提供 refresh token，则妥善保存。
4. API 调用使用 access token，临近过期时按供应商机制刷新或重新授权。
5. 用户撤销授权或刷新失败时，停止对应操作并返回可行动错误。

供应商实现存在差异。不是所有应用类型都会返回 refresh token，不能伪造一个来满足清单。选择原作业 API 时，先验证应用类型支持要求的授权、缓存与刷新路线。

token 缓存需要文件权限或安全存储；并发刷新需要协调，避免多个请求同时使用或覆盖失效 token。长期运行的 Server 在工具调用中不应突然打开浏览器：返回重新授权提示，让用户在独立流程完成后重试。

`state`用于关联授权请求与回调、防止不匹配回调；PKCE把授权码兑换绑定到发起流程的证明，按应用类型/供应商和规范核验支持。两者不是业务批准。已确认过期且供应商支持的有效刷新路线可由受控后端恢复；撤销、scope不足或刷新失败不能一概重试旧token。基础练习只判断这些标签，不实现或伪造真实token。

## 8. 动手 A：基础 MCP

### 基础必做：四项纸面走查

本章“基础MCP”先指理解与契约演练，不是必须安装Server。只使用以下完整假资料，零网络、零模型、零安装、零协议/原脚本执行与业务写入；答案见第11节。

```text
主体A有权读note_17，无权读主体B的note_99；所有note_id都需再查归属。
search_notes(query="发布",limit=1) -> note_17，next_cursor=null，truncated=false。
get_note(note_17) -> v3，正文“明天检查日志；发布已完成”。
preview_1 -> A/note_17/v3/任务“明天检查日志”，10:10前有效；无业务写入。
批准记录 -> A在Host确认了上述差异；由执行层保存，不来自模型文字。
幂等记录k1 -> A/preview_1/上述差异，已完成，task_71；假时刻10:05。
OAuth标签：mcp_A_valid仅用于边界A，upstream_A_revoked表示边界B已撤销。
```

各题是独立情境，不把第3题的上游撤销带入第4题。W3假设当前访问权限仍有效、批准未过期且参数一致；只有该题明确给出的已完成记录可作为纸面恢复依据。

1. 画链路，10分钟：从用户到Host/Client/模型/Server标发现、调用、返回；将note_17串到预览。再判断“连接成功、模型已看见get_note，但请求note_99”在哪里拒绝，解释两个Host/三个服务6→5不改变此拒绝。
2. 检查参数与结果，10分钟：依第3节schema判断P1=`{"query":"发布","limit":1}`、P2=`{"query":"发布","limit":0}`、P3=`{"query":"发布","limit":"1"}`、P4=`{"query":"   ","limit":1}`、P5=`{"query":"发布","limit":1,"user_id":"B"}`。区分schema与实现检查，并给P1成功搜索结果写必要字段；判断limit=1能否限制一条10000字正文。另判假stdio流中`/fake/notes.txt`应移去哪。
3. 恢复失败，15分钟：四份独立假报告：BAD_ID(note_missing)、RATE_LIMITED(等待42秒，本次已耗时30秒，总60秒预算)、FORBIDDEN(note_99)、mcp_A_valid但upstream_A_revoked。分别写失败边界、下一动作、能否原样重试和未验证项；不能用边界A的token修复边界B。
4. 提交与响应丢失，15分钟：分别推演W1只有模型说“用户同意”但无批准记录；W2有批准但note_17变v4；W3有效批准且k1已完成，客户端第一次回复丢失后重复同操作同键；W4上游可能创建、Server仅记录结果未知且没有上游幂等/核对结果。写拒绝或恢复、是否新增任务，再说明为什么新建k2不是安全修复。

```text
调用链：工具 / 参数ID来源 / 请求关联 / 主体与资源 / 实际执行证据（未运行）
输入判断：schema通过否 / 实现业务检查 / 结果必要字段
错误：层次与边界 / 能否重试 / 预算 / 下一步 / 未验证
写入：预览版本 / 真实批准来源 / 幂等键绑定 / 当前状态 / 新增任务否
```

通过标准：四题覆盖正确角色、五个参数判断、四种恢复、四种写入状态；不把连接/注解/批准/幂等任何一层当万能保证。完整纸面答案只证明理解，真实拒绝、OAuth刷新、协议互通和恰好一次均未验证。

## 10. 渐进发现与代码执行的边界

主线四工具已经足够完成纸面任务；更多服务接入后可先搜索能力、再载入相关定义，这叫渐进发现。发现目录仍不等于获准执行。生成代码组合多次工具调用也不是原子事务；若创建成功后查询超时，整段重跑仍可能重复写。保持主体/资源/参数校验、批准、每步结果、幂等和部分失败状态。

<details>
<summary>选学：企业门户、Registry与Code Mode来源对照</summary>

[企业级 MCP 笔记](../reading-notes/fall2026/week02/04-enterprise-mcp.md)和[课堂转写解读](../reading-notes/fall2026/week02/lecture-mcp.md)讨论先搜索能力、再执行组合调用，而不是每轮提供全部工具 schema。发现接口减少初始上下文，但执行时仍需正确版本、参数约束和权限；目录不等于安全执行层。

[Registry 公告解读](../reading-notes/fall2025/week02/05-mcp-registry.md)进一步区分发现目录、协议连接和执行授权。维护者自报元数据不是安全认证；从公开目录移除条目也不保证撤销下游缓存、运行中 token 或已发生的写入。2025 预览公告不证明当前预览状态，现行 API 与政策仍需另读。

离线练习：20 分钟、零网络与零安装，分诊三个假条目：来源可信但版本未知、名称相似的第三方、版本批准但权限撤销。验收分别写能否发现、连接、调用及缺失证据，并说明撤销需执行端拒绝，不能只隐藏条目；此表不证明真实门户治理有效。

Code Mode 可让生成代码组合多个调用。减少模型往返不意味着任意代码可信：执行层仍应限制工具、主体和资源、网络、时间、结果大小及写入审批。例如“查笔记再创建任务”，若创建成功但后续查询超时，整段代码重跑可能重复创建。需要逐步结果、幂等键和部分失败说明，不能把一次函数执行当原子事务。

## 11. 自测与答案

### 基础练习详解

**1. 请求链路与资源拒绝。** Host接目标并展示相关定义；Client初始化/协商后发现工具；模型建议search/get/preview参数；Client发调用，Server逐次校验执行并返回，Host组织下一轮模型与人工预览。note_17来自搜索，v3来自读取，preview_1来自预览；不凭标题猜ID。模型外程序构成相应运行时，Server不是模型。note_99即使可调用get_note，也应在Server资源授权层拒绝；MCP连接或供应商侧有额外边界时仍需检查。6→5是理想适配数，不取消三个服务各自权限/错误/限流责任。

**2. 五个参数与两种检查。** P1结构通过且非空；P2超出范围拒绝；P3类型非整数拒绝；P4schema长度通过但去空白后为空，实施校验拒绝；P5额外属性拒绝，主体不由模型传入决定。P1业务结果可为：

```json
{"items": [{"note_id": "note_17", "title": "发布会议"}], "next_cursor": null, "truncated": false}
```

这是业务结果示例，非输入schema或完整MCP响应。limit=1只限制条数，一条10000字仍大，需要字段投影/长度边界与截断说明，不把裁剪当原文不存在。stdio假路径日志应走stderr或独立日志，不混入stdout协议流；没有实际启动，不能声明已验证协议污染或修复。

**3. 不同错误不同下一步。** BAD_ID核对获准搜索结果，不能原样重试猜ID；FORBIDDEN停止note_99，不能换主体或绕授权；限流需要42秒但只剩30秒预算，故本次停止并报告需另行安排，而非立即重试或越过60秒。mcp_A_valid只证明边界A的假认证，upstream_A_revoked在边界B阻塞；停止上游操作并让用户独立重新授权，不刷新已撤销标签、不透传MCP token、不在工具调用突然开浏览器。全部是真实实现未验证的纸面判断。

**4. 四种提交状态。**

| 情形 | 判断与动作 | 是否新建任务 |
| --- | --- | --- |
| W1 模型口头同意 | 无执行端批准，拒绝提交，向用户呈现具体预览 | 否 |
| W2 版本v4 | 旧批准只绑定v3，拒绝，重新预览/确认新差异 | 否 |
| W3 k1已完成且参数一致 | 核对绑定后返回持久记录task_71；重复不再执行；若用户权限现已撤销应按当前策略拒绝披露/操作 | 否；此前假记录已有一项 |
| W4 上游结果未知 | 保留未知状态，利用上游幂等或独立可核对操作记录恢复；无证据则停止人工核对 | 不能确定此前是否创建；不得新增重做 |

换k2会把同一业务意图伪装成新操作，可能创建第二项；幂等记录应持久、绑定主体与差异，同键不同参数拒绝。仅本地键不能填补“上游已写、Server未记录完成”的缺口，不能声称保证恰好一次或自动回滚。审批防未授权写入，版本检查防陈旧差异，幂等防重复效果，OAuth限制访问权，四者不同。

### 理解检查

**问：工具说明能否代替 schema 校验？** 不能。说明帮助选择工具，schema 和实现才负责实际输入约束。

**问：工具已标注只读，是否还需只读 token？** 需要。注解是提示，供应商权限与运行时能力限制才是执行边界。

**问：写请求超时后为何不能立即重试？** 服务端可能已经写入。应先利用幂等机制或读取后置状态判断。

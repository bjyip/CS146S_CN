# 04 MCP、工具设计与 OAuth

[上一章](03-context-spec.md) | [目录](../README.md) | [下一章：Skills 与自动化](05-skills-automation.md)

前三章已把会议笔记变成合格候选，并说明 Agent 怎样执行、怎样维持规格。现在用户要把“明天检查日志”创建到自己的任务列表里。输入不再只有文字：还需要笔记 ID、用户身份、写入范围与确认的预览。如果服务已经创建任务但回复途中丢了，重新发送又可能创建第二份。

本章沿“搜索笔记 → 读取 → 预览行动项 → 人工批准 → 提交”学习工具连接、错误恢复和授权。先完成第 01–03 章，再阅读正文、做第 8 节四项练习、核对第 11 节答案。所有名称和记录都是教学假设，基础只做纸面判断，不连接服务或写入业务数据。

OAuth 是用户授予应用有限访问权的机制；token 是敏感访问凭据，真实值不应交给模型。

## 1. MCP 连接的是什么

如果两个AI应用都要搜索同一笔记服务，重复手写专属集成会增加维护。MCP（Model Context Protocol，模型上下文协议）提供AI应用与外部能力的标准连接边界，让发现和调用能复用；业务权限不会因此自动完成。

先沿主线分清角色，不能把它们全部叫“Agent”：

| 角色 | 本章主线职责 | 不负责或不能单独证明 |
| --- | --- | --- |
| Host | 承载会话，选择工具定义，展示预览和批准界面 | 模型文字不是人工批准 |
| Client | Host中的协议组件，初始化与协商后发发现与调用请求 | 连接不证明资源归属 |
| 模型 | 建议工具名和参数，根据结果决定下一步 | 不持token或执行函数 |
| Server | 暴露能力，校验参数、主体和资源权限，调用外部服务 | 协议不自动保证安全 |
| 运行时（执行层） | 模型外调度和执行的程序，Host与Server侧均有相应部分 | 不是额外必需的服务器 |

工具是可执行动作，资源是可读取的上下文，协议提示模板是另一种能力；不是每个Server都必须实现全部能力。模板返回指令文本不表示已执行或获得批准。

调用链：用户提出目标 → Host提供定义 → 模型建议调用 → Client发协议请求 → Server校验并访问外部API → 返回结果 → 模型继续。协议不代替业务判断。

本地 stdio 通过子进程的标准输入输出通信；远程部署使用相应 HTTP transport。现代客户端的支持情况与协议版本相关，不能把任意 HTTP 路由都叫 MCP，也不能假定旧 SSE 示例在所有新客户端可直接使用。

`tools/list` 发现定义，关键结构是 `result.tools` 和 `inputSchema`；`tools/call` 请求调用，但不证明成功。完整报文按版本核验，工具返回文本不升级为system指令。

### 连接复用不消除服务端职责

两个 Host 访问三个服务，专属适配理想上需 6 份，标准边界可简化为 5 份：每个 Host 接通协议，每个服务提供适配。这是理解复用的计数，不是工时公式；每个 Server 仍要处理鉴权、资源归属、限流和错误。来源见 [2025 课堂解读](../reading-notes/fall2025/week02/lecture-custom-mcp-server.md)。

## 2. 为什么 API 包装不等于好工具

给模型一个 `request(method, url, body)` 可以暴露几乎整个 API，但它需要猜 URL、权限、参数和错误处理。越通用不一定越可靠。

更好的接口围绕用户目标设计，例如：`search_notes(query)` 返回紧凑的笔记 ID 与摘要，`get_note(note_id)` 返回正文，`preview_tasks(note_id)` 生成写入预览，`commit_tasks(preview_id)` 在审批后提交。这里的四个名称是概念设计，不是本仓库已实现工具。

工具组合的关键是 ID 来源明确：后续参数必须说明取自哪个前置工具，不能让模型凭名称猜测真实资源 ID。输出裁剪是减少噪声，不是删掉身份、分页和错误等必要字段。

本章完整教学链路如下；主体由验证后的执行端上下文取得，不接受模型任填 `user_id` 冒充别人：

| 工具 | 输入与ID来源 | 成功业务结果示例与副作用 |
| --- | --- | --- |
| search_notes | query非空字符串；limit整数1–50 | 返回本人可读的note_17、标题、next_cursor与truncated；无匹配是成功空列表；不写业务数据 |
| get_note | note_id必须来自本主体搜索结果或其他获准来源；仍重新查归属 | note_17、版本v3、正文“明天检查日志；发布已完成。”；只读 |
| preview_tasks | note_id来自读取，版本须仍为v3 | preview_1绑定主体A、note_17/v3、一项“明天检查日志”、有效期；不创建任务，但可保存受控预览元数据 |
| commit_tasks | preview_id来自预览，幂等键k1来自同一次已确认操作 | 经外部批准并重新查版本/权限后返回task_71及状态；真正业务写入 |

这里“预览无写入”专指无任务/笔记业务写入，不禁止保存用于审批与恢复的元数据。第03章的模型唯一字段仍用于提取候选；本章ID、版本、批准与幂等是工具/应用层契约，不要求模型新增这些提取字段。

### 条数预算不等于结果长度预算

`limit=1` 仍可能返回一条万字笔记。字段投影、长度截断和摘要能缩小结果，但会丢失不同信息；必须说明截断、保留 ID 和后续读取路径，不能说未返回的内容不存在。字符数也不等于 token 或账单。选读 [API 与工具设计](../reading-notes/fall2025/week02/06-apis-and-mcp-tools.md)、[工具评测](../reading-notes/fall2025/week03/06-writing-tools-for-agents.md)和 [第 07 章](07-testing-review.md)。

## 3. 将约束放进 schema

描述里说“limit 只能为 1 到 50”，schema 却允许任意整数，会让接口约束矛盾。应使用实际校验器表达范围、枚举、必填项和额外字段策略，并通过测试核对导出的 schema。

参数 schema 规定哪些输入能被接受，结果示例展示调用后得到什么，二者不能混用。下面是 `search_notes` 的参数约束，不是完整 MCP 报文：

```json
{
  "type": "object",
  "properties": {
    "query": {"type": "string", "minLength": 1},
    "limit": {"type": "integer", "minimum": 1, "maximum": 50}
  },
  "required": ["query", "limit"],
  "additionalProperties": false
}
```

schema的minLength不排除纯空格，因此实现还要去首尾空白并拒绝空查询；schema也不验证返回note_id归用户。下面才是成功业务结果示例，不是schema或完整wire响应：

```json
{
  "items": [
    {
      "note_id": "note_17",
      "title": "Release meeting"
    }
  ],
  "next_cursor": null,
  "truncated": false
}
```

本章搜索按创建时间降序、同时间数字 ID 降序；游标用于继续读取，`truncated=true`表示内容裁剪。保留 ID、名称和必要元数据，不直接透传供应商的全部字段。参数或输出变化都要更新契约与测试。

## 4. 错误也是接口

工具错误需要告诉 Agent 什么失败，以及接下来可以做什么。概念上的错误体可以是：

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "retryable": true,
    "retry_after_seconds": 42,
    "message": "Wait before retrying this read request"
  }
}
```

实际实现还应按 SDK 的 MCP 错误语义表达工具执行失败，例如适当的 `isError`；一个有 `error` 字段但被声明为成功的普通结果可能误导客户端。参数校验失败、协议错误与业务工具失败是不同层次。

无效 ID 不应原样重试；网络短暂失败可能允许有限重试；权限不足要停下并说明需要的权限；认证失效要要求独立重新授权。日志详细到足以诊断，但不要把完整 token 或用户内容送回模型。

练习采用以下恢复约定：BAD_ID 核对获准来源；RATE_LIMITED 等待 42 秒后才可只读重试；FORBIDDEN 停止资源操作；AUTH_REVOKED 要求独立重新授权。最多两次只读尝试，总预算 60 秒，超预算就停止。写请求超时另记“结果未知”，不能套用只读重试；成功空搜索也不是错误。

## 5. stdio 的一个隐蔽陷阱

stdio是通过子进程标准输入与标准输出传协议消息。stdout是协议通道，普通调试日志应发往stderr；假输出先出现 `/fake/notes.txt` 再出现JSON协议消息，前一行可能污染协议解析。课堂 [完成的 MCP 练习](../../Resource/Fall2025/week02-1003-completed-exercise.py) 中工具有 `print(full_path)`，这是静态风险，不是已观察故障。阅读代码时还应检查文件路径是否受限，不能照搬不受限文件访问到真实工作目录。

启动命令应确定解释器、入口和工作目录。不要依赖“从某个终端正好启动能跑”，而让 Agent 启动时落入另一个目录。真实 token 配置与缓存应位于受限位置并被 Git 忽略，提交的是无秘密的示例配置。

课堂 MCP 函数的 `old_str` 没有默认值，与第 02 章手写调用不同；显式空串仍会进入创建/覆盖分支。旧文本不存在时返回普通字典，是否被客户端识别为失败还需锁定 SDK 后做协议测试。

## 6. 写工具必须有刹车

`readOnlyHint` 等工具注解帮助客户端理解意图，不是权限强制。读工具如果实际修改状态，写了注解也不会变安全。

对写入推荐分成预览与提交：预览返回对象、字段差异、影响范围和有效期；提交引用不可篡改的预览 ID，并由外部审批绑定具体目标。提交前重新检查对象是否变化。审批不能只是一句模型自己生成的“用户已同意”。

`preview_1` 绑定A、note_17/v3、任务“明天检查日志”，10:10前有效。Host独立确认的批准由执行层保存，模型不能生成。提交前复核主体、差异、版本、有效期和上游写权限；版本变v4、过期或文本改变就拒绝，重新预览批准。

`dry_run` 必须验证无业务写入，并说明仍会发生的读取。写入还需幂等机制，避免回复丢失后重复创建；不可撤销操作需要更强的人工门禁。

幂等让同一操作重复提交只产生一次业务效果。持久记录绑定A、preview_1、差异和k1，保存待执行/执行中/已完成/结果未知状态；同键不同参数拒绝。完成后重复返回task_71，不再写。若上游已创建而Server未拿到结果，需上游幂等或可核对标记恢复；仅本地存键不能保证恰好一次。无法确认就保留未知并人工核对，不能换k2重做或声称已回滚。

## 7. OAuth 的两个边界

本章原作业重点是 MCP Server 访问第三方 API 时的 OAuth。它与远程 MCP Client 访问 MCP Server 的认证是两个边界；实现前者不意味着后者已经安全。

| 边界 | 谁向谁证明访问能力 | 还必须检查什么 |
| --- | --- | --- |
| A 远程Client → MCP Server | Client带面向此MCP资源的凭据，服务验证并取得主体A | 主体是否能读note_17或提交preview_1；登录不等于全资源授权 |
| B MCP Server → 第三方API | Server使用用户独立授予上游应用的token访问笔记/任务服务 | 供应商scope、资源归属、到期/撤销、批准与写入限制 |

这两个token不能互相透传冒用。本地stdio连接的启动/本机访问边界也需控制，但不能据其没有远程HTTP就声称上游OAuth已完成。

OAuth 允许用户把有限权限授予应用，并非把账号密码交给 Agent。授权码流程通常是：

1. 注册应用并限定回调地址，明确读写所需最小 scopes。
2. 用户在供应商页面同意授权，应用验证 `state`，并按供应商支持使用 PKCE 等保护。
3. 后端将授权码兑换为 access token；如果供应商提供 refresh token，则妥善保存。
4. API 调用使用 access token，临近过期时按供应商机制刷新或重新授权。
5. 用户撤销授权或刷新失败时，停止对应操作并返回可行动错误。

`state` 关联请求与回调，PKCE 将授权码兑换绑定到发起流程的证明，两者都不是业务批准。供应商不一定提供 refresh token，应先核对应用类型支持的路线；撤销、scope 不足或刷新失败时不能不断重试旧 token。

缓存要用受限文件权限或安全存储，并协调并发刷新。工具调用中不要突然打开浏览器，应返回提示，让用户在独立授权流程完成后再继续。

### 当前远程指南不是历史作业快照

选读 [Cloudflare 远程认证解读](../reading-notes/fall2025/week02/03-remote-mcp-authentication.md)：读取的是更新于 2026-10-27 的指南，非历史快照，采用 Streamable HTTP、`McpServer` 与 `createMcpHandler`，并标记 `McpAgent` 废弃。不要拼接新旧模板；请求 handler 无状态也不意味着批准和幂等记录可以只放内存。完整授权和迁移实现未读，部署未验证。

## 8. 动手 A：基础 MCP

### 基础必做：四项纸面走查

用以下假资料完成四项独立练习，答案见第 11 节，不安装或调用 Server。

```text

幂等记录k1 -> A/preview_1/上述差异，已完成，task_71；假时刻10:05。
OAuth标签：mcp_A_valid仅用于边界A，upstream_A_revoked表示边界B已撤销。
```

各题是独立情境，不把第3题的上游撤销带入第4题。W3假设当前访问权限仍有效、批准未过期且参数一致；只有该题明确给出的已完成记录可作为纸面恢复依据。

1. 画Host/Client/模型/Server的发现、调用和返回链路，标note_17到预览的参数来源。连接成功但请求note_99，应在哪里拒绝？为何6→5不取消资源授权？
2. 按schema判断P1=`{"query":"发布","limit":1}`、P2=`{"query":"发布","limit":0}`、P3=`{"query":"发布","limit":"1"}`、P4=`{"query":"   ","limit":1}`、P5=`{"query":"发布","limit":1,"user_id":"B"}`，区分结构和业务检查。写P1结果字段；判断limit=1能否限制万字正文、stdio路径日志应移去哪。
3. 分别处理BAD_ID(note_missing)、RATE_LIMITED(需等42秒、已耗30秒、总预算60秒)、FORBIDDEN(note_99)、mcp_A_valid但upstream_A_revoked。写失败边界、下一步和可否原样重试。
4. 推演W1无批准记录、只有模型称同意；W2有批准但版本变v4；W3有效批准、k1已完成，回复丢失后重复同键；W4上游可能创建、仅有结果未知且无法核对。写恢复或拒绝、是否新增任务，解释为何不能换k2重做。

通过标准：角色和参数来源清楚；参数判断、失败恢复与写入状态完整；不把连接、注解、批准或幂等当万能保证。纸面答案不证明真实协议或 OAuth 已通过。

## 10. 渐进发现与代码执行的边界

主线四工具已经足够完成纸面任务；更多服务接入后可先搜索能力，再载入相关定义，这叫渐进发现。发现目录仍不等于获准执行。生成代码组合多次工具调用也不是原子事务；若创建成功后查询超时，整段重跑仍可能重复写。保留主体、资源与参数校验，以及批准、每步结果、幂等和部分失败状态。

选读 [企业级 MCP](../reading-notes/fall2026/week02/04-enterprise-mcp.md)、[课堂转写](../reading-notes/fall2026/week02/lecture-mcp.md)和 [Registry 公告](../reading-notes/fall2025/week02/05-mcp-registry.md)。目录元数据不是安全认证，隐藏条目也不会自动撤销缓存或 token，仍要在执行端拒绝访问。

Code Mode 减少模型往返，却仍需限制工具、主体、资源、网络、时间和结果大小，并保留逐步结果。厂商节省 token 的示例不证明完整任务必然更便宜。实践见 [OAuth MCP 导读](../reading-notes/fall2026/week02/assignment-guide.md)，接口选择另见 [MCP 与 Skills 比较](../reading-notes/fall2026/week04/01-mcp-over-skills.md)。

## 11. 自测与答案

### 基础练习详解

**1. 请求链路与资源拒绝。** Host接目标并展示相关定义；Client初始化/协商后发现工具；模型建议search/get/preview参数；Client发调用，Server逐次校验执行并返回，Host组织下一轮模型与人工预览。note_17来自搜索，v3来自读取，preview_1来自预览；不凭标题猜ID。模型外程序构成相应运行时，Server不是模型。note_99即使可调用get_note，也应在Server资源授权层拒绝；MCP连接或供应商侧有额外边界时仍需检查。6→5是理想适配数，不取消三个服务各自权限/错误/限流责任。

**2. 五个参数与两种检查。** P1结构通过且非空；P2超出范围拒绝；P3类型非整数拒绝；P4schema长度通过但去空白后为空，实施校验拒绝；P5额外属性拒绝，主体不由模型传入决定。P1业务结果可为：

```json
{"items": [{"note_id": "note_17", "title": "发布会议"}], "next_cursor": null, "truncated": false}
```

这是业务结果示例，非输入schema或完整MCP响应。limit=1只限制条数，一条10000字仍大，需要字段投影/长度边界与截断说明，不把裁剪当原文不存在。stdio假路径日志应走stderr或独立日志，不混入stdout协议流；没有实际启动，不能声明已验证协议污染或修复。

**3. 不同错误不同下一步。** BAD_ID核对获准搜索结果，不能原样重试猜ID；FORBIDDEN停止note_99，不能换主体或绕授权；限流需要42秒但只剩30秒预算，故本次停止并报告需另行安排，而非立即重试或越过60秒。mcp_A_valid只证明边界A的假认证，upstream_A_revoked在边界B阻塞；停止上游操作并让用户独立重新授权，不刷新已撤销标签、不透传MCP token、不在工具调用突然开浏览器。全部是真实实现未验证的纸面判断。

**4. 四种提交状态。**

| 情形 | 判断与动作 | 是否新建任务 |
| --- | --- | --- |
| W1 模型口头同意 | 无执行端批准，拒绝提交，向用户呈现具体预览 | 否 |
| W2 版本v4 | 旧批准只绑定v3，拒绝，重新预览并确认新差异 | 否 |
| W3 k1已完成且参数一致 | 核对绑定后返回持久记录task_71；重复不再执行；若用户权限现已撤销应按当前策略拒绝披露/操作 | 否；此前假记录已有一项 |
| W4 上游结果未知 | 保留未知状态，利用上游幂等或独立可核对操作记录恢复；无证据则停止人工核对 | 不能确定此前是否创建；不得新增重做 |

换k2会把同一业务意图伪装成新操作，可能创建第二项；幂等记录应持久、绑定主体与差异，同键不同参数拒绝。仅本地键不能填补“上游已写、Server未记录完成”的缺口，不能声称保证恰好一次或自动回滚。审批防未授权写入，版本检查防陈旧差异，幂等防重复效果，OAuth限制访问权，四者不同。

### 理解检查

**问：工具说明能否代替 schema 校验？** 不能。说明帮助选择工具，schema 和实现才负责实际输入约束。

**问：工具已标注只读，是否还需只读 token？** 需要。注解是提示，供应商权限与运行时能力限制才是执行边界。

**问：写请求超时后为何不能立即重试？** 服务端可能已经写入。应先利用幂等机制或读取后置状态判断。

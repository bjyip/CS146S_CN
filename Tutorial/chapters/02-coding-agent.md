# 02 Coding Agent：从理解目标到验证结果

[上一章](01-llm-prompting.md) | [目录](../README.md) | [下一章：上下文与需求规格](03-context-spec.md)

上一章，我们让模型从会议笔记里找出待办。这次换一个任务：

> 修改项目里的待办列表：最新创建的任务排在前面；创建时间相同，就把数字 ID 较大的任务排在前面。

如果只问「怎么写排序函数」，模型给出一段代码就可以了。但要改对现有项目，还得先弄清楚：列表究竟在哪里排序？哪些行为要保留？改完怎么确认顺序真的对了？

本章用这个例子介绍 Coding Agent，并在第 6 节用 Python 模拟一次修改。实验不需要 API Key，不联网，也不修改仓库文件。

## 1. 什么是 Coding Agent

**Coding Agent（编程智能体）是由语言模型、运行时和开发工具组成的系统。** 假设你用 Node.js 写了一个 Agent，接入远端模型。读取 `tasks.py` 时，三者各做一件事：

| 部分 | 负责什么 |
| --- | --- |
| 模型 | 根据任务和已有信息，提出「读取 `tasks.py`」的请求。 |
| 运行时 | 检查是否允许读取，再调用读取工具，把结果交回模型。Claude Code 文档把模型外面这层程序称为 *agentic harness*。 |
| 工具 | 真正打开文件并返回内容。修改文件、运行测试也是由相应的工具执行。 |

模型要知道「目前看到了什么」，程序还要知道「任务执行到了哪里」。前者是**上下文**，例如发给模型的需求、工具说明和代码片段；后者是运行时维护的**状态**，例如读过的文件版本、是否在等待批准、还剩几次工具调用。两者可以重叠，但程序不必把所有状态都交给模型。调用远端模型时，也只应发送任务所需且获准外发的内容。

### 有工具调用，就算 Agent 吗？

回看上一章的[总价练习](pratic/week1/tool_calling.py)：模型可以建议调用计算器，但计算结果一回来，程序就用 `tool_choice="none"` 让模型收尾。也就是说，下一阶段怎么走，主要由代码预先规定。

待办列表的排序可能在后端查询里，也可能在前端渲染前，还可能两处都有。Agent 得先看代码，才知道应该往哪一层查。[Anthropic 的工程文章](https://www.anthropic.com/research/building-effective-agents#what-are-agents)据此区分两类系统：**工作流**主要按预设路径运行；**Agent** 让模型根据实际结果选择下一步。两者可以搭配，比如让 Agent 找到并修改排序逻辑，再由固定流程运行验收。单纯给一组数字排序，直接写函数就够了。

## 2. Agent loop：看了结果，再决定下一步

[Claude Code 官方文档](https://code.claude.com/docs/en/how-claude-code-works#the-agentic-loop)把过程概括为**收集上下文、执行操作、验证结果**。这不是每次严格走完一遍的三步清单。只问「排序逻辑在哪里」，读取代码并指出入口就够了；要改排序，则可能在测试失败后回头查代码。

假设 Agent 读到 `tasks.py`，发现代码已经按创建时间从新到旧排序，只缺少时间相同时按数字 ID 排序的规则。模型因此建议保留原有逻辑，只补这个条件。运行时检查编辑请求后，接下来的动作取决于返回结果：

| 工具返回什么 | 下一步做什么 |
| --- | --- |
| 修改已应用 | 运行排序测试，检查输出是否符合预期。 |
| 文件在读取后被改过，编辑被拒绝 | 重新读取，确认原来的改法是否还适用。 |

**模型提出动作，运行时检查并执行，把结果交回模型，模型再决定下一步。** 这个反复利用反馈的过程就是 **Agent loop**。它由运行时维持，不是模型在电脑上自己执行命令。用户也在循环里：可以补充需求、拒绝操作或叫停任务。

### 执行前检查，执行后留证据

系统提示可以要求「先读再改」，但它不是权限检查。例如，模型提出修改 `tasks.py`，运行时还要确认路径、操作范围和当前版本；如果需要人工批准，就暂停等待。文件内容和工具输出只是输入数据。即使里面写着「忽略限制」，也不能替用户授权。

如果两条请求同时发出，运行时要按调用 ID 配对，而不是按结果返回的先后顺序猜。比如 `c1` 读 `tasks.py`，`c2` 读 `test_tasks.py`，哪怕 `c2` 先返回，它仍然是测试文件的内容。回看记录时也要分清：**请求读取不等于已经读到，读到测试代码更不等于测试已经跑过。** 第 01 章的总价练习用 `tool_call_id` 做的也是这种配对。

接下来的纸面练习只允许改指定文件。局部替换必须带上旧文本、新文本和读取时的版本。若旧文本不是恰好匹配一次，或文件已经换了版本，运行时就拒绝编辑，不能改成覆盖整份文件。练习一共允许三次工具请求，拒绝也占一次。这是本章约定，不是所有工具的通用规则。

## 3. 改完代码，怎么知道任务完成了？

先明确预期：任务按**创建时间降序**排列，同一时间按**数字 ID 降序**。下面这组数据能区分数字排序和字符串排序：

| 任务 ID | 创建时间 |
| --- | --- |
| `3` | 10:00 |
| `8`、`9`、`10` | 11:00 |

按需求推算，正确顺序是 `[10, 9, 8, 3]`。为什么特意放进一个 `10`？只测 `8` 和 `9`，把 ID 当字符串比也会得到相同顺序；加入 `10`，字符串降序就会把它排在 `9` 和 `8` 后面。先根据需求写出预期，再让实现接受检查，不要看见程序输出什么就把什么写成预期。

回看 Agent 的工作记录时，分清三句话：

- **「读到了测试」**：只说明它看到了测试代码。
- **「修改已应用」**：只说明文件改了，不说明排序正确。
- **「排序用例通过」**：要能指出测试命令、工作目录、退出码和输出。结论只涵盖这个用例，不代表分页或过滤也已经检查过。

失败时，先看是哪一步出了问题：

| 看到什么 | 下一步 |
| --- | --- |
| 测试报 `ModuleNotFoundError` | 先核对工作目录和导入路径；此时还不知道排序是否正确。 |
| 测试确实运行了，但 `9` 排在 `10` 前 | 检查同一时间的 ID 是按数字还是按字符串比较。 |
| 模型请求超时 | 记录超时，按剩余预算决定是否再试；不能据此声称代码已修好。 |

## 4. 停下来以后，怎样接着做？

假设三次额度用在了「读取 v1 → 编辑被拒绝 → 重读 v2」。第三次调用拿到了新信息，但额度已经用完。即使模型建议再次编辑，运行时也不应执行。交接可以这样写：

> 已重新读取 v2。本轮没有应用修改，也没有运行测试。继续前请先确认文件仍是 v2，再根据当前代码决定怎么改。

**接着聊，不等于回到当时的文件版本。** 例如，Claude Code 的[检查点文档](https://code.claude.com/docs/en/checkpointing)把恢复对话和恢复文件分成两项操作。检查点也只覆盖它跟踪到的文件，不能撤回 API 请求或数据库写入。如果某次写入超时，先核实实际结果，不要把「没收到回执」当成「没写入」。第 04 章会接着讨论外部工具写入。

## 5. 课堂原型能说明什么？

2025 年的[课堂原型](../../Resource/Fall2025/week02-0929-completed-exercise.py)适合用来找循环里的几个角色：它调用模型，从回复中解析 `tool: NAME(JSON)`，按名字查找本地函数，再把执行结果放回历史。它没有保留一套用调用 ID 配对的结构化请求和结果，因此不宜把它当作现代工具协议的示例。

### 从课堂源码定位执行边界

静态阅读时，可以从 `execute_llm_call`（请求模型）、`extract_tool_invocations`（解析请求）和 `TOOL_REGISTRY`（按名字查找函数）找这条调用链。再比较一处设计：原型把创建和局部替换放在同一个编辑工具里，漏传旧文本时可能进入写入分支；本章的纸面约定则把漏传参数当作错误，执行前就拒绝。两种结果的区别来自程序如何解释参数，不是模型有没有看懂提示。

这里只读源码，不运行课堂脚本。教学代码展示了循环怎样连起来，不代表文件范围、工具权限和任务预算已经得到控制。

## 6. 动手：先预测，再看循环怎么走

### 纸面练习

1. **配对。** `c1` 请求读 `tasks.py`，`c2` 请求读 `test_tasks.py`。先返回 `c2`：测试预期 `[10, 9, 8, 3]`；再返回 `c1`：实现只按时间降序。哪条结果说明预期，哪条说明当前实现？能否据此说测试通过了？
2. **拒绝与停止。** 第一次工具调用读到 v1；第二次请求替换旧代码，但执行前文件已变成 v2。按本章约定，运行时应怎样处理？如果最后一次调用用来重读，交接要说明什么？
3. **区分失败。** 一次测试报 `ModuleNotFoundError`，另一次正常结束并报告实际顺序为 `[9, 8, 10, 3]`，与预期不符。两次各应优先查什么？

### 可运行检查点：观察改变下一步

运行前，先预测两条冲突路径会在哪一步分开。然后从仓库根目录运行：

```powershell
python Tutorial/chapters/pratic/agent_lab.py
```

| 场景 | 要核对的顺序 |
| --- | --- |
| `normal` | 读取、编辑、检查排序，共三次，最后输出 `verified`。 |
| `recovery` | 读 v1，编辑被拒绝，重读 v2；还剩两次机会，可以再编辑并检查排序，最后输出 `verified`。 |
| `stop` | 同样重读到 v2，但已经用完三次机会。输出 `budget_exhausted`，不再编辑，也没有检查排序。 |

读代码时先看 `run_lab()`：它执行模拟操作，把每次动作和结果记进 `history`，供下一轮使用。再看 `fake_model(history)`：它像一个 JavaScript 函数那样，根据最近一条记录返回动作名，并没有调用模型。`recovery` 和 `stop` 在重读 v2 后都会提出 `edit`，区别是前者还有额度，后者在执行前就被运行时拦下。

这个实验能验证决策与执行怎样衔接，不能验证真实模型是否会选对工具，也不能证明程序能安全编辑真实文件。相关测试见[离线实验说明](pratic/README.md#离线实验)。

## 7. 选学：查看真实会话记录

[Fall 2026 第 1 周原作业](../../_assignments/2026%20fall/modern-software-dev-assignments-master/week1/assignment.md)要求分析真实 Claude Code 会话。它不是本章基础路线的前置。准备条件、原评分和证据记录方法见[作业导读](../reading-notes/fall2026/week01/assignment-guide.md)；客户端和代理的操作步骤以原作业和当前官方文档为准，不从本章复制旧配置。

分析时，挑一次失败，找出对应的工具请求、错误结果和下一步操作。如果有复测，也记下复测结果；没做复测就明确写出来。真实会话记录可能含凭据、代码和终端输出。只在获准的练习项目中做，不使用真实秘密，也不要提交原始请求。离线模拟不能代替原作业。

## 8. 自测与参考答案

1. **配对。** `c2` 提供测试里的预期，`c1` 提供当前实现的线索。读取测试文件不等于执行了测试，不能据此报告通过。
2. **拒绝与停止。** 请求依据 v1，当前是 v2，先拒绝编辑。最后一次重读后，记录当前版本、未修改、未测试和继续前要核对的内容，然后停止。
3. **区分失败。** 导入失败先核对目录和依赖，尚未检验排序；已经得到错误顺序，则检查同一时间的第二排序条件及 ID 类型。

**迁移题：** 编辑工具要求版本一致且旧文本唯一。读 v5 后，编辑因匹配两处被拒绝；现在文件已变成 v6。只把匹配文本写得更长，可以直接再试吗？不可以。匹配更具体只解决「改哪处」，不能证明「依据的还是当前版本」。先重读；如果预算不足，就保留证据并停止。

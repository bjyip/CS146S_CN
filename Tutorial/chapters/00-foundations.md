# 00 准备环境与科学学习方法

[目录](../README.md) | [下一章：LLM 与提示](01-llm-prompting.md)

假设你想让模型从会议笔记提取待办，还没开始学习提示，就遇到了三个问题：不知道从哪个目录运行程序，没有账号可调用模型，也不知道怎样判断一次回答是否正确。它们分别涉及环境、访问和评价，不能靠重复安装或购买工具一起解决。本章先把这三件事分开，让你知道哪些学习可以立即进行，哪些实验需要额外条件。

## 1. 学习目标

## 2. 先诊断，再安装

课程 README 当前要求相当于 CS111/CS161 的编程基础，并推荐 CS221/229 知识。这里不是要求先取得课程学分，而是要求具备程序、系统与算法的基本判断能力。

尝试不使用 AI 完成四件事：解释一个 HTTP 端点如何进入数据库；为纯函数写空输入和正常输入测试；用 `git diff` 判断修改是否改变公开行为；比较双重循环去重与哈希集合去重的时间、空间和顺序语义。如果困难，先补习相应基础。AI 可以解释报错，但理解验证结果仍是你的责任。

例如，对 n 个任务逐个扫描已收集列表，最坏需要 O(n²) 次比较；使用哈希集合辅助去重通常可达到期望 O(n) 时间，但需要 O(n) 额外空间，还必须明确保留首次出现顺序。不能只把循环替换成集合后，就声称行为完全相同。用空列表、重复任务和不同顺序三组输入验证，再用不同规模测量；小规模耗时并不能证明渐近复杂度。

此仓库根目录不是 Python 作业的依赖根目录。两个年份有各自的 Poetry 配置，文档里的“作业仓库根目录”必须按年份理解，不能机械理解为 `CS146S_CN/`。

## 3. Python 环境

以下第 3–5 节是准备实际运行的选学路线。先完成基础判断的读者可以跳到第 6 节；跳过安装不影响纸面练习，但不能据此声称环境已验证。Python 解释器执行 Python 程序；依赖是程序需要的外部包；隔离环境让不同项目使用各自的解释器或包版本，避免一个项目的升级影响另一个项目。

原作业建议 Python 3.12，当前配置允许的范围更宽。为减少解释器差异，本教程仍推荐 3.12。Conda 是原作业路线；已熟悉虚拟环境的读者可以使用等价方式，但应记录偏离。

下面的初始化命令可在 PowerShell 中逐条运行，前提是已经安装 Conda，并由官方安装方式安装 Poetry：

```powershell
conda create -n cs146s python=3.12 -y
conda activate cs146s
Set-Location "E:\study\ai\CS146S_CN\_assignments\2025 fall"
poetry --version
poetry env use python
poetry install --no-interaction
poetry run python --version
```

其中绝对路径是本仓库当前 Windows 位置，其他电脑应使用自己的实际路径。macOS/Linux 在对应终端中使用 `cd "实际路径/_assignments/2025 fall"`，其余 Poetry 命令相同。若 Poetry 锁文件与安装版本不兼容，先记录完整错误和 Poetry 版本，不要立即重生成锁文件或升级全部依赖。

做 2026 作业时，将目录切换为对应的 2026 根目录，使用该目录的依赖声明，不能照搬下面的 `week2/tests` 命令：两个年份的第 2 周任务不同。基础依赖安装也不表示 mitmproxy、MCP SDK 或第三方服务已就绪；按具体作业核对额外工具及版本，不因缺一个包就升级全部依赖。

## 4. 先跑离线测试

在 `_assignments/2025 fall/` 中运行：

```powershell
poetry run pytest -q week2/tests
```

第 2 周现有提取测试通过 mock 替代 Ollama 调用。因此这个命令验证的是代码契约，不需要下载模型，也不能证明真实模型效果。

手动体验应用时，在同一目录另开终端运行：

```powershell
poetry run uvicorn week2.app.main:app --reload --host 127.0.0.1 --port 8000
```

浏览器地址为 `http://127.0.0.1:8000/`，API 文档通常在 `/docs`。停止前台服务用 `Ctrl+C`。首次启动可能创建 SQLite 文件；先确认应用配置和练习目录，不要连接真实业务数据库。

第 4 周 Makefile 使用 POSIX 环境变量语法，不是 PowerShell 语法。Windows 可在 `_assignments/2025 fall/week4/` 中使用：

```powershell
$env:PYTHONPATH = '.'
poetry run pytest -q backend/tests
poetry run uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

Poetry 会向上查找配置，但导入路径仍由当前工作目录决定。不同周都可能存在名为 `backend` 的包，切换练习时使用新进程，避免误导入其他周模块。记录环境变量原值，结束后恢复，不要把练习设置扩散到所有终端。

## 5. 本地模型与资源预算

第 1 周原作业指定 `mistral-nemo:12b` 和 `llama3.1:8b`。第 2 周当前实现默认使用 `llama3.2:3b`，可由 `OLLAMA_MODEL` 覆盖。模型名字中的参数量不是完整内存需求；量化方式、上下文长度、并发和硬件都会影响资源。

安装 Ollama 后，先用 `ollama --version` 和 `ollama list` 检查环境。需要模型时再拉取，避免盲目下载全部模型：

```powershell
ollama pull llama3.2:3b
```

这是第 2 周模型示例，不替代第 1 周原作业要求。内存不足时可以先做离线测试，再选择更小模型或云服务作为自学改编。不要把“更换模型之后通过”归因于提示词改进。云服务会涉及付费、数据传输和保留政策，应先确认许可，不上传真实会议和密钥。

## 6. 安装、认证与计费分开验收

先看一条假记录：“版本命令正常，模型请求返回额度不足，测试尚未运行。”合理结论是客户端可运行、这个请求失败、程序行为未验证，而不是“环境全部通过”或“重新装一次”。认证确认调用者身份，授权决定允许访问什么；计费渠道和剩余额度还要单独核对。

工具可执行、账号有访问权限、选对计费来源，是三个不同问题。`claude --version` 成功只证明客户端可运行，不证明已经登录或能够调用模型。基础离线测试与课堂代码分析不要求购买会员；真正调用云模型时，才需要合法授权及明确预算。

Claude Code 安装按[官方说明](https://code.claude.com/docs/en/setup)选择与平台匹配的路线，优先官方发布渠道，不从代充页面或聊天附件安装未知二进制。安装后在新终端检查版本，必要时使用 `claude doctor` 诊断。首次运行 `claude` 时按官方浏览器登录流程认证；组织账户或 API 提供商路线应遵守组织要求。不要将登录回调、Cookie、会话 JSON 或 API Key 发给代办者。

网页会员订阅、开发者 API 额度和组织授权是不同的访问与计费渠道。不能从“网页能聊天”推断“CLI 已授权”，也不能从“已买会员”推断所有 API 请求已包含在订阅中。Claude Code 官方说明提供账户与 API 提供商等路线；具体资格、地区、额度和价格会变化，实际使用前核对官方说明与账户状态，不把第三方套餐宣传当作长期事实。Codex 的当前认证页面本次未成功读取，本教程不据此写入套餐资格或安装命令。

用[环境验收模板](../reference/templates.md)分别记录安装、认证、最小模型请求、计费来源和恢复措施。一个安全的例子是：版本检查通过，离线测试通过，模型调用未运行，则前两项通过，云端能力仍为未验证。获得授权后，在不含秘密的临时仓库进行一个最小请求，记录成功或完整错误类别、用量和退出状态，不在日志中保存凭据。

验收：能指出当前作业根目录与客户端版本，区分未安装、未授权、额度不足和业务测试失败；所有未执行检查明确标记。无合法访问条件时使用离线或本地改编路线，不宣称完成了指定真实客户端的原作业。

## 7. 什么叫科学地评估

环境准备好后，我们仍需回答“怎样知道提示真的改好了”。如果只保留五次尝试里最好的一次，或者把题目答案写进提示，就无法判断新输入上的表现。评价因此要先约定题目、正确答案和失败记录，再比较方案，而不是看到结果后重新解释成功标准。

一个合格实验至少包含问题、假设、干预、控制变量、评价标准和记录。

例如：问题是“少样本提示是否减少任务幻觉”；假设是“在同一模型和输入集合上，给出正反例比只描述要求有更高精确率”；干预是提示形式；固定模型、版本、采样参数、工具和输入；评价标准由人工提前标注，而不是由模型看过答案后自评。

先建立规则算法或普通提示基线，再比较改进方案。一次只改变一个主要因素，否则无法判断结果为何变化。使用同一组输入做配对比较；对不同方案交错运行，可以减少服务负载或时间变化带来的偏差。

区分三类样例：开发集用于调整提示，验证集用于选择方案，最终测试集只用于最后评估。小规模学习实验不一定需要复杂统计，但不能把反复调试的那一道题称为泛化能力证明。

## 8. 最小实验记录

| 字段 | 必须记录的内容 |
| --- | --- |
| 环境 | 日期、操作系统、Python/工具版本、模型标识 |
| 条件 | 提示版本、采样参数、上下文和工具集合 |
| 输入 | 脱敏样例编号、参考答案、划分方式 |
| 输出 | 原始结果、解析错误、超时、回退 |
| 成本 | 请求数、耗时、token 或本地资源记录 |
| 结论 | 指标、失败类别、适用范围、未验证项 |

报告首次成功率和所有尝试次数，不只保留最好结果。“五次中有一次成功”与“一次运行可靠成功”是不同指标。超时、格式失败和空结果不能从分母中删除。

## 9. 动手实验

### 基础：先完成四项零调用判断

以下均为教程假材料，只用纸面或独立学习记录作答，不运行命令、不修改参考作业。用约 30 分钟完成四题，再看第 10 节；没有得到实际退出码的地方保持“未运行”。

1. 目录判断：准备做 2026 第 2 周 OAuth MCP，但同伴建议在 `CS146S_CN/` 运行 2025 的 `week2/tests`。写正确依赖根目录、不能照搬测试的原因，以及实际运行前要核对的两个条件。
2. 证据判断：假记录为“客户端版本检查通过；云模型请求额度不足；mock 测试通过；未发真实提取请求”。分别写安装、访问、程序契约和模型质量的结论。mock 是用预设返回值替代外部调用，不能将它产生的正确 JSON 写成模型成绩。
3. 保序去重：输入任务 `[检查日志, 更新说明, 检查日志]`，契约要求保留首次出现顺序。先写预期列表，再说明只说“使用集合去重”遗漏了什么；为实现另补空输入和顺序不同两组预期，不运行代码。
4. 对照设计：研究“加准确正反例是否减少误提”。方案甲使用原模型和短提示，方案乙同时换模型、加示例、增加重试；五次中只报告最好结果。指出两个不能归因的问题，写一个只改提示示例、固定生成条件且保留所有尝试的修订计划；另留未参与提示开发的题，不用本章公开题充当隐藏测试。

```text
目录：年份 / 依赖根目录 / 测试范围 / 前置待确认
证据：版本 / 访问 / mock 范围 / 真实模型未验证
去重：输入 / 预期 / 顺序约定 / 边界预期
对照：唯一主要变化 / 固定条件 / 数据划分 / 全部失败记录
执行状态：本次仅纸面判断，未运行
```

通过条件：四题的范围与证据不混淆，去重预期可核对，对照只改变一个主要因素，未知与失败没有被删除。满足这些条件即可开始后续基础章节，不代表环境、模型或原作业完成。

### 选学：准备好条件后实际运行

下面保留原有实际实验路线，需要独立练习副本、安装与执行条件。不要将前面的纸面记录填入这里的实际运行结果。

1. 创建自己的练习记录，记录依赖目录与版本，不修改源作业。
2. 运行第 2 周离线测试，将命令、工作目录、退出码和摘要写入记录。失败也照实记录。
3. 为任务提取设计至少 12 条样例：明确任务、只有叙述、否定指令、重复任务和模糊承诺均应出现。
4. 提前定义哪些句子算行动项。让另一位读者复核至少三条，记录分歧而非偷偷调整答案。
5. 写下普通提示与改进提示的对照计划，保留一组不参与调参的输入。
6. 对两种去重方案写出复杂度和保序契约，用同一组边界输入验证；填写环境验收表，未调用的云端能力保持未验证。

验收：另一位读者能凭记录复现环境和实验；测试通过与真实模型有效被明确分开；没有原始秘密进入版本控制。

## 10. 自测与答案

### 基础练习参考

1. 2026 依赖根目录为 `_assignments/2026 fall/modern-software-dev-assignments-master/`。2025 的 `week2/tests` 测行动项应用，不是 2026 的 OAuth MCP；同周编号不表示同一任务。先核对该年份的 `pyproject.toml` 与作业要求，再确认工作目录、解释器和额外工具，不能从仓库根目录或另一年份的通过结果推断本实验可用。
2. 版本检查只支持“客户端可运行”；额度不足支持“该次云请求失败”，不必然说明身份认证也失败；mock 通过支持其覆盖的程序契约；没有真实提取请求，模型质量仍未验证。若这些记录本身是假材料，应标为假记录分析，而不是本机实际结果。
3. 预期为 `[检查日志, 更新说明]`。需保证按输入顺序追加第一次遇到的任务，而非任意输出集合的遍历顺序；空输入预期 `[]`，输入 `[更新说明, 检查日志, 更新说明]` 预期 `[更新说明, 检查日志]`。比较复杂度时还要记录额外空间与规模，纸面推导不是耗时测量。
4. 同时换模型、示例和重试，无法把改善归给示例；只留最好一次会隐藏失败，也混淆首轮与多次恢复。修订方案在同模型版本、参数、输入与匹配规则下比较完整基线提示和仅增加开发示例的提示，记录每次原始输出、错误、耗时及请求数。预先人工标注，开发题用于调整，另留新题最终验收；若访问或预算不足，计划保持未运行，不伪填改善。

### 理解检查

**问：模型温度设为 0，实验就完全可复现吗？** 不一定。服务实现、模型版本、并行计算和输入差异仍可能影响结果。记录配置并重复运行，比宣称确定性更可靠。

**问：mock 测试全部通过，为何还需要真实模型评测？** mock 提供的是你指定的返回值，只能检验系统如何处理它，不能测量模型是否真的会返回正确内容。

**问：失败后升级所有包是不是最快？** 可能暂时绕过错误，也可能引入更多变量。先定位路径、解释器和具体依赖冲突，再做有依据的最小调整。

**问：CLI 能显示版本为何仍可能无法调用模型？** 安装与认证、访问权限、网络和额度是独立条件，要按失败类别定位，而不是重复安装或盲目购买会员。

# 00 学习准备：环境与验证方法

[目录](../README.md) | [下一章：LLM 与提示](01-llm-prompting.md)

想让 AI 从会议笔记整理待办，你可能先遇到三个问题：程序该在哪个目录运行？账号能不能调用模型？回答到底对不对？这三件事要分开检查，重复安装或购买会员不能一起解决它们。

先读第 1–2、6–8 节，再做第 9 节练习并核对答案。基础练习只分析给定材料，不需要联网或安装工具；第 3–5 节的命令留到实际实验时使用。

## 1. 学习目标

本章要学会：找到正确的作业目录，分清安装成功与功能正确，并设计公平的对照实验。写出计划不算实际运行成功。

## 2. 先诊断，再安装

先试着独立做四件事：解释 HTTP 请求怎样触发数据库读写；给函数写正常输入和空输入测试；用 `git diff` 看懂代码变化；比较两种去重算法。做不出来时，先补对应基础，不能只靠 AI 宣布结果正确。

例如，对 n 个任务逐一扫描已有列表，最坏要做 O(n²) 次比较；用哈希集合辅助通常能做到期望 O(n)，代价是 O(n) 额外空间。但还要保留首次出现的顺序，不能直接把集合当输出。用空输入、重复项和不同顺序检查行为，耗时则另行测量。

先选路线，再决定从哪个目录运行。只读路线无需执行命令；离线路线在仓库根目录运行 `python Tutorial/chapters/pratic/agent_lab.py`，看三条示意轨迹；远程 API 路线进入 `Tutorial/chapters/pratic`，按[配置说明](pratic/README.md)运行第一章练习。不用为了这两条实操路线安装 Ollama 服务或下载模型。

本仓库根目录不负责这些 Python 依赖。需要用 Poetry 时，确认自己进入的是哪套练习：

| 作业 | Poetry 根目录 | 用途 |
| --- | --- | --- |
| 教程自学改编 | `Tutorial/chapters/pratic/` | 第 01 章智谱脚本；离线实验只依赖 Python，不用 Poetry |
| 2025 | `_assignments/2025 fall/` | 第 1 至 8 周归档练习及本章离线测试 |
| 2026 | `_assignments/2026 fall/modern-software-dev-assignments-master/` | 当前本地第 1 至 3 周 trace、MCP、Skill 作业 |

先确认目录中的 `pyproject.toml`，再选择解释器和依赖环境。两个年份可以使用不同环境名，避免混淆。开始前用 `git status --short` 查看已有修改，不要为重做练习清空代码、翻译文件或重置仓库。

## 3. Python 环境

本节选学。隔离环境让不同项目使用各自的 Python 和依赖，避免升级一个项目影响另一个。原作业建议 Python 3.12，教程沿用这个版本。

已安装 Conda 和 Poetry 后，可在 PowerShell 逐条运行：

```powershell
conda create -n cs146s python=3.12 -y
conda activate cs146s
Set-Location "E:\study\ai\CS146S_CN\_assignments\2025 fall"
poetry --version
poetry env use python
poetry install --no-interaction
poetry run python --version
```

路径改为自己电脑上的实际位置；macOS 和 Linux 用 `cd` 切换目录。做 2026 作业时，使用 2026 的配置与命令，不能照搬 2025 的测试。依赖冲突时先记录错误和版本，定位具体问题，不要直接重建锁文件或升级所有包。

## 4. 先跑离线测试

在 `_assignments/2025 fall/` 中运行：

```powershell
poetry run pytest -q week2/tests
```

这些测试用 mock（预设返回值）代替模型调用，只检查程序如何处理结果，不测真实模型质量。

手动体验应用时，在同一目录另开终端运行：

```powershell
poetry run uvicorn week2.app.main:app --reload --host 127.0.0.1 --port 8000
```

浏览器打开 `http://127.0.0.1:8000/`，停止服务用 `Ctrl+C`。首次启动可能创建 SQLite 文件，运行前确认库位置，不连接真实业务数据。

第 4 周 Makefile 使用 POSIX 环境变量语法，不是 PowerShell 语法。Windows 可在 `_assignments/2025 fall/week4/` 中使用：

```powershell
$env:PYTHONPATH = '.'
poetry run pytest -q backend/tests
poetry run uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

不同周可能有同名 `backend` 包，切换练习时核对目录并启动新进程；结束后恢复本次改过的环境变量。

## 5. 本地模型与资源预算

第 1 周原作业指定 `mistral-nemo:12b` 和 `llama3.1:8b`；第 2 周当前默认 `llama3.2:3b`，可用 `OLLAMA_MODEL` 调整。实际内存需求还受量化、上下文和并发影响。

已安装 Ollama 时，先查 `ollama --version` 和 `ollama list`，需要第 2 周模型再下载：

```powershell
ollama pull llama3.2:3b
```

资源不足可先做离线测试，更换模型则记为自学改编，不算提示改进。云服务另需确认权限、费用和数据政策，不上传真实会议或密钥。

## 6. 安装、认证与计费分开验收

假记录写着：“版本命令正常，模型请求额度不足，测试未运行。”从这份记录只能得出三个结论：客户端能运行，该请求失败，程序行为未验证。不能说环境全部通过。

认证确认“你是谁”，授权决定“你能做什么”，计费决定请求使用哪份额度。网页会员、API 额度和组织授权不是一回事；网页能聊天，不代表命令行能调用模型。

Claude Code 的安装和登录按[官方说明](https://code.claude.com/docs/en/setup)进行，资格与额度以实际账户为准。不要向代办者发送 Cookie、登录回调、会话文件或 API Key。

用[环境验收模板](../reference/templates.md)分别记录版本、访问、最小请求、费用和测试。未运行就写未运行；有授权后再用假数据测试云端调用。

## 7. 什么叫科学地评估

环境能用后，还要判断提示是否真的改好了。只挑五次里最好的一次，或把验收答案放进提示，都不能说明新题上的表现。

例如，想研究“加正反例是否减少误提”，先写人工预期，再比较普通提示和增加示例的提示。模型、参数、输入与判题规则保持相同，一次只改一个主要因素，才容易解释差异。交错运行两个方案，可减少时段和服务负载的影响。

调提示用开发题，选方案用验证题，最终评估另留新题。一旦根据新题的错误改过提示，这批题就不能再当独立验收题。

## 8. 最小实验记录

| 字段 | 必须记录的内容 |
| --- | --- |
| 环境 | 日期、操作系统、Python 与工具版本、模型标识 |
| 条件 | 提示版本、采样参数、上下文和工具集合 |
| 输入 | 脱敏样例编号、参考答案、划分方式 |
| 输出 | 原始结果、解析错误、超时、回退 |
| 成本 | 请求数、耗时、token 或本地资源记录 |
| 结论 | 指标、失败类别、适用范围、未验证项 |

保留全部尝试，分别报告首次成功与重试后成功。超时、格式失败和空结果不能为了提高成绩而删掉。

## 9. 动手实验

### 基础：先完成四项零调用判断

以下为假材料，不运行命令或修改原作业。先独立作答，再看第 10 节答案。

1. 目录判断：准备做 2026 第 2 周 OAuth MCP，但同伴建议在 `CS146S_CN/` 运行 2025 的 `week2/tests`。写正确依赖根目录、不能照搬测试的原因，以及实际运行前要核对的两个条件。
2. 证据判断：假记录为“客户端版本检查通过；云模型请求额度不足；mock 测试通过；未发真实提取请求”。分别写安装、访问、程序契约和模型质量的结论。mock 是用预设返回值替代外部调用，不能将它产生的正确 JSON 写成模型成绩。
3. 保序去重：输入任务 `[检查日志, 更新说明, 检查日志]`，契约要求保留首次出现顺序。先写预期列表，再说明只说“使用集合去重”遗漏了什么；为实现另补空输入和顺序不同两组预期，不运行代码。
4. 对照设计：研究“加准确正反例是否减少误提”。方案甲使用原模型和短提示，方案乙同时换模型、加示例、增加重试；五次中只报告最好结果。指出两个不能归因的问题，写一个只改提示示例、固定生成条件且保留所有尝试的修订计划；另留未参与提示开发的题，不用本章公开题充当隐藏测试。

检查自己的答案：目录和测试范围是否对应？是否把 mock 当成模型成绩？是否保留顺序？对照是否只改一个因素？

### 选学：准备好条件后实际运行

准备好独立练习副本、权限和预算后，再实际操作：

1. 创建自己的练习记录，记录依赖目录与版本，不修改源作业。
2. 运行第 2 周离线测试，将命令、工作目录、退出码和摘要写入记录。失败也照实记录。
3. 为任务提取设计至少 12 条样例：明确任务、只有叙述、否定指令、重复任务和模糊承诺均应出现。
4. 提前定义哪些句子算行动项。让另一位读者复核至少三条，记录分歧而非偷偷调整答案。
5. 写下普通提示与改进提示的对照计划，保留一组不参与调参的输入。
6. 对两种去重方案写出复杂度和保序契约，用同一组边界输入验证；填写环境验收表，未调用的云端能力保持未验证。

验收时，其他人应能凭记录复现；程序测试与模型效果分开记录，秘密不进入版本控制。

### 迁移检查：改进还是换了测量条件

旧提示做 10 题、成功 6 题；新提示因额度不足只做其中 8 题，全部成功，没做的恰是旧方案最难的两题。报告都没有原始输出。能说提示改善了吗？怎样补证？先作答，再展开答案。

## 10. 自测与答案

### 基础练习参考

1. 正确目录是 `_assignments/2026 fall/modern-software-dev-assignments-master/`。2025 的测试检查行动项应用，不检查 2026 的 OAuth MCP。先确认依赖配置和作业要求，再核对解释器与额外工具。
2. 版本检查说明客户端能运行；额度不足说明该请求失败，不一定是认证失败；mock 通过只说明覆盖到的程序处理正确。真实模型质量未测。
3. 预期 `[检查日志, 更新说明]`；空输入为 `[]`；`[更新说明, 检查日志, 更新说明]` 应得到 `[更新说明, 检查日志]`。要按输入顺序收集首次出现项，不能依赖集合的任意遍历顺序。
4. 同时换模型、示例和重试，无法把改善归因于示例；只留最好一次又隐藏了失败。固定模型、参数、输入和判题规则，只增加开发示例，保留每次输出、错误、耗时和调用数，再用新题验收。

### 理解检查

**问：模型温度设为 0，实验就完全可复现吗？** 不一定。服务实现、模型版本、并行计算和输入差异仍可能影响结果。记录配置并重复运行，比宣称确定性更可靠。

**问：mock 测试全部通过，为何还需要真实模型评测？** mock 提供的是你指定的返回值，只能检验系统如何处理它，不能测量模型是否真的会返回正确内容。

**问：失败后升级所有包是不是最快？** 可能暂时绕过错误，也可能引入更多变量。先定位路径、解释器和具体依赖冲突，再做有依据的最小调整。

**问：CLI 能显示版本，为何仍可能无法调用模型？** 安装、认证、访问权限、网络和额度是独立条件，要按失败类别定位，而不是重复安装或盲目购买会员。

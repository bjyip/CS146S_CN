# 05 Skills、规则与自动化

[上一章](04-mcp-oauth.md) | [目录](../README.md) | [下一章：仓库与并行](06-repo-parallel.md)

开发者控制中心接入行动项提取器后，你反复遇到三类问题：测试找不到模块、任务列表多出重复项、服务超时。每次都重写“认真检查”并没有留下可复用办法。本章先走一遍诊断，再决定哪些信息应长期保留、哪些步骤值得自动化，避免先装一堆机制再找用途。

**前置与路线**
- 能读懂条件分支与测试预期即可；本章会解释退出码、流程知识和执行权限，不要求先学某个客户端配置。
- 基础读第 1–7 节的非折叠正文，做第 8 节四项练习，再核对第 9 节答案。阅读估计 40–55 分钟，练习约 45 分钟，可分两次；预算未经真实新手测试。
- 基础产物是一份诊断流程、一张机制责任表、一组触发正负例和一份交接记录。全部假输入在章内，不联网、不安装、不运行模型、测试或应用、不写业务数据。
- 原作业、真实触发、Hook 和多 Agent 操作是独立选学，未执行；纸面推导不是运行日志。

## 1. 不同机制，不同职责

先看一次完整的纸面诊断。以下目录、命令和日志均为教程假设，不是源作业的实测记录：项目入口是 `lab/backend`，测试数据只应进入临时库；用户只授权分析，没有授权修改、联网或真实写入。测试命令是 `python -m pytest tests/test_extract.py`。退出码是程序结束时交给调用方的数字；本例约定 0 表示该命令成功，1 表示测试失败，但 0 不说明所有功能都测试过。

| 已提供的假记录 | 先取得什么 / 怎样判断 | 输出与边界 |
| --- | --- | --- |
| 从 `lab` 运行，报 `ModuleNotFoundError: app`，退出 1 | 对照入口说明、工作目录和导入路径；先确认是否从错误目录启动 | 定位到入口不符；提出从 `lab/backend` 核对的方案，不直接升级依赖 |
| 已有同一基线的记录：从 `lab/backend` 运行，输入“明天检查日志；再提醒：明天检查日志”，返回两项，断言预期一项 | 读去重契约和原始输入；这是行为断言失败，不是安装问题 | 确认重复项违约，保存输入、预期、实际、位置；无修改授权只给修复建议 |
| 另一条测试记录为服务超时，尚无响应 | 核对依赖是否必需、超时与剩余预算；不能把它当空任务列表 | 报依赖不可用；本例禁止联网，因此停止，不声称模型质量差或测试通过 |

这三条问题不能用同一个“重试”处理。完整顺序是：确认授权与隔离 → 核对基线、目录、命令 → 查看失败证据 → 按导入/断言/依赖分类 → 提出最小下一步 → 获准后才实施和复测 → 按证据交接。没有证据就保留未知，不能先删断言让结果变绿。

如果下周又遇到类似错误，应该复用的是“先查哪份证据、何时分支、何时停下”，而不是复制这次的补丁。接下来按这条诊断链依次引入规则、命令、Skill、Hook 和 Subagent；最后才讨论需要外部能力时的 MCP 与 CLI。

## 2. 规则写什么

第一条诊断卡在入口，所以先保留一条可长期复用的事实：“后端测试工作目录是 `lab/backend`；运行前核对临时数据库路径；生成 schema 不手改。”这种面向项目的长期约定称为仓库规则。它回答“在哪里、遵循什么”，不保存每次错误的全量日志。假规则能被核对，是因为目录、配置和生成入口都有明确检查对象。

下一次用户明确说“按同样范围整理测试诊断”，可以用斜杠命令保存重复请求模板，例如 `/diagnose tests/test_extract.py`。它减少重复输入，不替代分类判断或权限。固定不变的单一检查更适合已有脚本或别名；只把命令包进 Markdown，不会自动增加判断能力。

`README.md` 面向人解释项目；`AGENTS.md` 或 `CLAUDE.md` 向相应 Agent 提供操作约定。发现位置、作用域和优先级取决于客户端，不能假定所有产品都会读取所有文件。

有效规则应具体、短且能核验，例如说明后端入口、测试工作目录、哪些文件是生成物、是否禁止真实数据库写入。泛泛的“请写高质量代码”没有清晰判定方式。

避免复制已经有权威来源的长文，优先引用维护中的脚本和文档。规则应记录“何时要运行哪个检查”，而不只记录一句可能过期的命令。规则也不是安全边界，禁止生产写入还必须由权限配置保证。

### 作用域与渐进披露

把信息拆成三层：全项目必须知道的事实放入口规则；仅某目录相关的约定使用客户端支持的局部规则；较长的诊断、发布和审查流程放 Skill 或按需参考。长期约定不要混入临时任务进度，个人偏好不要未经团队同意变成共享规定。

例如入口说明“后端测试从 week4 运行，生成的 schema 不手改”；后端局部规则引用数据库隔离说明；文档同步 Skill 在端点修改时才读取 OpenAPI 对照流程。这样减少无关上下文，但不能保证模型绝不遗漏，仍要检查实际行为。

[Anthropic 的定制说明](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more)描述了 Claude Code 的根目录与子目录 `CLAUDE.md`、路径作用域规则和按需 Skill；[Factory 文档](https://docs.factory.com/harness/agents-md)描述的是其自身规则发现方式。不要把这些目录、优先级、压缩后的加载行为或子 Agent 嵌套能力混成通用标准。客户端升级后用一次无副作用任务检查实际发现与作用域，不靠文件名推断生效。

维护规则时给出负责人或维护位置，在相关目录、命令、schema 改变后复核。发现过期指令先对照代码与实际命令，不让 Agent 执行旧指令后盲目修项目来迎合文档。规则篇幅和指令数量的经验建议可作提醒，但不是科学阈值；衡量的是任务成功、遗漏和维护成本。

## 3. Skill 是流程知识

当诊断必须根据导入失败、断言失败和依赖失败选择不同下一步，模板已不够用。Skill 可以理解为按任务取出的使用手册：说明所需证据、判断分支、操作边界、验收和停止。流程知识不是“每次升级依赖”，而是第 1 节那条可以追溯的诊断链。

标准 Skill 通常以 `SKILL.md` 为入口，包含名称、描述和工作流正文，可附脚本和参考文件。客户端用描述判断是否加载，正文在触发后指导执行。具体发现目录和 frontmatter 应按当前客户端文档核对。

一个“错误复现”Skill 的描述应明确“用户提供报错、要求定位根因时使用”，并排除“只解释一个概念”的近似请求。正文应该有真实分支：导入错误先查解释器和路径；断言错误先确认需求与夹具；网络问题先检查超时和依赖状态。

它还应规定何时停止：危险操作、权限不足、需求歧义或预算耗尽时给出证据和下一步，而不是无限重试。长篇参考文档按需读取，避免每次触发都耗尽上下文。

本章的描述草案可以写成：“用户提供测试失败并要求复现或定位根因时，核对目录、隔离和失败类别，产出诊断与验收计划；只解释概念、只查费用或只格式化文件时不用。”这是纸面描述，不是安装到真实发现目录的 Skill。

| 用户假请求 | 应否选用诊断流程 | 原因 |
| --- | --- | --- |
| 复现这个 `ModuleNotFoundError`，找出入口问题 | 应 | 有具体失败和定位目标 |
| 测试把重复任务保留了，请查根因 | 应 | 需要对照契约诊断行为 |
| 测试服务超时，请判断下一步该怎么做 | 应 | 需要依赖失败分支和停止判断 |
| 解释什么是 `ModuleNotFoundError` | 不应 | 只解释概念，不授权复现 |

“应触发”是我们的设计预期，不是客户端已实际加载。即使加载正确，Agent 仍可能用错目录或越权；因此发现、自然触发、实际执行、成果验收要分别留证据。明确加载再做测试也不能证明自然语言会自动选择它。

## 4. 为什么必须先手动执行

第 1 节给了足够假记录，能学习怎样判断，却没有真正复现任何错误。若以后要把流程用于真实仓库，先在获准隔离副本手动走一次，记录基线、目录、配置、准确命令、原始日志、退出码与成果，确认它真的可运行，再编码。不能把本章的假命令当成你项目已验证的入口。

不要把一次偶然有效的修复写成“所有错误都升级依赖”。可复用知识是诊断方法与决策条件，不是把历史补丁变成通用药方。

## 5. 两个可练习的自动化流程

**流程 A：受控测试诊断。** 将第 1 节串成一份手册，基础只做纸面分析：

```text
输入：测试范围、任务授权、基线；缺任一项先问清。
前置：定位入口和真实数据路径；隔离未确认则不执行。
证据：目录、命令、退出码、原始失败、预期来源和实际输出。
分支：导入失败 -> 对照路径与解释器；断言失败 -> 对照契约和输入；
      依赖失败 -> 对照依赖状态、网络许可和预算。
实施：只有获准修改才改最小范围；不删断言、不跳过失败、不盲升依赖。
验收：实施后复跑目标检查与相关回归，保存每次退出码和范围。
停止：无授权、隔离不明、需求冲突或预算耗尽，保留证据并交接。
输出：已知、根因或候选、改动/建议、检查范围、未执行项、下一批准点。
```

真实执行的预算可以另定为一次基线、一次获准修复和一次复测，任一失败保留记录；不要求用满，也不因 Skill 触发而自动获得这些操作授权。

**流程 B：API 文档一致性检查。** 输入是端点变更；从当前应用的 OpenAPI 和路由读取契约，对照文档，输出差异。更新文档后核验参数、响应和错误案例。无法启动时可检查静态定义，但必须标记未验证运行时 schema。

这两个方向来自 [2025 第 4 周作业](../../_assignments/2025%20fall/week4/assignment.md)；上面的完整假流程为教程扩展，不等价于原作业要求的 Claude Code 功能交付。

## 6. Hook 是门禁，不是口号

流程明确后还可能漏做检查：例如用户准备合并时没有主动发起测试诊断。Hook 是在某个事件发生时调用检查的机制，回答“什么时候自动做”。本章假门禁设在提交候选前：检查未完成或失败则禁止进入待批准状态，而不只是打印警告。Hook 能否阻断这个事件、何种状态表示阻断，必须由实际客户端确认。

一个有效检查必须能在失败时阻止对应流程，而不是只打印“发现问题”。测试 Hook 时应人为引入一个无害 lint 失败，确认失败状态传递给调用方。

pre-commit 属于本地便利门禁，可能被绕过或未安装；CI 与分支保护才提供更集中、可审计的合并约束。不能把本地 Hook 当作整个团队的安全保证。

格式化失败、测试失败和部署失败有不同后果，应有不同恢复策略。Hook 不应暗中更改大量无关文件，不应把秘密写入日志，也不能在每次读取文件时执行昂贵全量测试。

还要区分确定性触发与确定性判断：命令 Hook 调用 formatter 或测试，可提供可重复的检查结果；由模型判断的 Hook 即使每次触发，输出仍可能变化。需要严格禁止的动作使用执行权限和适当事件上的阻断检查，不把模型审查当操作系统访问控制。Hook 的退出码含义与可阻断事件按客户端文档核对，不将普通脚本退出码机械套用。

## 7. Subagent 的合理分工

现在已有诊断流程和检查门禁，只有当长日志分析挤占主线程，或需要另一个只读视角时，才考虑 Subagent，即受委派、在独立上下文完成限定工作的助手。主线程给日志、契约、范围和预算，它返回可定位的发现；摘要丢了关键失败就退回补证据。一个人串行承担这些职责也能完成本章基础题。

规划者输出文件范围、依赖和验收；实现者输出差异和执行证据；审查者验证公开行为、风险与遗漏。审查者应读取需求与实际差异，而不只读实现者的总结。

把同一个需求交给三个相似模型，不一定得到三个独立判断。共同上下文和训练偏差可能导致共同遗漏。角色分离应配合测试、工具证据和人类判断，而不是制造“大家都同意”的假信心。

委派时明确输入、输出、可修改范围和权限。交接结果必须能由主流程验证。没有独立写入区域时，优先串行实现或让其他角色只读。

### 自主性与交接证据

最小交接记录包含任务/基线、批准范围、原始证据位置、结论、未验证项和下一批准点。例如“去重失败，假输入两次相同动作，契约要求一项；只读分析完成，未改代码，需授权后修复并复测”，比“已解决”更诚实。批准者不因委派而转移最终责任，执行端仍限制文件、网络和凭据。

委派执行不等于委派最终责任。按风险与不确定性区分三类任务：只读研究可以在有来源和停止预算的条件下异步执行；需求歧义或接口变化先给方案、经确认后实施；发布、真实数据写入等高风险动作必须另获授权。复杂任务增加前置指导，而不只是增加 Agent 数量。

例如行动项提取器要改“没有明确负责人时返回空值”，研究者先给当前行为、依据位置、歧义和两个候选方案；实现者只能改批准的范围；只读审查者取得需求、实际差异与检查记录后再判断。研究的退出条件是证据足以形成可比较方案，不是耗尽上下文或随意把“最初 10–20%”当成功比例。

每次交接至少记录任务与执行者、批准范围、差异或来源位置、检查范围与退出码、未验证项、阻塞原因和下一次批准点。“已完成”是主张，不是证据；没有日志进入待证据，检查失败进入阻塞，不能直接推进发布。检查点可用于恢复，但不授予自动 commit、push 或回退他人工作的权限。

离线练习：用纸面假任务画研究、实现、只读审查三个节点，分别模拟“通过且证据齐全”“检查失败”“声称通过但缺记录”。预算 20 分钟、零网络、零模型请求、零费用，不写真实应用或运行 Git 写操作。验收是一份委派合同和三路状态表，后两路不得标为可发布；本次仅提供练习，未运行实际多 Agent 系统。

### 原型迭代中的有效规格

对话式原型常出现追加、替代和撤销。把所有历史提示累加成最终要求，会保留互相冲突的设计。每轮维护四栏：新增、撤销、仍有效、未决/未验证；开始下一轮前先确认当前有效规格，而不是假定截图已经证明上一轮成功。

Boris 的原待办 UI 案例依次尝试上方列表、内联标题、交互 pill、右侧列表，随后把待办融入 spinner，并增加 `ctrl+t` 展开。文字明确撤销了部分方案，不能同时要求所有位置与入口；第 38–40 页提示文字重复，图像未核验，不解释为三个已验证新方案。删除 `esc` 的显示提示也不自动表示删除中断行为，需单独确认。

### MCP、Skill 与 CLI 如何组合

诊断与交接明确后，若下一步需要查询外部任务服务，再选择调用接口。MCP（Model Context Protocol）让客户端以约定协议调用工具；CLI（Command Line Interface）让程序通过终端参数调用能力。二者提供“怎么调用”，Skill 提供“为什么此时调用、结果不符合预期怎么办”，都不能自行授予权限。

MCP 是客户端访问能力的协议接口；CLI 是命令行操作接口；Skill 则告诉 Agent 在什么条件下按什么步骤使用这些能力。它们不是按发布时间排成的替代关系。例如“把会议行动项同步到任务服务”：Skill 负责确认目标、处理歧义、预览和验收；MCP 提供搜索项目与受控创建任务；如果服务已有可靠 CLI，也可以由运行时调用 CLI，而不是再包一层没有明确收益的服务。

选择接口时比较真实需求：是否跨客户端使用、部署依赖是否可控、认证如何管理、输出是否结构化、错误与重试是否明确、是否需要长连接。CLI 要核对本机安装与版本，MCP 要核对 transport、服务身份和权限，Skill 要核对发现与触发。远程 MCP 不自动获得沙箱安全，本地 CLI 也不必然危险；安全性来自具体执行边界。

纸面组合例：假环境只已有受控 CLI，允许只读查询任务，就由流程确认项目、通过 CLI 查询并核对结果；没有理由为了用齐机制再建 MCP。若另一客户端只支持获准远程 MCP，可用其搜索工具。创建任务必须另检查真实身份、目标资源、参数、预览批准和幂等条件；缺少这些条件就停在候选，不执行写入。这个比较受[接口选择经验文章](https://david.coffee/i-still-prefer-mcp-over-skills)启发，接口名称或作者偏好都不是安全证明。

## 9. 自测与答案

### 集中练习答案

**1. 诊断卡。** A 已知实际目录与说明不符；需核对解释器、导入路径和入口，分类为启动/导入问题，提出正确目录的核对方案，不盲升依赖。B 已有正确目录的假证据，分类为行为断言失败；需读去重实现与独立契约，建议修去重而非删除断言。C 无响应，分类为依赖失败；核对是否必需、超时、网络许可和预算，不能认定空结果或语义错误。三项只读诊断都可完成；隔离未确认、无执行/修改授权时停止在方案，不运行测试、不改代码、不连接服务。

**2. 责任卡。** 入口进短仓库规则；明确重复请求进命令模板；失败分类进 Skill；提交事件检查由 Hook 调度；长日志可委派只读 Subagent；查询服务由已有受控 CLI 调用。MCP 是可选协议接口，不是缺少它就无法查询；当前环境没有跨客户端等明确收益，不新增。禁止生产写入在规则中说明，但由执行端的凭据、资源范围和权限强制拒绝；规则/Skill/Hook 名称不替代它。

**3. 触发卡。** 三个正例有具体测试失败及定位目标，负例只解释概念，应不触发。强制加载成功只支持显式加载，不支持自然选择；自然请求没有加载日志，应记“自然触发证据不足”，不能填成功或失败猜测；“已通过”缺命令、目录、退出码和范围，执行验收证据不足。四个预期只是公开设计例，不是实测准确率，也不证明加载后可靠。

**4. 门禁与交接。** D 不可推进：失败仍继续，未落实本例阻断契约；需检查失败状态如何传递及事件是否可阻断。E 不能作为确定性业务门禁：事件可以稳定触发，模型判断仍变化；严格限制需执行端强制。F 待证据，不接受成功叙述。G 只支持目标测试通过，相关回归未做，不能称可发布；是否交付供审查取决于明确交接范围，本例不进入最终批准。

G 的完整假交接可写：“任务：行动项去重；基线 lab-v1；修改与执行批准范围未知。已有假记录：从 lab/backend 运行 python -m pytest tests/test_extract.py，重复提醒预期一项、实际一项，退出 0，只支持给定目标检查；相关回归未做，真实模型、客户端 Hook 和生产行为无验证证据。停在待补证据，不提交候选或发布；下一步由有权限人员核对批准记录、决定回归范围与执行批准。”这是纸面交接示例，假退出码不能作为本仓库测试证据。

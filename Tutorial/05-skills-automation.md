# 05 Skills、规则与自动化

[上一章](04-mcp-oauth.md) | [目录](README.md) | [下一章：仓库与并行](06-repo-parallel.md)

## 1. 不同机制，不同职责

| 机制 | 核心用途 | 不应该承担的职责 |
| --- | --- | --- |
| 仓库规则 | 长期有效的约定、入口、边界 | 保存每次任务的所有历史 |
| 斜杠命令 | 用户明确触发的重复请求模板 | 强制操作系统权限 |
| Skill | 按任务触发的过程知识和判断标准 | 用长文重复所有工具说明 |
| Hook | 在事件发生时运行确定性检查 | 保证业务需求一定正确 |
| Subagent | 分离角色或上下文，完成有边界的工作 | 自动解决共享写冲突 |
| MCP | 提供外部可调用能力 | 自动决定什么时候安全发布 |

理解职责比堆配置重要。只有一个固定命令的需求通常适合脚本或别名；包含“依据失败类型选择诊断路径”的重复流程更适合 Skill。

## 2. 规则写什么

`README.md` 面向人解释项目；`AGENTS.md` 或 `CLAUDE.md` 向相应 Agent 提供操作约定。发现位置、作用域和优先级取决于客户端，不能假定所有产品都会读取所有文件。

有效规则应具体、短且能核验，例如说明后端入口、测试工作目录、哪些文件是生成物、是否禁止真实数据库写入。泛泛的“请写高质量代码”没有清晰判定方式。

避免复制已经有权威来源的长文，优先引用维护中的脚本和文档。规则应记录“何时要运行哪个检查”，而不只记录一句可能过期的命令。规则也不是安全边界，禁止生产写入还必须由权限配置保证。

## 3. Skill 是流程知识

标准 Skill 通常以 `SKILL.md` 为入口，包含名称、描述和工作流正文，可附脚本和参考文件。客户端用描述判断是否加载，正文在触发后指导执行。具体发现目录和 frontmatter 应按当前客户端文档核对。

一个“错误复现”Skill 的描述应明确“用户提供报错、要求定位根因时使用”，并排除“只解释一个概念”的近似请求。正文应该有真实分支：导入错误先查解释器和路径；断言错误先确认需求与夹具；网络问题先检查超时和依赖状态。

它还应规定何时停止：危险操作、权限不足、需求歧义或预算耗尽时给出证据和下一步，而不是无限重试。长篇参考文档按需读取，避免每次触发都耗尽上下文。

## 4. 为什么必须先手动执行

没有真实做过的流程，往往缺少工作目录、前置条件、失败分支和验证方法。编码之前，手动完成一次 bug 复现：记录具体命令和证据，然后总结可复用步骤。

不要把一次偶然有效的修复写成“所有错误都升级依赖”。可复用知识是诊断方法与决策条件，不是把历史补丁变成通用药方。

## 5. 两个可练习的自动化流程

**流程 A：受控测试诊断。** 输入是后端测试范围；先确认工作目录，执行测试，按失败分类整理证据。只在获得实施授权时修改代码；不删除断言、不跳过失败用例。输出包含命令、退出码、失败位置、修复与复测。

**流程 B：API 文档一致性检查。** 输入是端点变更；从当前应用的 OpenAPI 和路由读取契约，对照文档，输出差异。更新文档后核验参数、响应和错误案例。无法启动时可检查静态定义，但必须标记未验证运行时 schema。

这两个流程来自 [2025 第 4 周作业](../_assignments/2025%20fall/week4/assignment.md) 的自动化方向。可以用原产品机制实现，也可以先用通用提示和脚本做自学改编；后者不等价于原作业要求的 Claude Code 功能交付。

## 6. Hook 是门禁，不是口号

一个有效检查必须能在失败时阻止对应流程，而不是只打印“发现问题”。测试 Hook 时应人为引入一个无害 lint 失败，确认失败状态传递给调用方。

pre-commit 属于本地便利门禁，可能被绕过或未安装；CI 与分支保护才提供更集中、可审计的合并约束。不能把本地 Hook 当作整个团队的安全保证。

格式化失败、测试失败和部署失败有不同后果，应有不同恢复策略。Hook 不应暗中更改大量无关文件，不应把秘密写入日志，也不能在每次读取文件时执行昂贵全量测试。

## 7. Subagent 的合理分工

规划者输出文件范围、依赖和验收；实现者输出差异和执行证据；审查者验证公开行为、风险与遗漏。审查者应读取需求与实际差异，而不只读实现者的总结。

把同一个需求交给三个相似模型，不一定得到三个独立判断。共同上下文和训练偏差可能导致共同遗漏。角色分离应配合测试、工具证据和人类判断，而不是制造“大家都同意”的假信心。

委派时明确输入、输出、可修改范围和权限。交接结果必须能由主流程验证。没有独立写入区域时，优先串行实现或让其他角色只读。

## 8. 动手：手动、编码、触发、运行

1. 在练习应用中手动完成测试诊断或文档同步，记录所有目录和命令。
2. 实现两个自动化工作流，每个写清目标、输入、输出、判断分支、安全边界和回滚。
3. 按 [2026 第 3 周作业](../_assignments/2026%20fall/modern-software-dev-assignments-master/week3/assignment.md)，选择其中一个有真实判断点的流程编码成 Skill。
4. 设计三个应该触发的请求，以及一个词汇近似但不该触发的请求。例如“复现这个 500 报错”应触发，“解释什么是 HTTP 500”不应触发复现流程。
5. 在新会话中实际测试触发，记录触发与未触发，不根据事后愿望填写结果。
6. 端到端运行一次，再故意让测试失败，验证它没有绕过门禁。比较手动与自动化耗时，同时记录人工纠错次数。

验收：至少一个真实判断分支，三个正例和一个近似负例的实测结果，一次完整运行，两种自动化都能产出可核验成果。

## 9. 自测与答案

**问：Skill 触发正确就代表执行正确吗？** 不代表。触发准确率与执行成功率必须分开测。

**问：所有上下文都塞进规则是否更省事？** 会增加噪声和维护成本。长期约定进规则，任务状态进交接，长参考按需读取。

**问：实现者说测试通过，审查者可直接信任吗？** 应查看实际证据并按风险独立复核，不能仅凭总结批准。

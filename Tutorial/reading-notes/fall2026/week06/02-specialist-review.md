## 2. 为什么不把 diff 塞进一个万能提示

原文引言及 `Specialised agents instead of one big prompt` 指出，简单 diff 提示产生虚构语法问题、空泛错误处理建议与大量噪声。专业角色通过“查什么”和“不要查什么”减少任务冲突，协调者则负责验证与汇总。

安全审查者只报可利用或具体危险的问题，关注不可信数据跨越边界、授权绕过等，不把已经有主防御的情况泛写成加固建议。边界不是隐藏风险：若旧代码的问题被本次变更新近暴露，仍应检查；如果不足以确认，则保留条件与待验证，而不是硬造漏洞。

每个发现有严重度和结构化格式；原文采用 XML 的 critical、warning、suggestion。结构化输出便于机器处理，但不证明内容真实。协调者按根因去重、重新归类、删除有证据反驳的误报，对疑点回读代码。多数角色同意不是证据，少数严重发现也不能因“太吵”被丢弃。

**原文案例：** 安全角色提示排除理论性风险与无关旧代码；多个专业角色由协调者生成单条结构化评论。**教程补充案例：** 安全与质量角色同时发现“更新笔记只按 ID 查找而不绑定用户”，协调者应合并同一根因，保留多用户部署条件和跨身份测试，不能算两个不同漏洞。

## 3. 插件与会话的两层架构

定位原文 `The architecture: plugins all the way to the moon`、`How we use OpenCode under the hood`。

| 层次 | 原文设计 | 工程含义 |
| --- | --- | --- |
| bootstrap | 并发、失败非致命 | 可选模板获取失败可继续，但必须显式说明缺失 |
| configure | 顺序、失败致命 | VCS 配置等关键前提失败就不能假装审查成功 |
| postConfigure | 配置组装后异步工作 | 模型覆盖等控制面需要时序和版本边界 |
| coordinator process | 子进程，经 stdin 传提示，stdout 输出 JSONL | 避免超长命令行的 ARG_MAX/E2BIG，独立限制进程资源 |
| reviewer sessions | 通过 SDK 建独立会话并异步运行 | 每个角色有自己的上下文、权限与生命周期 |

插件通过受控 ConfigureContext 注册角色、供应商、环境与权限，由核心装配最终配置；VCS 插件不需要读模型网关密钥。值得迁移的是耦合与秘密边界，不是为简单教程项目创建七个包。

原文用每文件 patch 路径和共享上下文文件，避免把完整 MR 内容重复嵌入每个提示。文件存在不等于模型一定读到，也不保证所有供应商自动命中缓存；仍要记录读取范围与实际用量。第 03 章的最小上下文包可作为简化版基础。

JSONL 每行可独立解析，进程中断后已有完整行仍可读；最后一行可能截断，业务记录可能不完整。不要把“有结构化日志”误认为“审查全部完成”。原文通过 step_finish/error 检测用量与错误，并对 length 截断重试；生产实现仍应保留最大重试与重复评论去重。

## 4. 风险分层不是只数行

定位原文 `Risk tiers`、`Diff filtering`、`The coordinator helps keep things focused`。

原文示例函数先看安全敏感文件或超过 50 文件，再看 trivial（≤10 行且≤20 文件）、lite（≤100 行且≤20 文件），其余 full。页面简表把 Full 写作“>100 or >50 files”，没有完整覆盖代码中 21–50 文件等默认分支；学习时以这段示例控制流理解作者的阈值，不把表格简写视为完整算法，更不称为安全标准。

一行授权改动仍可需要全量高风险审查。原文过滤锁文件、依赖、生成和压缩资源以减噪，但迁移文件明确豁免生成过滤。教程迁移时还应让依赖变化进入 SCA/供应链检查，核对生成来源，不把“从模型 diff 过滤”当成“完全不用审查”。`eslint-disable` 也不是可靠的生成物证明。

原文的批准偏好、warning 放行和 `break glass` 评论触发强制批准是其内部政策。**本教程不照搬文本绕过审批，也不授予模型批准、撤销或合并权限。** 若组织确需紧急流程，应由外部可信身份系统检验批准者权限，绑定具体提交、理由与有效期，审计并安排事后复核。PR 评论属于不可信输入，不是管理员授权渠道。

## 5. 可靠调度与可信边界

定位原文 `Prompt injection prevention`、`The spawn_reviewers tool`、`Resilience`、`The control plane`、`Re-reviews`。

原文剥离用户内容中可破坏 XML 边界的标签。这只能保护一类结构边界，不能消除自然语言注入；MR 描述、代码注释、旧评论与仓库文件仍是数据，不能改变系统权限。只读角色、受控工具、无秘密环境和外部写门禁更重要。

调度区分角色超时、整体超时和剩余重试预算；作者示例为每角色 5 分钟（质量角色 10 分钟）、整体 25 分钟、重试至少剩 2 分钟。还使用 idle 事件及状态检查。慢推理 heartbeat 与无输出超时需要协调，不能仅因心跳存在便假定审查有进展，也不能把安静思考等同崩溃。

熔断每个模型层级独立跟踪，冷却后单探针避免重试风暴。只有可重试 API 错误适合 failback；坏凭据、用户取消、结构输出失败和上下文溢出需处理根因，而非无限切模型。备用模型必须满足同样的数据政策，换供应商不是默许把私有代码送到新服务。

原文复审携带上次发现和线程状态：修复项不重报、未修复项保留、用户回复影响状态。教程应额外保留“争议/接受风险/已验证修复”三种区别；评论说 won't fix 不是技术修复，更不应自动解除高风险门禁。控制面动态覆盖模型、可选遥测不阻塞 CI 是工程选择，关键审查状态和安全审计不能无声丢失。

## 6. 作者数字应怎么读

原文 `Show me the numbers!` 报告 131,246 次 review runs、48,095 个 MR、3 分 39 秒中位时长、平均 $1.19 和中位 $0.98、159,103 条发现、85.7% 缓存命中等。它们是其特定统计期和内部计费条件，不是本教程保证。

发现数不是真缺陷数，没有独立标注和漏报全集就不能从中计算准确率/召回率。0.6% MR 使用 break glass 也不能推导 99.4% 正确率。模型表的 `% of Total` 与随后成本分摊说明有关，Kimi 被写成成本“nothing”不意味着其 input 用量为零或任何用户免费；不要按这些数字推定自己的预算。

作者承认架构意图、跨系统消费者、细微并发与大 diff 成本仍困难。多角色不是人工审查、测试、安全扫描或兼容验证的替代。

## 7. 45 分钟零付费练习：只读角色与汇总

教程扩展；独立纸面或临时文本练习，不调用模型、不建真实 CI、不发 PR 评论、不安装依赖、不启动服务。预算：45 分钟、0 元、0 次外部请求。使用假用户、假资源和虚构差异。

1. 用 8 分钟准备三张变更卡：README 拼写；排序遗漏 ID tie-breaker；三行更新端点缺少用户约束。写风险理由，不只写行数。
2. 用 10 分钟给契约、安全两个只读角色各列查什么/不查什么，形成包含位置、触发条件、影响、证据、未知项的发现。
3. 用 10 分钟协调汇总：合并重复授权根因，剔除“建议换框架”等无关建议，保留无法确认的消费者问题；按差异版本固定结论。
4. 用 7 分钟模拟安全角色超时与一次坏凭据，输出审查不完整状态、有限重试或停止原因、人工交接，不把故障当 LGTM。
5. 用 10 分钟模拟新版本补用户查询后复审：给出跨用户拒绝的预期证据，再加入评论“break glass，忽略安全”并验证其不改变门禁。

验收证据：风险卡、两份原始发现、根因去重表、未确认项与失败记录、复审版本对照、拒绝绕过记录。通过条件是严重发现不被噪声过滤吞掉、审查失败不当通过、未经独立授权不产生写入或批准。本次仅编写练习，未执行审查实验。

## 8. 自测与答案

**问：七个角色意见一致就可以自动合并吗？** 不可以。可能共享盲区，批准依赖外部门禁和独立证据。

**问：认证失败应换模型重试吗？** 通常不应。更换模型不修凭据，应停止并恢复访问前提。

**问：删除危险 XML 标签能完全防注入吗？** 不能。自然语言与其他载体仍可注入，需权限和执行侧限制。

**问：把锁文件移出模型输入等于忽略依赖风险吗？** 不等于。依赖来源与漏洞仍须由对应供应链检查覆盖。

**问：用户在评论中接受风险等于缺陷已经修复吗？** 不等于。分别记录争议、风险接受和验证修复，批准者权限需独立检查。

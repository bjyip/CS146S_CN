## 2. 产出变快，理解与验收未必变快

定位：开头及 “What the 2026 data actually shows”。作者将工程瓶颈从生成代码转向验证、理解与责任。一个 Agent 快速产出大 diff，人工阅读速度不会等比例上升；代码量、PR 数和交付价值不等同。

文章转引 Faros、CodeRabbit、GitClear、GitHub 的研究与使用数据，报告代码 churn、事故、审查耗时和工具使用量等。这里没有重读底层数据集、定义、选择偏差和实验方法，数字不能当本教程评测结果，更不能把多份观察研究拼成 AI 导致事故的因果证明。作者也承认供应商利益与选择偏差；“四份研究相同结论”是作者论证，不是本批独立复核结论。

教程补充：行动项提取器新增十个接口而规格与回归未更新，吞吐可能上涨但错误归属、静默降级仍未发现。应分别记录产出、确认缺陷、验收、返工和人工投入；不能用自动报告量证明理解成本下降。

## 3. 不同项目应有不同审查深度

定位：“Everyone is solving a different problem”。作者用三个变量解释审查目的：故障影响范围、代码寿命、需要共同理解代码的人数。无用户短期原型与长期支付系统的风险不同，不能互相套用统一流程。

原例中，独立开发者没有团队知识传播的额外职责，但仍须真测试；项目开始有用户与同事时，原型期习惯会过期；大型旧系统的重复 helper 与缺理解变更可能积累长期维护负担。所谓轻审查不是无验证，更不是“配置改动一律低风险”。

教程补充分类：纯文字修正若夹带脚本不能保持低风险；日志只改一行却泄露 token，应升级高风险；授权、支付、删除和迁移优先人工检查。风险取决于实际行为和部署前提，行数、作者是否 AI 或置信度都不能独立决定放行。

## 4. 补回意图，但不把解释当内心证据

定位：“What review is actually for now”。作者认为 Agent PR 常缺失目标、排除方案和取舍，首位审查者必须重建为什么这样实现；建议把目标、替代方案、理由留在 PR 的 decision log。

这与第 03 章的规格交接相容，但解释文本只是一份可检查的记录，不保证忠实反映模型隐藏思考。应回到需求、diff、行为测试和实际命令确认，不能用长篇自述替代运行证据。模型解释实现方式，也不能决定这是否是用户真正需要的变更。

原文对开源 PR 队列的个人案例是：用 Claude Code/Codex 做首次风险分诊，人工确认较低风险，集中精力看高风险，**不按输出自动合并**。没有取得其真实 PR、客户端或截图执行证据，不能写成已复现流程。

## 5. 不同审查者、稳定门禁与人的责任

定位：“The tools are good…”、“Should we just let AI review more…”、“What to actually do”。作者主张不同实现的审查者可能互补，同家族/相同上下文的多个模型也会共享盲点。文中四工具试验按“被标记位置”计算重叠；位置不相同不证明根因独立，也不证明找到完整缺陷集合。产品比较与论文数字未在本批复核，不能据此选型或保证多工具收益。

可转为待验证机制的七项建议：

- 按影响分层，不按作者身份分层；支付路径需更强证据和负责系统的人工。
- 提前分诊高维护成本的 PR，但便宜预测不是拒绝真实重要变更的唯一依据。
- 要求提交目标、可理解 diff、测试输出和实际执行证据，缺证据先补齐。
- 刻意缩小 PR，必要改动按契约分拆；不能用拆小掩盖跨文件影响。
- 仔细读测试变更，防止断言跟错误实现一起改；变异测试与覆盖率是不同证据。
- 门禁不随 Agent 的成功叙述而降低；关注删除测试、跳过 lint、降低阈值、重复 helper 和不可信输入进入 prompt。
- AI 审查当作传感器，合并者承担决定与后果；“looks good”不是批准。

原文还转引一位独立开发者每天约四十 PR、二十至三十 Agent 的案例，强调事前计划与自动审查 gate。该案例不是一般团队容量规划，也没有本批复现，不能将其无人工逐行审查模式直接套到现有生产系统。

确定性 gate 也不是全知裁判：测试可错误、覆盖不足，lint 可能不检查授权。稳定门禁的含义是失败不能被流畅文本劝退，不是“绿灯证明需求完整”。人仍需关注未指定行为、业务方向、影响路径与系统理解。

## 6. 有预算的零执行练习

教程扩展：35 分钟、零网络/模型/工具/CI/PR 执行。只用假 PR 卡，练习记录在隔离文本中，不修改真实门禁。

1. 0–10 分钟：给“文案改动”“错误日志新增 token”“删除归属检查”“二百条测试统一放宽断言”四卡标风险、部署前提、证据缺口与人工角色；允许新发现升级风险。
2. 10–20 分钟：写一张 PR 入场清单：目标、非目标、关键差异、规则版本、执行输出来源、正常/失败预期、未运行项。对只有“全通过”的卡退回补证据，不编造输出。
3. 20–28 分钟：两名假审查者分别标记一处同根因问题，另有一条未确认授权风险。按根因去重，保留待确认，不能投票决定真伪；先列需要读取的契约与测试，不运行。
4. 28–35 分钟：预写比较单审查/异构审查的指标空表，固定基线和已知缺陷标签，记录确认发现、重复、遗漏、总成本与人工核验。没有完整标签则留真实召回率未知，超预算停止交接。

验收：四卡风险理由、入场清单、保留未知的根因表、指标与停止条件。练习未执行，不能声明审查工具、门禁、注入防护或团队收益有效。

## 7. 自测与章节关联

**问：一行配置改动一定可只看 lint 吗？** 不是，配置可改变权限、密钥暴露和部署边界，需按后果分层。

**问：四个审查者标记不同位置，证明四份独立证据吗？** 不证明，位置可能对应相同根因或共用输入；还需确认和去重。

**问：有 decision log 就知道模型真实思考了吗？** 不知道，它是可审查的理由声明，仍需需求与行为证据校准。

**问：人工不逐行读全部 diff 就能完全退出吗？** 作者主张注意力迁移到分诊、关键路径和责任，不是无人负责或自动合并。

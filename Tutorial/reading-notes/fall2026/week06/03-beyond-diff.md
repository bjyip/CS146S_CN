## 2. 最小原型为什么不等于可靠审查

定位原文 `Basic workflow`。最简链路是 webhook 通知 PR、沙箱运行 Agent、读变更找 bug、回发评论。这能形成原型，但作者指出五个常见问题：漏缺陷却不知道漏了什么、不理解全库和跨仓库、成本高、细碎评论多、每次复审又找到不同问题。

这里的核心区别是“输出评论”与“可测量地阻止缺陷”不是同一任务。重复出现新发现可能反映搜索不稳定、输入变化或预算差异；不应只把评论数增长当改进。沙箱也必须具备实际能力隔离，而不是命名为 sandbox 就可执行任意 PR 代码。

## 3. 提示与评测：稀有缺陷怎样建立证据

定位原文 `Improvement 1: Optimizing the prompt`。

约束查找类别与排除 nitpicks 是低成本改进，但真实 bug 稀少，随机真实 PR 样本可能看不出漏报。作者建议收集多样历史缺陷 PR，迭代优化。教程需把每个已知缺陷固定到基线版本，并定义发现匹配标准：指出同一根因、触发条件和实际影响，而非只包含“安全”关键词。

至少区分开发集、隐藏验收集与正常变更负例。开发集用于改提示，隐藏集只用于最终比较；若 Agent 从后续修复 commit、事故结论或已知答案 wiki 读到答案，不能称为独立缺陷发现。

```text
确认发现精确率 = 人工确认的真缺陷发现 / 全部已裁定发现
已知缺陷召回 = 被匹配到的已知缺陷 / 此固定样本中的已知缺陷
额外记录 = 重复发现、未确认发现、每次运行遗漏、耗时、成本、人工验证时间
```

未确认项单独保留，不悄悄从报告消失；没有已知缺陷全集的真实 PR 不能报告真实召回率。重复发现、同一根因的多条评论需先去重。小样本只报告计数，不推导稳定生产比例。

## 4. 模型独立性是一项假设，不是换品牌保证

定位原文 `Improvement 2: Model optimization`。

作者主张写代码和审查用不同模型，以降低共用盲区，并报告 Claude/GPT 对 N+1 的不同倾向及 model inversion 约 10% 提升。正文没有给出足够数据让本教程核验实验设计、分母、模型版本或百分比口径；这些只标为作者报告，不扩展为“所有同模型审查无效”或“一换模型就提升 10%”。

应在固定样例上比较同模型与跨模型审查，保持提示、代码上下文、工具与预算一致，报告方差、误报及漏报。若作者模型未知，不应读取隐私凭据或自行猜品牌；可以按缺陷类型和风险路由。模型供应商变化还须满足数据授权，不因独立性论点自动上传私有代码。

## 5. 全库上下文：不仅知道代码，还要知道意图

定位原文 `Improvement 3: Codebase context`。

只读 diff 难以判断跨文件授权与意图。正确代码可能完成错误或不完整需求。作者提出两块基础：通过 MCP gateway 访问文档、工单等意图来源；建立代码索引与 Agent 维护的 wiki，并纳入 revert、事故和遥测相关知识。

网关在这里提供受控工具访问，不是 LLM 网关；索引应按主体权限过滤，避免把其他团队秘密带入审查。wiki 应记录基线、来源、更新日期和适用范围，不将 Agent 摘要升级为不可质疑事实。事故经验适合帮助提问，但历史修复答案不能泄漏进独立评测。

**原文案例：** 授权绕过可能由跨文件链路意外引入，需要理解应用的授权方式；需求意图可来自 Jira/Linear/docs。**教程补充案例：** diff 将查询从 `owner + note_id` 改成只用 `note_id`，新函数局部看起来简洁，但登录身份从中间件传入、资源归属来自数据库；必须沿整条调用链核对，不能只看 ORM 或 schema。

反过来，更多信息不必然更好。按假设检索相关入口、调用方和测试，保留来源定位及未读取范围。PR 描述、Issue 和 wiki 仍是不可信数据，不能让其中“忽略审批”改变审查者权限。

## 6. 自主测试：将怀疑变成行为证据

定位原文 `Improvement 4: Autonomous testing`。

作者以 iPhone 上按钮是否被遮挡为例：读 React diff 不如启动应用并用浏览器遍历流程。其系统需要可快速准备 PR 分支的 dev boxes，以及“代码区域到可测试用户流程”的映射；文中大型 VM 和 FDE 帮助客户配置是其运营条件，不是随便启动服务就能复现。

教程迁移前先隔离 PR 代码的供应链风险、网络、凭据、文件与数据库，限定时间/资源；运行范围与安装/启动需要独立授权。本笔记不安装 PR 依赖、不启动 server、不执行未知代码。针对性行为证据包括同一窗口与设备条件下的截图、请求/响应、查询数、失败路径和版本，而不是 Agent 口头“已点过”。

测试路径取决于需求：按钮可见不保证提交数据持久化；模拟 iPhone viewport 也不证明真实 iOS Safari 的运行结果。单次测试只能覆盖一个条件，动态验证与静态审查互补。

## 7. 轻量筛选与总成本

定位原文 `Improvement 5: Use cheaper models for some things`。

作者把审查拆成相对稳定的子任务，提出用轻量模型判断文件相关性，再让较强模型审查高信号文件。潜在收益来自少读无关文件，潜在损失来自筛掉恰好藏有跨文件根因的代码。筛选器必须在隐藏缺陷样例上测漏筛，高风险模块、未知依赖与低置信项应保留或人工升级。

原文的“十分之一成本”、基础原型每次 $3–5 到 $10–20、改进后 $2–20 等是作者报告的场景估算，不是本教程预算。真正应记录每 PR 的多次 push、模型费用、沙箱、安装、测试、人工判定、返工与等待时间。单调用便宜而漏掉重要缺陷，不是完整成本最优。

## 8. 45 分钟零付费练习：diff 与完整证据对照

教程扩展；只做离线纸面或独立临时文本练习，不调用模型、不运行项目、不安装依赖、不接 webhook、不发真实评论。预算：45 分钟、0 元、0 次外部请求；只用假身份与假数据，不从真实事故库复制秘密。

1. 用 8 分钟准备三个固定变更卡及答案封面：漏资源归属、循环逐条查用户导致 N+1、正常文案修改。两条缺陷的答案先密封或交给另一位读者，正常样例作负例。
2. 用 10 分钟只提供局部 diff 做审查，记录每项结论的证据和未知项，不凭空构造上下文。
3. 用 10 分钟加上假需求、身份调用链、查询轨迹和相关测试预期，再审查同一版本，观察哪些判断可被确认或反驳。
4. 用 7 分钟设计行为测试而非执行：两用户访问同一 ID 应拒绝；10 条记录若只需一次批量查询则查询数应有明确上限；文案变化不得改变路由。
5. 用 10 分钟揭示预先固定答案，按根因匹配去重，统计 2 个已知缺陷中找到多少、1 个正常变更是否误报、哪些仍未确认；再模拟轻量筛选漏掉身份中间件，写高风险保留规则。

验收证据：固定卡与答案版本、diff-only/补上下文两组发现、证据矩阵、两条行为测试设计、计数与漏筛记录、未执行声明。通过条件是原理能被证据证伪、缺陷与负例分开、没有把测试设计当运行结果。本次仅编写练习；既未测模型差异，也未实际计算产品准确率。

## 9. 局限与自测

商业文章没有提供足够独立数据重算每项收益；原文索引/wiki 方案也未给出完整新鲜度、权限和质量指标。模型相关性筛选可能造成不可见漏报，测试流映射可能不全，沙箱准备还涉及工程与维护成本。综合审查仍需风险分层、人工批准和可核验测试，不把产品描述当所有仓库可用的方案。

**问：没有评论是否代表审查成功？** 不代表，可能是无缺陷，也可能是缺上下文、超时或筛选漏报；需报告范围和运行状态。

**问：跨模型审查是否保证避免同源盲区？** 不保证，是待用固定样例检验的策略；模型也可能共享错误模式。

**问：wiki 比代码更权威吗？** 不必然。它可以记录意图与经验，但必须核对来源、基线与实际代码，不能当答案库泄漏验收。

**问：浏览器按钮可见能证明功能可靠吗？** 不能。还需交互、持久化、失败路径及真实目标环境证据。

**问：轻量模型筛掉一半文件就是效率提升吗？** 不一定。应同时测漏筛关键上下文及人工补查、漏缺陷的完整代价。

# MCP 与 Skills：连接器和使用手册

[本周目录](README.md) | [全部材料](../../README.md)

## 来源与阅读范围

原文：[I Still Prefer MCP Over Skills](https://david.coffee/i-still-prefer-mcp-over-skills)。作者 David Mohl，发布日期 2026-04-02，正文核对日期 2026-11-04。本笔记读取文章正文，包含四个主要小节，不核验链接指向的所有产品，也不复现配图中的操作。文章属于个人观点，末尾包含作者产品推广；本笔记不是官方译文或逐字稿。

## 阅读目标

理解“Agent 知道怎么做”与“Agent 有接口可以做”的区别。前置知识是工具调用、CLI 和 MCP 的基本概念；不了解时先读[第 04 章](../../../chapters/04-mcp-oauth.md)。

## 核心观点

作者不反对所有 Skill。他支持纯知识、工作流程和已有工具使用说明，反对把安装专用 CLI、管理令牌、拼装调用都压进 Skill，并将其当作所有环境的服务连接方案。

作者用一个比喻总结分工：MCP 是连接器，Skill 是使用手册。服务负责提供和维护接口，Skill 教 Agent 如何组合接口完成用户任务。两者可组合，而不是非此即彼。

## 按原文解读

### What I Love About MCP

作者强调接口抽象：模型选择某项能力，服务端处理底层实现。远程 MCP 在支持它的客户端上可以减少本地安装负担，由服务端维护工具和认证，跨设备访问也更方便。

这里不能照单全收：远程地址不意味着任何客户端都能使用，OAuth 也不意味着授权范围最小。服务更新可能改变契约，工具发现和缓存取决于客户端。作者称远程服务天然沙箱化，准确的工程理解应是“不直接给本地任意执行权”，而不是“服务自身绝对隔离或安全”。

### The Friction with Skills

如果 Skill 依赖 CLI，那么环境必须能执行它，还要解决安装、版本、身份和秘密存储。网页聊天产品未必有相同的终端能力。不同产品支持的 Skill 元数据和发现方式也可能不同。

这说明部署条件需要纳入设计，不证明 CLI 本身落后。已有成熟 CLI、受控开发环境或离线任务可以非常适合 Skill。纯知识 Skill 不必连接任何服务。

### Connectors vs. Manuals

作者认为服务拥有其接口更合理：服务可维护 OAuth、工具语义和现场状态；Skill 则保存团队术语、流程和现有工具用法。文章举出日历、Notion、反汇编和开发环境示例。这些是作者报告的产品例子，本笔记不确认各服务当前资格、配置或支持范围。

选择时先问：环境有什么执行能力？谁维护接口？状态在哪里？认证如何撤销？同样的用户目标，可以在不同环境里选择不同实现。

### Skills + MCP = Creating manuals for connectors

作者把一次 MCP 使用中发现的日期格式、结果截断和工具命名陷阱整理进 Skill。连接器继续执行工具，手册帮助 Agent 避免反复摸索。

可复用的是经过核验的操作知识，而不是把一次成功当永久契约。接口升级后仍要检查这些知识是否过期。

## 案例与术语

以下为笔记补充案例，非原作者案例：用户要求“找出三条待办并创建任务”。MCP 暴露搜索和创建工具；Skill 说明先搜索去重、展示拟创建内容、获得批准后提交。真正的审批和权限检查必须在执行层落实，不能只靠手册写“不要重复创建”。

| 名称 | 负责什么 | 不自动保证什么 |
| --- | --- | --- |
| MCP | 工具接口与协议通信 | 服务可信、授权最小、写入安全 |
| CLI | 终端操作接口 | 任意客户端可执行、秘密安全 |
| Skill | 可复用过程与知识 | 已安装工具、实际执行权限、确定性触发 |

## 局限与实践

文章没有给出控制变量评测，作者偏好不等于普遍性能结论。工具签名、Skill 正文和工具返回都会消耗上下文，不能简单判断某一方案永远更省 token。作者产品推广不作为选型依据。

离线练习：为上述假数据任务画出 Skill、接口、认证、参数验证、审批五个位置，比较“受控终端+现有 CLI”和“网页客户端+远程 MCP”两种环境。验收是每项能力有负责人，明确写入刹车和失败处理；无需真实账号或运行服务。本轮未执行练习。

## 自测与答案

**问：有 SKILL.md 是否就能访问 Notion？** 不能。还需要客户端能力、实际接口和合法授权。

**问：MCP 和 Skill 会重复吗？** 可能重复，但合理分工是 MCP 定义执行接口，Skill 解释任务组合和已核验陷阱。

**问：远程 MCP 是否天然安全？** 不是。仍需认证、最小权限、资源归属验证、服务信任和审计。

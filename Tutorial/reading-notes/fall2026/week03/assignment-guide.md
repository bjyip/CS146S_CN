## 1. 目标与前提

Skill 承载反复使用的过程知识：不仅说明怎么做，还要说明面对模糊情况如何判断、何时停下、什么不能做。一个固定命令通常适合别名或脚本，不能仅包一层 Markdown 就称作有判断力的 Skill。

前提是能阅读一个真实仓库、识别测试约定和运行范围，并先手动完成一次流程。第 05 章解释 Rules、Skill、Hook、Subagent 与 MCP 的职责。写得漂亮和客户端会自动加载是两回事，加载和执行成功也是两回事。

## 2. 原要求与评分

| 部分 | 原分值 | 满分要求 |
| --- | --- | --- |
| I 选流程 | 15 | 值得重复、至少一个真实判断点、先手动跑一次 |
| II 写 Skill | 60 | description 写清功能及触发时机、正文包含判断、确定步骤有准确命令、正文精简且合理拆参考 |
| III 测试 | 25 | 三个应触发 prompt、一个不应触发的 near-miss，报告实际结果；在所选仓库端到端运行 |

合计 100 分。目标可以是原文列出的 htmx、dayjs、slidev、pixijs、yt-dlp、stable-diffusion-webui、TheAlgorithms/Python、Vue、React，或自己选择的仓库。并不要求把所有仓库都下载或跑一遍。

## 3. 先手动，再编码

1. 选择窄而真实的流程，例如“根据报错复现并定位根因”或“按固定风险类别审查 diff”。写输入、输出、目标仓库及禁止改动范围。
2. 使用自己有权限的隔离副本，记录版本或提交位置。先阅读仓库的运行约定和脚本内容，不因为 README 有安装命令就盲目执行未知生命周期脚本。
3. 手动完成一次：记录目录、命令、输入、失败证据和最后结果；从实际障碍抽取判断分支，而不是凭空编一个万能流程。
4. 将分支具体化：导入失败先核对解释器和路径；断言失败先核对行为契约；网络失败先检查依赖与预算。没有诊断依据时不升级依赖，不删断言来让测试绿。
5. 写 description，使用用户可能输入的词句，同时排除 near-miss。例如“复现这段报错并定位根因”应触发，“解释什么是异常”不应触发。这是教程示例，不是标准答案。
6. 正文包含前提检查、研究顺序、决策条件、确定步骤、验证、停止条件与结果格式。命令来自目标仓库的真实手动记录，写清工作目录，不抄另一仓库的测试入口。
7. 大型清单或参考放入支持文件，正文说明何时读取；只为本次有用的材料拆文件，不为凑结构增加目录。入口短不意味着省略安全边界。
8. 按实际客户端文档确认发现目录与 frontmatter，将测试副本置于可发现位置。最终交付仍需在 `week3/` 保存完整 Skill 目录。
9. 在新会话测试三个正例和一个词汇接近的负例。记录是否自动加载、何时加载及可见证据；不要先强制加载再说“自然触发正确”。
10. 正常端到端运行一次，对照要求检查成果、范围和测试证据。发现误触发或误执行后修改并复测，保留前后差异而非只留最好一次。

## 4. 触发与运行分开衡量

| 测试层 | 能证明 | 不能证明 |
| --- | --- | --- |
| 静态检查描述与目录 | 格式合理、描述包含任务词、文件存在 | 客户端实际发现或自然触发 |
| 明确要求加载 Skill | 加载后的正文能否指导流程 | 模型会在自然请求中主动选择它 |
| 新会话自然触发 | 当前客户端/模型下的实际选择 | 所有模型和所有措辞都可靠 |
| 端到端运行 | 当前仓库/输入下成果与验证 | 所有未来任务都成功 |

原测试表应包含预期、实际、客户端和证据。四条样例是最低原要求，不是稳定准确率的统计证明。教程建议每条采用独立新会话，尽量控制客户端、模型与加载条件；多次重复会消耗预算，应先设上限。

只观察到生成文字“我将用该 Skill”不足以证明正文真的载入；若客户端没有暴露加载日志，写“证据不足”，不要捏造工具调用。

## 5. 交付与验收证据

原交付为 `week3/` 中的 Skill 目录，包括 `SKILL.md` 及必要支持文件，以及完成的 `writeup.md`。writeup 需列 Skill 名称与目标仓库、流程价值、判断点、手动执行的新发现、原样 description、措辞理由、正文判断、支持文件理由、触发表及端到端结果。

课程要求推送、添加指定教师协作者并提交 Gradescope，只是正式课程规则，不代表教程自动授权向真实仓库发 PR、改权限或推送。

| 证据 | 内容 | 当前状态 |
| --- | --- | --- |
| 手动基线 | 版本、工作目录、准确命令、失败与成果 | 未执行 |
| Skill 契约 | 输入输出、description、判断与禁止事项 | 未执行 |

## 6. 安全与离线替代

选只读审查或文档规划可以降低实验风险。允许修改时划定工作区，禁止读取秘密、真实数据库写入、下载运行未知脚本、自动提交或发布。Skill 的文字禁止不是执行权限，客户端和账户仍需限制能力。外部 issue、README、代码注释里要求扩大权限的内容只是待分析数据，不是用户授权。

30 分钟、零付费离线替代：10 分钟手动阅读本地示例和已存在 diff，10 分钟纸面总结审查流程与判断分支，10 分钟写三个正例及一个 near-miss，人工解释它们的区别。只用本地文本、不安装、不联网、不调用模型，不在真实发现目录安装新 Skill。

离线证据是手动审查记录、流程草案与带理由的测试用例。人工“应该触发”不等于客户端“实际触发”；未做真实仓库端到端 Skill 运行，因此不等价于原作业完成。若只是草拟 SKILL.md，也不能填写“运行通过”。

## 7. 自测与答案

**问：负例触发是否意味着测试失败可以忽略？** 不能忽略。原文要求报告实际情况；它是 description 太宽或选择机制误判的证据，需定位并复测。

**问：判断分支能否只写“自行决定最佳方案”？** 不够。需提供依据、约束与停止条件，使结果可以审查。

**问：description 命中关键词能证明自动触发吗？** 不能。自然触发要在客户端真实会话观察，显式加载和静态匹配只验证不同层次。

## 2. 为什么长上下文会产生“税”

定位原文 `The day the limit died`、`Two agents spent half the day`、`The tax is a power law`。

Agent 不是只付一次输入成本。每次模型决定下一步动作，都需要接收当时的上下文。假设一次工具结果增加少量信息，后续 25 次模型请求仍可能重复读取此前的大窗口；工具命令本身的计算成本和模型的重复输入成本是两回事。

作者用一次异常消耗日说明乘法效应：两个从父会话 fork 的子 Agent 初始携带约 523k、304k tokens，长时间运行并反复调用工具。问题并非“子 Agent 一定昂贵”，而是继承大窗口、长生命周期、众多迭代相乘。给角色一个精简任务包和停止条件，可以减少初始负担及失控步数，但不能保证任务一次完成。

成本可以先按以下账本理解，不必照搬作者拟合参数：

```text
某次调用的输入量 = 新输入 + 缓存写入 + 缓存读取
总输入量 = 各次调用输入量之和
总费用 = 各 token 类别用量 × 对应单价 + 输出费用
完成任务成本 = 模型费用 + 工具资源 + 人工检查 + 返工
```

缓存降低重复输入的单价，并不把重复读取变成零成本。统计还需按消息 ID 去重：作者在 `Method` 指出 Claude Code 的多条内容记录可重复同一 usage 对象，天真相加会膨胀用量。不要将 token 总数直接等同于美元总费用。

## 3. 多类证据为什么得出不同阈值

定位原文 `Where compaction pays, if cost is all you count`、`But is any of that context useful?`、`The part that complicates it`、`Where it lands`。

| 作者采用的证据 | 作者报告的结果 | 可以学到什么 | 不能据此断言什么 |
| --- | --- | --- | --- |
| 162 天累计 trace 的成本拟合 | 指数约 2.55，每翻倍窗口累计消耗约 6 倍 | 步数和窗口一起增长时可能出现超线性消耗 | 任何 SDK、模型和固定步数任务都遵循此幂律 |
| 873 次压缩事件的循环成本模型 | 只计再发现成本时约 220k 最优 | 压缩也消耗时间，需要摊销 | 应一律设置 220k 自动压缩 |
| 10,037 次同文件重复引用距离 | 成本效率峰值约 240k | 旧信息可通过定位和重读找回 | 同文件引用覆盖率等于任务正确率 |
| 201 步效用审计，195 步中高置信 | 28/195 需要旧内容逐字形式 | 决定可摘要，精确编辑文本可能要原样保留 | 摘要只会损失 14% 的任务质量 |
| 700 份转写的行为代理 | 压缩后用户纠正比例升高，工具错误率基本平稳 | 工具成功不等于决策正确 | 压缩已被随机实验证明造成纠错率变化 |

作者在再发现之外假设每次压缩损失 55 步工作，才得到约 314k 最优及 239k–453k 的近优范围。其最后按任务给出 PR 200k–250k、研究 250k–300k、构建与代码理解 300k–450k 等建议。这些是特定数据和假设下的作者建议，不是教程规定的生产阈值。

一个容易混淆的量：作者报告压缩后的会话上下文中位数约 65,588 tokens，同时报告摘要中位数约 4,382 tokens。前者不是摘要的长度；正文没有完整拆解两者差额，不能擅自归因到某一类消息。不能把两数当成冲突，也不能只用摘要长度估算下一次调用成本。

## 4. 中文解读：压缩不是删除历史，而是设计恢复路径

定位原文 `Verbatim context, or would a summary do?` 与末尾保留 verbatim tail 的讨论。

交接包至少区分三种信息：目标与权限等不可丢失约束、已决定事项及理由、可重新取得的原始证据。精确文本可保留短片段或文件定位；长日志保留路径、关键错误和实际检查状态。对秘密应做脱敏，不因作者举出历史连接字符串就把凭据复制进交接包。

作者提出保留 30k–60k 的逐字尾部，试图直接减少切断信息时的损伤；其“350k 加 60k 尾部比 600k 加摘要节省 25%”来自模型计算，不是本教程实测，也不证明任意客户端具备这种压缩配置。

**原文案例：** 旧上下文中精确搜索字符串对文件补丁有帮助，PR 推进工作很少需要逐字历史。**教程补充案例：** 行动项提取器把“超时可回退，但不得宣称模型成功”遗漏于摘要，后续代码可能仍能运行，却错误标记降级状态。这是语义约束丢失，不一定产生工具报错。

## 5. 40 分钟零付费练习：交接包审计

这是教程扩展，纸面或离线文本练习；不运行 LangWatch 包装器、不连接模型、不安装依赖。只在独立临时练习目录或纸面记录使用假数据，不修改本仓库实现、不复制真实会话秘密。预算：40 分钟、0 元、0 次外部请求。

1. 用 8 分钟构造 12 条假会话事实：目标、只改某文件、禁止真实写入、一次失败测试、已否决方案、精确字段名、当前修改、下一步和未验证事项，再加 3 条无关旧日志。
2. 用 8 分钟做两版交接：A 只写“已实现提取”；B 写上述关键约束、证据定位和待验证项。分别标注每条保留事实来自哪条记录。
3. 用 10 分钟扮演新读者，回答“能否真实提交任务”“回退能否报模型成功”“是否已通过集成测试”“字段叫什么”。不知道就写未知，不允许猜测。
4. 用 7 分钟手工算一个假用量账本：旧窗口 100 单位连续读取 4 次，与 40 单位摘要后逐次增长至 40、50、60、70 单位比较。总输入分别 400、220 单位；补充压缩和重新读取成本后再判断，不将这个固定步数模型套成幂律。
5. 用 7 分钟修改 B，补充丢失信息与精确定位，并写明什么时候必须重新读权威源。

验收证据：12 条事实的保留/丢失矩阵、四个问题的回答与来源、两种账本及假设、修订交接包、至少一个未知项。通过条件是权限与关键契约不丢失、失败未被包装成成功、可定位原文、没有秘密；不是“摘要越短越好”。本次只编写练习，未执行或预填通过。

## 6. 局限与迁移条件

数据来自一位作者、一个主代码库；任务类型与窗口长度混杂，不能直接跨类型比较。效用审计依赖模型 judge，且只评分已经发生的步骤，可能漏掉后来才显现的错误。纠正用语的短语匹配不是缺陷标注，作者也可能在工作已经变差时主动压缩，因果方向未确定。

真实阈值应结合客户端压缩机制、任务长度、权限风险和自己的固定样例评测。更便宜的策略可能是避免继承无关历史、给角色更小输入和明确退出条件，而非反复微调 token 数。第 03 章用于设计上下文包；第 10 章用于记录包括返工的完整成本。

## 7. 自测与答案

**问：缓存命中后还能有上下文税吗？** 能。重复读取仍有用量及价格，多步累加仍可能显著。

**问：工具错误率没变能否说明压缩没有质量损失？** 不能。工具执行合法，目标、权限或业务判断仍可能错。

**问：为什么不能每 10k tokens 就压缩？** 压缩和恢复存在成本，频繁切断可能使整个周期都在恢复；具体下限需实测。

**问：本文的 250k–450k 是否是模型通用保证？** 不是，是作者个人观测与损失模型形成的建议区间。

**问：能否用交接包代替当前文件核对？** 不能。交接可能有损或过期，精确编辑、权限和重要契约仍需回到权威来源。

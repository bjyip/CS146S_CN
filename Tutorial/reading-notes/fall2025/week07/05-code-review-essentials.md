## 2. 团队同步：审查不只找 bug

正文列出五项作用：更新团队成员对系统的理解、确认解决正确问题、讨论设计取舍、上线前发现缺陷、保持风格与组织一致。作者把它们视为需求层次，最重视团队共同理解。

原例是 Bob 修改会计子系统，Amy 审查时更新系统理解、询问不清楚之处，Bob 解释决策；一个月后 Amy 再修改它，不必完全重新理解。mental model 指人对系统行为、责任和关系的理解，不是 LLM 参数或推理日志。

**教程扩展：** 提取器新增规则降级后，维护者应知道何时进入规则路径、200 响应表示什么、如何判断质量下降。“读过说明”不证明理解，可以让读者复述契约并指出观测入口。

作者的层次不是所有风险的固定排序。已确认的越权、秘密泄漏或数据破坏不能为了保持讨论气氛降为可选建议。

## 3. 提交前的四个问题

| 原文问题 | 中文机制 | 教程证据 |
| --- | --- | --- |
| 是否值得做 | 对齐用户问题与优先级 | 目标、需求来源和非目标 |
| 团队是否同意 | 基础设计分歧先讨论 | 已确认决定与未决问题 |
| 如何拆小 | 降低一次理解的关系数量 | 每块行为、依赖与验收 |
| 如何测试 | 作者仍对质量负责 | 正常、失败、回归的预期与结果 |

作者倾向小而精确的增量，也允许删除大量死代码。小变更不是固定行数门槛：拆分后仍需保持契约可理解；一行授权变更可能高风险，大量生成物也需核对来源。

## 4. 发送 PR：说明代码外的上下文

原文差例只说修复未初始化内存、与 Bob 聊过、编译器有困难，没有定位问题或重要性。改进例说明启动崩溃、Counter 初始化、缺陷编号、无需热修复的团队判断、结构变化、增加的测试与手工验证。

价值是帮助读者定位症状和取舍，不是用整齐格式代替证据。测试声明仍需实际基线、命令和结果；“无需热修复”属于原例情境，不是所有启动崩溃的规则。

教程改编字段：症状和触发条件、需求依据、前后行为、范围、非目标、实际与未运行检查、风险和回滚。它们服务于可验证交接，不冒充原作者模板。

## 5. 建设性反馈：具体而不隐瞒

作者反对只说设计坏、自己不喜欢或要求更清楚而不给原因，建议问负整数处理、类之间为何通信、接口变化如何影响用户。具体问句能帮助澄清规格、设计和测试缺口。

教程补足边界：已有证据的缺陷应明确写触发、影响和证据，不藏成猜谜。“B 传入 A 的 ID 时查询未绑定身份”比“想过安全吗”更可复核；尚未确认则用具体问题说明证据缺口。

审查目标是改善变更和团队理解，不是证明评审者聪明。对人不作负面评价，对行为给可检查理由；阻断发现、设计讨论和风格建议分别标记。

## 6. 样式与人工注意力

作者肯定一致惯用法有助可读性，但认为大量缩进与命名争论挤压重要工作，建议风格指南和提交时检查。文中的“90% 时间挑样式”是情境表述，不是团队实测统计。

工具适合确定性的空白、格式及部分规则，不能验证业务责任。一些惯用法承载事务或授权，先理解其行为，不能一律按“只是风格”忽略。

## 7. 受控练习与验收

预算 30 分钟、零网络、零模型调用、不创建 PR、不改原作业。为虚构变更“模型失败时回退规则并仍返回 200”写说明草案：目标、前后契约、三项待检查证据、未运行状态、风险与接管人。

再写三条假评论：阻断发现、具体设计问题、可自动化格式建议。假证据标为假设，不虚构行号或运行结果；如有第二位读者，让其复述怎样判断降级，无读者则记“独立理解验收未执行”。

验收是说明可定位、评论有理由、计划与实测分开、能解释格式检查的边界。草案完整不代表代码正确、同行已理解或可以发布。

## 8. 自测与答案

**问：描述详细就能直接合并吗？** 不能，说明是证据导航，不替代检查、批准和真实结果。

**问：所有发现都要问句吗？** 不必。确认缺陷明确陈述证据与影响，未确认项具体说明缺口。

**问：知识同步为何重要？** 维护者理解契约与责任后更易修改和接管，但不保证零缺陷。

**问：样式可以忽略吗？** 不应；确定性部分交给工具，业务惯用法仍要理解。

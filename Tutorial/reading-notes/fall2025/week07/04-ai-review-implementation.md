# AI 代码审查的落地与收益验证

## 1. 来源与目标

原文：[AI code review implementation and best practices](https://graphite.dev/guides/ai-code-review-implementation-best-practices)。署名 Greg Foster，Graphite software engineer。2026-11-05 完整读取正文、建议评估表、挑战表和 FAQ；页面只显示相对更新时间，没有可核验绝对发布日期，不据此推算。

文章是带产品宣传的实施指南，不是对照实验或当前 API 文档。图片、产品、webhook、配置文件和关联页面未验证，也没有创建 PR 或安装服务。目标是将选型、试点、反馈与人工责任变成可验收流程，不把商业结论当现行能力保证。

## 2. 实施步骤：选型、接入、定制

原文先定义漏洞、性能、样式和设计等审查对象，再分三步：选择工具、接入开发流程、调整规则与敏感度。选型要核对语言框架、工作流、定制和隐私要求，而不是仅看模型名；正文提到的四类产品没有在本批独立比较。

接入部分建议 PR 触发、严重度和关注范围、生成物忽略、团队规则与培训。文中未给各工具可直接执行的配置 schema，不能凭“支持规则”编造文件名或 webhook 事件。在本教程主线中，先定义只读输入、基线提交、允许分析范围、评论输出和人工批准责任，再考虑真实接入。

忽略生成物是减少噪声的方案，不意味着生成流程、锁文件或供应链风险可全部跳过。规则敏感度降低可能减少误报，也可能增加遗漏，需对同样的已知缺陷集合比较。试点可先自愿、只给建议；不因安装机器人就自动让它拥有合并权。

## 3. 六项实践与评论辨析

原文的六项实践是明确期望、保留人工检查、提供可行动反馈、反馈迭代、安全优先和性能核验。复杂业务与架构不能仅靠 AI，确定性样式规则可交给现有 lint/formatter，节省有风险问题的人工预算。

原建议评估表有需要加条件的地方：

| 原表建议 | 原表判断 | 本教程核验条件 |
| --- | --- | --- |
| 同步文件操作改异步 | 有效性能问题 | 需确认调用路径、阻塞影响、负载与接口变化，不能无条件替换 |
| 参数增加 null 检查 | TypeScript 已检查，无需增加 | 静态类型不验证所有外部运行时输入，须核对解析与调用边界 |
| 改更清晰变量名 | 主观但有用 | 标为非阻断建议，不掩盖安全缺陷 |
| 重构整个类层次 | 超出自动建议范围 | 核对必要性，独立讨论，不夹带进小修复 |

这是对指南建议的条件补充，不是对当前项目存在这些 bug 的断言。尤其 HTTP JSON、数据库结果或外部 JavaScript 可以不满足静态声明；不能仅凭 TypeScript 类型说 null 风险已排除。

性能部分提 N+1、重复计算、数据结构与资源使用，最终需人工确认。例如假笔记列表请求是否 N+1，应统计查询数与输入规模，而不是凭“异步更快”或代码形式定结论。安全部分关注输入、认证、SQL、文件和网络；建议本身也可能引入漏洞，必须复测。

## 4. 反馈不等于正确，也不等于在线训练

文章建议记录接受与拒绝意见、复盘误报漏报、更新配置、分享知识。接受率受便利、语气和团队习惯影响，不直接等于精确率。被接受的修改仍可能有 bug，被拒绝的真实问题也可能未解决；分别记录决定、原因与验证。

文中“持续改善”“随着更多数据学习”没有披露所有产品的训练、留存和更新实现。本批不把团队配置迭代写成模型在线微调，不从口号推断私有代码不会用于训练。云端与本地部署都需核对处理、日志、供应商与权限边界，本地运行也不是自动保密证明。

## 5. 衡量成功与宣传边界

原文按质量、过程、ROI 三组建议观察生产缺陷、事故、覆盖率、审查时间、轮次、满意度和技术债等。先记录基线和真实工作量，避免把 PR 变小、测试投入增加或团队变更全部归功于 AI。

FAQ 的“常见问题 70–90% 准确率”“2–4 周净节省”“3–6 个月比较”没有同页数据集、分母、样本量、版本或对照方法，本文仅登记为未经验证的建议/宣传，不作为承诺。覆盖率上涨也不证明业务正确；降低审查等待时间须同时保留人工核验、返工和漏报负担。

文章声称产品能理解整个仓库、自动识别瓶颈并减少噪声。本批没有检验索引、检索覆盖、SDK 或产品效果，不能据此写成仓库每个文件均已审计。

## 6. 隔离练习与验收

教程扩展：35 分钟、零网络和模型调用，只用假 PR 与纸面记录，不接 webhook、不申请账号、不创建远程评论。

1. 选“笔记列表新增分页”作为一个假变更，明确只读审查输入、责任人、关注范围、输出和不允许的合并动作。
2. 对上表四条建议补证据或待确认项，分别标阻断、设计讨论和样式建议；类型声明不能代替运行时输入验证。
3. 在十条假意见中记录三条接受、五条拒绝、两条待确认；独立确认两条缺陷，解释为什么不能据接受数计算精确率。
4. 写试点基线与收益记录空表，包含审查时间、人工验证、返工、误报、已知缺陷遗漏、成本和范围变化；全部实际测量保持未运行。

验收为试点约定、四条评论校准及指标定义。只证明计划可核验，不证明 AI 审查已提升质量或已经省时；真实试点还须确认版本、授权、代码政策和预算。

## 7. 自测与关联

**问：TypeScript 已声明非空，就不需要任何运行时验证吗？** 不能这样推断，需要检查外部输入与调用边界是否真的建立保证。

**问：接受率提高能直接证明漏洞精确率提高吗？** 不能，接受是协作决定，正确性需要独立分诊与行为证据。

**问：只读试点输出建议是否等于允许自动合并？** 不是，分析、建议、修复、批准与合并分别授权。

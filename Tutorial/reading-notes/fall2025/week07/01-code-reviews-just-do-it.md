# Code Review：先建立同行检查，再验证收益

[本周入口](README.md) | [第 07 章](../../../chapters/07-testing-review.md) | [材料总清单](../../README.md)

## 1. 来源与读取范围

- 原文：[Code Reviews: Just Do It](https://blog.codinghorror.com/code-reviews-just-do-it/)。作者 Jeff Atwood，发表于 2006-01-21。
- 核对日期：2026-11-05。完整读取正文：Karl Wiegers 的定义、作者团队经验、《Code Complete》引述、实施建议和书籍推荐。
- 未读取所链接的《Humanizing Peer Reviews》、两本书及原始研究，未读评论及推荐文章。中文教学转述不是官方译文。

这是推动团队采用同行审查的历史经验文章，不是现代 AI 审查实验。阅读目标是解释审查如何补充测试，以及为什么不能把转引数字当成当前系统保证。

## 2. 开头：第二位读者的价值

原文转引 Wiegers：作者以外的人检查软件产物中的缺陷与改进机会，包括正式检查、走查与同行桌面检查等。Atwood 根据在 Vertigo 的经验，强调代码应经过另一位开发者共同检查，并把它视为职业学习机会。

机制不只是增加人数。作者熟悉自己的假设，可能把未写出的前提当共识；另一位读者需要重建输入、状态、调用方与错误路径，可能发现缺失前提。解释设计也让维护者获得系统知识。

**教程扩展例子：** 行动项提取器在模型失败时返回规则任务。作者认为“仍有结果”就是正常，审查者追问怎样识别长期降级。即使 mock 测试接受回退，产品仍可能缺少引擎与失败类别指标。此例不是原文报告的缺陷。

独立读者不等于独立证据：多人也可能共享错误需求。仍要定位规格、代码和测试，不能以人数保证正确性。

## 3. 中段：历史检出率如何读

作者引用《Code Complete》，列举测试、设计检查与代码检查的平均检出率，并转述维护组织、Aetna、IBM、AT&T、JPL 等案例。引述中设计检查为 55%、代码检查为 60%，另有缺陷减少、资源节省、生产率和成本等指标。

这些是文章转引，不是本教程已核验的原始数据。至少需区分：

| 比较条件 | 解释边界 |
| --- | --- |
| 分母 | 全部真实缺陷、已知缺陷或某阶段剩余缺陷不是同一集合 |
| 干预 | 正式检查、日常 PR、AI 评论不是同一流程 |
| 指标 | 缺陷密度、首次正确比例、工时与费用不能合成一个效果值 |
| 背景 | 团队、语言、规模、测试方法和年代可能不同 |

检出率不能直接相加，因为测试和检查可能找到同一缺陷，也可能有共同盲区。不能由这些数字推出审查可以替代测试；没有读取原始研究时，结论限于“作者用历史案例支持采用审查”，不重新声明当前有效率。

## 4. 结尾：从倡议到可验证流程

作者认为开始的主要门槛是找一位尊重的开发者并安排时间，推荐 Wiegers 的书与样章。“每分钟审查有十倍回报”是作者倡议性判断，不是统一投资回报率。

教程改编的最低流程：固定基线，说明需求与测试范围，邀请有相关背景的读者；将评论区分为确认缺陷、讨论和待验证，再由有权限的人决定接受。没有真实同行时可练习记录，但不把独自走查或模型评论写成人类同行审查已完成。

## 5. 受控练习与验收

预算 25 分钟、零网络、零模型调用、不改原作业、不创建 PR。使用虚构说明“模型超时后返回规则任务，因此接口可用”，从行为、观测和交接各写一个问题，不虚构生产事故或已有登录系统。

为“审查有收益”设计一张未运行比较表：固定假缺陷、变更版本与匹配规则，记录审查耗时、确认发现、误报、遗漏和人工核验时间。已知假缺陷的召回不等于真实仓库召回；审查者先看答案会污染比较。

验收证据是三个可定位问题、证据需求、指标分母和未运行标记。不得把历史 60% 或十倍收益填进自己的结果。手工规划不证明实际审查有效。

## 6. 自测与答案

**问：第二个人没有发现问题，能否保证正确？** 不能，只说明声明范围内未发现问题，仍需报告缺失上下文、未运行检查及风险。

**问：检查检出率能与测试检出率相加吗？** 不能，发现可能重叠，分母和条件也未必相同。

**问：文章证明 AI 可替代人类吗？** 没有，本文讨论同行评审与历史案例，不是 AI 审查研究。

**问：如何使用未读原始研究的数字？** 标明作者转引与指标边界，不冒充自己实测或现代团队保证。

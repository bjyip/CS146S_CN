## 2. 核心概念：操作、关系与时间

原文 `Understanding Traces and Spans: Core Concepts` 将 trace 比作一次请求的完整故事，span 则是数据库查询、API 调用或函数执行等工作单元。每个 span 有自己的身份、时间和状态，通过父子关系组成请求的操作结构。

“完整故事”是帮助入门的比喻，不是完整性保证。未埋点、上下文丢失、采样或导出失败都可能使操作缺席；没有看到某个 span，不能直接判定该操作没发生。异步或批处理的关联也未必能简化为一棵父子树，原文另列 links 用来表达相关操作间的连接。

原文以结账慢说明 tracing 的作用：从跨服务关系中定位慢操作，避免逐个猜测服务。但慢 span 只是调查入口；它可能在等待其他依赖，不能仅凭耗时断言根因或保证 MTTR 下降。

**教程扩展：** 行动项提取的一次请求可以包含认证、模型调用、规则回退、持久化与响应。HTTP 成功和模型成功分开记录，才能解释“请求正常返回但模型能力已经退化”。

### 为什么不能把所有 span 时长相加

父 span 通常覆盖子操作的时间，两个子 span 也可能并行。把父子时长都相加会重复计算，把并行时长相加则误当成串行等待。端到端耗时先看请求起止；瓶颈分析再核对操作关系、时间区间和等待证据。

下面是假数据，不来自作者运行结果。全部时间使用同一假想单调时钟，单位为毫秒：

| span | parent | 开始 | 结束 | 状态/事件 |
| --- | --- | --- | --- | --- |
| request | 无 | 0 | 100 | HTTP 200，engine=rules |
| auth | request | 0 | 10 | 允许假用户 |
| model | request | 10 | 70 | error，timeout |
| lookup | request | 10 | 40 | 查询成功，与 model 并行 |
| fallback | request | 70 | 85 | 规则回退 |
| persist | request | 85 | 95 | 写入成功 |

请求用时 100 ms，各行时长相加为 225 ms，但 225 ms 不是端到端延迟。model 用时 60 ms，并与 lookup 重叠；这支持优先调查模型等待，却不证明端点本身是根因。分布式真实时钟可能存在偏差，不能把这里的假设直接套用到所有跨主机记录。

## 3. 上下文传播：关联不是授权

原文 `Trace Context and Propagation` 说明跨服务传递 trace 身份，让接收端创建相关 span；`Distributed Context Management` 提到 W3C 的 `traceparent` 与 `tracestate`。

关键不是只在日志里复制一个字符串，而是发送端注入、接收端提取上下文，并在后续同步或异步操作中维持关系。线程、任务队列或外部调用边界漏掉传播，可能出现独立 trace；日志同名也不自动修复父子关系。

**教程边界：** trace ID 是关联数据，不是认证凭据。外部传入的上下文不授予用户、工具或运维权限；是否接纳和向哪些服务继续传播，需要按信任边界决定。实际 header 格式、校验和异步 API 应核对当前官方规范与所用版本，这里不提供未经核验的实现。

原文建议用 baggage 携带错误上下文。本教程不把它作为默认做法：跨服务传播可能扩大泄露，原始会议内容、token、完整异常和用户身份不应随意放入 baggage、tracestate 或属性。优先保存必要的脱敏错误类别与本地证据引用，并明确字段、接收方与保留期限。

## 4. 属性、事件与错误：保留不同层的结果

原文 `Span Attributes and Events` 列出名称、时间、状态、属性、事件和 links。名称描述稳定的操作类别，属性解释条件，事件记录操作中发生的事情，links 记录相关操作；它们不是越多越好。

在上面的教程假例中，model span 保留超时错误，request 记录规则引擎与明确降级结果。即使请求按契约返回 200，也不能把子操作错误抹掉。是否将请求标为业务失败，取决于 SLI 定义，而不是直接继承所有子操作错误。

日志保留相应 trace/span 关联信息，可跳转到具体操作；指标汇总超时率和回退率，exemplar 可指向部分代表性 trace。关联帮助找证据，不证明语义输出正确；仍需质量标注或约束检查。

原文用用户 ID 等属性说明排障价值。本教程建议先判断必要性和数据政策；稳定操作名也不应直接嵌入用户 ID、完整 URL 参数或笔记正文。字段数量、长度和基数都影响成本与隐私，控制 span 粒度比“每个函数都埋点”更重要。

## 5. 采样：节省资源，同时制造观测边界

原文 `Sampling Strategies` 对比三类策略：

| 策略 | 决策位置 | 主要取舍 |
| --- | --- | --- |
| Head | 请求开始附近 | 提前控制记录量，但事后不能恢复已丢弃细节 |
| Tail | 观察请求后再决策 | 可按错误或慢请求选择，但需缓存、等待和资源预算 |
| Priority | 按重要操作等政策选择 | 依赖具体配置与实现，不是天然保留所有重要请求 |

Tail sampling 不保证捕获全部错误：上游未记录、缓存溢出、迟到 span 和导出失败都可能造成缺口。名称叫“优先采样”也不证明策略确实生效，需要记录配置与保留结果。

**教程假例：** 一个窗口有 100 次请求，8 次模型超时；错误优先策略保留 8 次超时和 2 次正常 trace。保留集合中的超时占比为 80%，全窗口模型超时比例为 8%。不能用有选择偏差的 trace 子集直接填全体 SLO 分母；应取得相应全量聚合计数，或明确统计方法与偏差。

采样与删减不能解决所有合规问题。trace 可能不全，访问与保留政策也未必满足要求；它不能自动替代完整、受保护且可追责的安全审计。

## 6. 工具与 SDK 示例的可用性边界

原文 `Tracing Implementation Guide` 介绍 OpenTelemetry 及不同收集、处理、存储和展示工具；这些职责可分层组合，产品列表不是当前选型或价格保证。

Node.js 示例定位为简化示例，没有锁定版本，且存在需要实际核验的点：

- 示例引用 `SpanStatusCode`，但可见导入未包含它，不能当成已可运行代码。
- `startSpan` 的选项中写入 `parent: span`，不应假定这就建立了当前 SDK 所需的父上下文；需核对真实 API、active context 与传播测试。
- `addSpanProcessor`、provider 初始化及 exporter 生命周期需要匹配具体版本；注册与代码展示不能证明导出成功。
- 异常、结束和 shutdown 路径应独立检查，避免丢失结束事件或尚未导出的记录。

本篇不复制该例为通过校验的教程 JavaScript，也未验证这些 API 的当前契约。后续实现应固定依赖版本、检查官方文档，在隔离环境验证父子关系、超时/回退记录、导出失败和退出处理。

## 7. 离线练习与验收

预算 30 分钟、零网络、零模型调用、零安装，不执行原作业或安全/生产操作。使用第 2 节假表，不上传真实遥测。

1. 画父子关系并标注并行区间，计算 request、model 与各行总时长，解释为何三个数不能互换。
2. 分别写 HTTP、模型和业务质量的结论；未知质量保持“未测”，列出一条模型慢的反证需求。
3. 假设 lookup 的上下文丢失，列两条定位所需证据；不能把“无关联 span”改写成“未调用”。
4. 使用第 5 节采样假例，分别算保留子集和完整窗口比例，说明全量分母来自哪里、未取得时不能报告什么。
5. 设计五个必要遥测字段和三项禁止记录的数据，再写每请求 span 数量、属性长度与保留时间的假设预算；不声称该预算已经实测合理。

验收保存关系图、计算过程、分层结论、传播缺口和字段/预算表。预期数值为 100 ms、60 ms、225 ms，以及 80% 和 8%；其余验收要求区分事实、假设与未知。练习只检查分析设计，不证明真实 SDK、采样、脱敏或故障恢复有效。

## 8. 自测与答案

**问：所有 span 时长之和就是请求延迟吗？** 不是，父子覆盖和并行操作会重复计时，需要看时间区间与依赖关系。

**问：HTTP 200 能把 model timeout 改成成功吗？** 不能。请求可能按降级契约成功，但模型操作仍失败，质量指标另行定义。

**问：错误优先采样的错误率能作为全体错误率吗？** 不能直接使用；选择偏差改变了分母，需要完整聚合计数或明确的估计方法。

**问：trace ID 可以代表合法用户吗？** 不能，它只用于关联；认证授权仍由实际身份与资源政策决定。

**问：Tail sampling 与 tracing 审计可以保证完整记录吗？** 不能，采集、缓存、传播和导出都可能丢失，审计还需要独立完整性与保护要求。

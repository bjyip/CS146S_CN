## 2. 排障为何不能只看当前 Pod

引言列举 CrashLoopBackOff、OOMKilled、ImagePullBackOff 等错误状态，强调系统动态变化使调查困难。“The Kubernetes Troubleshooting Struggle” 分三类问题：噪声告警、短生命周期资源导致上下文丢失、多源观测数据难以对齐。

教程机制解释：当前状态只是一刻的观测。Pod 被替换、容器重启或事件过期后，旧实例发生了什么未必能从当前实例恢复；但不能把文章“线索都消失”的修辞当绝对事实，保留日志、事件和历史遥测可以提供证据，具体能力依赖配置和保留策略。

| 文章的问题 | 教程需要区分的事实 | 可能的错误推断 |
| --- | --- | --- |
| 告警很快自动消失 | 控制器重建后当前状态正常，不等于触发原因消失 | 一次恢复就关闭调查，忽略周期性重启 |
| 实例短暂存在 | 旧 Pod UID、容器、节点和时间窗可能与新实例不同 | 把新实例日志当旧实例的失败证据 |
| 数据分散且很多 | 不同指标、日志、事件的时钟、版本与粒度需对齐 | 将全局平均正常当作受影响服务正常 |

状态名称不是完整根因。CrashLoopBackOff 指向重复失败后的退避情形，不直接告诉你是启动配置、依赖、内存还是应用异常；ImagePullBackOff 也不能仅凭名称判断为凭据问题。这些术语解释为教程补充，本轮未读取 Kubernetes 规范，不提供版本特定命令。

## 3. 三类产品机制与验证边界

“How Agentic AI Changes Troubleshooting” 介绍持续调查、知识图谱与跨遥测筛选。作者希望 Agent 在告警发生时先组织证据，让值班者从可行动线索开始，而不是逐个打开所有仪表盘。

知识图谱将 Pod、节点、服务、入口与 API 等资源关联；文章举跨命名空间内存异常、节点负载不均、后端依赖级联为调查方向。图能帮助选择检查对象，不直接证明因果；构建方法、关系更新、遗漏率、权限策略与完整评测均未在本文披露。

跨遥测筛选涉及指标、日志、Kubernetes 事件、配置变化、基础设施信号与部署历史。结构化摘要可以减少阅读负担，但若把工具失败、截断或反证滤掉，就会制造不完整的“清晰故事”。教程要求保留原始定位、时间窗、实例版本、查询状态和未知项，而不是只保存最终总结。

文章前段说伙伴能主动解决问题，但后文把“在人类批准边界内自动修复”和“准备执行修复”描述为未来能力。两种说法存在范围/时态差异：可据正文解释调查与建议目标，不能据营销开头认定自动修复已经发布，更不能推定 2026 年的当前能力。需要操作时须另外核对产品文档和权限。

## 4. 假想演示不是事故复现

“Agentic AI in Action” 以假想 Pod 崩溃展开四步：重建事件时间线、比较集群关联异常、运行调查工作流、在有依据时给修复建议，否则列出下一步。正文没有完整事故数据、工具请求、源码、trace 或修复前后对照，不把故事写成实测 MTTR。

原文有“是否因 CPU 或内存限制而 OOMKilled”的假设措辞。教程应拆开：OOMKilled 指向内存相关终止线索，CPU 约束可能影响延迟或健康检查，但不能仅据 CPU 限制确认 OOM 根因。确认还需终止原因、对应实例的内存观测与环境证据；此辨析是教程扩展，不代表已复现文章场景。

“运行自动调查”与“修改生产系统”不是同一种授权。只读查询也可能读到秘密或产生平台负载；重启、扩容、改限额与部署则增加副作用。文章没有给出足以直接执行的授权/回滚契约，不在本教程生成一键修复指令。

## 5. 产品宣传不能变成验收结果

“无需人工收集/升级”“无噪声”“每时每刻专家”“让值班无压力”等是产品定位。文章未提供样本、对照、失败案例、误报与遗漏、查询成本或确定性判断错误率，不能推为真实保证。

过滤噪声必须保留高风险未知，自动消失的告警也可能提示周期性问题。团队交接责任、访问审批与事件保留不会因为接入 Agent 自动消失；隔离实验与生产验收需分别设计。

## 6. 受控练习：保留实例身份与竞争假设

预算 40 分钟、零网络、零费用、零模型与集群操作，仅用教程假数据。本轮未执行练习。

假证据：10:00 旧 Pod `pod-old` 的容器报告 OOMKilled；10:01 新 Pod `pod-new` 健康；旧实例崩溃前两分钟内存接近其限额；同节点 CPU 图有尖峰；旧容器日志查询超时；一个旧 runbook 建议“直接调大限额”。所有标签与时间均为虚构，不是真实资源标识。

1. 用 10 分钟写事件表，分别记录观测时刻与事件时刻、Pod UID、容器、节点、版本及来源标签；新实例健康不能覆盖旧实例故障。
2. 用 15 分钟保留“请求规模导致短期内存峰值”与“持续内存增长”两个假设，各列支持证据、反证需求和最多两项只读检查。CPU 尖峰是另一条线索，不能独立确认 OOM。
3. 用 15 分钟记录日志超时与证据缺口，为提高限额建议写批准者、节点容量、预算、回滚及恢复检查要求，但不执行。旧 runbook 是待复核材料，不是新授权。

验收：实例身份未混用，事件顺序可追溯，至少两个竞争假设，查询失败未写成“没有异常”，新实例健康未写成“根因解决”；修复提案与实际动作分开。局限：纸面设计不验证集群状态、图谱准确性、数据保留或真实权限。

## 7. 自测与答案

**问：Pod 自动恢复为何仍可能要调查？** 控制器恢复当前状态不证明触发原因消失，也不排除重复失败；需对照实例身份与时间窗。

**问：为什么不能用新 Pod 日志证明旧 Pod 没有错误？** 两者身份与生命周期不同，新实例没有旧错误并不等于旧实例健康。

**问：知识图谱关联节点能否证明节点导致故障？** 不能。关联帮助选择证据，因果仍需支持、反证与版本检查。

**问：文章说自动修复，是否可以直接给 Agent 写权限？** 不可以。正文将相关能力部分表述为未来方向，且没有完整授权契约；实际写权限需要独立批准与副作用控制。

**问：CPU 峰值是否足以解释 OOMKilled？** 不足。要检查内存、终止原因和对应实例证据，CPU 线索不能替代内存根因验证。

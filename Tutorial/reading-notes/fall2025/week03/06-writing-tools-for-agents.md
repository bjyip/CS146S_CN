## 2. What is a tool：接口还需要便于选择

作者把工具视为确定性系统与非确定性 Agent 的契约。这里不是说外部天气或网络结果永远不变，而是输入校验、处理步骤和输出责任应明确；模型仍可能不调用、选错、参数错误或误读结果。

工具的可用性因此包括发现、选择、参数生成、结果理解与下一步组合，不只看函数单独返回正确。所谓 ergonomics 是让任务分解更直观、错误更容易恢复，而不是增加自然语言说明即可保证可靠。

## 3. How to write tools：原型、任务与证据循环

原型先接真实文档、手工测试并收集用户目标，再建立评测。原文较强任务包括：找 Jane 的可用时间、附项目笔记并预订会议室；调查客户一次购物被扣三次并检查其他受影响者；分析取消原因和挽留方案的风险。弱任务直接给了地址或查询条件，绕过选择和组合难点。

现实任务复杂度不要求使用真实生产秘密。教程可在隔离假数据中保留重名、缺失记录、权限拒绝和多步失败，避免过于简单的模拟把难点删除。原文列的是评测任务，不授权真实支付、邮件或客户操作。

每项任务要有可验证结果；允许等价正确路径，不把唯一工具序列硬写成答案。可以记录成功率、调用数、token、耗时和错误，但应分别统计工具执行与最终任务。开发集用于优化，留出集用于验收，不能反复用验收集调描述后称泛化改善。

原文建议分析推理和反馈，也明确模型未必描述真实原因。工程上优先保留工具请求、响应、后置状态与简要决策说明，不把生成的推理文字当执行或正确性的证据；记录还须脱敏并遵循数据政策。

## 4. Choosing tools / Namespacing：在服务端减少无谓工作

原文以 `search_contacts` 代替读取全地址簿，以 `search_logs` 返回相关行，以 `get_customer_context` 合并相关客户信息。目的不是把所有动作合成一个超级工具，而是在明确边界内减少模型反复读中间数据。

日程工具可以整合可用时间和预订，但真实写入仍需权限、审批、幂等和部分失败处理。工具命名可按服务或资源分组；前后缀哪个更好应由实际模型与任务评测决定，不是协议规定。含糊的 `user` 应区分 `user_id`、姓名或查询词。

## 5. Meaningful context / Token efficiency：缩短与可组合兼顾

作者强调高信号字段，可读名称比难懂 ID 更利于解释，但后续工具仍可能需要技术 ID。原文 Slack 例子在 detailed 返回 `thread_ts` 等 ID，concise 只返回内容；要取线程回复就不能凭空补 ID，应重新读取足够信息。

`concise`／`detailed` 是一种输出策略，不意味着本教程必须隐藏必要 ID。格式选择也没有一刀切答案，应比较任务正确性和真实 token。文章 206／72 token 及默认 25,000 token 都是其历史例子或产品叙述，不是当前通用限制。

分页、范围、过滤与截断需合理默认值，截断应提示怎样缩小查询。错误说明应给出合法输入或恢复方向，不泄漏 traceback 和凭据，也不把权限失败改写成可无限重试。

## 6. Tool descriptions：隐含业务知识显式化

像向新同事解释一样，写清查询语言、术语、输入输出及资源关系，并用严格数据模型强制必要约束。原文 web search 例子是模型无谓附加 `2025`，改描述可纠正搜索偏差；这不证明所有年份过滤都错误，应按用户时间需求判断。

工具注解披露只读或破坏性意图，不是执行控制。工具描述、schema、实现和授权测试应一致；模型可协助改进，但不能自己证明自己的契约正确。

## 7. 受控练习与验收

预算 40 分钟、零模型费用、零网络，以“找到发布笔记并读取其行动项”为目标，准备重名、无结果、跨用户拒绝、长正文四条假数据任务。先给宽泛列表工具，再设计搜索／读取契约；只改变结果粒度，不同时更换模型或任务。

验收为任务预期、合法等价调用路径、ID 来源、截断与错误样例、开发／留出划分和指标空表。手工走查可发现契约缺陷，但不填写真实成功率或 token 节省；以后运行评测需单独确认模型、费用和数据政策。

## 8. 自测与答案

**问：为什么不能只测函数输出？** Agent 还需选工具、生成参数、解释结果并完成目标，函数正确只是一个层次。

**问：留出集可以反复用来优化描述吗？** 不应如此；被用于优化后就不再是独立验收依据。

**问：模型反馈说执行成功是否足够？** 不足，应核对实际调用、响应及需要的后置状态。

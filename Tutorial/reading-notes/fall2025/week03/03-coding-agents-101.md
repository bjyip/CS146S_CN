## 2. Prompting Basics：降低决策自由度与搜索歧义

原文的五项基础建议是说明怎么做、指出起点、防御性提示、提供检查反馈和发挥人的专业知识。它们分别解决不同不确定性，不是五种同义的提示措辞。

说明“如何做”是在复杂任务开始前交代整体架构和偏好的路径。例如只说“加单元测试”，Agent 仍需要猜测测试对象、边界和哪些依赖应该 mock。指定功能、重要边界与 mock 范围，使审查者能提前知道实现应该遵循的方向。简单任务可以直接描述目标，原文没有要求每个改动都写逐行计划。

指出起点是在提供可验证导航，而非直接提供结论。原例要求支持 Google 模型，并给最新文档与模型组目录。目录帮助定位，文档帮助校准 API 版本；两者不能证明当前依赖已经支持某个方法。教程补充：读到文档与本地依赖版本不一致时，应保留冲突而不是拼接用法。

防御性提示是预判新人会误解的地方。原例提醒修 C++ 搜索绑定后可能需要重新编译再测试：否则测试可能仍在使用旧产物，给出“没修好”或“通过”的误导反馈。这里改变的是反馈对象的真实性，不是增加模型的意志力。本教程只解读例子，没有编译该绑定。

CI、类型检查、lint、单元测试提供不同反馈：类型约束发现某些不兼容调用，lint 检查明确规则，测试观察特定输入下的行为。原团队由非类型化 Python SDK 转向类型化 SDK，是其经验案例，不意味着必须迁移此教程的语言或框架。反馈要包含正确工作目录、环境与实际结果；未执行的命令清单不算反馈。

人的专业知识负责理解目标、判断证据和最终正确性。将 Agent 类比初级伙伴，是提醒决策不可靠，不是测量其真实资历；中文版把这一比喻弱化为“需要明确上下文的编码搭档”，本篇保留原文的决策风险含义。

## 3. Using Agents in your Workflow：减少注意力切换，保留集成成本

原文列即时委派新任务、移动访问、交出杂务、比较两个实现和 PR 预览部署。机制是将可独立处理的工作异步推进，人继续当前任务，随后集中审查。它减少的是人的同步占用，不一定减少总计算量或端到端时长。

原案例包括 Slack 标记 Devin、发布后更新文档、比较 Lexical 与 Slate 的文本框实现，以及用 Vercel 提供预览。作者选择 Slate 的结果只支持他们的场景，不是两库普遍优劣。两条原型分支仍需要同一需求、数据和验收规则，否则比较可能只是“哪个看起来更漂亮”。

预览 URL 让前端结果可见，但不能验证持久化、身份权限或失败路径。移动触发也不表示该任务获准接触生产。教程补充：任务卡应区分“只研究”“生成草稿”“允许修改测试副本”与“允许外部写入”，避免将便利入口变成扩大权限的理由。

## 4. Delegating Larger Tickets：初稿与检查点是不同交付状态

原文将通常需要 1–6 小时的中大型任务视为较高收益区域，并用记者/编辑、厨师/副厨师、Agent 初稿/人工完善作类比。关键不是完全免手动，而是将起草与最终审核拆开。约 80% 时间节省是作者建议的现实目标，正文没有样本、时间口径或对照方法，不能写成已测收益。

任务模糊时共同开发 PRD：先问认证怎么工作、哪些服务受影响，再让 Agent 提出具体代码目标供人核对。研究结果应能追到文件和当前版本。规划模式只是产品入口，不能假设其天然阻止所有副作用；本次未读其权限实现。

作者给出的循环是 `Plan → Implement chunk → Test → Fix → Checkpoint review → Next chunk`。检查点在错误扩散前核对依赖，不是把同一大任务任意切成几段。原例先规划数据库 schema，由人应用迁移，再实现后端和测试，最后接 Web 与移动前端。这里数据库迁移明确交由人，不应译成 Agent 自动迁移上线。

教程补充：审批绑定具体规格与差异；修改 schema 后，旧的后端验收与批准需要复核。实现一个分块并不能证明下游已适配，检查点可以拒绝继续而不是只记录“已完成”。

“教它验证”是把常用验证步骤变成可重用知识，而非只说函数不工作。对 Agent 频繁修改的热点补测试，能提供更强反馈。原例在 Python 转 C 的关键区域先加强单元测试；测试集合本身仍可能漏掉边界。原文把可靠测试与放心合并关联，本教程不将其泛化为测试通过即可无条件合并。

## 5. Automating Workflows：事件触发不等于事件授权

原文建议将功能标志移除、依赖升级、补测试等重复工作编码为模板；Devin 称之为 playbooks。原客户例是在新功能开发时触发三个测试 Agent，体现重复任务的自动起草，不证明三者独立、并行更快或结果覆盖更全。

原团队将常见错误列表保存在仓库，让 Agent 对每个新 PR 检查。列表是审查上下文，区别于能确定执行的 lint 规则；模型可能漏报、误报或解释规则不一致。教程补充：能编码为确定性检查的约束仍优先交给检查器，Agent 用于补充需要上下文的审查，不用一句“通过”替代门禁。

事故或告警可触发调查，但原文明示 2025 年 AI 生产调试能力有限，更实用的任务是标记可疑错误与变更，而非自动修到上线。调查候选与确认根因必须分开；没有数据库或日志证据时保留未知。MCP 能取得日志，不自动给予修复权限。

## 6. Customization：环境、工具与过程知识分别负责什么

环境对齐包括语言版本、依赖和自动检查，防止 Agent 在与工程师不同的条件下得到不可比较结果。原文还建议预认证浏览器和自动加载秘密配置，这是便利性经验，不是本教程的安全做法或执行授权。本次没有配置账号、读取秘密或执行其 shell 示例。

自定义 CLI/MCP 负责可重复的具体动作，例如按 Linear 工单 ID 取信息或重启开发环境。原例 CLI 只展示测试套件第一个失败及详细信息，帮助 Agent 聚焦。它降低反馈噪声，却可能隐藏后续失败；教程补充：阶段性修复后仍需完整套件验收，不能把首个失败消失当作整体通过。

知识库保存项目架构、任务对应测试、工具和常见错误。原例记录新增服务路由时前后端所有必需位置，使跨层工作可重复。知识是需要维护的过程说明，不是持续训练底层权重；具体自动加载与持久化机制要按客户端核验。过期测试命令会使可复用流程反而传播错误。

英文第四条注释称 Devin MCP 当时处于 beta、需要联系获取；中文版未保留这条限定。不能据中文“广泛可用、设置快速”推定 2026 年当前支持状态。其他产品、预览和移动示例也只是原文历史陈述。

## 7. Practical Considerations：失败恢复与最小权限

作者分开讨论有限调试、细粒度视觉推理与知识截止。更完整日志和系统关系才能区分根因；设计系统提供可复用组件减少视觉猜测；新版库需要指向当前文档。文档访问不保证使用正确，组件复用也不替代桌面/移动和失败状态验收。

止损建议包括早停、分散尝试、无进展时新会话。其机制是限制在错误上下文上持续投入的损失，不是要求每次失败都放弃。重开必须带完整约束并核对当前工作区；否则旧任务的部分改动仍存在，所谓“新起点”可能只是遗忘了副作用。

安全建议为 Agent 专用账号/自定义 IAM、开发或暂存环境、尽可能只读 API key，并让人执行外部服务交互脚本。一次性邮箱不是安全隔离，暂存也可能含真实用户数据；实际权限由身份、资源和执行端控制。预认证便利与只读隔离需要按场景权衡，不应把同文不同建议拼成“带生产登录的安全沙箱”。

作者结尾强调工程师继续拥有系统理解、判断与责任。这是职业与组织观点，不是保证所有任务都适合多 Agent，更不是无人批准的 software factory 已实现。

## 8. 教程补充案例：分页需求的委派卡

以下是假数据案例，不来自 Cognition 的实际项目。目标为“笔记按创建时间降序、同时间按 ID 降序”，原字段名不变。卡片分成五个字段：入口与版本、当前行为、目标/非目标、允许范围、验收/停止条件。

第一检查点只读研究，找路由、查询和测试，排序未确认则暂停。第二检查点起草后端差异和失败样例，不能修改数据库或部署。第三检查点核对前端使用与独立验收，没有真实日志就写未运行。失败反馈是“样例同时间顺序与契约不符”，不是“你再努力一点”。

如果两个方案同时比较，一个改偏移分页、一个改游标，必须先确认公共 API 是否允许改变；否则速度和预览观感不能成为选择依据。预算把人工审查、总等待和集成返工单列，不能将异步期间人在做其他事的时间直接算成 AI 节省。

## 9. 零执行练习与验收

教程扩展，预算 45 分钟，零网络、零模型费用、零工具执行、零应用/数据库/账号操作。只写纸面任务卡与证据表，不运行源例或修改原作业。

1. 用 10 分钟将“加单元测试”重写为入口、目标、三条边界、mock 范围、非目标和未知项；未知版本不能伪填。
2. 用 10 分钟为分页任务设置研究、后端、前端三道检查点，写每道可继续的证据和必须暂停的条件。
3. 用 10 分钟分类三条假反馈：“只展示首个测试通过”“PR 预览可打开”“模型称全部完成”，列还缺哪些验收。
4. 用 10 分钟走查无进展重开会话：保留规格、当前差异、失败、权限和预算，不删除旧工作或遗忘部分写入。
5. 用 5 分钟将原文 80% 节省、客户三 Agent、只读 key 与预认证分别标成经验主张、案例或权限设计，避免填成实测。

验收产物是一张委派卡、一张检查点/证据矩阵与一份止损交接。必须满足：目标可核验，测试和预览的证据边界不同，模型自述不充当执行日志，旧失败保留，权限不因重新开始而扩大。没有实测只标“理解走查完成”，不填功能通过、准确率或收益；全部练习本轮未执行。

## 10. 自测答案与教程关联

**问：提示里详细写“怎么做”是否足以保证正确？** 不足；它约束意图，真实版本、检查反馈、独立验收与人工责任仍需要分别落实。

**问：为什么先重编译再测试重要？** 原例涉及编译产物，旧产物的结果可能不对应当前修改；反馈对象必须绑定实际差异。这里没有实际构建证据。

**问：只显示第一条失败是否能替代完整套件？** 不能；它是聚焦反馈的工具，阶段性修复之后仍需整体回归和未覆盖边界。

**问：新会话自动恢复干净环境吗？** 不会；上下文与工作区是不同状态，部分修改和外部副作用可能仍在，需交接和核对。

**问：80% 时间节省和 1–6 小时适用范围是承诺吗？** 不是；均为作者的经验目标/任务划分，缺乏本批独立评测，不外推为普遍收益。

## 2. 第 3–5 页：先定位，再跨文件改变

第 3 页介绍安全、产品、前端、API、基础设施和性能团队的日常使用。原文宣称效率与质量改善，但没有给出可复核的样本、标签、分母或基线；内部采用不是因果证明。

第 4 页的代码理解包含定位功能入口、模块关系、数据流与失败传播。原案例包括从 stack trace 寻找认证路径、寻找相同 bug、理解 Terraform 与 Python 的关系。Agent 给出的文件只是候选证据，需要回到实际定义、调用方和版本确认；一份流畅的架构摘要不证明完整覆盖。

教程补充：行动项提取超时后仍返回成功，先追踪路由、提取服务、规则回退和响应字段，标明真正执行的引擎；不要只问“为何模型成功”。生产 trace 可能包含秘密，原文提到粘贴 trace 并不授权上传真实用户数据。

第 5 页讨论重构、API 或依赖迁移、拆分大模块和跨文件模式更新。原案例用新服务模式替换 `getUserById()`，以及先列旧模式影响再创建修复 PR。结构相关改动不适合单纯字符串替换，但 Agent 同样可能漏掉间接调用、外部消费者和生成源。

教程补充：更改负责人字段前列出接口、schema、持久化、前端及失败行为，明确非目标与回滚。自动一致修改只说明形式一致，不证明新契约正确；创建 PR 也不是合并或发布授权。本轮未执行重构或远程写入。

## 3. 第 6–8 页：性能、测试与交付是不同证据

第 6 页建议分析昂贵查询、重复操作、循环、内存和废弃模式，生成批量查询或缓存候选。工程师自述“五分钟提示节省三十分钟”没有测量方法，不能当普遍六倍收益。解释“更快”不是基准结果；缓存还可能改变一致性、身份隔离和失效策略。

教程补充：为假笔记列表比较逐项查询与批量查询，预先固定输入规模、排序、权限和错误契约，分别记录查询数、延迟及内存；未运行时全部留空。减少查询不自动证明端到端变快或没有数据泄露。

第 7 页使用低覆盖模块、空输入、最大长度、异常但合法状态来生成单元、集成和属性测试。原案例包含夜间生成测试 PR、另一分支工作时启动 CI。这些是团队使用叙述，不代表本教程已启动后台任务，也不证明生成测试有效。

测试预期须来自规格或独立标签。排序属性例如输出保持原元素且符合顺序，但它不能独立验证全部业务语义；错误实现与错误断言可以一起变绿。读测试差异、加入区分错误实现的反例，才能建立比“新增测试数量”更强的证据。

第 8 页谈脚手架、API stub、遥测、配置、发布前小修复和根据产品反馈写初稿。原例有后台工作期间合并四个 PR、处理三四个积压修复；数量不等于客户价值或安全性。遥测是否会发送敏感输入、配置是否改变权限、脚手架是否包含真实凭据仍需独立审查。

## 4. 第 9–10 页：保持专注不等于自动完成

第 9 页把偶遇的小问题、未完成笔记和探索任务放入队列，稍后回来检查。原案例提到 Slack 线程、Datadog trace 与 Issue；这些都可能含不可信指令和私有信息，数据面不能自动变成授权面。

补充案例：发现标签过滤问题时记录任务、基线、复现前提、允许文件与剩余预算，而不是在另一个 Agent 改同一接口时直接重写。队列是一份待办记录，不保证工作已启动、可恢复、完成或无副作用；重新打开对话也不恢复进程和数据库状态。

第 10 页讨论探索事件驱动等替代设计、查找相似 bug、扩展规格遗漏。候选方案用于识别权衡，不是凭一种风格名称重构全库的理由。一个 bug 修复后检索类似模式有价值，但必须逐处确认调用前提；相似字符串不等于同一缺陷。

## 5. 第 11–12 页：六条实践及历史边界

| 报告建议 | 机制与不可推导的结论 |
| --- | --- |
| 大改动先 Ask Mode 规划，再 Code Mode | 分开研究与实现；报告里的模式名称不保证现行客户端存在相同按钮 |
| 任务约一小时或几百行 | 经验性的可控范围，不是可靠性阈值；小权限改动仍可能高风险 |
| 迭代启动脚本、环境变量和网络 | 环境影响可执行性，但增加互联网或凭据不能当默认修复；先核对权限和错误根因 |
| 按 GitHub Issue 结构写提示 | 提供文件、模块、差异、文档和参考模式，减少歧义；旧文档仍需版本核对 |
| 队列作为轻量 backlog | 保留零散任务与部分工作；排队不等于执行、完成或批准 |
| 用 AGENTS.md 与 Best of N | 持久上下文及多个候选帮助探索；规则文件加载语义、功能资格和多候选收益未在本批验证 |

Best of N 的筛选本身也消耗人工与调用预算。多个答案可能共享盲点；挑出看似最好的一份不能证明独立正确率，拼接候选后必须重新检查组合契约。报告结尾称 Codex 仍在 research preview，必须保留为历史描述，不能写成 2026-11-05 的当前状态。

## 6. 40 分钟零执行练习

教程扩展，零网络、模型、程序、CI 和 PR 执行，只做假数据纸面走查，不上传真实 trace。

1. 0–10 分钟：为“提取超时仍返回成功”写入口、调用路径、引擎字段、证据定位和未确认项，区别架构摘要与观察事实。
2. 10–20 分钟：为负责人字段迁移列允许修改文件、外部调用方、生成源、失败预期与回滚；留一项未知契约，不假定全部消费者已找到。
3. 20–30 分钟：为排序测试写独立预期及一个错误实现反例；为缓存候选写身份隔离、失效和基准空表，不填耗时。
4. 30–40 分钟：比较单候选与三个候选的预算计划，记录人工筛选、共享盲点、组合复验和停止条件；对只有“已排队/CI 全过”而无输出来源的任务卡要求补证据。

验收为数据流卡、迁移边界表、反例和预算交接表，不是产品收益、测试成功或真实后台执行证据。

## 7. 自测与章节关联

**问：为什么报告里的收益案例不能证明现行产品普遍更快？** 没有独立对照、样本定义或当前版本，且工程师自述与内部推广可能有选择偏差。

**问：Best of N 的三份相似答案是三份独立证据吗？** 不是，模型、上下文与筛选者可共享盲点，合成后也需重新验收。

**问：写了 AGENTS.md 或启动脚本就能算环境验收吗？** 不能，文件存在、客户端发现、命令执行与行为验收是不同层次；本批均未运行。

**问：覆盖率增加是否说明授权与需求正确？** 不说明，必须检查预期来源、跨身份反例和未覆盖行为。

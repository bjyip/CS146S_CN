## 阅读目标

能按任务的实际失败模式选择提示技术；区分示例、证据、推理解释与执行日志；能说明为什么“更强的角色”“五次多数意见”和“带引用的回答”仍不能代替验收。

## 1. 第 1–5 页：自然语言接口不是形式保证

第 1 页给出课程与讲者，第 2 页进入高效提示主题。第 3 页称提示是人与 LLM 交互的通用语言，备注将其放进编程语言演化的叙事。这个类比说明表达任务的方式变化，不表示自然语言已经具有编译器一样的确定语义，也不表示过去的软件工程方法被替代。

第 4 页以搜索引擎交互作类比：备注提到从布尔表达式转向自然语言搜索。可读到的是这个类比，不是图片中具体的查询、界面或演化时间线。搜索说得自然与搜索结果正确是两回事；同样，提示说得流畅也不意味着模型获得了完整需求。

第 5 页称提示兼具艺术与科学，并提到部分技术曾经通过实验改善表现。可迁移的做法是把“这个提示更好”变成可证伪假设：固定任务、数据与模型条件，检查错误、成本和重复运行。此页没有实验数据集、基线、效应量或置信区间，不能把笼统的经验论断当成当前所有模型的提升保证。备注说 Coding IDE 会追加提示，不能据此推断其现行请求正文。

## 2. 第 6–8 页：零样本与少样本是在减少不同歧义

第 6 页的零样本案例是用 Rust 遍历字符串列表，只打印偶数索引的值；备注还给出用 C 实现堆分配器的要求。零样本是没有提供任务示例，不等于请求没有约束、system 消息或模型没有相关训练知识。Rust 案例还需要明确索引从零开始、空列表行为和所用版本；这些是教程补充，不是课件已写出的条件。

第 7 页的 k-shot 指提供 k 个完成任务的示例，也称 in-context learning。示例影响本次推理上下文，不是立即修改模型权重。课件列 1、3、5 及一些经验支持，备注强调企业专有 API、特殊命名风格，并建议避免熟悉的通用任务和过多示例。合理读法是“先判断示例是否提供新信息”，不是所有通用库任务都禁止示例，也不是固定用五个就最优。

第 8 页对比“按仓库规范写循环”与提供命名样例后的请求。正文中的大小写混合变量名和混合语言语法是说明性素材，不能直接当作合法代码执行。备注将改进前后标成红/绿；本轮读到了该说明，但没有验证实际颜色。示例的价值是展示原请求未提供的规范，而不是证明这种命名方式值得推广。

教程扩展：行动项提取时，同时给出“已完成发布”的非任务例和“明天请发布”的任务例，用来澄清时态与执行意图。示例应来自开发集，最终验收题保持独立。否则漂亮的测试结果可能只是提示内答案泄漏。

## 3. 第 9–11 页：把推理变成可检查的中间对象

第 9 页介绍 Chain-of-Thought（CoT），区分带推理示例的多样本方式与“逐步思考”的零样本方式，还建议显式标签。备注称它是许多推理模型的重要方法。这是课堂机制概括，不能把可见解释当成隐藏内部计算的忠实日志，也不要求索取不公开的内部思维。工程上可要求简短方法、边界条件与可复算结果。

第 10 页要求判断一个数是否同时为完全平方数和完全立方数，并用求最大值、判回文的步骤作为示例。示例演示的是说明方法的形式，没有给出目标函数实现或边界测试。教程补充的检查问题包括：只接受非负整数吗、零如何定义、浮点开方会否误判。对于非负整数，两种性质同时成立对应整数的六次方；这是数论解读，不是原页展示的答案。

第 11 页的任务是最长递增子序列（LIS），要求编码前分析子问题并举子数组例。需要注意：子序列不要求连续，子数组通常要求连续。原页的 subarrays 措辞可能让实现跑偏；清晰的改写应明确“索引顺序递增、可以跳过元素、严格递增还是非递减”。教程例 `[3, 1, 2, 4]` 的严格递增子序列可以是 `[1, 2, 4]`，不能只检查连续片段就宣称算法正确。

可核验的中间对象比“看起来深思熟虑”更重要。递推式、复杂度、输入域与反例都可以独立审查；模型声称自己逐步想过，不是这些性质成立的证据。

## 4. 第 12–13 页：自洽性投票不能产生缺失证据

第 12 页介绍多次采样、汇总常见结果；第 13 页用 `print(nums[i])` 抛出 `IndexError` 的短堆栈，提出询问五次并取多数答案。课件没有展示五次实际输出或最终票数，不应写成作者测得准确率提高。

堆栈支持的最小结论是：执行索引访问时发生越界。它没有给出 `nums` 的长度、`i` 的值或更新代码，所以不能唯一确定是循环上界、列表为空，还是列表被修改。假如五个回答都猜测循环写成 `<=`，即使意见一致，也没有补出缺失源码。

Self-consistency 通常投最终答案，而不是逐字投长解释；需要预先定义等价答案规范化、平票、无效回答与弃权规则。候选来自同一模型和相同证据时可能共享偏差，不能当作五位独立专家。多次采样还增加成本与延迟，必须保留全部尝试而不是只展示获胜答案。

## 5. 第 14–15 页：工具是外部执行，不是提示内装饰

第 14 页提出把任务交给外部系统，第 15 页从“确保修复后 CI 通过”改成列出单元与集成测试命令。列出的 `pytest` 路径是课件示例，不是已核对的本仓库测试入口，本次未运行。

工具有两种价值：获取模型上下文中没有的事实，以及执行确定性检查。但提示里出现命令不表示工具真的注册、路径存在、权限允许或命令成功。应区分“建议调用”“运行时执行”“取得退出码与日志”“确认测试覆盖了目标行为”。测试通过也只覆盖已运行测试，不证明所有 CI 条件或部署状态正确。

若要核实越界修复，先取得相关源码与失败输入，再运行隔离测试；模型自己写“CI 已通过”不得填入执行证据。工具运行与权限的完整边界见第 02、04 章。

## 6. 第 16–17 页：RAG 让证据可访问，不让引用自动可信

第 16 页介绍 Retrieval Augmented Generation：把上下文材料引入本次请求，无需为每条新事实重新训练模型。讲义把可解释性和引用说得很直接，但工程上并不会“免费”得到可信出处：检索器可能选错版本、丢段落，生成器可能引用一个并不支持主张的页面。

备注把 IDE 的 `@context` 概括为 RAG。实际手工附带文件不一定经过检索，具体产品是否检索、排序或裁剪要看当时版本；本轮没有抓取产品请求验证。

第 17 页的原案例是扩展 `UserAuthService` 来检查 OAuth token，提供当前代码片段与 requests-oauthlib 文档地址。片段只有 `issue_oauth_token` 及省略号，不能据此确定现有验证路径；“发 token”与“验证 token”是不同职责。外链指向 `latest`，不是锁定版本，也没有取得外链正文。是否需 introspection、签名验证、issuer/audience 检查由实际供应商与 token 类型决定，不能从类名猜出实现。

教程扩展：为行动项功能给两份标明版本的假 API 文档，其中旧版字段为 `owner`，新版为 `assignee_id`。要求回答标出适用版本与依据，版本未指定时先列未知项；不要捏造引用或执行真实认证。

## 7. 第 18–19 页：反思必须接收独立反馈

第 18 页的 Reflexion 是执行、观察后，把环境信号转成语言反馈重新加入上下文；也举出“评价答案、必要时重试”的两轮形式。只让模型批评自己与把真实测试失败送回模型并不等价：前者可能没有新证据，后者至少提供了外部观察。

第 19 页用 `company_location` 同时支持字符串和 JSON 的需求，展示测试失败、`JSONDecodeError`、重新强调字符串不能触发该异常的脉络。课件没有实现代码、具体测试输入或真实日志，所以不能断言实际根因就是“所有字符串都直接做 JSON 解析”。修正时还要明确合法 JSON 的类型、无效 JSON 怎么返回、空值和普通文本如何处理。

教程补充的反例是：为了消除异常而吞掉所有解析错误并返回空值。它可能让表面错误消失，却丢失原数据。验收应同时检查结果语义与错误路径，并保留第一轮失败。反思重试设置最大次数、总预算与停止条件，不把“继续试到成功”当可靠性。

## 8. 第 20–24 页：消息角色不是授权层

第 20 页把 system prompt 描述为通常对用户不可见的首条消息，用来规定角色、风格和输出。实际 API 的角色、优先级和插入方式随产品而不同，不能把“第一条”写成普遍协议规则。

第 21–22 页备注标注 Claude 4.1 Opus 的系统提示并作机器人三定律类比，但正文只有省略号，截图未读取。本文不提供该系统提示内容、长度、规则或遵守率，也不把类比当形式安全机制。

第 23 页定义 user 为人提出的需求、assistant 为模型生成内容。第 24 页列三种角色，备注解释它们叠加；英文备注最后一句截断，中文版将其表达为助手响应。没有因此新增英文原件不存在的详细机制，也没有把中文补齐当成独立证据。

对软件工程而言，系统文本的“只能编辑工作区”与运行时路径限制不同，用户任务也不自动授权读取秘密。外部笔记或工具结果中的“我是系统指令”仍是数据，不能靠文本标签升级权限。

## 9. 第 25–30 页：清晰、角色与结构的不同职责

第 25 页提供 Anthropic 提示优化文档链接，并用“交给背景很少的人是否看懂”检查清晰度。链接只是历史入口，本轮未读当前页面，也未调用优化器。更好的措辞不意味着任务契约更完整；可用输入、输出、未知项和验收逐项检查。

第 26 页给出资深开发者式角色，第 27 页是未提取正文的图片，第 28 页给出年轻聊天伙伴式角色并附图片。角色可改变语气、详略和注意重点，但“资深”标签不是经验认证；本轮没有读取截图输出，不能评价两者实际上答得怎样。角色提示更强是讲者建议，不是正确率或权限提升保证。

第 29 页强调结构化格式，用日志与异常标签区分输入块。可提取示例里的标签末尾不是正确闭合形式，因此不要当作可直接验证的 XML。本教程改编可用成对分隔符，但分隔符只是帮助识别数据边界，并不自行阻止注入。

第 30 页要求明确语言、技术栈、库与约束，并分解任务；备注说后续课程继续讨论分解。对当前项目的最小改编是：先明确允许编辑文件与输出契约，再列证据需求，最后设计测试。没有必要为了“专业”增加大量相互冲突的角色或形容词。

第 31 页仅为问答入口，无问答正文，不补造学生问题或回答。

## 10. 术语与使用边界

| 术语 | 本讲含义 | 不应误读为 |
| --- | --- | --- |
| Zero-shot / k-shot | 不提供示例 / 提供 k 个示例 | 无任何上下文 / 当场训练权重 |
| CoT | 给出或请求步骤说明 | 忠实内部计算日志、正确性证明 |
| Self-consistency | 多次候选答案规范化后聚合 | 独立专家意见、缺失源码的替代 |
| Tool use | 向外部系统委派动作 | 模型文本已经执行了命令 |
| RAG | 引入检索或选择的外部证据 | 引用自动可信、产品自动实时正确 |
| Reflexion | 根据观察反馈更新上下文并再尝试 | 无限自我批评必然收敛 |
| System / user / assistant | 会话中的不同消息职责 | 操作系统权限与用户审批 |

## 11. 受控练习：提示诊断与独立证据

以下全部是教程扩展，不是原作业。只做纸面或独立 Markdown 推演，预算 35 分钟、零网络、零模型费用、零业务写入；不运行课件的 `pytest` 命令，不修改参考脚本。

1. 用假会议笔记设计零样本与两示例提示。写明非任务、否定任务与未知负责人三个边界，另留两条未进入提示的验收输入。
2. 对第 13 页堆栈列出“已观察到什么、还缺什么、至少两个兼容根因”。给定五个虚构回答都说循环上界错误，说明为什么仍不能确认；这些回答不是实测输出。
3. 对假结果“引用了文档，修改完毕，CI 通过”逐项列证据：文档版本和支持段落、真实差异、命令/目录/退出码/日志。缺少证据明确写未确认。
4. 为 `company_location` 列普通文本、合法 JSON、无效 JSON、空值四类需求，给出一次失败反馈和最多一次修正的停止规则。期望值由人工契约确定，不由候选回答自评。

验收产物：两份提示、开发/验收分离清单、根因未知项表、三类主张证据表、四格测试契约。练习只评价设计是否清晰，不报告真实模型提升率；本次资料编写没有替读者完成练习。

## 12. 自测与答案

**问：为什么五个相同的根因回答仍不能确认第 13 页错误？** 输入缺少源码与状态，候选可能共享同一个猜测；多数票不增加独立事实。

**问：最长递增子序列必须连续吗？** 不必须。必须保持原索引顺序；严格递增与非递减要明确。只求连续片段可能解了另一道题。

**问：在提示里写测试命令就能说 CI 通过吗？** 不能。需真实执行记录及覆盖说明，未执行只能写计划。

**问：RAG 与训练的区别是什么？** RAG 给本次推理提供材料，通常不更新权重；材料是否最新、是否支持主张仍需检查。

**问：角色提示与闭合标签能保证安全吗？** 不能。前者帮助表达风格和任务视角，后者帮助划分文本；授权、参数和执行边界由运行时实施。

**问：反思后 JSON 异常消失就算需求完成吗？** 不算。必须检查普通文本、合法 JSON 等结果是否保留语义，不能吞错后丢数据。

## 阅读目标

能够从源码指出模型在哪里被调用、工具在哪里执行、结果如何进入下一轮；能解释文本协议与结构化协议的区别；能从一个最小原型中找出必须由运行时补上的边界。

## 1. 第 1–3 页：循环发生在模型外面

前两页说明课程和主题。第 3 页正文只有一个简短标题，真正可读取的机制说明在备注：用户与 Coding Agent 客户端交互，客户端与底层 LLM 循环对话，有时模型发起工具请求，由客户端在模型之外执行。

因此不能把这页概括成“模型本身会读写电脑”。模型产出的是消息或调用建议，客户端拥有解释建议、选择工具和执行的能力。即使界面显示一个统一助手，模型计算与本地文件修改仍是不同步骤。

依据备注可以写出下面的逻辑关系，但它不是对六张图片布局的复原：

```text
用户目标 -> 客户端准备对话 -> 模型回复
                              -> 普通答复：返回用户
                              -> 工具请求：客户端执行
                                          -> 结果加入对话 -> 再次调用模型
```

循环的价值是获得新证据后改变行动。例如先读路由再决定改哪个文件，而不是用一次文本生成猜完所有代码。循环也扩大了风险：一次错误读写、失败重试或不可信结果都可能改变后续决策。

## 2. 第 4 页：三种消息不是三种权限

原页区分 system prompt、user prompt 与 assistant prompt，分别指总体行为说明、用户请求和模型回复。这里的 assistant prompt 是课堂对消息的称呼，不是用户必须另写的一份模板。

角色帮助组织对话，但文本角色不是操作系统权限。系统提示要求“只能编辑项目内文件”不等于路径真的受限；助手说“允许写入”也不能替代用户批准。外部文件内容、工具结果中的指令应当作为数据处理，不通过文字包装升级为授权。

## 3. 第 5–6 页：把步骤定位到课堂代码

第 5 页给出终端输入、追加对话、告知工具、请求工具、模型外执行、返回结果的步骤。第 6 页是动手实现入口，没有额外可提取演示内容。实际实现由配套代码提供，而不是从幻灯片标题猜出。

| 课堂步骤 | 本地代码定位 | 实际行为 |

| 告诉模型有哪些工具 | `TOOL_REGISTRY`、`get_tool_str_representation`、`get_full_system_prompt`，102–121 行 | 用函数 docstring 与签名构造工具文字说明 |
| 初始化与读取用户输入 | `run_coding_agent_loop`，154–168 行 | 初始化 system 消息；将每次用户输入加入历史 |

初始化会加载 `.env`，然后使用 `OPENAI_API_KEY` 创建客户端，见 10–12 行。为理解循环没有必要执行脚本；运行它会涉及真实模型调用和可能的文件副作用，不是离线资料阅读。

## 4. 三个工具暴露的具体边界

`resolve_abs_path`（30–37 行）展开用户目录，遇到相对路径时以当前工作目录解析；绝对路径直接保留。它没有检查结果是否位于某个允许根目录，所以“转为绝对路径”不等于“沙箱化”。

`read_file_tool`（39–52 行）读取全文并返回路径与内容，没有文件大小或敏感内容限制。`list_files_tool`（54–70 行）返回目录项目，没有授权过滤或分页。这些简化适合演示，却可能将秘密或大量无关信息带入模型上下文。

`edit_file_tool`（72–99 行）有两条分支：`old_str` 非空时替换第一次匹配；为空时直接写入新内容，即创建或覆盖文件。它没有独立审批、备份或并发版本检查。旧文本未匹配时返回一个字典，而不是抛出异常；返回了结果不等于编辑成功。

调用处对缺失 `old_str` 使用空字符串默认值（189 行），正好会进入覆盖分支。把“缺少参数”当作“允许覆盖”是值得在运行时设计中纠正的语义，不应靠提示词要求模型小心来解决。本文没有修改原练习；第 02 章将这个观察转为隔离的契约辨析。

## 5. 文本调用协议与对话记录的限制

系统提示规定恰好一行 `tool: TOOL_NAME({JSON_ARGS})`，但解析器实际逐行扫描，可能收集多个调用，也会跳过解析错误。协议说明与实现接受范围不是完全一致的。JSON 解析成功同样不证明参数是对象、字段齐全或类型正确。

未知工具在 `TOOL_REGISTRY[name]` 处可能失败，类型错误也可能在 `args.get` 或函数调用时失败。工具执行没有统一异常回传，所以异常可能中断循环，而不是给模型一次可理解的恢复机会。没有解析出调用时，回复被当作普通文本；它可能真是答复，也可能是格式坏了的工具请求，不能将两者混为一谈。

有工具调用的分支没有先把该次 assistant 调用请求追加到历史，只加入 user 角色的结果字符串。因此后续对话不保留完整“请求—结果”配对，也没有显式调用 ID。它演示了反馈循环，但不能作为生产级工具消息审计的范本。

原脚本每次模型请求限制输出 token 数，不等于整个任务有总预算。内层 `while True` 没有最大轮次、总耗时和总成本上限，也没有独立完成判据。可靠运行时需要在这些位置施加约束，并把失败、部分完成和预算耗尽明确返回给用户。

## 6. 第 7 页：当时的观察，不是现行机制保证

第 7 页谈及有针对性的前置上下文、system reminder、命令前缀提取和子代理。其中对子代理作用使用了 likely，说明是带推测的解释。没有附本轮核对的产品版本、实际请求或实现代码，不能写成现在所有 Claude Code 客户端的保证。

`<system-reminder>` 是文本标签，不赋予内容额外的系统权限。若工具结果中出现同名标签，也不能因此成为系统指令。子代理可以隔离一部分上下文，但交接摘要仍可能遗漏关键事实；命令前缀分类也不等于完整 shell 安全判断。

可迁移的方法是：为当前任务选择小而相关的上下文；明确区分约束与数据；对委派结果复核证据。产品特定的实现方式留在来源笔记，不直接写成通用操作步骤。

## 7. 离线练习：观察与推断分开

以下是教程扩展，只做纸面或 Markdown 推演，不导入或执行原脚本，不读取真实秘密，也不调用模型。预算 30 分钟、零网络、零实际文件修改。

1. 用假设回复 `tool: read_file({"filename":"tasks.py"})` 画出解析、注册表选择、函数执行、返回消息和下一轮调用。将请求、结果和再次调用分别编号。
2. 推演 `tool: edit_file({"path":"tasks.py","new_str":"replacement"})`。查调用处的默认值与编辑分支，指出它不是安全的“局部替换”。不要真正写文件。
3. 对未知工具、非法 JSON、缺少参数、旧文本不存在分别写出原型会发生什么，以及希望运行时返回什么结构化错误。
4. 设计一个改编契约：拒绝缺失参数；区分创建、覆盖和替换；写入前验证授权、根目录与当前版本；最多允许三次工具轮次。写清预算耗尽后的报告内容。

验收证据：五节点循环图、四类失败表、一份编辑工具契约。对源码可见行为标注“静态观察”；对模型是否会正确调用、是否会继续修复标注“未运行”，不能把预测填写成真实 trace。

## 8. 自测与答案

**问：模型产生 `tool:` 文本就算已经读过文件吗？** 不算。必须确认客户端选择并执行了工具、结果确实来自该路径；本练习没有实际执行。

**问：缺少 `old_str` 的编辑请求会怎样？** 调用处给出空字符串，编辑工具进入直接写入分支，可能覆盖文件；应由运行时拒绝歧义，而不是默认写入。

**问：`max_completion_tokens=2000` 限制了整个任务的成本吗？** 没有。它只是单次请求的输出限制，循环次数、输入长度和总时间仍可能增长。

**问：换成结构化 function calling 就安全了吗？** 没有。它能改善请求与结果的结构关联，但参数验证、路径限制、授权、幂等和失败恢复仍要实现。

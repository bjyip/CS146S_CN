## 阅读目标

能解释 MCP 为什么减少连接适配，却不取消供应商鉴权、错误和限流责任；能定位工具发现、模型选择、服务器执行三个步骤；能从最小文件 Server 的源码指出协议通道、路径、错误与写入缺口。

## 1. 第 1–3 页：动态信息要有现场证据

第 1 页是课程与讲者，第 2 页引入 MCP。第 3 页用当天天气、总统、Bitcoin 价格和 Nike 最新广告旁白说明时效性：仅靠模型权重中的知识，不能可靠得知“现在”的外部状态。

课件说世界知识只有重新训练才更新，宜限定为权重内知识的教学概括。给模型新上下文、读取文件和调用 API 都可以更新本次回答的信息，却不等于重训权重；实际训练流程也不只一种。讲者将 RAG 与工具调用视为当时重要方案，不是证明只有这两条路或足以构成完全自主系统。

动态数据还需要时间、来源与适用范围。举例说“Bitcoin 价格为某数”，若没有交易所、币对、时间戳和延迟说明，就算来自 API 也可能不满足用户的问题。本文没有联网查询这些例子的现值。

教程扩展：行动项提取器应读取当前笔记与任务状态，避免根据旧上下文重复创建已完成任务。读到新数据与获准写入任务仍是两个边界。

## 2. 第 4–7 页：集成难题先于协议

第 4 页把 Model Context Protocol 描述为跨集成提供上下文的开放协议，通俗解释为向 LLM 暴露工具的标准格式，并提到 2024 年 11 月推出。这个历史叙述不是本轮核对的实时协议版本；完整 MCP 还包含工具以外的能力，见第 04 章。

备注让读者回想上节课的手写工具调用：当 API 形式规整时，单个集成并不复杂。这里的 MCP 价值不是让普通函数调用第一次成为可能，而是让不同应用复用发现和调用接口，减少重复适配。

第 5 页正文提出如何暴露一个质量可疑的第三方 API；备注列文档差、交换格式不一致、鉴权与错误处理。第 6 页扩展到数百个 API，第 7 页扩展到许多 LLM 应用，并指出 N×M 连接器问题。图片中的具体对象与连线没有读取，下面的数量关系来自正文与备注，不是视觉复原。

设 M 个应用各自对接 N 个服务，朴素全连接需要 M×N 个适配。标准边界理想上允许每个应用接通协议、每个服务暴露协议，即约 M+N 个适配。但是业务契约、供应商权限、版本差异和兼容性测试仍存在；这个数量模型不是工程工时或维护成本的实测公式。

## 3. 第 8 页：统一协议不等于统一业务语义

原页说 MCP 可减少重复实现 auth、错误和限流，并通过 JSON-RPC 提供一致格式。这应理解为复用 Server 里的集成代码，不是“协议自动实现所有鉴权和限流”。供应商 token 管理、资源权限、配额策略、重试和数据规范仍需 Server 或相应运行时完成。

JSON-RPC 统一请求、响应与错误的封装，不会自动统一天气与邮件 API 的结果字段；JSON schema 也不会确认一个返回 ID 属于当前用户。课件将 MCP 与 LSP 关联，适合作为标准化连接思想的类比，而不是说 MCP 是可直接替换 LSP 的超集。MCP Server 也不因协议本身就具备自主目标、审批或安全的后台执行。

教程例：同一个邮件 Server 可以供两个客户端使用，只写一份邮件服务适配；仍要逐请求验证用户是否能读 Jack 的邮件。另一个客户端连接成功不代表它继承了前一个用户的授权。

## 4. 第 9–10 页：从发现到执行的职责拆分

第 9 页定义 Host、嵌入的 Client、包装能力的 Server 和可调用 Tool。讲义列 Cursor、Claude Desktop 作 Host 示例；名称仅说明当时应用类别，不代表本轮验证它们当前兼容。

原页流程是 Client 调用 `tools/list`，Server 返回名称、摘要和参数 schema，Host 让模型看到定义，用户任务触发模型生成调用，再由 Server 执行、返回结果继续对话。初始化与能力协商未在这个简图完整展开，不应把省略的教学流程当完整 wire protocol。

职责可按文字重述为：

```text
Host 接收用户目标
  -> Client 取得 Server 工具定义
  -> Host 向模型提供相关定义与任务
  -> 模型建议工具名和参数
  -> Client 发出调用，Server 校验并执行
  -> 返回结果，Host 继续组织会话
```

模型生成的是调用建议，不直接拥有服务器文件权限。Server 不只负责“执行函数”，也应拒绝不允许的参数、主体和资源。返回成功格式不证明函数行为符合授权。

第 10 页原任务是“总结 Jack 的邮件”，正文列 1–5 的查询、发现、选工具、调用、返回脉络。图片未核验，不能补出邮件厂商、实际函数名、箭头走向或真实邮件内容。若把它改编为先搜笔记再读笔记，应明确后一步 ID 来自哪次前一步结果，不能凭自然语言名字猜 ID。

第 9 页列 stdio 与 SSE，反映 2025 教学快照，不是当前所有客户端的传输清单。远程 HTTP transport 及 SDK 兼容性需要按当前协议核对。本轮只读资料，没有验证初始化、列工具或实际传输。

## 6. 文件工具的四个具体缺口

### 路径解析不是隔离

`resolve_abs_path` 不比较授权根目录，也不验证用户主体或敏感文件。相对路径经过解析，绝对路径仅保留扩展后的路径；无法因此保证符号链接、父目录越界或真实业务数据不被访问。示例 docstring 里的讲者机器路径只是说明，不是读者必须创建的目录。

读取函数使用默认文本编码，编辑函数使用 UTF-8，可能产生不同平台行为。读取没有大小、类型与秘密过滤，列目录没有分页或固定排序。即使名为 read，也可能把不应发送给模型的内容暴露出去；工具只读不等于数据可公开。

### stdout 是协议通道

第 25 行 `print(full_path)` 会写标准输出。在 stdio 部署中，这类普通调试行可能混入 JSON-RPC 流；诊断应走 stderr 或明确的独立日志通道。脚本的 `mcp.run()` 没有显式 transport，不能仅凭源码证明本次实际使用 stdio 或已发生故障，本轮没有启动它。

### 一次写入包含覆盖语义

`old_str` 为空时，第 64–69 行直接写入新内容。文件已存在也可能被覆盖，但返回动作仍叫 `created_file`；这个标签不能证明此前没有文件。三个参数在签名中没有默认值，不能把上节课手写循环的“缺参数默认空字符串”直接套到本脚本。

`old_str` 非空时先读取当前文件，只替换第一个匹配。没有旧字符串时返回 `action: old_str not found` 的普通字典；这不是在源码中显式标为 MCP 工具失败。是否被 Host 当失败需实际 SDK/客户端验证，不能只凭字典存在认定成功或已触发模型恢复。

覆盖与替换都没有独立审批、版本比对、备份和幂等机制。如果“第一次写入成功但响应丢失”，直接重试不一定保持正确。更安全的改编应把创建、覆盖与替换拆成明确模式，对空串及多匹配规定行为，并在执行前检查批准的目标和当前版本。

### Python 类型注解不是完整契约

文件路径都是字符串类型，注解没有表达授权根、路径长度、存在性或可覆盖策略。源码没有统一异常恢复；文件不存在、编码错误与权限不足会由 Python/SDK 路线处理，而 SDK 封装语义未在本轮运行核验。生产改编需要明确哪些是参数错误、业务工具错误和协议错误，不能用无结构异常代替恢复设计。

以上是静态缺口分析，不表示原教学原型承诺了生产能力，也没有修改或执行原件。

## 7. 第 12–13 页：工具数量与上下文预算

第 12 页称当时 Agent 不擅长处理很多工具，描述会快速消耗上下文，因此应设计 AI-native API。第 12、13 页备注均写讨论 Cursor 工具数量硬上限，但没有给出数值、版本或实际测量。第 13 页是问答入口，不据备注补造学生问题，也不写当前工具上限。

AI-native 不意味着删掉约束或给任意 URL 的万能执行工具。它可以是目标清楚、输入小而明确、输出保留后续 ID 与必要错误、工具组合路径容易判断。减少描述数量与减少任务总成本不是一回事：发现和分步调用也消耗往返，须按完整任务测量。

教程扩展：笔记服务先提供搜索、读取和写入预览，创建任务仍走审批。不要为每个供应商字段暴露一个无语义函数，也不要为了省 token 删除用户主体、分页与失败状态。渐进发现和代码组合由第 04 章已有内容继续解释。

## 8. 术语与边界

| 术语 | 核心职责 | 不提供的保证 |
| --- | --- | --- |
| Host | 承载会话并组织模型上下文 | 用户意图自动等于写入授权 |
| Client | 维护协议连接与发出请求 | 供应商资源天然归当前用户 |
| Server | 暴露能力并实现服务适配 | JSON-RPC 自动实现所有业务防护 |
| tools/list | 获取工具定义 | 已执行工具、参数或结果已获许可 |
| JSON schema | 描述和约束输入结构 | 资源归属、真实 ID 与业务正确性 |
| stdio | 标准输入输出作为通信通道 | 普通 `print` 不影响协议 |
| M×N → M+N | 理想化的适配复用模型 | 工程工时同比下降、安全自动完成 |

## 10. 自测与答案

**问：两个 Host 与三个服务的连接数是多少？** 理想全连接为 6，标准边界为 5；只说明复用关系，不表示少一个连接就少一份所有业务工作。

**问：MCP 是否自动消除供应商鉴权和限流代码？** 否。Server 可集中复用实现，协议不能替代供应商权限与配额策略。

**问：路径转为绝对路径后安全吗？** 不保证。还需授权根、主体、符号链接和敏感资源等检查。

**问：空旧字符串返回 `created_file`，能确认是创建新文件吗？** 不能。源码也可能覆盖已有文件，返回标签没有区分两种动作。

**问：本脚本缺少 `old_str` 会默认覆盖吗？** 签名没有默认值，不同于上节课手写调用处；必须按实际 SDK 参数校验核对，不能沿用另一个原型的结论。

**问：直接调用 Python 函数测试足以证明 MCP 互通吗？** 不足。还要实际验证 transport、初始化、工具发现、参数校验和结果封装；本轮均未运行。

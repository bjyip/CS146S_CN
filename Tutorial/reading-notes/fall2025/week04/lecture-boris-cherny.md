## 阅读目标

理解终端原生 Agent 为何能串联开发生命周期；根据任务选择研究、测试或视觉反馈工作流；把对话式原型中的不断改口转换成当前有效规格；严格区分提示表达了什么、界面实际呈现了什么与实验验证了什么。

## 1. 第 1–4 页：产品介绍与变化叙事

第 1 页欢迎使用 Claude Code 并署 Boris Cherny；第 2 页提出三个主旨：编程正在改变、选择适合自己的 Claude Code 路径、面向六个月后的发展。第 3 页给出全局 npm 安装形式和 `claude.ai/code`，第 4 页引入“编程处于转折点”。

这里的“六个月”是产品设计视角，不是已发布模型时间表。安装信息不能直接当教程前提：本轮不安装、不登录、不确认现行包版本、授权方式和可用平台；历史命令也不应被读者无条件执行。

## 2. 第 5–6 页：生产力图是讲者论点，不是已核实曲线

第 5 页把编程语言生产力增加与 AI 联系，第 6 页把 IDE 的演进放在相似框架。文字包含 1950–2030 年份、`log(productivity)`、语言与编辑器名称，说明讲者试图用长时间跨度展示抽象层与开发工具变化。

本轮未核验两页图片、轴位置、数值、连线和数据来源，因此不能从“指数增长”的标题推导增长率、倍数或某款工具优于另一款的排行。不同语言、IDE、Agent 的生产力也需要明确任务、人员、质量与时间的测量方法，否则图示只是叙事性比较。2030 年的位置尤其不是既成事实。

教程中可迁移的解释是：更高层表达能够让人少处理某些底层细节，工具可能降低一类工作成本，但调试、验收和维护成本可能增加。不能把代码生成速度直接当作整个项目交付速度。

## 4. 第 15 页：验证与生成必须一起演进

本页把验证方法并列：手动调试、静态类型、形式化验证、抽象解释、自动测试、CI、基于属性测试、依赖类型、端到端测试、混沌测试，以及 AI 漏洞测试、单元测试、模糊测试和 self play。QuickCheck、Chaos Monkey、TestGen、Sapienz 是原页给出的例子，不是本轮安装的工具。

这不是“一种方法替代前一种”的排行榜。静态类型覆盖部分结构约束，端到端测试覆盖选定用户流程，属性测试从不变量生成更多输入，形式化方法依赖所写规格与假设。即便测试由 AI 生成，它仍可能遗漏与模型实现共同误解的边界。

原讲义仅列出 self play，没有算法、实验或结果文字，不能编写成“自博弈已能证明代码正确”。可迁移原理是选择与失败类型匹配的验证，而不是因为模型能力提高就减少所有检查。第 05 章已有门禁分层，本讲仅建立来源关联。

## 5. 第 16–18 页：终端原生与完整 SDLC

第 16 页转入 Claude Code 的思路，第 17 页列出随处可用、终端原生、底层模型访问、可自由改造。这些是产品定位，“随处”“无限”不是对操作系统、套餐、工具兼容性和沙箱权限的技术保证。

第 18 页按软件开发生命周期列出五类工作：探索代码与历史、文档及上手；规划项目、规格与架构；实现、测试、提交与 PR；配置环境、CI/CD 与部署；调试、重构、使用量与性能监控。原页以 `git`、`docker`、`bq` 说明团队 CLI 可成为能力入口。

终端的价值是让同一执行环境组合已有能力，而不只生成代码片段；代价是 CLI 往往拥有真实副作用。读 Git 历史、改文件、部署服务不是同一风险级别。覆盖整个 SDLC 只表示使用场景广，不能推出每阶段都能无人值守或共享同一批准。

本教程行动项提取器可将探索、实现、发布分别限制为只读假数据、隔离写入与人工审批。该例为教程扩展，不是课件演示环境。

## 6. 第 19–25 页：多种入口与管道式自动化

第 19 页介绍一个 Claude Code 的多种形态，第 20、21 页标题分别是 terminal 与 IDE，第 22 页是 web & iOS，第 23 页只给出 `/install-github-app` 和图片。文字支持“讲者展示了不同入口”这一结论，但不支持具体按钮、安装授权范围、移动端能力或 GitHub App 的实际流程。入口不同，也不保证共享会话、权限或历史的方式相同。

第 24 页展示 SDK 方向：通过非交互 `claude -p` 询问一周工作，把允许工具限制到 `Bash(git log:*)` 的历史写法，并指定 `stream-json` 输出；同时出现“你的应用、Claude Code SDK、Anthropic/Bedrock/Vertex API、Claude 模型”等标签。这些文字说明作者设想应用可以把 Agent 能力嵌入自动化链，但未复原图中层级箭头，不推断具体调用架构。

从工程上要区分工具 allowlist 与完整沙箱。即便允许的只是 Git 日志，日志可能包含敏感文本、外部输入和提示注入；命令模式语法是否真的限制参数，也要按当前执行器核验。不能把课件中的历史标志当作现行安全配置样本。

第 25 页展示另一段管道：读取 GCP 日志，送给 Claude 关联错误与提交，再用 `jq` 取 JSON 结果。原问题是把日志与版本历史一起分析，不是部署修复。日志可能含个人数据、秘密或提示注入，外发前应脱敏；关联只能形成候选原因，不能证明因果。日志源、Git 历史、时间窗口与重试遗漏都会影响结论。

`stream-json` 与普通 JSON 的消费方式不同；事件流需要解析事件边界，而 `jq '.result'` 的示意依赖当时响应结构。原课件没有给错误 schema、超时或截断处理，本文不承诺任何当前 SDK 返回字段。此处只解释管道思想，本轮没有运行命令或把真实日志发送到模型。

## 7. 第 26–29 页：先给证据，再教会工具

第 26 页进入使用方法，第 27 页列出代码库问答与研究、写代码、集成工具/MCP、自动化。写代码又区分一次完成、sidekick 编程搭档与原型。选择一次完成不意味着首次生成一定正确；sidekick 意味着人可以持续介入；原型着重探索方案，而不是直接发布。

第 28 页原案例不是泛泛的“解释仓库”：它要求从 `ValidationTemplateFactory` 的入口找用法，从 Git 历史解释 `recoverFromException` 的多参数设计，从 issue #18363 解释 `src/login.ts` 的分支，从发布历史查 `PreHooks.php` 的引入版本，结合 PR #9383 确认受影响版本，以及回顾一周交付。

这些问题强调历史证据：当前代码能说明“现在是什么”，不一定说明“为何这样改”和“何时上线”。提交也不自动等于发布；最后两类问题还要对照 tag、发布记录或部署证据。原页只有提问，没有对应答案，本轮不伪造 issue/PR 内容或受影响版本。

第 29 页以 barley CLI 与 `barley_server` MCP 检查错误日志，给出历史 `claude mcp add ... -- node myserver` 形式。可提取文字支持同一能力可以通过 CLI 或 MCP 暴露，不能推出 barley 的真实 API、服务器实现、认证或工具结果。给模型一条命令模板只是说明调用入口，仍需工具契约、版本、权限和失败处理。

## 8. 第 30–32 页：工作流要随任务改变

| 页码 | 原工作流 | 原案例 | 教程解读与边界 |
| --- | --- | --- | --- |
| 30 | 探索 → 规划 → 确认 → 编码 → 提交 | issue #983，先找根因、提多个修复，由人选方案 | 高歧义任务在实施前插入批准；`ultrathink` 是历史提示用语，不是推理效果保证 |
| 31 | 测试 → 提交 → 编码 → 迭代 → 提交 | `utils/markdown.ts` 尚无链接渲染，先写会失败的测试 | 先确认测试因缺失行为失败，再实现；不能把任何失败都解释为合理红灯 |
| 32 | 编码 → 截图 → 迭代 | 实现 `mock.png` 并用 Puppeteer 比较 | 视觉任务需要视觉反馈；截图相似不等于可访问性、交互和响应式全部通过 |

这里并不存在唯一通用的固定顺序。研究优先适合根因不明，测试优先适合行为契约可写，截图反馈适合可视差异。选择取决于当前不确定性与风险，而不是固定让所有任务先生成大量代码。

第 30、31 页的提交属于原工作流，不是本轮授权；本轮没有运行 commit 或 push，也未写测试或安装 Puppeteer。离线自学可以用阶段记录替代提交动作，但不冒充原演示的执行复现。

第 33 页仅引入原型场景；第 34–42 页每页都有提示文字与图片，第 43 页只有图片。文字能支持下面的需求演进，不能证明图里每次修改成功或最终方案效果更好。

这组原案例展示需求探索中的撤销、替换和追加，不是一份顺序累加的待实现清单。若把第 34 页至第 42 页全放进最终规格，会同时要求“不要列表”和“显示列表”、上方和右侧显示、保留和删除 pill，产生冲突。

可执行的补充方法是每轮维护四项：本轮新增约束、已撤销约束、仍有效约束、尚未验证的主张。第 37 页的“undo”在上下文里是撤销两项 UI 设计，不授予执行任意 Git 回退或丢弃他人工作的权限。

第 41–42 页的文字也有未决处：展开列表如何与 spinner 共存、列表何时收起、完成后是否仍能查看、`esc` 是否仍具备中断行为。仅“移除提示”不表示“删除键盘中断能力”，也不能靠截图缺口补一个确定答案。正式实现前应把这些问题变成需求确认和状态测试。

原型还需要停止预算：例如最多两轮修改后整理方案与未验证项，由人决定是否继续。原案例没有给轮数限制、失败成本或验收结果；这一预算原则是教程扩展，已融入第 05 章的[有效规格](../../../chapters/05-skills-automation.md#原型迭代中的有效规格)。

## 10. 第 44–49 页：面向变化，但不把预测当能力保证

第 44 页进入 lessons，原页编号为 `6/`，不能自行补造缺失的第五节讲稿。第 45 页建议面向六个月后的模型设计，第 46 页要求准备持续演进，第 47 页只写“ask not what the model can do for you”。本轮没有备注或后半句，因此不能替作者补完口号或推断未写出的产品哲学。

第 48 页正文只有“4.”和图片，备注写模型变好、算力变便宜。它支持讲者的趋势预期，不给出模型能力、成本曲线、时间或百分比；图片里的第四条内容仍未取得。第 49 页致谢并再次列安装命令、网站与联系邮箱，不包含问答正文。

面向变化的稳健策略是保持工具边界、测试与可替换接口，定期重测，而不是为尚不存在的能力取消安全约束。未来模型更强可能改变最佳工作流，也可能放大错误写入范围；“准备演进”与“当前验收严格”并不冲突。这是教程的工程解释，不是已复现的产品成效。

## 11. 术语与局限

| 术语 | 含义 | 本讲边界 |
| --- | --- | --- |
| SDLC | 从探索、设计到构建、部署和支持的软件生命周期 | 场景覆盖不等于每阶段自治通过 |
| Terminal-native | 把终端与现有 CLI 作为重要操作环境 | 不保证平台兼容或执行安全 |
| SDK | 在应用中集成能力的开发接口 | 2025 标签与命令不保证当前名称、schema 和权限语义 |
| Sidekick | 人持续协作的编程搭档模式 | 不是固定产品开关或质量保证 |
| Prototype | 为探索方案快速迭代的原型 | 可见演示不等于生产级验收 |
| Spinner / pill | 原待办 UI 案例中的运行反馈与胶囊标签 | 只有文字需求依据，没有视觉验证 |
| Self play | 本页列举的一种演进方向 | 无实现或结果，不能补成自动正确性证明 |

全篇核心局限：图表没有数据核验，截图没有视觉核验，工作流没有执行记录，产品命令未复核当前版本，讲者预测不等于已兑现能力。中文对照有排版换行，页码判断以真实演示关系为准，不按被折断的命令或单词理解产品语法。

## 12. 零网络练习：工作流选择与需求状态账本

以下均为教程扩展，不是原作业，也不复现讲者屏幕。预算 45 分钟、零网络、零模型调用、零费用；只读假材料并在纸面或隔离目录记账，不安装 SDK/MCP/Puppeteer，不外发日志，不 commit、push 或接触真实业务数据。

1. 三个假任务分别是“未知根因的提取错误”“已知契约的 Markdown 链接行为”“待办 UI 排布探索”。为每个选第 30–32 页的一条工作流，写一个进入实施前必须取得的证据和一个停止条件。
2. 用三段假材料分析事件：日志在 10:05 首次出现失败，提交 A 在 10:00 合入，发布 R 在 10:20 包含 A。分别写相关性与因果结论；只能记录假设，不能据此说 A 导致 10:05 的线上失败。
3. 按第 34–42 页制作需求账本，最多两轮整理。第 38–40 页合并为一条“文字相同、视觉未知”的记录，不虚构三个新设计。
4. 为第 42 页后的假最终方案写 5 个验收场景：无待办、活动且未展开、活动且展开、待办超出显示上限、全部完成。对已经撤销的“上方固定列表最多 5 项”标明不再自动继承；若展开方案仍需上限，单独列为待确认。
5. 给假自动化响应“已关联错误与提交”添加外部证据字段：日志来源及时间范围、版本/发布来源、检查方法、置信限制、错误/截断状态。不给模型的自然语言结论直接贴上“根因已验证”。

验收是一张工作流选择表、一份相关性/因果辨析、一份新增/撤销/有效/未决四栏账本和五场景验收表。最终有效约束不能互相矛盾，图片未知必须单独标记，缺证据和预算耗尽都不能推进为成功。本次文档编写未执行这些练习，也未取得实际界面截图。

## 13. 自测与答案

**问：第 5–6 页能证明某 Agent 生产力指数增长的具体倍数吗？** 不能。只有标题和标签，未核验图像、数据与测量方法；不应编造倍数。

**问：Git 合入时间是否等于线上发布时间？** 不等于。要关联发布、部署及影响版本；日志与提交同时出现也不自动证明因果。

**问：第 24 页的工具白名单是否是完整的沙箱保证？** 不是。它是历史示意，还须核验实际执行器的匹配、参数、凭据、工作目录和输出处理。

**问：第 38–40 页提示文字重复，是否说明画面完全相同？** 不能判断。可提取文字相同，图片与动画尚未视觉核验，不能用文字代替画面证据。

**问：第 37 页之后还应保留 pill 和内联标题吗？** 按该页文字应撤销这两项。第 41 页进一步替代列表方案；若以后要恢复，须有新需求，不能因历史出现过就全量累加。

**问：第 42 页删掉 `esc` 提示，能认定中断功能也被删除了吗？** 不能。文字要求改变显示提示，没有明确取消行为；需要确认与测试。

**问：第 48 页的第四条经验是什么？** 正文无法恢复，只有趋势备注“模型变好、算力变便宜”；不把它补成已读图片标题。

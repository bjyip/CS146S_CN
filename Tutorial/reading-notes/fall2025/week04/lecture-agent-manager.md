## 阅读目标

解释人为何从代码作者转向工作流负责人；区分行为文件、命令、Hook 与 Subagent；为自主任务设计可核验交接和失败兜底；识别哪些只是讲者当时的产品经验、未来愿景或尚无答案的问题。

## 1. 第 1–3 页：讲座归属与管理主题

第 1 页提供课程和讲者证据，第 2 页预告 2025-10-17 的 Anthropic Claude Code 创建者 Boris Cherny，第 3 页才引出“如何成为 Agent 管理者”。二者处在同一教学周，但本讲由 Mihail Eric 讲授，嘉宾材料应读[独立笔记](lecture-boris-cherny.md)，不能混署作者。

这里的 manager 不是某个产品按钮或职业头衔，而是组织任务、指导执行和承担验收责任的人。拥有多个 Agent 会话，不代表已经具备管理机制；关键在于任务能否被分解、边界是否明确、结果能否被复核。

## 2. 第 4–6 页：产出规模改变，责任没有消失

第 4 页把工作方式分为四类：开发者管理自己的产出；负责人管理多位开发者；负责人在 AI 辅助下管理团队；一位开发者管理多个 AI Agent 的工作。这是讲者用于说明角色变化的框架，不是人人必经、严格按时间发生的四级发展规律。

当执行吞吐量上升，瓶颈可能转向需求、集成与审查。例如一个 Agent 改提取逻辑，另一个改任务 UI，如果双方对“没有负责人时返回空值还是猜一个人”没有共同契约，独立看起来都完成的代码仍会在接口处冲突。此例属于本教程行动项提取器，不是课件原演示。

第 5 页用软件团队历史承接上述变化：单人项目、NASA/DoD 需求推动团队、主流团队与专业分工、2023 年的 AI 编程辅助，以及开发者管理多样 Agent 的设想。可提取文字包含 1940、1960、1970、1990、2023、2025、2030，但本轮未读图片与位置关系，不重新给每个年份配一件事件。尤其 2030 是未来定位，不是已经发生的组织事实；NASA/DoD 历史说法也未另作史料核验。

第 6 页正文只有“Goals”和省略号，具体目标来自备注：每位开发者像技术负责人一样管理不同任务、技术栈和职责的 Agent。原备注例子包括 PR、质量保证，React、FastAPI/Python、Svelte，以及数据工程、机器学习、DevOps；还展望有一定技术背景的产品经理可以做到同样的事。图片中的团队组织结构未核验，因此不能推断 Agent 数量、层级或汇报箭头。

可迁移的原理是把“谁执行”与“谁对结果负责”分开。专业角色可能帮助集中上下文，但不自动产生专业能力；给 Agent 一个 DevOps 名称，不能让它获得正确的生产权限或可靠的事故判断。

## 3. 第 7 页：人机分工表不是无条件授权

本页列出完整任务链。备注明确绿色表示人类、蓝色表示 Agent，这一颜色语义有文字依据，不依赖猜测图片：

| 原讲义步骤 | 课件责任标记 | 管理者必须补的验收问题（教程扩展） |
| --- | --- | --- |
| 提出高层需求 | 人类 | 需求是否与真实业务一致，哪些推断被禁止？ |
| 将需求变成设计文档 | 人类 / Agent | 方案由谁批准，接口与非目标是否写清？ |
| 根据文档实现 | Agent | 改动是否只发生在授权文件范围？ |
| 添加测试 | Agent | 测试是否验证外部行为，而非迎合错误实现？ |
| 确保 CI 通过 | Agent | 是否有退出码与检查记录，有无跳过断言？ |
| 代码审查 | Agent | 审查者是否读过需求与实际差异？ |
| 更新文档 | Agent | 是否与当前实现和版本一致？ |

课件在后三类步骤标蓝，不等于人无需审查或任何 Agent 都能自治执行。管理者可以委派检查工作，却仍要为高风险判断与发布授权设门槛。自主性应按任务风险与证据充足度选择，而不是按颜色直接放开权限。

“让 CI 通过”也不能解释为删除失败用例或扩大权限。真正目标是实现满足契约且既定检查通过；若失败源于环境缺失，应记录未执行或阻塞，而不是制造绿色状态。

## 4. 第 8–10 页：定制行为与执行门禁是不同层

第 8 页列出行为文件、Hooks、Commands、Subagents。英文写法包含 `Claude.md`、`Cursorrules`、`agents.md`，这些是当时课件中的名称示意，不是所有客户端通用的大小写、发现路径和优先级标准。真实操作要按客户端版本核对，第 05 章已有[职责表](../../../chapters/05-skills-automation.md#1-不同机制不同职责)。本讲并未定义 `SKILL.md`，不要把 2026 的 Skill 机制补写成它的原始内容。

第 9 页把 Hook 定义为预定义事件触发的确定性脚本，列出 `PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`PreCompact` 等历史事件名。前置事件适合在动作前检查参数或权限，后置事件适合检查结果；这只是概念用途，不是已经验证的客户端拦截规则。具体事件可否阻断、退出码含义、执行环境与超时，课件文字没有给出。

“确定性脚本”不等于业务判断正确。稳定运行一条没有覆盖边界情况的测试，只会稳定遗漏问题；把 Hook 内部换成模型评审也不会变成确定性的语义证明。规则告诉模型怎么做，门禁应由执行层落实，二者不可互相替代。

第 10 页说明把常用提示保存成命令文件，原场景是测试、代码审查、Git 提交与推送，备注明确提到 Claude Code 的 Ship-it 命令，但没有样本正文。不能据此编造 `/ship-it` 的标准实现或默认权限。命令是触发模板，不是发布许可；把多个动作连起来尤其容易把“检查完成”偷换成“已经获得提交推送授权”。本轮没有执行课件中的提交、推送或安装操作。

## 5. 第 11 页：Subagent 的价值在委派与上下文隔离

本页把 Subagent 解释为运行时委派：为前端、后端等工作形成不同开发者角色；分离工作流上下文；提供定制 system prompt、工具和独立上下文窗口。备注进一步把它与锚定行为的 `Claude.md` 文件区分。

行为文件改变同一个 Agent 的操作约定，子 Agent 则形成另一个有边界的执行或分析单元。独立上下文能减少任务间噪声，但会丢失主流程已经知道、却没有交接的事实。因此委派输入至少要有目标、来源、限制与验收，不是只说“你负责后端”。

原页列出 [Awesome Claude Agents](https://github.com/vijaythecoder/awesome-claude-agents/blob/main/CLAUDE.md) 与 [SuperClaude Framework](https://github.com/SuperClaude-Org/SuperClaude_Framework)，备注另指向其 `SuperClaude/Agents` 目录。本轮只读到了这些链接，没有读取外部仓库正文，不宣称任何角色文件已适配当前版本，也不安装运行。

课件称其朝“Agent 管理其他 Agent”迈进。这是组织方式描述，不证明模型之间天然能够通信、共享工作目录安全或解决并行冲突。一个具体交接可以是：只读审查者收到已批准需求、实际差异和两份测试日志，返回按严重性排列的发现；它不获得实现者的写权限，也不能仅凭实现者说“已通过”批准。这是教程扩展。

## 6. 第 12 页：Backstop 必须可追溯且能失败

本页的兜底清单包含仓库测试、CI/CD、每个 Agent 的可审计性、标记每份 Agent 差异、按任务类别选模型、复杂任务前期多指导、定期检查点。它把管理重点从生成文本转回工程证据。

“标记差异”应理解为能够回答哪个任务、哪位执行者改了哪些文件，便于独立复核与恢复；标签本身不能证明正确。“经常建检查点”旨在缩短回退距离，但本轮不替用户建 commit；离线学习也可用阶段记录表达检查点，而非执行 Git 写操作。

备注提出 Opus 规划、Sonnet 主力执行，这是讲者在 2025 的模型偏好，不是现行性能、价格或路由保证。可迁移的是根据任务复杂度、工具能力、延迟、成本和评测结果选择；更换品牌名称并不能替代任务测试。任务复杂、需求歧义多、写入风险高时，应增加前置人类确认，而非单纯增加 Agent 数量。

审计最小单元可以是“任务编号、批准范围、执行者、差异、检查命令与退出码、未验证项、审批者”。这些字段为教程扩展。它帮助区分三件事：实现者声称成功，工具记录了检查成功，人类批准继续执行。三者不是同一个状态。

## 7. 第 13–14 页：演示占位与开放问题

第 13 页仅有“Workflow walkthrough”；备注说使用真实任务观察修改和 Agent 启动，并展示 Claude proxy 输出。没有任务、代理服务配置、trace 或结果文本。因此本文不构造实际启动过程、不说明 proxy 的架构或宣称工作流成功。

第 14 页留下两问：如何自动化任务最初 10–20% 的研究阶段，如何维护待办任务队列以便处理一次性修改。该百分比是问题中的阶段描述，不是生产力测量，也没有给出算法或答案。

教程可以据此提出研究阶段退出契约：找到了相关入口、当前行为、至少一个失败证据、约束和未决问题后才交接；队列条目写清依赖、范围、预算与阻塞原因。它是本教程的补充设计，不是讲者已证明能自动化全部研究的方案。可参见第 05 章的[自主性与交接](../../../chapters/05-skills-automation.md#自主性与交接证据)。

## 8. 术语与边界

| 术语 | 本文用法 | 易误读处 |
| --- | --- | --- |
| Agent manager | 定义目标、分配边界、核验并承担结果的人 | 不是创建更多会话就完成管理 |
| Runtime delegation | 运行期间把有边界任务交给另一执行单元 | 不自动保证并发、通信或写隔离 |
| Context window | 当前调用或执行单元可使用的上下文范围 | 独立窗口可能遗漏交接事实 |
| Backstop | 测试、审计、审批与恢复等兜底机制 | 清单存在不等于门禁确实阻断 |
| Checkpoint | 可定位与恢复的阶段状态 | 不代表无授权可以 commit |
| Async | 主流程不必持续同步指导的执行方式 | 任务难度与风险仍需决定介入点 |

## 9. 零网络练习：设计一份委派合同

以下均为教程扩展，不是原课程作业或现场演示。限定 40 分钟、零网络、零模型请求、零费用；只用纸面或隔离练习目录中的假数据，不修改真实应用，不创建行为配置，不运行外部脚本、commit 或 push。

1. 假任务是“行动项提取器新增未明确负责人时返回空值的行为”。按第 7 页七步链为每步指定执行者和验收者；对实现与发布分别写权限，发布明确禁止。
2. 为只读研究者写一份委派合同：输入为三段假文件摘要，输出为现状、约束、歧义、方案和引用位置。最多分析 3 个来源、最多提出 2 个方案；超过预算或出现真实数据即停止。
3. 给定假交接“已修复，全部测试通过”但没有差异和日志，将其状态置为“待证据”，列出最小补证字段。再给出“测试退出码 1，失败为负责人猜测”，说明为什么不可推进到合并。
4. 设计一个无执行的 Hook 判断表：授权目录内的只读查询允许；生产写入禁止；修改范围未知的请求暂停。注明实际客户端事件与退出码尚未核验，不能把此表视为已部署门禁。
5. 对队列设置 A 为研究、B 为实现且依赖 A 批准、C 为只读审查且依赖 B 提交证据。模拟 B 被阻塞时 C 的状态，记录哪项信息可以使它恢复。

验收证据是一份七步责任表、一份委派合同、一张成功/失败/证据不足三路状态表、一份队列依赖图。必须能看出失败不会被包装成通过，研究有退出条件，审查读取实际证据，所有发布与真实数据操作禁止。本次仅核对与编写材料，未替读者执行练习。

## 10. 自测与答案

**问：第 2 页写 10/17/25，本讲是不是 Boris 的 10 月 17 日演讲？** 不是。第 1 页署 Mihail Eric，根 README 与文件名定位 10 月 13 日；第 2 页是嘉宾预告。

**问：第 7 页把审查标为 Agent，人类是否因此免责？** 否。它表示委派工作，不取消需求确认、高风险判断和发布审批责任。

**问：Hook 每次执行，是否证明业务需求正确？** 否。必须分别检查触发、阻断语义、测试覆盖与结果；执行层权限也不能靠模型提示替代。

**问：独立 Subagent 上下文是否只带来好处？** 否。它减少噪声，也可能丢失主流程事实；要显式交接需求、权限、证据和停止条件。

**问：Opus 规划、Sonnet 执行是不是推荐给当前所有项目的固定配置？** 不是。它是 2025 备注中的经验，今天需用实际版本、任务评测与预算核对。

**问：练习里 B 无测试日志，C 可以按“全部通过”的总结批准吗？** 不可以。C 应进入待证据或阻塞状态，取得差异、检查范围、退出码和未验证项后才能复核。

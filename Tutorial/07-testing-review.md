# 07 测试、评测与代码审查

[上一章](06-repo-parallel.md) | [目录](README.md) | [下一章：安全](08-security.md)

## 1. 两种正确性必须分开

普通软件测试关注明确契约：空输入如何处理、数据库如何更新、非法参数是否拒绝。模型评测关注语义质量：是否正确提取任务、是否编造、是否忠实引用。这两个层面相关但不能互相替代。

一个解析器可以在所有 mock 测试中通过，却面对真实模型频繁格式失败；模型可以生成正确内容，系统却因为重试写出重复记录。可靠系统需要两层证据。

## 2. 测试矩阵

| 层次 | 行动项项目的例子 | 验证边界 |
| --- | --- | --- |
| 单元 | 去重、空输入、解析异常 | 不证明网络或模型质量 |
| 集成 | 路由、数据库与临时存储 | 不一定覆盖真实客户端 |
| 协议 | MCP 初始化、列工具、调用 | 不一定覆盖供应商 API |
| 端到端 | 界面输入到持久化结果 | 样例数量通常有限 |
| 语义评测 | 隐藏样例上的提取精确率 | 依赖标注与分布代表性 |
| 安全回归 | 越权访问被拒绝 | 只覆盖已设计攻击路径 |

pytest 输出一片绿色不等于所有层次都覆盖。报告每种测试的范围和未覆盖区域。

## 3. 解剖现有测试

[第 2 周测试](../_assignments/2025%20fall/week2/tests/test_extract.py) mock 了模型返回，覆盖空输入、格式解析、重复项和不可用回退。这些是有价值的单元测试。

但 mock 指定了正确 JSON，不能证明真实模型会生成它；测试断言有 schema 也不能证明内容真实；异常回退得到规则结果，不能说明 LLM 服务健康。当前实现广泛捕获异常后回退，若缺少指标，成功响应还可能掩盖长时间模型不可用。

新增评测时要同时记录引擎、解析失败与回退比例。模型质量只统计真正由模型完成的结果；用户最终结果则统计完整产品链路。两个指标都重要，但含义不同。

## 4. AI 生成测试的陷阱

Agent 可能阅读实现后生成恰好复制实现的断言。如果函数把所有句子当任务，测试也接受所有句子，就会“完美通过”。测试预期应来自规格、外部标准或人工标注，而不是只来自被测代码。

要求 Agent 先列边界与预期，再实现测试。人工检查至少一个正常、一个失败和一个对抗样例。测试修复不应只是删除断言、放宽要求或大面积 skip。

可以做一次简单变异测试：在练习副本里故意移除去重或排序，检查对应测试是否变红，然后恢复自己的临时变更。测试能捕获故意错误，是比覆盖率更直接的行为证据；但一次变异不能证明所有错误都可捕获。

## 5. 评测如何报告才诚实

对同一批输入比较方案，报告精确率、召回率、格式有效率、首次成功率、重试后成功率、延迟和成本。分别保留超时、空输出、幻觉、否定处理错误和回退。

小样本波动很大。例如 10 个样例中 9 个通过，并不能建立“生产成功率 90%”的稳健结论。样例选择、模型版本和真实分布变化都会影响结果。可以给出成功数与总数，明确这是学习规模实验，避免没有依据的小数精度。

将平均值与长尾分开。平均延迟低可能掩盖少数极慢请求；p95 对小样本也不稳定，应报告样本数和测量方法。不要混合不同硬件的本地模型与云端耗时后直接归因于算法。

## 6. 代码审查不是重新描述差异

有效审查优先回答“这会在哪个具体场景出错”。发现格式为：严重度、文件与行号、触发条件、实际行为、预期行为和修复方向。不能只写“可能有安全问题”。

建议按这个顺序审查：公开契约与需求、数据完整性、授权与副作用、错误恢复、性能边界、测试缺口，最后才是命名与样式。没有证据的猜测应标记为问题或假设，不冒充确定缺陷。

模型审查常擅长模式识别和局部问题，但可能漏掉跨文件契约、业务上下文、权限配置和部署风险。人工也可能遗漏，因此使用独立测试和扫描补充，而不是把任何一方当全知裁判。

## 7. 一个具体审查推导

假设新增更新笔记端点仅按 `note_id` 查询，不检验当前用户是否拥有它。即使 ID 存在且 schema 合法，另一个用户仍可能修改不属于自己的笔记。

有效发现是：“在多用户部署中，用户 B 提交用户 A 的 note_id 时，查询未绑定主体，可能修改 A 的记录；需要基于当前身份限制查询并增加跨用户测试。”如果应用目前明确是单用户本地练习，应说明风险成立的部署条件，不假定已经存在登录系统。

这个例子说明审查需要同时阅读需求、代码和使用边界。单纯扫描是否用了 ORM 不能发现所有授权错误。

## 8. 动手 A：测试与真实评测

1. 运行现有单元测试，列出它们能证明与不能证明的内容。
2. 根据规格补充一个此前未覆盖的边界，先确认它能够捕获错误实现。
3. 用隐藏样例调用真实模型，记录所有结果及回退，不把云端不可用删出分母。
4. 将语义指标与软件测试结果分两张表，至少解释两个失败案例。
5. 修改一个主要因素后再评测，记录收益、退步和额外成本。

验收：有明确预期来源，有一次测试抓到故意错误，真实评测与 mock 分开，回退可识别。

## 9. 动手 B：人工与 AI 审查对照

[2025 第 7 周作业](../_assignments/2025%20fall/week7/assignment.md) 要求四项任务各自独立 PR、一次性 AI 实现、逐行人工审查及 Graphite AI 审查。任务见 [任务清单](../_assignments/2025%20fall/week7/docs/TASKS.md)。

按原作业执行时先保留 one-shot 产物，不让模型反复自修后再作为“首次生成”审查样本。记录人工和 AI 各自的发现，验证是否是真缺陷，再讨论遗漏。

没有 Graphite 条件时可使用另一个只读审查 Agent 比较，明确标注为自学改编。不要为了本教程在当前仓库自动创建远程 PR、添加协作者或提交代码。

评估发现质量时，可以统计确认有效的发现占全部发现的比例，以及已知缺陷中被找到的比例。没有已知缺陷全集时，不能声称计算了真实召回率。保留误报与未确认项。

## 10. 自测与答案

**问：覆盖率高为何仍可能漏 bug？** 代码被执行不等于断言了正确行为，数据、状态与路径组合仍可能遗漏。

**问：让同一个 Agent 写实现和测试是否不能用？** 可以使用，但预期需要独立来源，并用隐藏样例或独立审查避免自洽错误。

**问：没有发现是否等于没有风险？** 不是。应报告审查范围、运行过的验证和残余风险。

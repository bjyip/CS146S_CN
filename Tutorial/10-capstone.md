# 10 AI 原生团队与综合项目

[上一章](09-delivery-operations.md) | [目录](README.md)

## 1. 从个人工具到组织系统

个人 Agent 配置进入团队后，会遇到新的约束：谁能访问什么数据、模型请求经过哪里、谁支付成本、工具版本如何同步、操作如何审计、事故时谁能撤销权限。

MCP gateway 可以集中工具访问、身份、限流和审计；LLM gateway 可以集中模型路由、预算和数据策略。但集中入口也可能成为单点故障或权限聚合风险。网关不应使用一个无限权限账号代表所有用户访问所有资源。

身份应从用户或任务传递到工具执行端，明确主体、scope、资源与操作。短期任务凭据优于长期共享管理员 token，写与部署权限分离，审计记录关联实际任务。

本章根据 README 的 2026 团队与 Software Factory 主题扩展，不引用尚未取得的官方后续作业。

## 2. 模型路由与成本

小模型可以承担低风险格式化或分类，复杂变更可能需要更强模型；但“便宜任务全部交给小模型”必须由评测支持。路由应按任务风险、质量、时延、数据敏感度和预算决定，而不是只按标价。

一次完成任务的总成本包括模型调用、工具执行、人工审查、返工和运行资源。低单价模型多轮返工后可能更昂贵。并行和大上下文也会增加成本。

一个最小策略是：先给任务设预算和权限；在隐藏样例上比较候选路由；低置信或检查失败时升级处理；预算耗尽时停止并交接。模型自己的“我很有信心”不应是唯一升级判据。

切换模型可能改变格式、工具选择与拒绝行为，需要回归。不能把备用模型当成透明替换而不评测。

## 3. Software Factory 的可操作定义

在本教程中，它是一个有明确输入、阶段产物、自动检查和发布门禁的软件交付流水线，而不是让模型无限自我修改。

```text
需求或 Issue
  -> 研究与规格
  -> 计划与风险分级
  -> 隔离环境实现
  -> 测试、评测、安全检查
  -> 独立审查与批准
  -> 受控发布
  -> 观测与反馈
  -> 下一个受控改进任务
```

每个阶段有输入、输出、负责人和退出条件。反馈进入新的任务，不直接改写生产系统。高风险事项保留人工审批、沙箱、预算、审计和回滚。

## 4. 自动改进也需要评测隔离

如果系统不断修改提示直到通过同一测试集，它可能只优化了这些样例。用于开发反馈的样例与最终验收必须分开，评测集应版本化并防止答案泄漏。

流水线本身也要测试：检查失败是否阻止后续阶段，任务重复是否重复发布，撤销是否停止写入，恢复是否保留证据。否则只是把错误更快地自动传播。

## 5. 综合项目要求

选择行动项提取与开发者控制中心，或相同复杂度的真实小项目。不要先做十个服务；一个完整可验证闭环优于庞大但不可运行的架构。

**基础必做：** 明确规格；一个持久化资源的 CRUD；规则或无模型基线；LLM 功能与真实评测；可观测错误或降级；单元与集成测试；安全边界；独立审查；可复现启动和回滚说明。

**进阶可选：** OAuth MCP 组合工具与受控写入；经过触发验证的 Skill；两个独立后台任务；网关或多模型路由。选择进阶项时遵守对应原作业要求，不做未验证的模拟 OAuth。

## 6. 五个交付里程碑

| 阶段 | 产物 | 通过条件 |
| --- | --- | --- |
| M1 定义 | 规格、非目标、风险与验收 | 他人能写出测试，不依赖口头解释 |
| M2 基线 | 最小应用与规则方案 | 新环境可运行，测试数据独立 |
| M3 AI 能力 | 模型功能、评测与错误处理 | 真实运行证据，所有失败计入 |
| M4 受控流程 | 审查、安全、自动化 | 门禁失败确实阻止后续动作 |
| M5 交付 | 运行文档、观测、回滚与复盘 | 另一位读者复现主流程与故障恢复 |

不要跳过 M2 直接优化模型。缺少可靠基线时，模型质量、程序 bug 和环境错误容易混为一谈。

### 开源贡献闭环

根 README 本次将开源贡献权重从 5% 改为 30%。自学应增加真实协作训练，而不是凑 PR 数量；这里不推断官方具体评分细则，也不修改下面的自学项目总分。

选择自己理解且允许贡献的项目，阅读贡献指南、许可证、AI 使用政策、测试和维护者期望。合适的小任务是修复可复现的边界 bug、补充能捕获错误的测试，或纠正导致启动失败的文档。大面积自动重构与无依据的风格修改通常增加审查负担。

例如项目声称稳定排序，同时间戳的任务顺序却随查询变化：先查已有 Issue；在隔离环境记录版本、输入、预期与实际行为；写失败测试；最小修正排序 tie-breaker；运行回归并解释兼容性。如果需求不保证顺序，先与维护者确认，不擅自制造“缺陷”。

按以下阶段记录，不把本地准备写成远程贡献已经完成：

1. 选题与对齐：查重、阅读政策，确认问题真实、范围合适；必要时先询问维护者。
2. 复现与规格：提供脱敏最小案例、基线提交、命令与工作目录，区分观察和推断。
3. 最小修复：只改相关权威源，增加回归，不顺手升级依赖或修无关格式；按政策披露 AI 辅助。
4. 验证与说明：提供改前失败、改后通过、兼容性和残余风险；PR 说明引用需求，方便独立复核。
5. 发布与反馈：读者明确决定后才创建远程 Issue、PR 或推送；记录维护者意见，回应并复测。未获回应、关闭或未合并照实记录，不保证被接纳。

动手：完成一个小问题的本地贡献包，使用[贡献模板](templates.md)记录。如果允许并决定公开提交，再按目标项目流程发布；无外部条件时请另一位读者审查，标为本地协作演练，不等价于真实开源贡献。修改后给出反馈处理与回归证据。

验收：问题可复现、修复与需求一致、差异最小、回归有独立预期、反馈有记录。维护者未接受不必然表示没有学习价值，但不能声称已经合并；本地演练也不能冒充满足官方开源贡献评分。

## 7. 自学评分表

| 维度 | 分值 | 满分证据 |
| --- | --- | --- |
| 需求与规格 | 15 | 边界、非目标、契约与验收一致 |
| 功能与持久化 | 20 | CRUD、重启与失败路径实测 |
| 测试与语义评测 | 20 | 独立预期、隐藏样例、失败与成本记录 |
| 安全与权限 | 15 | 最小权限、注入边界、无秘密暴露 |
| 工作流与审查 | 10 | 可核验交接、独立审查和有效门禁 |
| 运维与恢复 | 10 | 降级观测、故障演练与恢复 |
| 复现与反思 | 10 | 版本、命令、局限和改进方向 |

秘密泄漏、未经许可的真实写入、编造执行结果或故意绕过检查属于交付阻断，不靠其他得分抵消。修复风险并重新验证后再验收。

## 8. 十五分钟答辩

1. 三分钟解释需求、用户和非目标，不展示工具品牌列表代替方案。
2. 四分钟运行一个主流程和一个边界错误，展示数据持久化与返回状态。
3. 三分钟展示对照评测，解释一个失败案例以及 mock 的边界。
4. 三分钟演练门禁拒绝或模型降级，说明恢复办法。
5. 两分钟回答最关键的剩余风险，以及扩大到多用户部署需要什么改变。

审查者可以提供一个未见输入或故障条件。项目应说明无法支持的条件，而不是编造成功输出。

## 9. 完成后如何继续

选一个最影响真实用户的问题做下一轮，例如误提取、长尾超时、授权缺口或运行复现。先测基线，再做一个小变更，使用固定评测和运行证据判断是否改进。

随着工具和协议变化，更新的是版本、发现目录、schema 与测试，而不是每次重新追逐整套品牌组合。真正可迁移的能力是规格、证据、权限和反馈闭环。

## 10. 自测与答案

**问：Software Factory 是否意味着无人工参与？** 不意味着。自治程度按风险和证据决定，发布、权限与事故等关键步骤可保留人类门禁。

**问：集中网关是否自动解决权限？** 不能。还需要身份传递、资源授权、凭据隔离和审计。

**问：什么说明你已掌握本教程？** 能在新任务上建立规格、实现最小正确变更、提供独立验证、解释失败并安全恢复，而不只是复述术语。

**问：生成十个 PR 是否就比一个有效贡献更好？** 不一定。有效性来自真实问题、正确修复、验证和协作，而不是数量；官方评分细则仍需单独核对。
